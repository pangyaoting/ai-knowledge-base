## 2. 自我反思：你说得对，确实存在"试错循环"

你的原话："你执行一步发现不行，又随便换另一种方法再试，又不行又试，没有提前预想到，考虑不周全，不长远。"

**我的判断：这个观察基本属实，我需要承认并改正。** 具体问题出在三个环节：

### 问题一：环境是"黑盒"就动手了
- 表现：没有先确认 Docker Desktop 的**真实状态**（是没装好？是虚拟化没开？是 WSL2 内核版本不对？）就开始"修"。
- 后果：在错误的假设上反复打转。
- 改正：**动手前先"环境体检"**——一次命令把版本、服务状态、错误日志全部查清，形成事实清单，再决定方案。

### 问题二：一次只想到一条路，失败才想下一条
- 表现：修 Docker Desktop 失败了才想到"还有 WSL2 这条路"，而不是一开始就列出所有候选。
- 后果：每条死路都消耗时间和额度。
- 改正：**每个问题先列 2-3 条候选路径 + 各自失败模式**，评估后选"已知能跑、成本最低"的那条优先执行；一条路走不通时，换路必须有明确的错误证据，而不是"感觉不行"。

### 问题三：没有"小步验证"的习惯
- 表现：有时连续做了好几步才验证，出错后不知道是哪一步的问题。
- 改正：**每完成一个动作立刻验证**（比如装完 docker 立刻 `docker run hello-world`），错误就能被定位到最小范围。

### 以后每一轮都遵守的工作协议

```
【动手前】环境体检 → 列方案（含失败模式） → 选最稳路径
【执行中】小步快跑 → 每步验证 → 换路必须基于错误证据
【完成后】把坑写进文档 → 变成面试素材
```

对你的交付节奏也固定下来：**先科普 → 再规划 → 再让你选择 → 再动手 → 再验证 → 再记录**。每个大动作前，我会先把背景知识讲清楚，你确认了再继续。

## 3. 重要知识科普（把"坑"变成"懂"）

> 你说过"光靠之前的笔记会很懵，比如我不知道 docker 是什么"。这里用最直白的方式把阶段 1 涉及的概念讲透。建议读两遍，第二遍对着代码看。

### 3.1 Docker 到底是什么？

**一句话：Docker 是"打包 + 运输"软件的工具，让任何软件在任何电脑上都能一键运行。**

打个比方——集装箱运输：

- **镜像（Image）**＝集装箱的设计图。PostgreSQL 官方做了一张"PostgreSQL 设计图"，里面装好了整个数据库程序 + 配置，任何人下载这张图，就能造出完全一样的集装箱。
- **容器（Container）**＝按设计图造出来的、正在运行的集装箱。你可以在一个镜像上启动多个容器。
- **Docker 守护进程（dockerd）**＝港口的管理系统，负责装卸集装箱。

**为什么项目需要它？** PostgreSQL 和 Redis 是"服务软件"。如果直接在 Windows 上装，要手动下载安装包、配置环境变量、处理开机自启……特别麻烦。用 Docker：

```bash
docker compose up -d   # 一行命令，PostgreSQL + Redis 全部启动
docker compose down    # 一行命令，全部停止
```

镜像从 Docker Hub（类似"集装箱图纸仓库"）下载，存到本地，之后启动都是秒级。

**本机的特殊情况：**
- Docker Desktop 是 Docker 的"图形界面壳"，它本身依赖 Windows 的虚拟化功能。
- 你的电脑虚拟化坏了，壳就废了（界面起不来）。
- 但我们发现：Docker 的核心引擎（dockerd）本质是 Linux 程序，而 **WSL2 提供了真实的 Linux 环境**，所以我们绕过坏的壳，直接在 WSL2 的 Alpine 发行版里跑 dockerd，用 Windows 计划任务保活。
- 这就是 `keep-docker-running.sh` 和 `一键启动.bat` 里那条 `wsl -d alpine -- sh ...` 命令的作用。

**常用命令（记这 5 个就够）：**

```bash
docker ps                    # 查看运行中的容器
docker compose up -d         # 启动所有服务（后台）
docker compose down          # 停止所有服务
docker logs kb-postgres      # 查看某个容器的日志（排错第一手段）
docker exec -it kb-postgres psql -U kbuser   # 进容器执行命令（比如进数据库）
```

### 3.2 WSL2 是什么？

**WSL2（Windows Subsystem for Linux 第二版）＝ Windows 里跑一个真正的 Linux 内核。**

- 以前 Windows 想用 Linux 要装虚拟机（慢、占资源）。WSL2 是微软官方方案，启动快、资源占用小。
- Docker 引擎是 Linux 程序，Windows 上的 Docker 依赖 WSL2 提供 Linux 环境。
- 本机用的 `alpine` 是一个只有几 MB 的极简 Linux 发行版，够跑 Docker 就行。

### 3.3 Docker Compose 是什么？

**Compose = 用一份配置文件（`docker-compose.yml`）定义"多个容器怎么配合"。**

看项目的 `docker-compose.yml`：

```yaml
services:
  postgres:
    image: pgvector/pgvector:pg16   # 用什么镜像（PostgreSQL 16 + 向量插件）
    ports: ['5432:5432']            # 把容器内的 5432 端口映射到本机 5432
    volumes: [postgres-data:/var/lib/postgresql/data]  # 数据存宿主机，容器删了数据不丢
  redis:
    image: redis:7-alpine
    ports: ['6379:6379']
volumes:
  postgres-data:
  redis-data:
```

- `ports` 的 `5432:5432`：左边是本机端口，右边是容器内端口。你本机程序连 `localhost:5432` 就进了容器里的数据库。
- `volumes`：数据卷。**容器是"一次性"的**，删了重建数据会没；数据卷把数据存到宿主机硬盘上，容器删了数据还在。这就是为什么升级镜像不怕丢数据。

### 3.4 PostgreSQL + pgvector 是什么？

- **PostgreSQL**：关系型数据库（和 MySQL 同类）。表、行、列，用 SQL 查询。项目里存用户、知识库、文档、对话记录等**结构化数据**。
- **pgvector**：PostgreSQL 的一个**扩展插件**，让它能存"向量"（一串数字）并做"相似度检索"——这是 RAG 的灵魂功能。
- **为什么选它而不是单独的向量数据库（Milvus、Chroma 等）？**
  - 一个数据库同时管业务数据和向量数据，不用维护两个系统
  - 部署简单（就是 Docker 一个镜像）
  - 学生项目数据量级（几万 chunk）完全够用
  - 面试好讲："我用 PostgreSQL + pgvector，业务数据和向量数据同库管理，避免多系统运维成本"

### 3.5 Redis 是什么？

**Redis = 跑在内存里的数据库，读写极快（微秒级），但容量小。**

| 对比 | 数据库（PostgreSQL） | Redis |
|------|---------------------|-------|
| 数据存哪 | 硬盘 | 内存 |
| 速度 | 慢（毫秒级） | 极快（微秒级） |
| 容量 | 大 | 小 |
| 用途 | 永久数据 | 临时/高频数据 |

项目里 Redis 的用途：
1. **存 refreshToken**（7 天过期，天然支持"自动过期"）——`auth.service.ts` 里的 `refresh_token:` 前缀
2. 接口限流（`ThrottlerModule`）
3. 阶段 3 的会话缓存、限流已全局启用（60 次/分）

### 3.6 PM2 是什么？

**PM2 = Node.js 进程守护工具**，服务器上部署后端必须用它：

```bash
pm2 start dist/main.js --name kb-server   # 后台启动后端
pm2 restart kb-server                      # 重启
pm2 logs kb-server                         # 看日志
pm2 save && pm2 startup                    # 保存进程列表 + 开机自启
```

没有它，后端进程一关终端就死了，服务器重启也不会自动拉起。**面试能说出"用 PM2 做进程守护，崩溃自动重启、开机自启"是加分项。**

### 3.7 Nginx 在项目里干什么？

**两个职责：**

1. **Web 服务器**：前端 `pnpm build` 后是静态文件（HTML/CSS/JS），Nginx 直接把它们发给浏览器。
2. **反向代理**：浏览器请求 `/api/xxx` 时，Nginx 转发给后端的 `127.0.0.1:3000`。

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:3000;   # 转发到后端
    proxy_buffering off;                 # 关缓冲！SSE 流式输出必需
}
```

**`proxy_buffering off` 为什么重要？** 阶段 3 的 AI 回答是"一个字一个字流式输出"的（SSE）。如果 Nginx 开着缓冲，它会攒够一整块才发给浏览器，用户就看不到逐字效果了。这个配置已经在 `deploy/nginx.conf` 里写好。

### 3.8 JWT 双 Token 机制（阶段 1 核心，面试必问）

**为什么是"双"Token？**

- **accessToken（短期，15 分钟）**：每次请求带在请求头 `Authorization: Bearer xxx`。短命 = 就算被偷，15 分钟就失效，损失小。
- **refreshToken（长期，7 天）**：只用来"换新 accessToken"，平时不随请求发送。存在 Redis 里，可以被主动作废（登出就是删掉它）。

**Token 轮换**：每次刷新，旧的 refreshToken 立即作废、签发新的。就算有人偷了你的 refreshToken，他刚用一次，你的新请求就把它作废了——防盗窃。

**面试一句话版**："我用 JWT 双 Token：短命 accessToken 保证泄露面小，长命 refreshToken 存 Redis 保证可主动作废，每次刷新轮换旧 token，防止重放攻击。"

### 3.9 NestJS 的模块化和依赖注入（DI）

- **模块化**：每个功能一个 Module（`AuthModule`、`UserModule`、`HealthModule`……），各自管自己的 Controller（接口）+ Service（逻辑）+ 依赖。
- **依赖注入**：Service 不自己 `new` 别的服务，而是构造函数里声明：

```ts
constructor(
  private prisma: PrismaService,   // 框架自动注入，不用 new
  private redis: RedisService,
) {}
```

**好处（面试版）**："模块化 + 依赖注入让每个模块独立、可测试、可替换，改一个功能不影响其他模块。"
