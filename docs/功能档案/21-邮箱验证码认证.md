# 阶段 4+：邮箱验证码认证（注册 / 找回密码 / 换绑邮箱）

> 一句话：**注册、忘记密码、更换邮箱**都要"真实邮箱 + 6 位验证码"验证，**登录只有邮箱 + 密码**——不用装验证器 App，符合普通用户习惯。
> 迭代记录：最初做的是 TOTP 双因素认证（docs/21 旧版），用户实测后反馈"登录还要打开验证器 App 太麻烦"，遂按"邮箱验证码"重构并移除 2FA。

---

## 一、大白话：为什么是"邮箱验证码"而不是别的

| 方案 | 优点 | 问题 |
|------|------|------|
| 短信验证码 | 人人有手机 | 每条短信都要钱、要资质，个人项目跑不起 |
| TOTP 验证器（原方案） | 免费、离线、安全 | 用户要先装 App 再扫码，**门槛太高**（真实反馈） |
| **邮箱验证码（现方案）** | 免费、无需装任何东西 | 邮箱可能被拦截（用开发模式/真实 SMTP 双通道应对） |

结论：**"验证真实邮箱"本身就够用了**——注册/找回/换绑必须验证邮箱所有权，而日常登录只验密码，体验和普通网站一致。

## 二、覆盖的四个场景

```
① 注册：输入真实邮箱 → 收验证码 → 输验证码 → 设密码+确认 → 直接进首页
② 登录：邮箱 + 密码（无验证码环节，一步完成）
③ 忘记密码：邮箱 + 验证码 → 设新密码 → 去登录
④ 更换邮箱（个人中心）：新邮箱 + 验证码 → 登录账号切换为新邮箱
```

## 三、实现拆解

### 1. 验证码服务（email-code.service）

- 6 位随机数字，Redis 存储：`email_code:{type}:{email}`，**10 分钟有效、60 秒重发限制**（防刷）；
- 消费即删除（一次性，用过就不能再用）；
- **双通道发送**：
  - 配置了 SMTP（`MAIL_HOST` 等）→ 真实邮件（nodemailer）；
  - 没配置 → **开发模式**：验证码随接口响应返回（本地联调零成本，生产配置 SMTP 后自动切换真实邮件，验证码绝不回传）；
- 场景分型 `register / forgot / bind`，验证码互不通用。

### 2. 认证接口（auth.controller）

```
POST /auth/send-code        @Public 发验证码（type: register|forgot|bind）
POST /auth/verify-code      @Public 只校验不消费（注册向导第①步用）
POST /auth/register         @Public 邮箱 + 验证码 + 密码 → Token
POST /auth/login            @Public 邮箱 + 密码 → Token（无 2FA 环节）
POST /auth/forgot-password  @Public 邮箱 + 验证码 → 设置新密码
POST /auth/bind-email       @登录   新邮箱 + 验证码 → 换绑
POST /auth/logout / refresh 不变
GET  /auth/profile          @登录   用户信息（已移除 totpEnabled）
POST /auth/delete-account   @登录   注销账号（需当前密码）
```

- 注册**先查邮箱是否已占用（409）再校验验证码**——已注册邮箱直接提示"该邮箱已被注册"，避免"验证码错误"误导（细节见踩坑）；
- 换绑邮箱校验新邮箱未被他人占用（ConflictException）。

### 3. 数据模型变更（迁移 20260818170000_remove_totp）

```sql
ALTER TABLE "users" DROP COLUMN IF EXISTS "totp_secret";
ALTER TABLE "users" DROP COLUMN IF EXISTS "totp_enabled";
ALTER TABLE "users" DROP COLUMN IF EXISTS "recovery_codes";
```

User 表回到最简：email / password / nickname / avatar。TOTP 依赖（otplib）与前端二维码依赖（qrcode）一并移除。

### 4. 前端

- **注册页**：两步向导——① 邮箱 + 发送验证码（60s 倒计时）+ 验证码；② 密码 + 确认密码 + 昵称（选填）。开发模式下后端返回的验证码自动填入（联调神器）；
- **登录页**：邮箱 + 密码 + 「忘记密码？」链接（原两步动态码 UI 删除）；
- **忘记密码页**：与注册同款两步向导（邮箱+验证码 → 新密码）；
- **个人中心**：资料（邮箱只读 + 提示换绑入口）/ 更换邮箱（新邮箱+验证码）/ 修改密码；
- 验证码输入框：6 位限制、数字键盘、自动完成。

## 四、踩过的坑（面试真实素材）

1. **注册的验证码先被消费**：第一次实现先 `verifyCode` 再查重，用户重复提交时验证码已被删除 → 报"验证码错误"而非"邮箱已被注册"，误导用户。修复：**先查邮箱占用（409），再校验验证码**。
2. **测试脚本把 token 传错位置**：接口信封 `{code,message,data}` 没解包、token 被当成第三个参数传入被忽略 → 全链路 401。教训：**写自测先确认接口契约（信封结构/参数位），失败先怀疑脚本而不是后端**。
3. **TOTP 时代的教训仍适用**：库的新版 API 返回值结构要实测（otplib v13 `verifySync` 返回 `{valid}` 对象）。

## 五、面试话术

- "验证码体系做了四个场景：注册、登录、忘记密码、换绑邮箱。核心是 Redis 存码：10 分钟有效、60 秒重发限制、消费即删，杜绝重放和刷接口。"
- "发送做了双通道：本地没配 SMTP 时走开发模式（验证码随响应返回，联调快）；生产配 SMTP 自动切真实邮件，验证码绝不回传。"
- "为什么不做短信/TOTP？短信要钱要资质；TOTP 用户要装 App，实测被吐槽门槛高。邮箱验证码零成本、零安装，且'验证邮箱所有权'在注册/找回/换绑场景已经足够安全。"
- "登录保持邮箱+密码一步完成——验证码只在敏感操作（注册/改密/换绑）出现，符合主流产品习惯。"
