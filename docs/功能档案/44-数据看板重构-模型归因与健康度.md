# 44 · 数据看板重构：模型归因、健康度与趋势

> 关联：`28-数据看板研究统计与用户头像.md`（初版）、`20-用户模型配置BYO.md`（为什么"模型消耗"是第一指标）
> 代码：`apps/server/src/modules/stats/stats.service.ts`、`apps/web/src/views/Dashboard.vue`
> 设计预览（静态模拟数据，可直接双击打开）：`docs/mockups/dashboard-preview.html`

## 1. 为什么要改

初版看板 = 8 张累计卡片 + 2 张图 + Top 知识库。三个维度的缺失：

| 缺失维度 | 初版的样子 | 问题 |
| --- | --- | --- |
| **变化** | 全是累计值（"消息总数 328"） | 看板的价值是"变化"而不是"存量"，没有环比就看不出趋势 |
| **行动指向** | Chunk 数、消息总数是技术指标 | 真正能"点了去处理"的信息（文档处理失败）完全没露出 |
| **结构分解** | Token 只有一个总数 + 三大类 | BYO Key 模式下**"哪个模型在烧 token"是用户最关心的指标**，却看不到 |

## 2. 新版布局（按"用户提问顺序"排，不是按系统模块排）

| 区域 | 回答的问题 | 内容 |
| --- | --- | --- |
| ① KPI 四联 | 出问题了吗？比之前好还是差？ | 首卡 = **本期 Token 总消耗 + 环比**；今日提问（环比昨日）；本期提问（环比上期）；文档失败告警 |
| ② Token 消耗 | 钱花在哪个模型/哪个功能？ | 左：**各模型 token 拆分**（占比 / 调用次数 / 均 token / 环比）；右：Token 构成（甜甜圈）+ Token 消耗趋势（三段堆叠） |
| ③ 资产与健康 | 家底多少？有没有事要处理？ | 资产规模小卡 + **文档处理健康度**（已处理/处理中/失败 + 失败引导） |
| ④ 活跃度趋势 | 这些数字怎么来的？ | 提问数趋势（实线本期 + 虚线上期）+ 24 小时提问时段分布 |
| ⑤ 研究与记忆 | 哪些功能在贡献？ | 研究任务状态分布 + 研究效率（均搜索轮数/精读页数/报告均 token）+ 记忆系统（摘要会话数、事实记忆总数与分类） |
| ⑥ 归因明细 | 具体是谁在消耗/被用？ | 最烧 Token 会话 Top5（**可点击直达该会话**）+ 被引用最多的资料 Top5 |
| ⑦ 最近活跃知识库 | 哪个库真在用？ | 文档数 / 切块数 / **本期被引用次数** / 最近更新 |

排序原则：**倒金字塔**——先给结论（KPI），再给证据（趋势），最后给明细（表格）。信息密度单调递增，可行动项（失败文档）放在第一屏。

## 3. 指标口径（逐个说清，避免"数字好看但不知道算什么"）

| 指标 | 口径 |
| --- | --- |
| 提问数 | 该用户的 `chat_messages` 中 `role='user'` 的消息数 |
| 对话 token | `assistant` 消息上记录的流式 usage（`prompt_tokens + completion_tokens`）；来源是 SSE 请求带 `stream_options.include_usage` |
| 研究 token | `reports.tokens_used` + `agent_tasks.tokens_used`（worker 累加的真实 usage） |
| **各模型 token** | 按 `chat_messages.model` 分组汇总。**只统计记录了模型名的回答**：加列前的历史为 `NULL` → **直接不计入**，不做"未记录"桶、不做估算 |
| 模型调用次数 | 该模型在本期的 assistant 消息数 |
| 环比（delta） | 与**上一等长周期**比较（近 7 天 vs 前 7 天、近 30 天 vs 前 30 天）；`全部`范围按月分桶、无环比 |
| 时段分布 | `role='user'` 消息按 **Asia/Shanghai** 的小时（0-23）分桶 |
| 被引用资料 / 知识库被引用 | `assistant` 消息 `sources.kb` 数组展开，按 `documentId` 关联 `documents` → `knowledge_bases` 聚合 |
| 文档健康度 | `documents.status` 归三档：`done` / 处理中（`pending`+`processing`）/ `failed` |
| 研究任务状态 | `reports.status` + `agent_tasks.status` 合并：完成 / 进行中 / 已停止（`cancelled`+`stopped`）/ 失败 |
| 记忆系统 | 启用摘要的会话 = `summary IS NOT NULL` 的会话数；事实记忆 = `user_memories` 总数与 `category` 分布 |
| 资产规模 | 知识库 / 文档 / Chunk / 会话 / 事实记忆；`avgChunksPerDoc` = Chunk ÷ 文档 |

**为什么不显示估算金额**：需要单价表，而模型单价会变、还会分阶梯与缓存命中折扣 —— 编一份价格表就是"数字精确但结论错误"。因此只展示 token，让用户按自己平台的实际单价心算。若将来要做，应做成"用户可填单价"，而不是内置价格。

**为什么不显示向量化（bge-m3）消耗**：它走**系统 key**（不是用户账单），且 `embedding.service` 目前**不记录 usage** —— 没有真数据可展示，所以不入模型账单。

## 4. 数据模型变更

| 变更 | 迁移 | 说明 |
| --- | --- | --- |
| `chat_messages.model TEXT` + 索引 | `20260910020000_add_chat_message_model` | 落库时写入**本条回答实际使用的模型**（图片问题会走视觉自动路由，所以取实际 `target.model` 而非会话绑定） |

## 5. 顺手修掉的时区 bug

初版 `fillLast7Days()` 用**服务器本地日期**（`getMonth()/getDate()`）生成 7 天桶，而 SQL 用 `AT TIME ZONE 'Asia/Shanghai'` 分组。容器 TZ 通常是 UTC → **两者错位，跨零点前后的数据会串到相邻天**。

新版统一：所有分桶（日/月/小时）都由 SQL 按 `Asia/Shanghai` 输出，补零桶列表用固定 `+08:00` 偏移（上海无夏令时）计算，两侧口径一致。

## 6. 性能与边界

| 项 | 现状 / 取舍 |
| --- | --- |
| 单次 overview | 约 25 个查询**并行**（`Promise.all`）；消息量小时毫秒级 |
| 偏重的两处 | `sources` jsonb 展开（被引用统计）与 `chunk.count`；消息数上万后建议加表达式索引 |
| 缓存 | **未加** Redis 缓存。理由：数据量还小，过早加会引入"数据可能过期"的心智负担；实测变慢后再加 60s 缓存（刷新按钮需要能穿透） |
| 历史 token | 无法按模型归因（`model IS NULL`），看板直接不计入 |
| "全部"范围 | 按月分 6 桶（含本月），无环比 |
| 深链 | 看板点击会话 → `/chat?session=<id>`，对话页 `onMounted` 读取 query 直达该会话 |

## 7. 面试可讲的点

1. **BYO 架构下的成本归因闭环**：token 在落库时就绑定"实际使用的模型"（含视觉路由），看板才能回答"钱花在哪个模型"。
2. **时区一致性**：SQL 分桶与 JS 补零桶必须同口径 —— 这是很容易"看起来对、跨零点就错"的经典 bug。
3. **不做假精确**：不内置模型单价、不为历史数据编造归因（明确标注"仅统计记录模型名之后"）。
4. **空桶补齐 + 上期虚线**：让"趋势"可读（连续时间轴 + 同周期对比），而不是只给一张柱状图。
5. **缓存是实测驱动**：先不加，测出慢再加 —— 而不是"看板就该缓存"。
