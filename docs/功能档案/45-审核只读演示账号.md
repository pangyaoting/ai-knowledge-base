# 45 · 审核只读演示账号（备案核验 / 面试展示）

> 一句话：给**公安备案审核员**和**面试官/HR**一个能进门看真实数据的账号，但用**服务端守卫**保证
> 他改不了任何数据、也花不掉平台一分钱。
> 代码：`apps/server/src/common/guards/demo-readonly.guard.ts`、`apps/web/src/config/demo.ts`、
> `Login.vue`（体验卡片）、`Layout.vue`（只读横幅）
> 关联：`部署运维/40-ICP备案与域名上线实战.md`（备案链路）、`20-用户模型配置BYO.md`（BYO 架构）

---

## 1. 起因：登录墙把"看内容的人"挡在外面

站点是 SPA + 全局路由守卫：**未登录访问任何页面都会被跳到 `/login`**。这带来两个实际问题：

| 谁 | 遇到的问题 |
|---|---|
| **公安备案审核员** | 备案表里填的"网站访问地址"就是首页，点开只看到登录框 → 无法确认"网站有真实内容、与备案描述一致" → 可能要求**补正** |
| **面试官 / HR** | 点简历上的项目链接，第一眼是登录页 → 看不到黑洞首页、知识库、看板，**简历项目价值直接打 7 折** |

## 2. 三个候选方案的取舍

| 方案 | 效果 | 成本 | 结论 |
|---|---|---|---|
| **游客可浏览全站**（页面能看、功能锁死） | 审核员/面试官能翻页面 | 要改 401 拦截器 + 8 个页面的游客态 + 逐按钮禁用，约 10~12 个文件 | ❌ 性价比低 |
| **只读演示账号**（本项目选它） | 进去看到的是**真实数据**（文档、对话带引用、报告、看板曲线） | 1 个后端守卫 + 1 个前端配置 + 2 处 UI | ✅ **选中** |
| 只公开首页 | 解决"第一眼"，但内页仍要登录 | 小 | 备选（本次未做） |

**为什么"看真实数据"比"看空页面"强**：审核员关心的是"这站是不是真在用、内容与备案一致"；
面试官关心的是"这人做出来的东西长什么样"。**空 UI 骨架两个问题都回答不了**，而演示账号里的
预置数据两个都答得上。

> 顺带排除了一个"看起来零成本"的做法：**数据看板**在游客态下是"一堆 0 的图表"，
> 比登录墙更难看 —— 这类页面天生不适合游客浏览，也印证了"只读演示账号"的方向。

## 3. 设计：三层安全边界（缺一不可）

| 层 | 内容 | 挡住什么 |
|---|---|---|
| ① **不绑任何模型配置** | BYO 架构没有"默认模型"（`chat.service.ts` 里 `resolveForChat` 返回 null 就直接回"请先选择模型"） | 对话、研究报告、自主研究 Agent **全部不可用** → 花不到大模型的 Token |
| ② **服务端只读守卫** | `DemoReadonlyGuard`：白名单邮箱的账号，**除 `GET/HEAD/OPTIONS` 外一律 403** | 上传/新建/修改/删除，以及**系统 Key 的消耗** |
| ③ **只放演示数据** | 演示账号里只有预置的知识库/对话/报告 | 看不到主账号的任何内容（`ownerId` 隔离） |

### 关键判断：为什么"不绑 Key"远远不够

"没绑模型 Key，所以用不了 AI" —— 这句只对**大模型**成立。站内还有**走系统 Key**的消耗点：

| 消耗点 | 触发方式 | 不绑 Key 能挡住吗 |
|---|---|---|
| 文档向量化（硅基流动 `bge-m3`） | **上传文档** → 异步解析分块 → 向量化 | ❌ **挡不住**（`embedding.service.ts` 读 `SILICONFLOW_API_KEY`） |
| 检索精排（`bge-reranker`） | 提问时重排 | ✅ 能（提问要先有模型配置） |
| 联网检索（Tavily） | 对话触发联网 | ✅ 能（同上） |

所以**必须在服务端拦写操作**。这也是本条设计里最容易被忽略的一环。

### 为什么按"邮箱白名单"而不是加数据库字段

`DEMO_READONLY_EMAILS=zhizhuojuzi.h@qq.com`（逗号分隔，支持多个）：

- **不改 schema、不加迁移** —— 演示账号本来就是一条运维约定，不值得为它动数据模型；
- **未配置该变量时守卫完全空转** —— 对不想用这个功能的部署零影响（默认 `DEMO_READONLY_EMAILS=` 为空）；
- 代价：邮箱是"约定"而不是"数据"，改账号要同时改 `.env` 与前端 `config/demo.ts`（**两处必须一致**）。

### 两个必须处理的细节

1. **白名单放开 `/auth/logout` 与 `/auth/refresh`**
   否则审核员登进来**退不出去**（点退出会被 403 顶回来，看起来像网站坏了）。
2. **守卫注册顺序**：`app.module.ts` 里必须排在 `JwtAuthGuard` **之后** ——
   多 `APP_GUARD` 按注册顺序执行，只读守卫依赖前者先把 `user`（含 `email`）挂到 `request` 上。
   （`jwt.strategy.ts` 的 `validate` 返回 `{ id, email, nickname, avatar }`，所以能按邮箱判定。）

## 4. 实现清单

| 文件 | 作用 |
|---|---|
| `apps/server/src/common/guards/demo-readonly.guard.ts` | 只读守卫本体（读 `.env` 白名单 → 非只读方法抛 `ForbiddenException`，带中文提示） |
| `apps/server/src/app.module.ts` | 注册为第二个 `APP_GUARD` |
| `.env.example` | 新增 `DEMO_READONLY_EMAILS` 说明（含"为什么不绑 Key 不够"） |
| `apps/web/src/config/demo.ts` | 演示账号展示配置（邮箱/密码/说明），设 `null` 即隐藏整张卡片 |
| `apps/web/src/views/Login.vue` | 「🔍 审核 / 访客体验（只读）」卡片 + **一键体验**（自动填表并登录） |
| `apps/web/src/views/Layout.vue` | 演示账号登录后顶部横幅：「只读演示账号：可浏览…写操作与 AI 功能已关闭」 |

> 横幅不是装饰：审核员点按钮被 403 时，**一眼知道是"演示限制"而不是"网站坏了"** —— 这是"给人看"的产品里
> 最容易被忽略的体验细节。

## 5. 怎么验证（不产生任何数据的探针）

**原理**：NestJS 里**守卫在 `ValidationPipe` 之前执行**。所以拿演示账号的 Token 打
`POST /api/knowledge`（创建知识库）并**故意传空 body `{}`**：

| 返回 | 含义 |
|---|---|
| **403**「演示账号为只读…」 | ✅ 守卫先拦下了（**参数校验根本没跑到**） |
| **400**「名称不能为空…」 | ❌ 守卫没生效（还在跑旧后端 / 没配 `.env`） |

两种情况都**不会创建任何数据**，所以可以放心反复探测。实测记录（`073dcbf` 部署时）：

```
#1~#4  写操作探针 -> HTTP 400 | 名称最多50个字符; 名称不能为空   ← 旧后端仍在跑
#5     写操作探针 -> HTTP 403 | 演示账号为只读：可以浏览全部页面与已有数据…  ← 新后端已上线
```

**前端验证有个坑**：Vite 会把被多个页面共享的模块（如 `config/site.ts`、`config/demo.ts`）
拆成**独立共享 chunk**，不一定落在某个页面分包里。所以想确认"字符串是否上线"，
必须在**主包 + 主包引用的全部分包**里搜，而不是只搜 `Login-*.js`。
（本项目工具：`.qatest/bundle-probe.mjs`，已 gitignore，用法 `node .qatest/bundle-probe.mjs "要找的字符串"`。）

## 6. 填演示数据的流程（临时放开 → 填 → 收回）

演示账号被守卫锁着写操作，所以预置数据要**临时**放开：

| 步 | 做什么 |
|---|---|
| 1 | 注释 `.env` 里的 `DEMO_READONLY_EMAILS` → `pm2 restart kb-server`（放开写权限） |
| 2 | 登录演示账号 → 建 2 个知识库 + 传 6~8 个文档（走系统 Key，**不花模型钱**，成本≈0） |
| 3 | **临时**给演示账号绑一份自己的模型配置 → 问 3~5 个问题 + 建 1 份研究报告（几万 Token，几毛钱） |
| 4 | **立刻删掉那份模型配置** |
| 5 | 恢复 `DEMO_READONLY_EMAILS` → `pm2 restart kb-server`（收回只读） |
| 6 | 复验：演示账号**无模型配置** + 写操作 **403** + 数据都还在 |

**第 4 步为什么安全**：`reports` / `agent_tasks` 里存的是**模型名快照**（不是外键），删配置不影响历史报告；
会话绑定的配置是 `onDelete: SetNull`，删了只回"未绑定"，**历史消息与看板统计全部保留**。

## 7. 坑清单

| 坑 | 现象 | 对策 |
|---|---|---|
| 靠前端藏按钮当"只读" | 观感上不能点，`curl` 一下就绕过了 | **安全边界必须在服务端**（前端只负责"解释为什么不能点"） |
| 以为"不绑 Key"就万事大吉 | 审核员点一下上传，就用你的**系统 Key** 跑了向量化 | 只读守卫拦写操作（见 §3 关键判断） |
| 忘了放开 `/auth/logout` | 审核员退不出去，看到 403 以为站坏了 | 白名单 `SAFE_WRITE_PATHS` |
| 守卫顺序写反 | `req.user` 还是 undefined → 白名单完全不生效（形同虚设） | 必须排在 `JwtAuthGuard` 之后 |
| `.env` 与前端配置不一致 | 页面展示的账号和后端认定的只读账号不是同一个 → **只读失效** | 两处一起改；改完用 §5 的空 body 探针验一次 |
| 只扫 `Login-*.js` 验证产物 | 找不到字符串，误判"部署失败" | 共享模块被拆成独立 chunk → 扫主包 + 全部分包 |
| QQ 邮箱的 `@foxmail.com` 别名 | 注册时 SMTP 报 `550 non-existent account` | foxmail 别名**不是自动拥有**的（要去 QQ 邮箱设置里绑），换一个真实邮箱或走开发模式 |

## 8. 面试可讲

1. **安全边界要落在服务端**："只读演示账号"如果只靠前端隐藏按钮，`curl` 一次就破了；
   真正的边界是全局守卫 + 邮箱白名单，前端只负责**解释**。
2. **成本意识**：BYO 架构下"没绑 Key"只挡住大模型调用，**平台自己的系统 Key**（向量化/重排）
   仍然会被写操作消耗 —— 归因成本时要按"消耗点"逐个过，而不是按"功能"粗略判断。
3. **不改 schema 的取舍**：为一条运维约定加数据库字段 + 迁移，成本高于收益；用环境变量白名单
   实现，且**未配置时零影响**（默认行为不变是能被安全引入生产的前提）。
4. **验证要设计成"零副作用"**：用空 body 打写接口，`403`/`400` 就能区分守卫生效与否
   （守卫在参数校验之前执行），**不产生任何数据**、可反复探测。
5. **给人看的产品要解释自己**：审核员被拦时会怀疑"网站坏了"，所以顶部横幅明说"只读演示"。
   技术正确 ≠ 体验正确。
