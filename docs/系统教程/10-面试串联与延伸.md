# 10 · 面试串联与延伸：把整本书讲成一个故事

> **本章地图**
> - 学什么：把前 9 章的知识串成一条能"一口气讲 10 分钟"的项目叙事；常见面试追问的应答框架；这本书没覆盖但值得继续深挖的方向
> - 代码在哪：无需新代码——本章是"合上书"的一章，全部引用前文已读过的文件

## 一、为什么需要"项目叙事"

面试官一天面 5~8 个人，每个人都在讲"我做了个 AI 项目"。**区别不在技术多深，而在你能不能让他 5 分钟内建立"这人不只是调 API"的印象。**

你需要的不是背 30 个知识点，而是**一条主线 + 三个高光时刻 + 一层防御**：

```
主线（30 秒）  ：这是个什么系统，解决什么问题
高光 1（2 分钟）：上传→向量化→检索→带来源回答 的完整链路
高光 2（2 分钟）：一个"反直觉"的工程决策（RRF 只看排名 / 门控宁缺毋滥 / BYO 成本转嫁）
高光 3（2 分钟）：一次真实的线上事故复盘（NUL 崩溃 / CI 假绿）
防御（1 分钟）  ：如果问你"哪里做得不好 / 下一步做什么"
```

这一章把每条线都给你配好"台词"——不是让你背，而是让你知道**每个知识点在故事里扮演什么角色**。

## 二、30 秒开场白（电梯版）

> "我做了一个**企业级 AI 知识库问答系统**：把文档（文本、代码、PDF）上传后自动解析、分块、向量化，之后用自然语言提问，系统先在你的文档里做**混合检索**（向量+关键词，按排名融合），再用重排模型精排，最后让大模型**看着资料回答**、每条都标引用来源。后端 NestJS + PostgreSQL(pgvector)，前端 Vue3，支持研究报告和自主研究 Agent 两种长任务，大模型 API 是**用户自带 Key**（BYO），平台只承担向量化成本——所以这个项目**自己跑起来几乎零成本**，但也因此很接近真实产品的成本模型。"

这一段埋了 5 个钩子：**混合检索、来源标注、长任务、BYO、pgvector**——面试官大概率会挑其中一个追问，而每一个你都有整章的内容可以展开。

## 三、高光时刻 1：把"上传一个文件"讲到"回答一个问题"

这是最完整的链路故事，也是检验你"是不是真做过"的标准问题。用第 03 + 04 章的内容，按顺序讲：

```
1. 上传（03 章）：用户拖一个项目文件夹进来
   → 逐个文件类型识别（文本/代码/PDF/Word/附件）
   → 内容哈希去重（同名同内容直接跳过，省 API 钱）
   → 入库即返回 <1s，真正的解析丢进 BullMQ 队列后台跑

2. 解析分块（03 章）：为什么"先切块"？
   → 整篇塞给模型：贵、超窗口、定位不了"哪段支撑回答"
   → 递归分块 500 字 + 100 字重叠（切在句子中间不丢边界）
   → 代码文件特殊处理（保缩进、按函数边界）；md 结构化分块（保标题层级）
   → P2 父子分块：父块当"容器"不嵌入，命中子块取父块全文喂模型

3. 向量化（03 章）：bge-m3 把每块变成 1024 维向量
   → 批量 10 个 + 指数退避（省 API 调用次数）
   → 写进 PostgreSQL pgvector（业务数据和向量同库，不用两套系统）

4. 提问检索（04 章）：用户问"怎么实现图片识别？"
   → 代码文件先查符号索引（C：直接命中函数实现，不等文本相似度）
   → 向量路（语义）+ 关键词路（pg_trgm 精确匹配）并行各召回 15 条
   → RRF 按排名融合（1/(60+rank)——为什么只比排名不比分数？两种检索的分数不可比）
   → bge-reranker 交叉编码器对 15 条精排 → 取 5 条
   → 相关性门控：分数不够 → 宁可不给，也不硬凑

5. 生成（05 章）：5 段资料 + 用户问题组装 Prompt → DeepSeek 流式
   → SSE 逐字推给前端，回答里标 [来源N]
   → 前端 rAF 节流渲染，点来源能跳回原文段落
```

**讲这段的节奏**：不要一口气背完。讲完"上传秒回"停一下（等他问为什么快，引到队列）；讲完"分块"停一下（等他问为什么重叠，引到边界语义）；**留白比填满更有面试效果**。

## 四、高光时刻 2：三个"反直觉"的工程决策

面试官最想听到的是**你做过取舍、知道为什么**，而不是"我用了 XXX 技术"。这三个决策是全书最能体现工程判断力的点：

### 决策 A：RRF 为什么只看排名、不看分数？（04 章）

```text
普通思路：把向量相似度 0.8 和关键词 TF-IDF 分数 2.3 加起来排序
问题：两种分数量纲不同、分布不同，加权是拍脑袋
RRF 思路：不管分数，只看"你在各自那一路排第几"，score = Σ 1/(60 + rank)
好处：鲁棒、零调参、两路分数不可比的问题直接消失
```

**台词**："如果面试官问你混合检索怎么融合，说 RRF 并且能解释'为什么不用加权求和'，就已经超过 90% 的候选人了。"

### 决策 B：相关性门控——宁可不答，也不乱答（04 章）

```text
默认直觉：检到什么就给什么，让模型自己判断
风险：检到不相关的资料 → 模型被误导 → 一本正经地胡说
本项目：检索质量有下限（相似度阈值 + 重排分数阈值），不够就明说
        "未检索到知识库资料"，或者允许模型用自身知识但必须披露
```

**台词**："检索质量不够时宁可拒绝——RAG 最大的幻觉来源不是模型，是喂进去的烂资料。这是我踩过坑才加的设计。"

### 决策 C：BYO——让用户带自己的 Key（07 章）

```text
常规 SaaS：平台统一调模型 API，成本平台扛 → 免费用户烧钱、收费用户嫌贵
本项目：用户绑定自己的 DeepSeek/硅基 Key，对话 token 用户自己付
安全：Key 用 AES-256-GCM 加密存库，接口永不回传明文
平台只承担：向量化（bge-m3）+ 重排（便宜可控）
结果：对话零边际成本，还顺带解决了"多用户共用 Key 的配额打架"
```

**台词**："这是我把它定位成'接近真实产品'的核心——真实产品必须回答'谁付模型钱'这个问题。"

## 五、高光时刻 3：一次真实的线上事故复盘

面试官问"讲一个你排过的最难的 bug"时，用这个（09 章有完整复盘）。**事故故事的万能结构：现象 → 猜测 → 定位 → 根因 → 修复 → 教训**：

### 事故：PostgreSQL 22P05 崩溃（NUL 字符）

```text
现象   ：线上突然 500，日志里 PostgreSQL 报 22P05 编码错误，重启恢复后再次出现
猜测   ：以为是并发问题 → 加锁 → 没解决 → 回到日志
定位   ：加日志发现崩溃总是发生在"写入某个特定文本"之后
根因   ：某次上传的文档/模型输出里夹带了 \u0000（NUL）字符，
        PG 的 text 类型不允许 NUL，一写就崩
修复   ：三层防线——源头清洗（解析时删控制字符）
              → 入队前清洗（用户消息落库前 sanitize）
              → 落库兜底（所有 JSON 序列化后再清洗一遍）
教训   ："线上事故往往不是一个大 bug，而是一个你没想过的输入边界"
```

**台词**："这个问题我查了很久，最后发现是**用户上传的文档里有 NUL 字符**——正常测试永远碰不到，只有真实数据会。从那以后我养成了习惯：**所有用户输入在落库前做边界清洗**。"

### 备选事故：CI 假绿（GITHUB_OUTPUT）

```text
现象   ：CI 全绿，但线上代码一直没更新
定位   ：发现 deploy job 的 condition 永远不满足——check job 输出 deploy_enabled 时
        只 echo 到了 stdout，没写进 GITHUB_OUTPUT，条件读到的永远是空
修复   ：echo "deploy_enabled=true" >> "$GITHUB_OUTPUT"
教训   ："CI 绿 ≠ 部署了"——要有产物校验（检查线上版本号）
```

**台词**："这个 bug 的教训是：**自动化出问题不可怕，可怕的是它假装成功**。所以我后来给部署加了'线上版本号比对'的校验。"

## 六、防御：高频追问与应答框架

把第 02-09 章每章末尾的"面试必背"题收集起来，这里给应答框架（详细答案回对应章节找）：

| 追问 | 一句话框架 | 详见 |
|---|---|---|
| 为什么用向量数据库？ | 语义检索；pgvector 和业务同库省一套系统；HNSW 索引毫秒级 | 04 |
| 分块多大？重叠多少？为什么？ | 500/100；切在句子中间不丢上下文；代码/结构化单独策略 | 03 |
| 为什么上传这么快？ | 异步队列：接口只做校验+落库+入队，解析后台跑 | 03/06 |
| SSE 和 WebSocket 怎么选？ | 单向流选 SSE：HTTP 兼容、自动重连、Nginx 关缓冲即可 | 05 |
| 为什么用 RRF 不用加权？ | 两路分数不可比，排名融合零调参鲁棒 | 04 |
| 重排为什么只排 15 条？ | 交叉编码器贵，两阶段"宽召回+精排"性价比最高 | 04 |
| 检索不到怎么办？ | 门控拒绝或披露自身知识，绝不硬凑 | 04 |
| 长任务为什么用队列？ | 同步会占死线程+浏览器等不到；队列给重试/并发/断点 | 06 |
| 怎么防止取消后还在扣 token？ | 条件更新(updateMany)原子门控 + 节间检查点 | 06 |
| 用户 Key 安全吗？ | AES-256-GCM 加密存库、不落明文、不回传 | 07 |
| Token 过期怎么办？ | 双 token + 无感刷新 + 并发队列排队重放 | 07 |
| 前端为什么用 KeepAlive？ | 切导航不重建大组件树；代价是定时器要 onDeactivated 暂停 | 08 |
| 流式回答为什么流畅？ | rAF 节流 + 渲染缓存：每帧最多一次 DOM 写入 | 08 |
| CI 怎么保证部署的是对的？ | check 双 job + 假绿事故教训 + 版本比对 | 09 |

## 七、如果被问"哪里做得不好 / 下一步做什么"

**不要只说"没有"，也不要说"都是坑"**。给一个有层次感的回答：

```text
现在的短板（诚实）：
1. 检索质量依赖 bge-m3 单模型，没做多路 embedding 对比实验（43 章蓝图里有规划）
2. 长任务（Agent）是"伪并行"——受单机 2C4G 限制，worker 并发低
3. 没有真正的多租户 SaaS 化：注册即用、无套餐/配额体系

下一步（有优先级）：
P0：RAG 评测集——建一个"问题→期望文档"的黄金集，量化召回率/准确率（现在靠手感）
P1：全文检索分流（已做）+ 按文档类型自适应分块策略
P2：Agent 记忆与多 Agent 协作
P3：做成多租户 SaaS：用量配额 + 计费 + 邀请制
```

这个回答同时展示：**自我认知（知道短板）+ 工程方法（评测驱动）+ 产品思维（商业化路径）**。

## 本章小结

这本书从"什么是 RAG"讲到"怎么把一个 RAG 应用做成接近真实产品的系统"：**数据模型打底（02）→ 文档流水线把内容变成向量（03）→ 检索内核决定回答质量（04）→ 对话引擎决定体验（05）→ 长任务编排撑起深度功能（06）→ 认证与 BYO 决定能不能商业化（07）→ 前端工程化决定手感（08）→ 测试部署决定可靠性（09）**。最后一章只是把散落的珍珠串成项链——真正的功夫，在你看书时做的每一个实验里。
