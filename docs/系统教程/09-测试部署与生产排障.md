## 一、先给结论："能跑"和"可靠"隔着三层

前八章，这个系统从零长到了"什么都能干"。但从"能干"到"**放心让它自己跑在公网上**"，中间隔着三件没有浪漫可言的事：

| 防线 | 回答什么问题 | 出问题时的代价 |
|---|---|---|
| **单元测试** | 代码改坏了，**我**知不知道？ | 分块器改坏 → 全库检索质量雪崩，而你还以为是模型不行 |
| **CI/CD** | 代码改坏了，**上线前**挡不挡得住？上线过程可不可重复？ | 坏代码 push 即上线，用户先于你发现 bug |
| **可观测/排障** | 线上真出事了，**多久能找到根因**？ | 面对 PostgreSQL 报错手足无措，靠"重启试试"过日子 |

这一章就是围绕这三层展开，并且全程用本项目真实发生过的事故当教材——尤其是两个"面试能整套复述"的素材：**CI 假绿**（绿了等于没部署）和 **NUL 字符崩溃**（一条不可见字符炸掉整条入库链）。

## 二、测试策略：为什么测"纯函数"性价比最高

### 2.1 测试金字塔：先分清要测什么

软件测试有个经典分层，越往下越便宜、越稳、越该多写：

```
        ▲  手工验证 / E2E       贵：要浏览器+服务器+数据库全起来，慢、脆
       / \
      /   \   集成测试           中：测"模块间协作"，要起依赖
     /     \
    /       \  单元测试          便宜：秒级跑完、稳定、定位精确 ← 本项目的重心
   ───────────────────────────────► 数量
```

E2E 最接近用户视角但最贵：本项目没有引入 Playwright/Cypress 一类的端到端测试——理由很实在：**单人维护 + 迭代极快 + 核心链路交互复杂**，E2E 脚本维护成本会吃掉写功能的时间。替代方案是把"最容易错、错了最致命"的**纯函数逻辑**用单测钉死，交互层靠第 08 章的组件拆分（逻辑收进容器 + 纯函数下沉 utils）保证"测得到"。

> 类比：盖楼时你不会每盖一层就搬真家具进去住一遍（E2E）；你会把**钢筋水泥抽样送实验室做强度试验**（单测）——便宜、可重复、坏了能精确到是哪批料。本项目把"钢筋"选得特别准：检索融合、文本分块、文件解析、目录树构建这类**输入→输出确定性极高**的函数，正是强度试验最划算的对象。

逐个看几个有代表性的，先看**检索的灵魂**——RRF 融合（rrf.spec.ts）：

```ts
// rrf.spec.ts（真实用例）
it('两路都命中的排在只命中一路的前面', () => {
  const vectorRows = [row('a'), row('b'), row('c')];   // 向量检索结果
  const keywordRows = [row('b'), row('d')];            // 关键词检索结果
  const merged = rrfMerge(vectorRows, keywordRows, 10);
  // b 两路都出现: 1/61 + 1/62；a: 1/61；d: 1/62；c: 1/63
  expect(merged[0].chunk_id).toBe('b');
  expect(merged.map((r) => r.chunk_id)).toEqual(['b', 'a', 'd', 'c']);
});

it('只依赖排名不依赖分数：分数不同的两路融合结果一致', () => {
  // ……同一份排名但分数不同，融合结果必须一致（RRF 的本质属性）……
});
```

为什么测它、为什么这些用例这么设计：

- RRF 的公式是 `score = Σ 1/(k + rank)`，**只认排名、不认分数**。第二条用例就是把这个"只认排名"的语义钉死——如果哪天实现里悄悄混进了相似度分数，这个测试会立刻报警，因为不同分数下融合结果不该变；
- `RRF_K` 用论文默认值 60 也被测了：这是检索质量的全局常数，谁也别想"优化"它而不自知；
- 这个文件**没有起数据库、没有调 pgvector**——输入就是两排假的行对象，几毫秒跑完。检索逻辑的正确性完全可以在不碰基础设施的前提下被验证，这正是纯函数测试的威力。

再看**文档入库第一道工序**——文本分块（text-splitter.spec.ts）：

```ts
it('重叠：相邻块尾部带 overlap 字尾巴，边界内容不丢', () => {
  const text = 'a'.repeat(400) + '边界词' + 'b'.repeat(400);
  const chunks = splitText(text, { chunkSize: 300, overlap: 50 });
  // 边界词至少出现在一个块里（拼接后可找回）
  expect(chunks.join('')).toContain('边界词');
  // 重叠生效：某块以重叠尾巴开头
  const tail = chunks[0].slice(-50);
  expect(chunks[1].startsWith(tail)).toBe(true);
});
```

这条用例验证的是 RAG 的生死线：**"切块会不会把关键内容切丢"**。如果分块器有 bug，把某个句子的中段丢掉，那么用户提问时这段内容就永远检索不回来——而单测用一段精心构造的文本（把"边界词"正好放在切点上）直接把这个风险钉死。9 个用例覆盖：短文本整块返回、超长多块且每块不超上限、重叠尾巴正确拼接、自然边界优先（句号不劈）、空输入返回空、代码分块的 prefix 拼接与超长单行硬切。

再看**NUL 事故的直接产物**——document-parser.spec.ts：

```ts
it('删除 NUL（\\u0000）——PG text 禁止存储的字符', () => {
  expect(sanitizeControlChars('a\u0000b')).toBe('ab');
  expect(sanitizeControlChars('\u0000')).toBe('');
});
it('删除其他 C0 控制字符，保留 \\t \\n', () => {
  expect(sanitizeControlChars('a\u0001b\u0007c\td\ne\u001f')).toBe('abc\td\ne');
});
```

这两条是第 5 节事故复盘里的"修复 1 的验收测试"——**先有事故、再有函数、再有测试**。测的不是"写得对不对"，而是"那个让全站崩溃的字符别再回来"。

`rag-aggregate`、`structured-splitter`、`code-indexer`、`file-profile`、`document-processor` 的思路一致：它们都是**输入输出确定性强、错了影响面大、且几乎无法用手工点页面验证**（谁会去构造一个 40 行的 markdown 表格来测分块？）。structured-splitter 有一条很妙："超长表格按行切分时每块都重复表头"——因为表格被切开后，只有表头重复才能让模型认出每块的列含义，这是 RAG 调优出来的语义细节，必须靠测试锁死。

**code-indexer.spec.ts（4 例）——代码文件 AST 级符号抽取**。给代码文件建索引时，需要知道里面有哪些函数/类/接口/常量以及它们的行号范围（供"按符号切块"）。它的测试覆盖了符号抽取最容易出错的三个面：

```ts
it('提取 TS 文件中的函数/类/接口/const', () => {
  // ……输入一段含 function/class/interface/type/const 的 TS 源码……
  const names = symbols.map((s) => `${s.kind}:${s.name}`);
  expect(names).toContain('function:parseUrl');
  expect(names).toContain('class:Parser');
  expect(names).toContain('interface:Options');
  // 行号范围：实现源码可按此切出
  expect(fn.startLine).toBeGreaterThanOrEqual(3);
  expect(fn.endLine).toBeGreaterThan(fn.startLine);
});

it('Vue SFC：抽取 script 块，识别 setup 顶层函数与组件名（行号对齐文件）', () => {
  // ……输入一段 .vue：<template> + <script setup lang="ts">……
  expect(symbols.some((s) => s.kind === 'function' && s.name === 'handleClick')).toBe(true);
  // 行号相对整个 vue 文件（script 内第 9 行，在文件里对应第 12 行附近）
  expect(fn.startLine).toBeGreaterThanOrEqual(9);
});
```

vue 那条用例尤其"凶"：抽取器要先剥掉 `<template>`、只分析 `<script>`，但**行号要算回整个 .vue 文件**（否则后续"按符号定位源码"会指错行）。这是本项目会真实索引自己仓库里的 `.vue` 文件才逼出来的需求——测试把它钉死后，谁改坏抽取逻辑都会立刻暴露。

**rag-aggregate.spec.ts（2 例）——全文模式的"把碎片拼回整篇"**。P0 全文模式（回答基于整个文档而非命中片段）需要把同一文档的多个 chunk 按 `chunk_index` 升序拼成一条全文。测试验证了两个**语义标记**：

```ts
it('多文档按 chunkIndex 排序拼接，每文档一条全文', () => {
  // 输入乱序的 chunk 行 → 输出按 chunk_index 排序拼好的全文
  expect(a.content).toBe('A1\nA2');
  expect(a.chunkIndex).toBe(-1);        // -1 = "全文块"标记（区别于检索命中的真实块号）
  expect(a.similarity).toBeNull();      // null = 非检索命中标记（来源面板据此不显示相似度）
});
```

这两行断言（`chunkIndex = -1`、`similarity = null`）保护的是一种**隐式协议**：前端来源面板用 `chunkIndex` 判断"能不能定位到原文片段"、用 `similarity` 决定"要不要展示相似度"——如果哪天实现把全文块的这两个字段填成了真实值，前端会把它当成"命中片段"去定位，UI 就错乱了。**测试在守护前后端之间看不见的约定**——这是纯函数测试最容易被低估的价值。

顺着这八个文件还能看出两个统一习惯：describe 用中文写"被测对象 + 业务语义"、spec 与被测源码同目录相邻——2.6 会连同命令一起讲透。

### 2.5 前端 3 个 spec：交互逻辑下沉到 utils 的回报

前端三个 spec 测的全是从巨石组件里**下沉出来的纯函数**（第 08 章 3.2 提过这个动作）——组件拆分顺便让它们变得可测：

**doc-tree.spec.ts（7 例）**——知识库文档管理页的目录树逻辑：

```ts
it('嵌套路径生成文件夹层级，文件夹排前、按名称排序', () => {
```

把"展平的文档数组"变成"带层级的树、文件夹统计 docCount/totalSize/chunkCount、展开/收起、按文件夹收集文件"——这套逻辑在页面里就是几百行 v-for + 递归，肉眼根本测不全，下沉成纯函数后 7 个用例覆盖所有分支。flat 的展开深度断言（`depth` 递增）锁死了"展开子文件夹"的语义。

```ts
it('浅色底（JS 黄）自动用深色文字', () => {
```

```ts
it('语言未知时转义 HTML，防注入', () => {

  expect(html).not.toMatch(/<script[\s>]/);   // 绝不能出现可执行的 script 标签
```

### 2.6 怎么跑这些测试：命令全景与组织习惯

根目录 `package.json` 有一条一键命令，把两端测试串起来：

```bash
# 根 package.json："test": "pnpm --filter @app/server test && pnpm --filter @app/web test"
pnpm test

# 分开跑：
pnpm --filter @app/server test          # 后端（jest，读 apps/server/jest.config.cjs）
pnpm --filter @app/web test             # 前端（vitest run，读 vite.config.ts 的 test 段）

# 后端只跑某一个文件 / 只看某个 describe（改到哪测到哪，秒级反馈）：
pnpm --filter @app/server exec jest rrf            # 只跑文件名含 rrf 的 spec
pnpm --filter @app/server exec jest --runInBand    # 串行跑全量（CI 同款姿势）
pnpm --filter @app/server exec jest -t "边界词"     # 只跑名称匹配的用例（中文也可匹配）
```

前端 vitest 同样支持只跑一个文件（`vitest run src/utils/doc-tree.spec.ts`）。CI 里跑的是全量（见 3.2），本地开发时"只跑自己动过的文件"就够了——**测试反馈要快到不打断思路**，这也是纯函数测试的另一个隐形红利：64 个用例全量也就几秒，改了立刻知道对错。

两个组织习惯顺带说透：

1. **spec 与被测源码同目录**：`utils/text-splitter.ts` 旁边就是 `utils/text-splitter.spec.ts`。改代码的人"低头就是测试"，新增文件时不会忘记配测试（忘配也会在 code review 时一眼看出"这个文件没有 .spec 邻居"）；
2. **describe 名 = 被测对象 + 业务语义**（如 `describe('rrfMerge 混合检索融合')`、`describe('splitText 递归字符分块')`）：失败信息可读，`jest -t` 也能按中文语义定向筛选——测试不只是"通过/失败"，还是**活文档**。

### 2.7 小结：这套测试布局的"性价比论证"

| 选择 | 为什么不那么做 |
|---|---|
| 测纯函数不测数据库/HTTP | 起真实依赖的测试慢、脆、要 mock 一堆东西；纯函数测试毫秒级且失败定位精确到函数 |
| 后端 38 例集中在前几章的"算法点" | 分块/RRF/解析是**不可见但决定质量**的代码，手工点页面验证不了 |
| 前端 26 例测 utils 不测组件 | 组件交互难测且频繁变；逻辑下沉 utils 后，一行断言覆盖一个分支 |
| 没有 E2E | 单人项目里 E2E 维护成本 > 收益，用"单测钉逻辑 + 手动回归主链路"替代 |

## 三、CI 双 job：为什么"检查"和"部署"必须分开

### 3.1 workflow 的骨架

`.github/workflows/deploy.yml` 的第一眼信息：

```yaml
name: CI/CD
on:
  push:
    branches: [main]      # push 到 main：检查 + 部署
  pull_request:
    branches: [main]      # 提 PR：只检查，不部署

jobs:
  check:   # job 1：代码检查与构建
  deploy:  # job 2：自动部署（needs: check，且仅 main）
```

两个 job 的职责划分是刻意的：

| | check | deploy |
|---|---|---|
| 触发 | 每次 push + 每个 PR | 只有 push 到 main |
| 做什么 | 全量质量门禁 | 把代码送上服务器 |
| 失败后果 | PR 合不进去、push 变红 | 线上保持旧版本（安全！） |
| 为什么存在 | **开发者最快知道"我改坏了没"** | **发布动作可控、可回滚、有记录** |

职责分离为什么重要，用两个场景说透：

1. **PR 阶段跑部署 = 灾难**：每个功能分支都去生产服务器上部署一次，线上会同时混着十个人的半成品。deploy 只在 `main` 上跑，天然保证"**只有合入主干的代码才可能上线**"——PR 是"能不能合"，main 的 push 才是"上不上线"。
2. **check 是 deploy 的前置闸门**：`deploy: needs: check`——检查不过，根本不会触发部署脚本。这比"部署脚本自己再查一遍"省事且可靠。

### 3.2 check job 十步拆解：4 步准备 + 6 步门禁，每一步为什么存在

```yaml
- uses: actions/checkout@v5                    # ① 拉取本次 push 的代码
- uses: pnpm/action-setup@v4                  # ② 装 pnpm（version: 11，与本地一致，避免 lockfile 兼容问题）
- uses: actions/setup-node@v5                 # ③ 装 Node（version: 24）+ cache: pnpm（缓存依赖加速）
- run: pnpm install --frozen-lockfile         # ④ 锁文件安装：任何人、任何时刻装出来都一样
- run: cd apps/server && npx prisma generate  # ⑤ 先生成 Prisma Client
- run: cd apps/server && npx tsc --noEmit     # ⑥ 后端类型检查
- run: cd apps/server && npx jest --silent    # ⑦ 后端 38 个单测
- run: pnpm --filter @app/web test            # ⑧ 前端 26 个单测（vitest）
- run: pnpm --filter @app/web build           # ⑨ 前端构建（vue-tsc + vite build）
- run: pnpm --filter @app/server build        # ⑩ 后端构建（nest build）
```

①~④ 是任何 CI 的"地基"（拉代码、装工具链、装依赖），⑤~⑩ 才是这道 job 真正的门禁，顺序也各有讲究：

- **⑤ 必须先于 ⑥**（workflow 注释原话）：全新环境不会自动生成 Prisma Client，缺了它 tsc 会报 `Prisma.sql` 等类型不存在——类型检查的前提是先把"从 schema 生成出来的类型"备好；
- **⑥ 后端类型检查**：`tsc --noEmit` 只查类型、不产出；挡的是"改了字段忘了改调用方"这一类编译期错误，比任何 lint 都硬；
- **⑦ 后端 38 个单测 / ⑧ 前端 26 个单测**：逻辑级回归——正是第 2 节逐个讲过的那 64 个用例；
- **⑨ 前端构建**：`apps/web` 的 `build` 脚本本身是 `vue-tsc --noEmit && vite build`——**前端类型检查其实藏在 build 里**，所以 ⑨ 不只是打包；
- **⑩ 后端构建**：`nest build` 产出 `dist/`，正是服务器上 `pm2` 跑的东西（`start:prod` = `node dist/main`）。

单测证明"逻辑对"，构建证明"产物出得来"，两者缺一不可：类型检查过了、单测绿了，构建仍可能因某个编译配置挂掉——⑨⑩ 就是把"上线前最后一分钟才炸"提前到 push 的那一刻。

### 3.3 最贵的教训：CI 假绿（GITHUB_OUTPUT）

这是本项目排障实录（部署运维/42）里的"最大坑"，也是本章最重要的面试素材。完整故事线：

**背景**：check 通过后，deploy job 需要一个开关——"服务器密钥配没配？没配就跳过部署，别让 CI 报红"。这个开关用 `secrets` 判断，但 GitHub Actions 的 **secrets 不能用在 `if:` 表达式里**，只能放进 env 给脚本读。于是有了"Check deploy config"这一步，把判断结果写进步骤输出：

```bash
# ❌ 事故版本（历史真实代码）：只 echo 到日志，没写进 GITHUB_OUTPUT
echo "deploy_enabled=true"
```

**现象链**（每一条都是真实的排查线索）：

1. NUL 事故的修复代码 push 后，**线上仍然复现**——代码没到服务器；
2. GitHub Actions 页面显示 run **Success，总时长仅 1m4s**——真部署（SSH + 装依赖 + 构建）不可能这么快，deploy job 根本没干活；
3. 服务器上 `pm2` 进程 uptime **75 小时**——从来没 restart 过；
4. 服务器 `dist` 里 `grep sanitizeControlChars` = 0——新代码根本没落地。

**真相**：GitHub Actions 的步骤输出**必须写入 `$GITHUB_OUTPUT` 文件**才能被后续步骤读取。错误写法只把 `deploy_enabled=true` echo 到了日志里，于是后续 `if: steps.deploy-check.outputs.deploy_enabled == 'true'` 拿到的**恒为空** → 条件永远不成立 → "Deploy to server" 步骤**每次静默跳过**。但 deploy job 没有失败步骤 → **整体显示绿**。假绿持续了多次 push，部署从未生效——**绿了，但等于没部署**。

**修复**（当前仓库 deploy.yml 已是修复版，注意两处 `>> "$GITHUB_OUTPUT"`）：

```bash
- name: Check deploy config
  id: deploy-check
  env:
    SERVER_HOST: ${{ secrets.SERVER_HOST }}
    SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
  run: |
    if [ -z "$SERVER_HOST" ] || [ -z "$SSH_PRIVATE_KEY" ]; then
      echo "未配置服务器密钥，跳过部署（CI 仍算通过）"
      echo "deploy_enabled=false" >> "$GITHUB_OUTPUT"   # ✅ 必须写进输出文件
    else
      echo "deploy_enabled=true" >> "$GITHUB_OUTPUT"    # ✅
    fi
```

**教训（面试话术）**：

> CI 绿 ≠ 部署成功。排障时先看 deploy job 内部的步骤是 executed 还是 skipped；绿 run 的**时长**是重要线索——真部署至少要几分钟，1 分钟以内的"成功"基本等于没部署。

配套的还有第三个隐藏坑：修好 GITHUB_OUTPUT 后 deploy 真跑了，又挂在 `/tmp/kb.tar.gz: Permission denied`——那是 9 月 1 日手动部署遗留的文件、属主是别的用户，`wget -O` 覆盖他人文件被拒。修复：下载前先 `rm -f /tmp/kb.tar.gz`，并在脚本开头 echo `whoami` 便于排查登录用户。**部署脚本要假设自己不是第一个碰这些文件的人。**

### 3.4 check 步骤失败 = 什么信号（红黄绿判读表）

学会读 CI 颜色之前，先背下"每一道 check 步骤失败说明什么"——它直接告诉你该去哪修：

| check 步骤失败 | 信号 | 去哪修 |
|---|---|---|
| `prisma generate` | Prisma schema 有语法错误，或依赖没装对 | `apps/server/prisma/schema.prisma` |
| `tsc --noEmit` | 后端类型错误 | 报错文件 + 类型定义 |
| `jest` | 后端逻辑回归（某个纯函数行为变了） | 对应的 spec 会精确指出是哪个函数 |
| `vitest` | 前端逻辑回归 | 对应 utils 的 spec |
| `web build` | vue-tsc 类型错误 或 打包失败 | 前端代码 / vite 配置 |
| `server build` | nest build 产物失败 | 后端代码 / nest-cli 配置 |

再背一个关键区分——**"设计内的跳过"和"设计外的跳过"不是一回事**：

| 看到的现象 | 是不是事故 | 判断依据 |
|---|---|---|
| PR 里 deploy job 显示 skipped | ✅ 正常 | deploy 本就只在 main 的 push 上跑 |
| main push 的绿 run，deploy job 显示 skipped | 🚨 假绿预警 | 除非服务器密钥没配（deploy-check 输出 false） |
| main push 的绿 run，deploy job 里 "Deploy to server" 步骤 skipped | 🚨 几乎肯定是 bug | 密钥明明配了却不部署 → 查上一步的输出是否写进了 GITHUB_OUTPUT |
| run 全绿但总时长 < 2 分钟（本项目的真部署要 3 分钟+） | 🚨 高度可疑 | 检查 deploy job 是否真的执行了 SSH |

假绿事故的深层教训其实是一句更朴素的话：**CI 是"脚本告诉你它干了什么"，不是"它真的干了什么"**。所以排障的第一步永远是核实"结果"而非信任"颜色"——进程 uptime、dist 里的代码、步骤的执行状态，这些是颜色背后的真相。

## 四、部署流水线拆解：GitHub Actions 到服务器的最后一公里

### 4.1 服务器最终架构（部署实录 docs/39 整理）

```
用户浏览器 ── http://<服务器公网IP>
        ▼
nginx (80) ─ gzip 压缩静态资源
  │  /api     → 反代 127.0.0.1:3000（SSE 关缓冲）
  │  /assets  → 前端 dist 静态文件（长缓存）
  │  /avatars → uploads/avatars（no-store，防头像缓存不刷新）
        ▼
pm2: kb-server（NestJS 编译产物 dist/main.js，端口 3000，只对内）
  ├─ PostgreSQL 16（docker，pgvector/pgvector:pg16，数据卷 /opt/kb/data/pg）
  ├─ Redis 7（docker，BullMQ 队列 + 会话缓存）
  └─ BullMQ worker：document-process / report-generate / agent-task 三条队列
```

要点：**3000 端口不对公网开放**，nginx 是唯一入口；前端是构建后的静态文件，由 nginx 直接吐给浏览器，NestJS 只处理 `/api`。

### 4.2 deploy job 的 SSH 脚本逐行拆解

deploy job 本体分两层：外层是**步骤壳**——`Check deploy config`（读 secrets、把 `deploy_enabled` 写进 GITHUB_OUTPUT，修复版已在 3.3 贴出）→ `Deploy to server`（受 `if: steps.deploy-check.outputs.deploy_enabled == 'true'` 门控，只有上一步输出 true 才执行）；内层才是真正干活的部分：`appleboy/ssh-action` 以 root 登录服务器后跑一大段 shell（`host`/`username`/`key` 全部来自 secrets，仓库里没有明文）。下面按真实脚本逐行拆内层（①~⑨ 与仓库 deploy.yml 一一对应）：

```bash
set -e                        # 任何一步失败立即退出（失败=本次部署中止）
cd /opt/kb

# ① 先删旧 tar 再下载：旧文件可能是其他用户创建，直接覆盖会 Permission denied
rm -f /tmp/kb.tar.gz
# ② 从 GitHub 加速代理下载代码包（为什么不用 git clone，见 4.3）
wget -q -O /tmp/kb.tar.gz "https://ghfast.top/https://github.com/<你的仓库>/archive/refs/heads/main.tar.gz"

# ③ 备份"机器上独有、代码库里没有"的东西：.env 与 uploads/
cp .env /opt/kb/.env.bak || true
mkdir -p /opt/kb/uploads.bak && cp -r uploads/* /opt/kb/uploads.bak/ 2>/dev/null || true

# ④ 全量替换代码目录（tar 解压无 .git，无法增量更新）
rm -rf ai-knowledge-base && tar -xzf /tmp/kb.tar.gz -C /opt/kb && mv ai-knowledge-base-main ai-knowledge-base

# ⑤ 恢复 .env 与 uploads（解压出的新目录没有 uploads/，必须先 mkdir 再 cp，
#    否则 cp 静默失败、头像/文档每次部署都丢——真实踩过的坑）
cp /opt/kb/.env.bak ai-knowledge-base/.env || true
mkdir -p ai-knowledge-base/uploads && cp -r /opt/kb/uploads.bak/* ai-knowledge-base/uploads/ 2>/dev/null || true

# ⑥ 装依赖（服务器无锁文件信任问题，用 --no-frozen-lockfile）
cd ai-knowledge-base && pnpm install --no-frozen-lockfile

# ⑦ 数据库迁移：.env 是唯一配置源，从项目根读取
npx prisma migrate deploy --schema apps/server/prisma/schema.prisma

# ⑧ 构建后端 + 重启进程
cd apps/server && npx prisma generate && pnpm build && cd ../..
export PATH="$PATH:$(npm prefix -g)/bin"    # pm2 全局 bin 不在 PATH 时的经典坑
pm2 restart kb-server

# ⑨ 最后构建前端静态文件
pnpm --filter @app/web build
```

### 4.3 为什么服务器不 git clone（偏门但重要的工程决策）

服务器**刻意不用 `git clone` + `git pull` 更新**，原因链：

1. **GitHub 链路不稳**：大陆服务器直连 GitHub 经常断（部署实录里真实报过 `GnuTLS recv error`）。走 `ghfast.top` 这类**加速代理下载 tar 包**反而稳定；
2. **tar 包没有 .git**：代理下载解压的是源码快照，所以"更新"= 每次**全量替换**目录。这带来一个副作用——代码目录里的用户文件（.env、uploads）每次都被抹掉，于是必须有第 ③⑤ 步的备份/恢复；
3. **git clone 方案被废弃**：早期曾为服务器配过专门的部署密钥对（kb_deploy），后被 tar 下载替代、弃用（docs/38 有记录）——少一把私钥少一个泄露面。

> 类比：git pull 像"看更新日志只拉增量"；tar 全量替换像"重新下一遍安装包"。后者笨，但在"到 GitHub 的路不稳定、又没有 .git 历史需求"的前提下，它反而最简单可靠。

### 4.4 uploads 的哲学：用户文件必须"部署不丢"

第 4.2 节里最绕的部分是 uploads 的备份恢复——为什么不能直接把 uploads 留在代码目录里、替换代码时不动它？因为替换是 `rm -rf ai-knowledge-base` 级别的**整目录清空**。目前方案是"备份 → 替换 → 恢复"三步曲，代码注释里也写明了两处真实教训：新目录**没有 uploads/，必须先 mkdir 再 cp**（否则 cp 静默失败、头像/文档每次部署都丢）。

更彻底的方案是把 uploads 和 .env 放到**代码目录之外**（数据卷/独立路径，部署时完全不触碰），这也是部署实录里标注的优化方向——"备份恢复"是现状，"移出代码目录"是更优解。**核心理念一句话：代码可以随时替换，用户的文件不行——凡是要长期存活的东西，都不该住在会被 rm -rf 的房子里。**

### 4.5 密钥配置：GitHub Secrets 与服务器公钥

自动部署链路一共要配三样东西（docs/38 详细讲了"凭据体系"）：

| 配置 | 位置 | 作用 |
|---|---|---|
| Secret `SERVER_HOST` | GitHub → Settings → Secrets → Actions | 服务器地址 |
| Secret `SSH_PRIVATE_KEY` | 同上 | CI 登录服务器的私钥（**值只在 GitHub Secrets，绝不在仓库**） |
| 公钥 | 服务器 `~/.ssh/authorized_keys` | 服务器"认识"这把私钥（白名单） |

私钥 = 钥匙（自己留着），公钥 = 锁（交给对方）。CI 拿私钥开锁，服务器用公钥验证，配对成功才放行。**没配 Secrets 时 deploy 自动跳过、CI 仍绿**——这是 3.3 节那个"部署开关"的用途：让 CI 在"还没配服务器"的阶段也能正常开发，不至于一 push 就红。

### 4.6 上线初期的坑：一张能当"部署经验"背的复盘表

部署实录（docs/39）把上线第一天踩的坑全部记了下来，这里按"坑 → 根因 → 对策"压缩成一张表——它同时是"如果让你从零部署这套系统，你会预先防什么"的答案：

| 坑 | 根因 | 对策（现在代码里能看到） |
|---|---|---|
| 迁移报 `extension "vector" is not available` | 官方 postgres 镜像不带 pgvector | 换 `pgvector/pgvector:pg16` 镜像 + `CREATE EXTENSION vector` |
| 迁移 SQL 报 `syntax error near "\u{feff}"` | Windows 生成的 migration.sql 带 UTF-8 BOM | 去 BOM 重跑 + `prisma migrate resolve --rolled-back` 标记失败迁移 |
| 迁移卡住报 P3009 | 首次失败记录留在 `_prisma_migrations` 表 | `prisma migrate resolve --rolled-back <name>` 后再 deploy |
| GitHub 直连断（GnuTLS recv error） | 大陆服务器到 GitHub 链路不稳 | 加速代理下载 tar（第 4.3 节），弃用 git clone |
| `pm2: command not found` | npm 全局 bin 不在 SSH 会话 PATH | `export PATH="$PATH:$(npm prefix -g)/bin"`（部署脚本里有） |
| 换头像 404 | nginx alias 目录和后端写入目录不一致 | 两端目录对齐到同一个 uploads 路径 |
| 换头像不刷新 | 头像 URL 固定 + 浏览器/nginx 缓存 | 前端 URL 带 `?v=n` 版本号 + nginx `no-store` |
| 带图消息重进会话"图片叠满屏" | 后端把 JSON 字符串直接返回，前端 `v-for` 字符串按字符遍历 | 后端 JSON.parse 成数组 + 前端 ChatMessageItem.vue 防御性解析（`Array.isArray` 判断，杜绝把字符串按字符拆成废图） |
| 进出对话页卡顿 | Transition 串行处理大组件树 + Canvas 每次重建 5000+ 粒子 | 去掉串行过渡、KeepAlive 暂停/恢复、流式 rAF 节流、渲染缓存（第 08 章） |

这张表最有价值的地方是**它横跨了部署期和体验期**——很多"部署问题"追到根因其实是应用层设计问题（JSON 双编码、Canvas 重建成本），反过来很多"体验问题"要改部署才能根治（nginx 缓存策略）。排障时不要被"这是运维问题"的标签框住。

再补一个藏在脚本顺序里的**抗风险设计**，值得在面试里主动讲：

> 部署脚本里 `pm2 restart kb-server` 是唯一的"切换点"——它之前的任何一步失败（`set -e` 直接退出）都不会动正在跑的进程：Node 进程把旧代码加载在内存里，只要不重启，线上就一直用旧版本稳定服务。所以**构建放在 restart 之前 = 天然带了一层"失败不切换"保护**：最坏情况是新代码没上去（run 变红），而不是线上被半成品打死。

## 五、生产事故复盘方法论：三个真实案例

### 5.1 通用方法论：复现 → 最小化 → 二分定位 → 修复 → 加回归测试

先立方法论，再用案例填充。任何线上问题都值得走这条链：

```
① 复现       把"偶发/环境相关"变成"稳定可复现"。不能复现 = 只能猜
② 最小化     砍掉无关因素，找到最小触发集（哪个文件、哪条路径、哪个字符）
③ 二分定位   在"输入链/代码链/部署链"里二分：先确定是哪一段（前端？后端？部署？数据？）
④ 修复       从根因修，不修表象
⑤ 回归测试   为这个 bug 写单测/检查项，保证它"永不复发"
```

案例一（NUL 崩溃）走的就是这条链；案例二（CI 假绿）的定位更是教科书级的"二分到部署链"。案例三（5.4 文档队列爆炸）换了一种形态：它没有"改一行逻辑"式的修复，而以**删掉一个功能**收尾——不是每起事故都以增加防御告终，有的以移除隐患告终。

### 5.2 案例 A：一条 NUL 字符炸掉整个入库链（PG 22P05）

**现象**（①复现——用户一操作就崩，天然可复现）：

> 用户上传一个含隐藏 NUL 字符的 HTML 文件，在对话里问"解析每行代码"，流式回答结束时落库崩溃：
> `PostgresError { code: "22P05", message: "unsupported Unicode escape sequence", detail: "\u0000 cannot be converted to text." }`

**关键知识点**：PostgreSQL 的 text 类型**明文禁止 NUL（\u0000）**——任何含 NUL 的字符串写入都会报 22P05（连 `chr(0)` 的比较都被禁止，这是附带发现：所以库里从来不存在 NUL 脏数据，写不进，清理 SQL 不需要）。

**②最小化 + ③二分**：问题在"落库"，但 NUL 从哪来？画一张"文本进数据库的路径表"，逐条核对哪条清洗了 NUL：

| 路径 | 清洗 NUL？ |
|---|---|
| 对话上传文件（extractFile） | ✅ 走 cleanText |
| 知识库入库 · md/txt | ✅ 走 cleanText |
| 知识库入库 · **代码/HTML** | ❌ **只 trim，漏清洗**（事故根因） |
| 模型回答落库 | ❌ 无兜底 |

根因链完整还原：用户把整个项目目录拖进知识库 → 损坏的 HTML 走 **code 路径**入库（该路径当时只做 `replace(/\r\n/g,'\n').trim()`，没删控制字符）→ NUL 跟着文本存进了 chunk → 对话绑定该知识库提问 → 检索命中含 NUL 的 chunk → 模型把这一行复述进回答 → 助手消息落库时 22P05 崩溃。

**④修复——三层防御**（不是只修一处）：

```ts
// 修复 1：源头清洗。document-parser.ts 新增导出（落库前第一道闸）
export function sanitizeControlChars(raw: string): string {
  return raw.replace(/[\u0000-\u0008\u000b\u000c\u000e-\u001f]/g, '');
}
// cleanText 改为复用它（行为不变），code 入库路径补上这层调用

// 修复 2：入库清洗。document-processor.service.ts 的 code 路径补 sanitizeControlChars

// 修复 3：落库兜底。chat.service.ts 里用户消息、助手回答、引用 sources JSON 全部清洗
// —— 防模型输出偶发夹带（最后一道闸，宁可多洗一次）
```

三层的关系是**纵深防御**：任何一层漏了，下一层还能接住。"源头不产生脏数据"是第一目标，但模型输出是不可控的第三方文本，所以**落库前必须有无条件兜底**。

**⑤回归测试**：为 document-parser.spec.ts 新增 5 个单测，验证 NUL 被删除、`\t \n` 被保留、普通文本原样返回——就是 2.3 节看到的那个文件。**先有事故，后有函数，后有测试。**

**复盘要点**：为什么排查链值得背？因为它展示了一种"**画路径表找漏洞**"的思维方式——不是盯着报错的那一行（落库），而是把所有"数据进库的入口"列出来逐个比对，二分出"哪条路径漏了清洗"。面试时把这套链讲下来，比背任何八股都硬。

### 5.3 案例 B：CI 假绿的排查链（详见 3.3）

案例 A 的代码修复 push 后**线上仍复现**——这正是案例 B 的入口。把它的排查链也提炼成方法论：

```
现象：修了还坏
├─ 第一步：代码真的上线了吗？看服务器 uptime（pm2）→ 75 小时没重启 → 没部署
├─ 第二步：为什么没部署？看 CI run → 总时长 1m4s、全绿 → 部署步骤被跳过
├─ 第三步：为什么被跳过？看 deploy job 步骤状态 → "Deploy to server" 是 skipped
└─ 第四步：为什么 skipped？看上一步输出 → GITHUB_OUTPUT 没写 → 条件恒不成立
```

**方法论要点：报错行号/进程 uptime/构建时长，都是"代码版本探测器"**。NUL 案例里报错行号是旧的、假绿案例里进程 uptime 是 75 小时——**任何"修了没效果"的问题，先怀疑"你修的那份代码到底在不在跑"**，再怀疑逻辑。

### 5.4 案例 C：文档队列爆炸事故（方案取舍的样本）

复盘一个项目早期出现过的队列事故：**文档队列爆炸**。

**机制**：解析队列之外曾实现过一个 `autoReindexStale()`——"自动重索引"函数：文档列表在**轮询刷新**（`findAll` 的上下文）时，会顺手把"`indexVersion` 落后于当前 `INDEX_VERSION`"的旧文档挑出来**重新入队**重建索引。本意是好的（索引规则升级后让旧文档自动追赶、用户无感），但触发点选错了地方——轮询每转一圈，`findAll` 返回的还是同一批"落后"文档 → 每次都把它们再次入队 → worker 刚处理完一批，下一轮轮询又补上一批，任务生成速度 ≥ 处理速度，形成自我放大的正反馈：

```
轮询 → findAll 看到 N 个落后文档 → 全部入队
  ↑                                    ↓
  └── worker 刚重建完，下一轮轮询又看到一批（重复入队）
```

队列长度只增不减：Redis 内存飙升、worker 无限空转，真正的用户上传任务被饿死在队尾。

**方案取舍**（这是比事故本身更值钱的思考过程）：

| 候选方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 保留自动重索引 + 加去重/幂等 | 用户省事 | 去重逻辑要覆盖所有入队路径，仍有漏网风险；自动动作的语义边界模糊 | 风险仍高 |
| **移除自动重索引，保留手动入口** | 语义清晰：只有用户显式操作才触发重建 | 用户要多点一次"重建" | ✅ 采纳 |

最终选择"**去自动化、留手动**"：入库（新增/替换/删除）由明确的上传动作驱动，本来就有事务边界；而"自动重索引"是一个**边界模糊的自我触发任务**——它想解决的"文档和源文件不一致"问题，实际上很少发生，为它承担队列爆炸的风险不值。

**今天的仓库对照**（给"改动真的落地了"一个可验证证据）：现在代码里已经搜不到 `autoReindexStale` 这个名字——它正是被这次取舍删掉的。`INDEX_VERSION` 目前只有一处写回：文档处理成功时（`document-processor.service.ts` 里 `data: { status: 'done', indexVersion: INDEX_VERSION }`），代码里没有任何"自动扫描→自动入队"的点；`indexVersion` 字段（02 章表结构里见过）保留下来，只当"文档是否落后于当前处理规则"的**标记**，配合显式的重索引入口（第 03 章）使用。

**通用教训**：凡是"系统自己给自己派活"的任务，都要问三个问题——**触发源是谁？会不会自我放大？没有它真的不行吗？** 队列型架构里，"自动"两个字要有比手动多十倍的警惕。

> 面试口径：讲这个事故的重点不是"队列爆了"，而是**复盘后主动做了一个减法**——把边界模糊的自动任务降级为显式动作。如果面试官问"你怎么看待自动化"，这就是"自动化不是越多越好"的真实论据。

### 5.5 事故复盘如何收尾：验证清单与"复盘文档"该记什么

一个事故从"修完"到"真结束"，中间还差一步：**验证**。NUL 事故的最终验证清单（docs/42 原文）是教科书级别的三步：

```text
① CI deploy 真执行 → 服务器 pm2 重启（进程 uptime 从 75 小时归零到 16 秒）
② 服务器 dist 里 grep 到新代码关键字（grep -c sanitizeControlChars = 1）
③ 用当初触发崩溃的同一个文件、同一个问题复测 → 不再报 22P05
```

注意每一步都在回答"**修复真的到达用户侧了吗**"：CI 绿只是第一步（且可能假绿），进程重启证明部署执行了，grep 证明代码真落地了，**复现原问题不再崩**才是最终裁判。这套"三级验证"（部署层 → 代码层 → 行为层）可以套用到任何线上修复。

复盘文档（docs/42 就是模板）建议固定记这几节，缺一不可：

| 复盘小节 | 记什么 | 为什么 |
|---|---|---|
| 现象 | 用户看到了什么、报错原文、发生位置 | 复现的起点，不记就没法回溯 |
| 排查链 | 每一步猜测、验证、排除（含走错的弯路） | 弯路比直路更有教学价值 |
| 根因 | 一句话说清"为什么 NUL 能一路走到数据库" | 根因不清的修复是碰运气 |
| 修复 | 改了什么、为什么这么改（含"为什么不那么改"） | 让后人理解取舍而非照抄 |
| 回归 | 补了哪些测试、验证清单的每一条 | 保证"永不复发"落到纸面 |
| 防复发 | 这个 bug 暴露了哪类系统性问题 | 单点修复治标，方法论升级治本 |

> 面试话术版：**"每次事故我都写复盘：现象 → 排查链 → 根因 → 三层修复 → 验证清单 → 补的回归测试。复盘文档不是给老板看的，是给三个月后的自己看的——同一类坑绝不允许踩第二次。"**

## 六、lint / format / git 规范：把规矩写进钩子

### 6.1 三层 Git 守门员

代码合入仓库前，有三道本地守门员（都在提交那一刻自动触发）：

```
git commit
  ├─ pre-commit 钩子 → npx lint-staged   （.husky/pre-commit）
  │     └─ 只对"本次暂存的文件"跑 prettier --write（.lintstagedrc.cjs）
  └─ commit-msg 钩子 → commitlint --edit  （.husky/commit-msg）
        └─ 校验提交信息格式（type + subject 规则）
```

husky 是"把钩子装进 .git"的工具：根 `package.json` 的 `prepare: husky install` 保证 `pnpm install` 后钩子自动就位（新机器 clone 下来不用手动配）。

### 6.2 commitlint：提交信息的格式警察

`commitlint.config.cjs` 继承 conventional 规范并自定义了 type 白名单：

```js
module.exports = {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'type-enum': [
      2,                          // 2 = error 级别
      'always',
      ['feat', 'fix', 'docs', 'style', 'refactor', 'perf', 'test', 'chore', 'ci', 'revert'],
    ],
  },
};
```

被拦下的两种典型提交：

```
feat: Add login button        # ❌ subject 以大写开头 —— conventional 继承规则
                                #    subject-case 禁止 sentence-case/upper-case
fix: login                    # ❌ type 不在白名单（应该用 fix 或 chore）
feat: add login button        # ✅ 通过
```

> 为什么连 subject 大小写都要管？提交信息会进入 `git log`、被自动生成 changelog 的工具解析、被同事扫读。**格式统一 = 历史可读**。门槛极低（多打一个小写字母），换来的是几千条提交信息风格一致。

### 6.3 lint-staged：只格式化"要提交的"

`.lintstagedrc.cjs` 就一行规则：

```js
module.exports = {
  '*.{ts,vue,js,json,md,cjs}': ['prettier --write'],
};
```

为什么 lint-staged 而不是"提交前全仓 prettier"？

1. **快**：大仓库全量格式化一次要几十秒，只处理暂存文件是毫秒级；
2. **不越权**：同事没提交的、正在改的文件，你的提交不该去动它；
3. **diff 干净**：只格式化自己改的行，PR 里不会混入无关的格式噪音。

（说明：仓库的 eslint 目前是本地手动跑的 `pnpm lint`（server + web 各配了 `--fix`），没有塞进 pre-commit——避免提交时被"自动改码"吓一跳。CI 的类型与构建检查承担了"防坏代码"的主力，见 3.2。）

## 七、监控与运维速查：真出事了，先跑什么

运维不是一门课，是一张**贴在手边的速查卡**。以下全部来自部署实录与排障实录（docs/38、39、42），地址/密钥一律用占位符。

### 7.1 一分钟体检

```bash
pm2 list                 # 后端进程状态（uptime 是"有没有重启过"的直接证据）
docker ps                # PG/Redis 容器是否活着
free -h && df -h /       # 内存 / 磁盘（2C4G 机器磁盘满=一切写操作开始报错）
pm2 logs kb-server --lines 50    # 后端日志：报错排查首选入口
```

### 7.2 后端（pm2）

```bash
pm2 logs kb-server --lines 50    # 看最近 50 行日志
pm2 restart kb-server            # 重启（部署脚本里最后一步就是它）
pm2 save                         # 保存进程列表（重启服务器后自动恢复）
```

后端跑的是 `apps/server/dist/main.js`（`nest build` 产物）——生产模式没有 dev 模式的 TS 即时编译开销，这也是"部署后上传变快"的原因之一（另一个原因是上传本来就是异步秒回，见 docs/38 的分析）。

### 7.3 前端与反代（nginx）

nginx 配置在服务器上（不在仓库内），关键点按部署实录整理：

```nginx
# 反代 API：SSE 流式必须关缓冲，否则"字是一个一个攒着到结束才吐"
location /api { proxy_pass http://127.0.0.1:3000; proxy_buffering off; ... }

location /assets { ... expires 30d; }   # 前端静态资源长缓存（文件名带 hash）
location /avatars { ... add_header Cache-Control "no-store"; }  # 头像防缓存

# 改完配置：先检查语法再平滑重载
nginx -t && systemctl reload nginx
```

SSE 关缓冲是对话流式能"边想边出字"的物理前提——nginx 默认会攒满 4KB/超时才吐，不关的话前端永远收不到流。

### 7.4 数据库

```bash
docker exec kb-postgres psql -U <用户> -d <库名> -c "SELECT count(*) FROM documents;"
# 备份：docker exec kb-postgres pg_dump -U <用户> <库名> > backup.sql
```

PostgreSQL 跑在 `pgvector/pgvector:pg16` 镜像（官方 postgres 镜像不带 pgvector 扩展——迁移时 `extension "vector" is not available` 是真实踩过的坑，部署实录有记录），数据卷在 `/opt/kb/data/pg`。

### 7.5 Redis 与队列

Redis 同时服务 BullMQ 三条队列：`document-process`（文档解析）、`report-generate`（研究报告）、`agent-task`（自主研究 Agent），默认键前缀是 `bull:`。

```bash
# 先看：某个队列里堆了多少任务（诊断"队列有没有堵"）
docker exec kb-redis redis-cli LLEN bull:document-process:wait

# 危险操作：清空某条队列（生产环境先想清楚——会把排队中的任务全丢掉）
docker exec kb-redis redis-cli DEL bull:document-process:wait \
  bull:document-process:active bull:document-process:delayed bull:document-process:failed

# 最稳妥的"重启大法"：队列卡死多半是 worker 假死，重启后端即可
pm2 restart kb-server
```

> 运维第一原则：**先看再动**。任何 `DEL`/`FLUSHDB` 前先 `KEYS`/`LLEN` 看一眼确认对象；队列里的任务丢了不可恢复，能靠重启解决的先用重启。

### 7.6 .env 职责与密钥安全（docs/38 全景）

服务器 `.env` 是**唯一配置源**（部署时从项目根读取跑迁移），每次 CI 部署自动备份到 `/opt/kb/.env.bak`。里面两套东西别搞混：

| 类别 | 变量示例 | 铁律 |
|---|---|---|
| 花钱的模型 Key | `SILICONFLOW_API_KEY`（Embedding/重排）、`TAVILY_API_KEY`（联网搜索） | 对话走用户 BYO Key（用户买单），平台只花 Embedding 的钱 |
| 免费的随机密钥 | `JWT_SECRET` / `JWT_REFRESH_SECRET` / `MODEL_KEY_SECRET` / `DATABASE_URL` 密码 | **改了要连带**：JWT 密钥改了所有人重新登录；`MODEL_KEY_SECRET`（AES-256-GCM 加密用户存的 Key）改了用户 Key 全解不开，要重绑 |

三条安全底线：**仓库里绝不出现任何 `sk-` 明文**；CI 私钥只在 GitHub Secrets；防火墙只开 22/80/443（3000 不对外）。

### 7.7 把速查串起来：一条完整故障响应时间线

把 7.1~7.6 的命令按"接到报警后 0~15 分钟"的时间线排一遍，就是一张可执行的响应剧本：

```text
第 0 分钟  先确认"最外层还活着吗"：curl -I http://<域名或IP>   # 404/502/超时各代表不同层挂了
第 1 分钟  后端进程与日志（排障首选入口）：
          pm2 list                                  # 进程在不在？uptime 多长？
          pm2 logs kb-server --lines 50             # 最近的报错栈
第 3 分钟  容器与资源：
          docker ps                                 # PG/Redis 活着吗（挂了是灾难级）
          free -h && df -h /                        # 内存/磁盘（磁盘满=写操作全崩）
第 5 分钟  反代与网络：
          nginx -t && systemctl reload nginx        # 配置坏了？改完忘重载？
          tail -n 50 /var/log/nginx/error.log       # 502 多半是后端没起来或超时
第 8 分钟  数据库与队列：
          docker exec kb-postgres psql -U <用户> -d <库名> -c "SELECT 1"   # 库活着？
          docker exec kb-redis redis-cli LLEN bull:document-process:wait   # 队列堵了？
第 10 分钟 二分定位到"哪一段"：前端静态页能开吗（nginx）？API 能通吗（后端）？
          数据能查吗（PG）？任务在跑吗（队列）？
第 15 分钟 处置 + 验证 + 记录：修复 → 用第 5.5 节的三级验证 → 补一条复盘
```

这张时间线刻意把"重启大法"放在后面——**先看再动**：pm2 restart 能解决 worker 假死，但解决不了"磁盘满了所以写库失败"；不先看日志就重启，等于带着眼罩修机器。

## 八、"线上问题怎么排查"：一套可以套用的方法论

把第 5 节的两个排查型案例（A：NUL 崩溃、B：CI 假绿）抽象成一张**排障流程图**，面试时照着讲，就是完整叙事：

```
现象来了
  │
  ├─ 先问：代码是"我想的那版"吗？
  │     pm2 uptime / 报错行号 / dist 里 grep 关键字 / CI 步骤是否真执行
  │     → 案例 B：75 小时 uptime + 1m4s 绿 run → "部署链"二分命中
  │
  ├─ 再问：数据是"我想的那样"吗？
  │     画"数据进系统的路径表"，逐条核对哪条漏了清洗/校验
  │     → 案例 A：code 路径只 trim 不洗 → "输入链"二分命中
  │
  ├─ 修复：从根因修，纵深防御（源头清洗 + 落库兜底，两层都要）
  │
  └─ 回归：为这个 bug 写测试/加检查项，保证永不复发
        → 案例 A 的 5 个 sanitize 单测
```

配套的三个高频追问口径：

| 面试官问 | 答法 |
|---|---|
| "遇到线上问题你一般怎么查？" | 复现 → 最小化 → 二分（代码/数据/部署三段）→ 根因修复 → 回归测试；先验证"跑的代码是不是我以为的那版" |
| "CI 绿了但功能坏了可能吗？" | 可能。案例：GITHUB_OUTPUT 没写导致部署步骤恒被跳过，run 全绿但线上是旧代码。判据：deploy job 步骤是否 skipped、总时长是否异常短、服务器 uptime |
| "怎么防止问题再犯？" | 三层：单测钉住纯函数逻辑、CI 门禁挡在合并前、事故后补回归测试（本项目的 sanitize 测试就是 22P05 事故的产物） |
| "你上线后遇到最难的问题是什么？" | 两个连环：NUL 崩溃（排查链 + 三层修复 + 5 个回归测试）→ 修复后仍复现 → 挖出 CI 假绿（GITHUB_OUTPUT）→ 又遇部署权限坑。完整故事线每段都能展开，是"真实线上排障"的最佳样本 |
| "部署失败了怎么办？用户会受伤吗？" | 会先慌但不会乱：`set -e` + pm2 restart 是唯一切换点——restart 前任何一步失败，旧进程仍在内存里稳定服务，线上不受影响；失败 = CI 变红 = 修好重推，不会出现"线上跑着半成品" |

## 九、动手实验

**实验 A：跑一次后端全量测试**
```bash
# 在仓库根目录执行（无需任何数据库/Redis/网络）
pnpm --filter @app/server exec jest --runInBand
```
预期输出：`Test Suites: 8 passed, 8 total`、`Tests: 38 passed, 38 total`（--runInBand 单进程串行跑，输出更稳；本项目实测约 7 秒跑完）。全部 38 个用例**零外部依赖**——这就是"测纯函数"的回报：任何人、任何机器、任何时候 clone 下来都能立刻全绿。

**实验 B：跑一次前端全量测试**
```bash
pnpm --filter @app/web test
```
预期输出：3 个 spec（doc-tree / file-icons / markdown）共 26 个用例通过。注意前端测试跑在 jsdom 环境（vite.config.ts 的 `test.environment`），因为 markdown 的复制按钮取码测试需要 DOM。

**实验 C：看 commitlint 拦下一条坏消息**
```bash
git add <任意文件>
git commit -m "feat: Add test"      # subject 大写开头 → 应被 commit-msg 钩子拦截并报错
git commit -m "feat: add test"      # 小写 → 通过
```
被拦的报错会指向 `subject-case` 规则（conventional 继承规则禁止 sentence-case/upper-case）。想本地快速验证规则本身，也可以直接跑：
```bash
npx commitlint --from HEAD~1 --to HEAD
```

**实验 D（可选）：给代码库加一条真测试**
在 `apps/server/src/modules/chat/` 新建 `demo.spec.ts`：测一个你刚写的纯函数，跑 `pnpm --filter @app/server exec jest demo`——体会"写一个用例 < 1 分钟、跑完 < 1 秒"的测试节奏，这是后端 38 例能长期维持全绿的原因。

## 十、自测题

1. **（面试必背）CI 假绿是怎么发生的？怎么一眼识破？**（提示：步骤输出必须写进 `$GITHUB_OUTPUT` 才能被后续 if 读取；没写 → 条件恒不成立 → 部署步骤静默跳过但 job 全绿。识破：看步骤是 executed 还是 skipped、run 总时长异常短、服务器 pm2 uptime 不归零、dist grep 新代码关键字为空）
2. **（面试必背）NUL 崩溃的完整排查链与三层修复是什么？**（提示：现象 22P05 → 画"文本进库路径表"二分出 code 路径漏清洗 → 源头 sanitizeControlChars + 入库路径补清洗 + 落库兜底三层防御 → 补 5 个单测回归；附带知识点：PG text 明文禁止 NUL，库中不会存在脏数据）
3. 测试金字塔是什么？本项目为什么把测试集中在"纯函数"上，而没有引入 E2E？（提示：单测便宜/稳定/定位准；分块/RRF/解析是看不见但决定质量、手工无法验证的逻辑；E2E 维护成本大于单人项目收益）
4. check 和 deploy 两个 CI job 为什么必须分开？PR 阶段如果也触发部署会怎样？
5. 服务器为什么用"下载 tar 全量替换"而不是 git clone/pull？这带来了什么必须处理的副作用？（提示：GitHub 链路不稳走加速代理；tar 无 .git 无法增量 → 每次全量替换 → .env/uploads 必须备份恢复；上传文件为什么"不该住在会被 rm -rf 的目录里"）
6. commitlint 拦什么样的提交？lint-staged 为什么只处理暂存文件而不是全仓格式化？（提示：type 白名单 + subject 大小写规则；速度、不越权、diff 干净）
