# 03 · 文档入库流水线：从上传文件到可检索向量

> **本章地图**

## 一、用户视角：把文件交给系统

打开知识库的文档管理页（`KnowledgeDocuments.vue`），看到的是 Cherry 风格的"选择即上传"界面：选文件/目录即自动上传，环形进度先"上传中"再"解析中"，列表里每行是 文件名 / 类型 / 大小 / 状态 / Chunk 数，md/ts 参与检索、图片等附件只保管，多级目录以文件夹树展示。

### 1.1 三种入口，一个动作

| 入口 | 触发 | 入库文件名 | 语义 |
|---|---|---|---|
| 顶部「选择文件」 | 文件多选 | 原名（`a.md`） | 追加/更新到根目录 |
| 顶部「选择目录」 | `<input webkitdirectory>` | 相对路径（`apps/server/src/a.ts`） | 整个项目一次进来，目录树被还原 |
| 文件夹行「上传到此处 / 替换」 | 同上 | `目标文件夹 + 相对路径` | 增量合入 / 整体替换某个虚拟文件夹 |

目录上传时文件名带相对路径，后端 `documents.filename` 直接存它，前端 `buildDocTree()` 据此渲染树。浏览器会把 multipart 里的路径分隔符剥掉，所以前端把相对路径放在**独立的 `name` 表单字段**里传（`uploadNameOf()`），而不是塞进 `file.name`。

### 1.2 两道自动过滤与硬性护栏

```ts
// 跳过构建产物/版本库/缓存目录，以及 .env、*.pem 等密钥文件（绝不让密钥喂给大模型）
const IGNORE_SEGMENT_RE =
  /(^|\/)(node_modules|\.git|dist|build|\.next|\.nuxt|coverage|__pycache__|\.idea|\.vscode|\.cache)(\/|$)/i;
const IGNORE_SENSITIVE_RE = /(^|\/)(\.env(\.[a-z0-9]+)?|[^/]*\.(pem|p12|pfx|key))$/i;
```

跳过时 toast「已自动跳过 N 个文件」；另有单次上限 `MAX_UPLOAD_FILES = 2000`、并发 `UPLOAD_CONCURRENCY = 5`（不并发 2000 个请求打爆服务器）。

### 1.3 环形进度为什么是两段式

```
uploading 阶段：ringPercent = 已传完文件数 / 总数    ← HTTP 传输进度
parsing 阶段：  ringPercent = (总数 − busy) / 总数    ← 轮询后端，busy = pending/processing
```

**"上传中"只统计 HTTP 传输**；文件传到服务器、接口返回后进入"解析中"。此时前端每 2 秒轮询一次列表，用 `mergeDocs()` 做**就地补丁**——已存在的行只更新 `status`/`error`/`chunk 数`，于是每完成一个文件那一行自己亮成"已完成"，你正在浏览的其他行与滚动位置不动。进度还写入 `sessionStorage`，**刷新页面不丢**（`onMounted` 发现还有 busy 文档就恢复轮询）。

### 1.4 替换的三种粒度

- **同名文件替换**（行内"更新"，`handleReplace`）：先上传新文件 → 轮询等它 done（`waitForDoc` 最多 60×2s）→ 才删旧文档——"新版本没成功，旧版本绝不动"（P0-3，见第八节）；
- **文件夹 → 文件夹**（`replaceFolderUpload`）：确认后并发上传，全部成功后删除本地已不存在的旧文档；
- **文件夹 → 单个文件**（`replaceFolderWithFile`）：文件放父目录，删掉整个文件夹。

> 用户感知到的"快/进度/替换"，全是**后端异步队列 + 前端轮询**的产物。下面从上传接口那几行代码开始逐层拆。

## 二、上传接口为什么"秒回"：异步边界画在哪

### 2.1 反直觉的事实：上传 ≠ 处理

看 `documents.controller.ts` 的上传接口，两个装饰器细节值得注意：

```ts
@Post(':id/documents')
@SkipThrottle() // 上传是批量操作（目录可能几百上千个文件），豁免全局 60/min 限流
@UseInterceptors(
  FileInterceptor('file', {
    storage: memoryStorage(),      // 先放内存，校验通过后才落盘（避免非法文件写盘）
    limits: { fileSize: MULTER_FILE_LIMIT }, // 兜底 50MB；真正的限制在 Service 按 .env 校验
  }),
)
upload(@CurrentUser('id') userId, @Param('id', ParseUUIDPipe) knowledgeBaseId,
       @UploadedFile() file, @Body('name') name?) {
  return this.documentsService.upload(userId, knowledgeBaseId, file, name);
}
```

而 `documents.service.ts` 的 `upload()` 只做五件事，**全程没有任何解析/分块/向量化**：

```ts
async upload(userId, knowledgeBaseId, file, name?) {
  // 1. 校验知识库归属（不属于当前用户 → 404）
  await this.knowledgeService.findOne(userId, knowledgeBaseId);
  // 2. 校验文件：非空、≤ MAX_FILE_SIZE_MB（默认 20MB）、内容非空
  const fileType = detectFileType(file.originalname);              // 类型识别，见第三节
  const originalName = name ? name : fixMojibakeFilename(file.originalname); // 修中文乱码
  // 2.5 内容哈希去重（见第九节）：同名+同内容 → 直接返回，不存盘不入队
  const unchanged = await this.prisma.document.findFirst({
    where: { knowledgeBaseId, filename: originalName, contentHash },
  });
  if (unchanged) return { skipped: true, filename: originalName };
  // 3. 存盘：UUID 改名防重名/防路径注入，扩展名保留
  const storedName = `${randomUUID()}.${fileType ?? rawExt}`;
  writeFileSync(join(UPLOAD_DIR, storedName), file.buffer);
  // 4. 建 Document 记录（status: 'pending'：已接收，待后台处理）
  const document = await this.prisma.document.create({ data: { ... } });
  // 4b. 同名旧文档标记 replacing（第八节的状态机）
  await this.prisma.document.updateMany({ where: { ... }, data: { status: 'replacing' } });
  // 5. 入队并立即返回——真正的重活在后台 worker 执行
  await this.queueService.addDocumentJob({ userId, documentId, knowledgeBaseId, ... });
  return this.prisma.document.findUnique({ where: { id: document.id }, include: { _count: ... } });
}
```

接口耗时 = 归属查询 + 磁盘写一个文件 + 一次 INSERT + 一次 Redis 入队 ≈ **几十毫秒**（大文件多花在写盘）——这就是用户感知的"秒回"。

### 2.2 为什么不能同步解析？

把解析放进请求线程会怎样？算一笔账：

- 单文件解析就可能秒级：PDF 要跑 `pdf-parse`、Word 要跑 `mammoth`；
- **向量化是外部 API**：一次嵌入走公网到硅基流动，几十到几百毫秒；一篇 100 块的长文要 10+ 次网络往返（批量 10），还带重试；
- **目录上传是 2000 个文件**：同步处理 = 一个 HTTP 请求挂几分钟——浏览器等不起，服务器连接被占死，用户关页面任务就断。

异步队列的本质是把**"请求生命周期"与"任务生命周期"解耦**：请求只负责"收货登记"，任务在 Redis 里独立存活——谁处理、失败几次、何时完成，都与当初那个 HTTP 请求无关。

### 2.3 队列配置即产品策略

`document-queue.service.ts` 是队列宿主：

```ts
const QUEUE_NAME = 'document-process';

onApplicationBootstrap() {
  this.queue = new Queue(QUEUE_NAME, { connection: this.connection });
  // concurrency 2：两个任务并行处理（embedding 是外部 API，并行能显著提速）
  this.worker = new Worker(QUEUE_NAME, async (job) => {
    await this.processor.processDocument(job.data as DocumentJobData);
  }, { connection: this.connection, concurrency: 2 });
}

async addDocumentJob(data: DocumentJobData): Promise<void> {
  await this.queue.add('process', data, {
    attempts: 3,                                 // 失败自动重试（如 embedding 临时网络错误）
    backoff: { type: 'exponential', delay: 2000 }, // 指数退避：2s → 4s → 8s
    removeOnComplete: true,                      // 完成即清，不让 Redis 堆积
    removeOnFail: 100,                           // 失败保留最近 100 条供排查
  });
}
```

| 配置 | 值 | 为什么 |
|---|---|---|
| `concurrency` | 2 | embedding 是 IO 等待多的外部 API，2 路并行吞吐翻倍又不至于打爆免费额度 |
| `attempts` | 3 | 公网抖动是常态，但 3 次不过说明文件真有问题 |
| `backoff` | 指数 2s 起 | 失败后立刻重试大概率再失败，指数退避给外部服务喘息时间 |
| `retryStrategy` | `min(times*500, 5000)` | Redis 重启后 worker 能可靠恢复消费 |
| `removeOnFail` | 100 | 失败的 job 是排查素材，保留现场 |

> **本节一句话**：上传接口做"最少必要工作"，重活交给**有重试、有并发上限、失败保留现场**的后台队列——用户看到的"快"，是架构把时间藏到了别处。

## 三、文件类型识别与分支：文本、代码、PDF/Word、附件

队列任务的数据载荷：

```ts
export interface DocumentJobData {
  userId: string;
  documentId: string;
  knowledgeBaseId: string;
  storedName: string;    // 磁盘文件名（uploads/uuid.txt）
  fileType: string;      // pdf / docx / md / txt / code
  originalName: string;  // 展示用文件名（可能带相对路径）
}
```

`fileType` 是整条流水线的"路由键"，由 `document-parser.ts` 的 `detectFileType()` 决定——**只认扩展名、不看文件内容**（这正是后面"二进制伪装"问题的伏笔）：

```ts
export type DocType = 'pdf' | 'docx' | 'md' | 'txt' | 'code';

export function detectFileType(filename: string): DocType | null {
  const ext = (filename.split('.').pop() ?? '').toLowerCase();
  if (ext === 'pdf') return 'pdf';
  if (ext === 'docx') return 'docx';
  if (ext === 'md' || ext === 'markdown') return 'md';
  if (ext === 'txt') return 'txt';
  if (CODE_EXTS.has(ext)) return 'code'; // CODE_EXTS：40+ 项，覆盖 ts/vue/py/go/json/yml/sql/…
  return null; // ← 关键：不在清单内 = 附件，不参与解析与检索
}
```

### 3.1 五种类型 → 三种命运

| 识别结果 | 代表 | 解析方式 | 分块方式 | 命运 |
|---|---|---|---|---|
| `pdf` | PDF | `pdf-parse` 抽取 | 字符分块 | 入队处理 |
| `docx` | Word | `mammoth.extractRawText` | 字符分块 | 入队处理 |
| `md` | Markdown | 直接 `toString('utf-8')` | **结构化分块**（P1/P2） | 入队处理 |
| `txt` | 纯文本 | 直接读 | 字符分块 | 入队处理 |
| `code` | 代码/配置 | 直接读 | **代码分块** + 符号索引 | 入队处理 |
| **null** | png/zip/未知扩展名 | 不解析 | 不分块 | **不入队**，status 直接 `done` |

`extractText()` 的 switch 就是这张表的实现：pdf → `pdfParse(buffer).text`；docx → `mammoth.extractRawText({ buffer }).value`；md/txt/code → `buffer.toString('utf-8')`；其余抛错。**附件分支**连队列都不进、同步完成（`documents.service.ts` upload 第 4a 步）：

```ts
if (!fileType) {
  await this.removeSameName(knowledgeBaseId, originalName, null); // 同名旧文档立即同步删
  const doc = await this.prisma.document.create({
    data: { ...,
      fileType: rawExt,   // 附件类型 = 原扩展名（png/zip/...），不是五种之一
      status: 'done',     // 附件无需后台处理，直接完成
      contentHash,
    },
  });
  return doc;             // chunk 数永远 = 0
}
```

为什么附件也入库？documents 表同时是"文件柜"（第 02 章：`fileType: png`、`chunk_count = 0` 即附件）。`fileType` 存 `rawExt` 是为了展示"这是 png/zip"。

> **设计判断**：可解析类型走"异步 + 状态机"，附件走"同步 + done"——附件没有"处理"这回事，不需要队列兜底。**一张表里两种生命周期**，靠 fileType 与 status 区分。

### 3.2 伪装的二进制在 worker 里被拦截

扩展名判定有个漏洞：**二进制改个 `.txt`/`.md`/`.ts` 后缀**（UTF-16 文本、损坏文件），UTF-8 强行解码得到一坨含 NUL/替换符的乱码。worker 开工第一件事就是"体检"（`document-processor.service.ts`）：

```ts
const rawText = await extractText(buffer, fileType as DocType);
const isCode = fileType === 'code';
// 二进制被误判成文本/代码：UTF-8 解码后 NUL/替换字符占比高 → 转为"附件"保管，不报解析失败
if (isCode || fileType === 'txt' || fileType === 'md') {
  const nullRatio = (rawText.match(/\u0000/g)?.length ?? 0) / Math.max(rawText.length, 1);
  const replRatio = (rawText.match(/\uFFFD/g)?.length ?? 0) / Math.max(rawText.length, 1);
  if (nullRatio > 0.01 || replRatio > 0.05) { // NUL > 1% 或 替换符 > 5%
    await this.prisma.document.update({
      where: { id: documentId },
      data: { status: 'done', error: null, fileType: 'bin' }, // 降级为附件
    });
    return; // 不解析、不分块、不向量化
  }
}
```

阈值是经验值：正常文本几乎无 NUL；UTF-16 中文按 UTF-8 解会大量产生 U+FFFD，占比轻松超 5%。**降级为附件而不是 failed**，是产品姿态：拖了个打不开的杂文件，系统"替你保管但不检索"，而不是列表出现一条刺眼的红色失败。

## 四、清洗：控制字符、NUL 崩溃事故与三层防线

### 4.1 事故现场：一次线上崩溃（PG 22P05）

`docs/部署运维/42-线上问题排查实录-NUL崩溃与CI假绿.md` 记录了真实事故：用户上传含隐藏 NUL 字符的 `14-综合案例.html`，对话里问"解析每行代码"，**流式回答结束时落库崩溃**：

```
PostgresError { code: "22P05", message: "unsupported Unicode escape sequence",
                detail: Some("\\u0000 cannot be converted to text.") }
```

**知识点：PostgreSQL 的 text 类型明文禁止 NUL（`\u0000`）**——任何含 NUL 的字符串写入都报 22P05（PG 内部用 C 字符串表示文本的历史约束，应用层绕不过，只能**进门之前删掉**）。事故链：

```
整项目目录拖进知识库 → 损坏的 .html 走 code 路径入库（当时只 trim，没删控制字符）
  → NUL 存进 chunks → 对话绑定该库提问，检索命中含 NUL 的块
  → 模型把该行复述进回答 → 落库 chatMessage.create → PG 22P05 崩溃
```

根因是**清洗路径不完整**：当时 md/txt 走 `cleanText`（会删控制字符），而 code 路径只做 `replace(/\r\n/g,'\n').trim()`——为保留缩进没走 cleanText，连控制字符也没删。**代码文件需要的是"删控制字符"而非"折叠空白"，两件事被错误绑定在一起。**

### 4.2 修复：抽出 sanitizeControlChars

修复 1：`document-parser.ts` 抽出独立清洗函数，`cleanText` 复用它（行为不变）：

```ts
/** 删除 C0 控制字符（保留 \t \n）。PG text 明文禁止 \u0000（NUL），落库会报 22P05。 */
export function sanitizeControlChars(raw: string): string {
  return raw.replace(/[\u0000-\u0008\u000b\u000c\u000e-\u001f]/g, '');
}

/** 文本清洗：去多余空行/空格/控制字符，统一换行 */
export function cleanText(raw: string): string {
  return sanitizeControlChars(
    raw
      .replace(/\r\n/g, '\n')        // Windows 换行 → Unix
      .replace(/[ \t]+/g, ' ')       // 连续空格/制表符 → 单个空格
      .replace(/\n{3,}/g, '\n\n'),   // 多余空行 → 最多一个
  ).trim();
}
```

正则区间要会读：`\u0009`（TAB）与 `\u000a`（LF）不在区间内——C0 里只保留 `\t\n`，`\u000d`（CR）删掉（换行统一到 `\n`）。单测锁死语义（`document-parser.spec.ts`）：

```ts
it('删除其他 C0 控制字符，保留 \\t \\n', () => {
  const input = 'a\u0001b\u0007c\td\ne\u001f';
  expect(sanitizeControlChars(input)).toBe('abc\td\ne');
});
```

修复 2：code 路径改为"**保留空白/缩进，但删控制字符**"（processor 里）：

```ts
// 代码文件不折叠空白/缩进（否则代码语义被破坏），但仍要删控制字符（\u0000 等）——
// 否则含 NUL 的代码/HTML 入库后，检索命中再落库会触发 PG 22P05 崩溃
const cleaned = isCode
  ? sanitizeControlChars(rawText).replace(/\r\n/g, '\n').trim()
  : cleanText(rawText);
```

### 4.3 三层防线：清洗为什么不能只做一次

NUL 能走到的路径不止入库一条。排查时梳理了**所有"文本进数据库"的路径**，逐条补漏，最终是三层防线：

| 层 | 位置 | 做什么 | 守哪条路 |
|---|---|---|---|
| 第一层：解析层清洗 | `document-parser.ts` + processor | `cleanText`/`sanitizeControlChars` 洗控制字符与脏格式 | 知识库入库的 md/txt/code |
| 第二层：入口体检 | processor 开工时 | 二进制误判检测，NUL/替换符占比高 → 降级附件 | 伪装成文本/代码的二进制（污染源在源头转掉） |
| 第三层：落库兜底 | `chat.service.ts` | 用户消息、助手回答、sources JSON 全部再过一次清洗 | 模型输出偶发夹带、对话上传、任何漏网之鱼 |

第三层长这样（chat.service 流式结束落库前统一清洗）：`content: sanitizeControlChars(question)`、`content: sanitizeControlChars(answer)`、`sanitizeControlChars(JSON.stringify({ kb, web }))`。

> 事故副产品知识点（docs/42 原文）：PG 连 `chr(0)` 比较都禁止，所以**数据库里从来不存在 NUL 脏数据——写不进去**。22P05 既是崩溃，也是最后一道天然防线：库永远干净，不需要清理 SQL；真正要防的是"崩在写入那一刻"。

**为什么防线要在每一扇门上？** 因为脏数据会在系统里旅行：chunk 入库 → 检索命中 → 模型复述 → 消息落库，任何一环漏了，炸点都在最下游最想不到的地方（一次聊天落库）。

## 五、分块演进史：从"切成 500 字"到"父子分块"

### 5.0 先回答"为什么必须分块"

整篇文档喂模型太长太贵，且"哪段相关"无从定位。分块让系统获得**检索粒度与引用粒度**——命中哪块就把哪块（连同上下文）给模型，还能回答"来源是《xx》第几段"。难处在于：**切法是检索质量的天花板**。这一节按时间线讲四代分块器，每一代都为了解决上一代暴露的真实问题：

```
v1    字符分块（splitText 500/100）         让"一切文件都能检索"
  ↓ 问题：表格行切碎、标题与正文分离、代码从函数中间劈开
v1.5  代码分块（splitCode 900 行边界）       解决代码语义破碎
  ↓ 问题：md 表格/长章节仍被拦腰切断
P1    结构化分块（splitStructuredMd 1200）  按标题分节、表格保表头、块带章节路径
  ↓ 问题：大章节/大表格超过单块上限，命中碎片缺上下文
P2    父子分块（parentId 自关联）            父块当容器、子块负责命中、命中取父块全文
```

### 5.1 第一代：递归字符分块（500/100）

`text-splitter.ts` 手写，思路抄 LangChain RecursiveCharacterTextSplitter：**优先按自然边界切，边界用完才硬切**。

```ts
const DEFAULT_SEPARATORS = ['\n\n', '\n', '。', '！', '？', '；', '，', ' '];

export function splitText(text: string, options: SplitOptions = {}): string[] {
  const chunkSize = options.chunkSize ?? 500; // 每块目标长度（字符）
  const overlap = options.overlap ?? 100;     // 相邻块重叠长度
  const chunks: string[] = [];
  recursiveSplit(text, DEFAULT_SEPARATORS, chunkSize, overlap, chunks);
  return chunks.filter((c) => c.trim().length > 0);
}
```

递归核心是**分隔符优先级**（段落 → 行 → 中文句读 → 空格 → 字符硬切）：

```ts
function recursiveSplit(text, separators, chunkSize, overlap, chunks): void {
  if (text.length <= chunkSize) { mergeChunk(text, chunks, chunkSize, overlap); return; }
  const [sep, ...rest] = separators;
  if (!sep) {
    // 没有可用分隔符：按 chunkSize 硬切（step 带 overlap，保证边界不丢）
    let pos = 0;
    while (pos < text.length) {
      mergeChunk(text.slice(pos, pos + chunkSize), chunks, chunkSize, overlap);
      pos += chunkSize - overlap;
    }
    return;
  }
  // 用"向后断言"分割，让每片保留末尾分隔符（如 "第一句。" 句号不丢）
  const parts = text.split(new RegExp(`(?<=${escapeRegExp(sep)})`));
  for (const part of parts) {
    if (part.length > chunkSize) recursiveSplit(part, rest, chunkSize, overlap, chunks);
    else mergeChunk(part, chunks, chunkSize, overlap); // 换更细的分隔符递归
  }
}
```

`mergeChunk` 管"装箱"：能并进上一块就并（避免一堆不足 100 字的碎块），并不下才开新块，**新块开头带上一块的尾巴 100 字**：

```ts
if (last.length + part.length <= chunkSize) {
  chunks[chunks.length - 1] = last + part;
} else {
  const tail = overlap > 0 ? last.slice(-overlap) : '';
  chunks.push(tail + part); // 答案若骑在块边界上，两边各有一份，不丢上下文
}
```

**为什么 overlap？** 答案内容若恰好被切在块边界，检索只会取到一半；重叠一段尾巴，边界内容在相邻两块各出现一次。参数在 processor 顶部定死：`CHUNK_SIZE = 500`、`CHUNK_OVERLAP = 100`。

**这一代解决**：任何纯文本都能切成语义相对完整、长度可控的块。**遗留问题**（驱动下一代）：① 表格行被切碎成无表头碎片；② 标题与正文分离、命中正文无章节上下文；③ 代码从函数中间被劈开。

### 5.2 第二代：代码分块（按行、空行边界、900 字符）

`splitCode()` 注释开门见山：**代码不适合用字符窗口切：会从函数中间劈开，语义碎掉**。策略换成**按行累积**，目标 900 字符，切点优先找空行（天然的函数/语句边界）：

```ts
export function splitCode(text: string, prefix = '', options: SplitOptions = {}): string[] {
  const target = options.chunkSize ?? 1000;
  const max = options.chunkSize ? options.chunkSize * 1.6 : 1800; // 硬上限，防"巨无霸块"
  const lines = text.split('\n');
  ...
  for (const line of lines) {
    if (line.length >= max) { /* 超长单行（minified 等）按 target-50 字符窗口硬切 */ continue; }
    const add = line.length + 1;
    if (curLen + add > target && cur.length > 0) {
      // 优先在空行处断开（函数/类/语句边界）
      const blankIdx = cur.map((l) => l.trim() === '').lastIndexOf(true);
      if (blankIdx > Math.floor(cur.length * 0.25)) { // 空行在合理位置（后 75%）
        push(cur.slice(0, blankIdx + 1));
        cur = cur.slice(blankIdx + 1);
      } else { push(cur); cur = []; }
    }
    cur.push(line);
    if (curLen >= max) { push(cur); cur = []; }
  }
  push(cur);
  return chunks;
}
```

两个细节值得背：**① `prefix` 拼到每块开头**——调用是 `splitCode(cleaned, \`文件: ${originalName}\`, { chunkSize: 900 })`，命中时模型立刻知道片段来自哪个文件（文本分块没有 prefix，"文件感"由 md 章节路径承担）；**② 单行 ≥ 上限（900×1.6=1440）按 850 字符窗口兜底**，否则得到"巨无霸 chunk"（嵌入失败或检索失真）。

**这一代解决**：函数/类不被劈开、片段自带文件身份。**遗留问题**：md 的表格/长章节依旧被切碎。

### 5.3 第三代（P1）：Markdown 结构化分块

`structured-splitter.ts` 注释写明动机："字符级分块会把文档拦腰切断——表格行切碎成无头碎片、章节标题与正文分离，检索命中一块时模型不知道它属于哪个章节、哪个表（本项目实测：docs/41 这类表格文档检索质量差）。"做法三步：

**① 按标题建层级栈，切成"章节段"，每段带完整章节路径前缀**：

```ts
const stack: Heading[] = [];
for (const rawLine of lines) {
  const m = /^(#{1,6})\s+(.+?)\s*#*\s*$/.exec(rawLine.trimEnd());
  if (m) {
    flush();  // 收尾上一节：cur 按当前路径切块输出
    while (stack.length && stack[stack.length - 1].level >= m[1].length) stack.pop();
    stack.push({ level: m[1].length, title: m[2].trim() });
    curPath = stack.map((h) => h.title.trim()).join(' > '); // 章节路径
    continue;
  }
  cur.push(rawLine);
}
```

于是 md 每块开头被注入"地址"，如 `W1 JavaScript 核心（上） > 周一 变量作用域与闭包`。

**② 表格当整体保留；超长表格按行切时重复注入表头**（表头上下文不丢）：

```ts
const tableText = [para.header, ...para.body].join('\n');
if (tableText.length <= maxChars) { pushBlock(tableText); continue; }
let group = []; let groupLen = para.header.length;
for (const row of para.body) {
  if (group.length && groupLen + row.length + 1 > maxChars) {
    pushBlock([para.header, ...group].join('\n')); // 每组重新拼上表头行
    group = []; groupLen = para.header.length;
  }
  group.push(row); groupLen += row.length + 1;
}
```

表格判定：连续 `|` 行且第二行匹配分隔行正则 `TABLE_SEP_RE = /^\|[\s:\-|]+\|?$/`。**③ 单块上限放大到 1200**（结构块保留整段上下文）；无标题文档自动降级：`return out.length ? out : splitText(text);`。

**这一代解决**：md 的"文件感 + 章节感 + 表格完整"。**遗留问题**：一个 5000 字的大章节切出的块之间没有层级关系——命中其中一小片时，拿不到"完整章节原文"。

### 5.4 第四代（P2）：父子分块——父块当容器，子块当探针

P2 的数据库形态第 02 章讲过（`parent_id` 自关联、父块 `embedding IS NULL` 是容器）。规划函数是纯函数（可单测，`planParentChildren` 在 processor 顶部）：

```ts
export function planParentChildren(
  parents: Array<{ id: string; content: string }>,
  childSize = CHILD_CHUNK_SIZE, // 500
): { embed; childRows } {
  const embed = []; const childRows = [];
  for (const p of parents) {
    if (p.content.length <= childSize) {
      embed.push({ id: p.id, content: p.content });         // 小章节：自己就是叶子
    } else {
      for (const piece of splitText(p.content, { chunkSize: childSize, overlap: CHILD_OVERLAP })) {
        childRows.push({ content: piece, parentId: p.id }); // 大章节：切成子块挂上去
      }
    }
  }
  return { embed, childRows };
}
```

落库在 `indexText()`（processor 里，上传队列与在线编辑共用）：**先删旧 chunk → 父块 createMany（不带向量）→ 按上述规划建子块（parentId 指向父块）→ 批量嵌入**。`indexText` 的分流签名一眼看懂：

```ts
// md 结构化父块 → 走 P2：父块 createMany 后 planParentChildren 再建子块，最后 embedRows(小父块+子块)
// prefix（代码）→ splitCode；其他 → splitText（均无父块，块自身即叶子）
const chunks = prefix ? splitCode(cleaned, prefix, { chunkSize: 900 })
                      : splitText(cleaned, { chunkSize: CHUNK_SIZE, overlap: CHUNK_OVERLAP });
```

落库后的形态（psql 可见三种行，动手实验会验证）：

```
chunks（文档 d1 = 两个大章节 + 一个小章节的 md）：
  id='p1'  第一章…(3000字)  parent_id=NULL  embedding=NULL   ← 父容器（不参与检索）
  id='p2'  第二章…(200字)   parent_id=NULL  embedding=[0.1…] ← 小父块 = 叶子
  id='c1'  第一章 第1片(500字) parent_id='p1' embedding=[0.2…] ← 子块（探针）
  id='c2'  第一章 第2片(500字) parent_id='p1' embedding=[0.3…] ← 子块（探针）
```

检索语义（第 04 章展开）：向量检索只命中带向量的行（子块/小父块），命中子块后沿 `parent_id` 找到父容器，**把父块全文交给模型**——模型拿到"整个第一章"，向量里存的又只是 500 字探针，不会因块太大而检索失真。**子块负责小、准（检索），父块负责大、全（喂模型）**；代价是一份大章节内容存两遍（父全文 + 子切片），刻意用空间换上下文。

### 5.5 四代分块对照（面试可背）

| 代 | 分块器 | 参数 | 服务对象 | 解决什么问题 |
|---|---|---|---|---|
| v1 | `splitText` | 500/100，自然边界优先 | txt、pdf、docx | 语义完整、长度可控的最小检索单元 |
| v1.5 | `splitCode` | 900，空行边界，块首带文件名 | code | 函数不被劈开；片段自带文件身份 |
| P1 | `splitStructuredMd` | 1200，章节路径，表格保表头 | md | 章节与表格上下文不丢；无标题自动降级 |
| P2 | 结构化父块 + `planParentChildren` | 父容器 + 500 子块 | md 大章节 | 命中取父块全文：检索准 + 上下文全 |

> **演进规律**（比背参数重要）：每一代都是**上一代在某类文件上实测检索质量差**之后的产物。骨架是**分块策略按文件类型分流**：`md → 结构化(+父子)`、`code → 代码分块`、其余 → 字符分块——这套分流本身由 INDEX_VERSION 管着（v1 只有字符分块，v2 起才有 P1/P2/C/A，见第十节）。

## 六、向量化：bge-m3 批量嵌入与 pgvector 写回

分块产出"文本"，要能语义检索得变成向量。整条流水线唯一的外部依赖：**硅基流动的 BGE-M3**（`embedding.service.ts`）。

### 6.1 为什么是 bge-m3、为什么走系统 Key

```ts
const EMBEDDING_MODEL = 'BAAI/bge-m3'; // 硅基流动，中文顶尖，1024 维
const BATCH_SIZE = 10;                 // 每批 10 个（bge-m3 支持批量，减少请求次数）
const MAX_RETRIES = 3;                 // 指数退避重试上限
const BATCH_DELAY_MS = 300;            // 批次间延时，防免费额度 QPS 限制
```

- bge-m3 中文检索顶尖，1024 维（schema 里 `vector(1024)` 的来源）；
- **嵌入不走用户的 BYO Key**（第 02 章 schema 注释）：嵌入质量必须全平台一致、成本可控，走平台自己的硅基流动 Key；BYO 只覆盖"生成"，不覆盖"索引"。

### 6.2 批量、退避、限速

```ts
async embedTexts(texts: string[]): Promise<number[][]> {
  const results: number[][] = [];
  for (let i = 0; i < texts.length; i += BATCH_SIZE) {
    const batch = texts.slice(i, i + BATCH_SIZE);
    results.push(...(await this.embedBatch(batch)));
    if (i + BATCH_SIZE < texts.length) {   // 批次间限速（最后一组不用等）
      await new Promise((r) => setTimeout(r, BATCH_DELAY_MS));
    }
  }
  return results;
}

private async embedBatch(batch: string[]): Promise<number[][]> {
  for (let attempt = 1; attempt <= MAX_RETRIES; attempt++) {
    try {
      const resp = await this.client.embeddings.create({ model: EMBEDDING_MODEL, input: batch });
      return resp.data.sort((a, b) => a.index - b.index).map((i) => i.embedding); // 按 index 排序保险
    } catch (err) {
      const delay = 500 * 2 ** (attempt - 1); // 500ms → 1s → 2s
      if (attempt < MAX_RETRIES) await new Promise((r) => setTimeout(r, delay));
    }
  }
  throw ...;
}
```

| 设计 | 为什么 |
|---|---|
| 批量 10 | 100 个 chunk 只调 10 次 API——请求数是主要成本与限流来源 |
| 指数退避 ×3 | 公网失败是常态，500ms→1s→2s 逐级退让；3 次不过抛错，交 BullMQ 的 attempts=3 再兜一轮（两层重试） |
| 批次间 300ms | 主动限速，好过被打回 429 再退避 |
| 按 index 排序 | 保证返回与输入一一对应 |

### 6.3 写回：为什么 embedding 用原始 SQL

Prisma Client 不认识 pgvector（第 02 章 `Unsupported("vector(1024)")` 占位），读写走 `$executeRaw`：

```ts
private async embedRows(rows: Array<{ id: string; content: string }>): Promise<void> {
  if (rows.length === 0) return;
  const vectors = await this.embeddingService.embedTexts(rows.map((r) => r.content));
  await this.prisma.$transaction(async (tx) => {
    for (let i = 0; i < rows.length; i++) {
      await tx.$executeRaw`
        UPDATE "chunks" SET "embedding" = ${toPgVector(vectors[i])}::vector WHERE "id" = ${rows[i].id}
      `;
    }
  });
}
```

注意**时序设计**：chunk 行先建（含 content，embedding 为 NULL），**向量后补**——这正是 schema 里 `embedding` 可空的原因：异步流水线必须"行先存在、向量后到"。父块永远不在 `embedRows` 名单里，所以 `embedding IS NULL` 不是"还没嵌入"，而是"设计上不嵌入"。

> **成本视角（面试加分）**：嵌入是流水线里唯一的真金白银（外部 API 按 token 计费）。前面所有"减少重复劳动"——内容哈希跳过、增量替换、显式重算——最终都汇到一句结论：**省嵌入调用**。

## 七、符号索引 C 与文件档案 A：给代码问答装"精确制导"

### 7.1 痛点：通用 RAG 答不好代码题

把整个项目目录喂进去后两类典型问题会翻车：**① 精确题**"`Settings.vue` 的 `onAvatarChange` 怎么实现的？"——问句与源码字面不同，向量难命中恰好含该函数名的一片；**② 泛化题**"登录鉴权的代码在哪个文件？"——答案散落几十个文件的几百个块里，文本片段检索根本没有"文件"粒度。解法不是换模型，而是给每个文件额外建两种结构化索引。

### 7.2 C：符号级索引（code_symbols）

`code-indexer.ts` 用 **TypeScript Compiler API 解析 AST**（typescript 包自带，行业标准，无第三方依赖）。处理器先声明可索引的语言：`CODE_SYMBOL_EXTS = ['ts','tsx','js','jsx','vue','mjs','cjs']`。核心提取（纯函数可单测）：

```ts
export function extractSymbols(fileName: string, source: string): CodeSymbol[] {
  const isVue = lower.endsWith('.vue');
  if (isVue) {
    // vue 先抽 <script> 块再喂 TS parser，并记录行号偏移（script 内行号 → 文件行号）
    code = VUE_SCRIPT_RE.exec(source)[1];
    lineOffset = source.slice(0, m.index).split('\n').length - 1;
  }
  const sf = ts.createSourceFile(fileName, code, ts.ScriptTarget.Latest, true,
                                 isTsx ? ts.ScriptKind.TSX : ts.ScriptKind.TS);
  for (const stmt of sf.statements) {
    const sym = symbolFromStatement(sf, stmt, lineOf, isVue);
    if (sym) symbols.push(sym);
  }
  return dedupe(symbols); // 按 kind:name 去重（vue 里 script 块与类型声明可能撞名）
}
```

`symbolFromStatement` 认六种顶层声明 → 产出 `{ name, kind, signature, startLine, endLine }`：`FunctionDeclaration → 'function'`、`ClassDeclaration → 'class'`、`InterfaceDeclaration → 'interface'`、`TypeAliasDeclaration → 'type'`、`EnumDeclaration → 'enum'`、`VariableStatement → const x 或箭头函数 → 'const'|'function'`。vue 特判：组件只有 `defineOptions({ name })` 时也产一条 `kind:'component'` 符号。处理器落库（**body 是按行号切出的实现快照**）：

```ts
await this.prisma.codeSymbol.createMany({
  data: symbols.map((s) => ({
    documentId, filename,
    symbolName: s.name, kind: s.kind,
    signature: s.signature, // 单行签名（120~200 字截断）
    body: lines.slice(s.startLine - 1, s.endLine).join('\n').trim(), // 实现源码快照
    startLine: s.startLine, endLine: s.endLine, // 1-based，引用可跳源文件对应行
  })),
});
```

检索语义（第 04 章展开）：问题出现 `onAvatarChange` → **符号名精确命中**（`@@index([symbolName])` 支持跨文件"谁定义了 X"）→ 直接返回 `body` 实现源码，**不靠向量碰运气，也不用回磁盘读原文件**。

### 7.3 A：文件档案（file_profiles）

符号解决"精确名字"，档案解决"泛化定位"（schema 注释原话："检索先档案命中锁定文件，再文件内检索——中文泛化问题也能定位到具体文件"）。`buildFileProfile()` 按类型生成 300~800 字档案文本：

```ts
const parts: string[] = [`文件：${filename}`, `类型：${typeName}`];
if (fileType === 'md') {
  // md 档案 = 文件名 + 章节标题地图（前 40 个标题，按层级缩进）
  parts.push('文档章节结构：');
  for (const m of headings) parts.push(`${'  '.repeat(depth)}${m[2].trim()}`);
} else if (fileType === 'code') {
  // 代码档案 = 文件名 + 符号清单（与 C 配合，前 60 个）→ “- 函数 uploadDocument（签名…）”
} else {
  parts.push('内容摘要：'); // 前 300 字
}
```

处理器把它单独向量化后 upsert 进 `file_profiles`（1:1 由 `documentId @unique` 表达），再 `$executeRaw` 写回档案自己的 embedding。注意 `indexProfile` 被整个 try-catch 包住、失败只记日志——**档案是增强层，任何失败不影响文档主流程**（静默降级）。

### 7.4 两级检索：先锁文件，再进文件

```
问"登录鉴权的代码在哪个文件？" → ① 档案层检索（file_profiles 向量，文件粒度）→ 锁定文件
                                 → ② 文件内检索（chunks 向量，scope 限该文件）→ 具体函数片段
问"Settings.vue 的 onAvatarChange 实现" → ① 符号名精确命中（symbol_name）→ 直接返回实现源码+行号
```

| 索引 | 表 | 粒度 | 擅长的问题 | 命中返回物 |
|---|---|---|---|---|
| 向量分块 | chunks | 500 字片段 | "……怎么实现的？"语义相近正文 | 片段（或父块全文） |
| C 符号 | code_symbols | 单个符号 | "onAvatarChange 实现"名字精确 | 实现源码 + 行号 |
| A 档案 | file_profiles | 整个文件 | "代码在哪个文件"泛化中文问 | 档案（文件定位） |

**一句话**：C 是"查字典"，A 是"查目录"——通用 RAG 只有正文一种检索物，代码问答需要三种各司其职。

## 八、同名替换状态机：replacing 的诞生与并发安全

### 8.1 场景与朴素方案的坑

用户经常**重传同名文件**（改了 `a.md` 再拖一次、改一行代码就重拖整个目录）。朴素方案"上传同名直接删旧版"有两个坑：① **中间真空期 + 失败丢数据**——新文件还没解析完旧版就没了，新文件解析失败时两头空；② **新旧并存像"新增"**——先建新再删旧，列表瞬间两个 `a.md`，用户以为传重复了。

### 8.2 第五态 replacing：新成功才删旧

第 02 章讲过 documents.status 官方四态之外还有第五态 `replacing`。它贯穿两端：

**上传端**（upload 第 4b 步）——新记录创建后**立刻**把同名稳定态旧版标成 replacing（列表显示"替换中"而非新旧并存）：

```ts
// 同名旧文档立即标记"替换中"（列表显示"替换中"而非新旧并存被误认为"新增"；
// 新文档解析失败时旧文档自动恢复为 done，不丢数据）。
// P0-4：只标稳定态旧版（done/failed），绝不动 pending/processing——
// 否则两个并发同名上传会互相把对方标成 replacing，双双误删。
await this.prisma.document.updateMany({
  where: { knowledgeBaseId, filename: originalName,
           id: { not: document.id }, status: { in: ['done', 'failed'] } },
  data: { status: 'replacing' },
}).catch(() => undefined); // 幂等：没有旧版时啥也不发生
```

**处理端**（processDocument）——新文档**全部处理成功之后**才删旧版：

```ts
// P0-4：只删稳定态旧版（done/failed/replacing），不删 pending/processing——
// 并发同名上传时，处理中的对方文档绝不会被删（否则双双消失/孤儿 chunk/误删磁盘）。
// 后完成者覆盖先完成者（替换语义），记录与磁盘始终一致。
const olds = await this.prisma.document.findMany({
  where: { knowledgeBaseId, filename: originalName,
           id: { not: documentId }, status: { in: ['done', 'failed', 'replacing'] } },
  select: { id: true, filepath: true },
});
for (const old of olds) {
  await this.prisma.document
    .deleteMany({ where: { id: old.id, status: { in: ['done', 'failed', 'replacing'] } } })
    .catch(() => undefined); // 幂等：对方可能已被另一并发任务删除
  try { unlinkSync(storedPath(old.filepath)); } catch { /* 文件可能已不存在 */ }
}
```

**失败端**（catch 块）——新文档失败时把被标成 replacing 的旧版**恢复为 done**，旧数据一条不丢：

```ts
catch (err) {
  await this.prisma.chunk.deleteMany({ where: { documentId } }).catch(() => undefined); // 清半成品
  await this.prisma.document
    .update({ where: { id: documentId }, data: { status: 'failed', error: message } })
    .catch(() => undefined);
  // 新文档失败 → 恢复被标记为"替换中"的旧文档（不丢旧数据）
  await this.prisma.document.updateMany({
    where: { knowledgeBaseId, filename: originalName, status: 'replacing' },
    data: { status: 'done', error: null },
  }).catch(() => undefined);
}
```

完整状态机（第 02 章画过，这里补"为什么"）：

```
        upload/入队               worker 开工              全部成功
  (无记录) ──────► pending ──────────► processing ──────────► done
                       │                   │                   ▲
                       │  worker 失败       │ worker 失败       │ 上传同名新文件
                       ▼                   ▼                   │
                     failed ◄──────────── failed               │
                       ▲                                       │
                       │ upload 同名文件（新文档入队）           │
                       └────────────── replacing ◄─────────────┘
                        （旧版被标记"替换中"：新文档成功后删除 / 失败后恢复 done）
```

### 8.3 并发安全：为什么"只动稳定态"是生死线

若 upload 把 pending/processing 的同名文档也标成 replacing，两个并发同名上传会互相标；worker 若也删 pending/processing，A 的 worker 会删掉 B 的进行中文档（双双消失/孤儿 chunk/误删磁盘）。所以两端的白名单一致且只含**稳定态**：

| 操作 | 允许触碰的状态 | 不允许 |
|---|---|---|
| upload 标 replacing | `done` / `failed` | `pending` / `processing`（对方也在传） |
| worker 删旧版 | `done` / `failed` / `replacing` | `pending` / `processing` |
| 失败恢复旧版 | 仅 `replacing` | 其他 |

加上 `deleteMany + where status` 与 `.catch(() => undefined)` 的**幂等删除**（并发删除只成功一次），最终语义：**后完成者覆盖先完成者，记录与磁盘始终一致**。

### 8.4 两个配套分支

- **附件替换走同步**：附件没有 worker 可依赖，上传时直接 `removeSameName(kb, name, null)` 删掉同名旧文档再建新的（第三节）——附件处理没有"成功/失败"过程，所以连 replacing 都不需要；
- **前端行内"更新"双保险**（`handleReplace`）：若新文件名 ≠ 旧文件名，前端先 upload、等新文档 done，再手动 delete 旧文档；文件名相同则完全交给后端队列自动替换（P0-3：新文档 failed 或超时 → 保留旧文档并明确提示"已保留原文档"）。

> **本节一句话**：replacing 不是为好看加的状态，它是**"先建新、成功才删旧"这个不可中断语义**在状态机里的显式表达——把"替换"变成两个可观察、可恢复的步骤，而不是一次危险的删除。

## 九、增量向量化：contentHash 去重，让"整目录重拖"几乎零成本

### 9.1 场景：目录重传是最常见操作

拖整个项目进知识库后改了三个文件，第二天**再把整个目录拖一遍**——用户心智是"同步更新"，服务器视角是 800 个上传请求。没有去重 = 800 个文件全部重新解析、重新调嵌入 API，而其中 797 个内容根本没变。

### 9.2 方案：SHA-256 指纹，同名 + 同内容才跳过

```ts
/** 文件内容哈希：SHA-256（增量向量化去重依据，与文件名无关） */
function hashFileContent(buffer: Buffer): string {
  return createHash('sha256').update(buffer).digest('hex');
}
```

上传第 2.5 步**先算哈希再决定要不要干活**（第 02 章 documents.content_hash 的来源）：

```ts
const contentHash = hashFileContent(file.buffer);
const unchanged = await this.prisma.document.findFirst({
  where: { knowledgeBaseId, filename: originalName, contentHash },
  select: { id: true },
});
if (unchanged) {
  this.logger.log(`内容未变化，跳过: ${originalName}`);
  return { skipped: true, filename: originalName };
}
```

命中时：**不存盘、不建记录、不入队**，直接返回 `{ skipped: true }`。前端据此统计"N 个内容未变化已跳过"（`uploadSkipped`），不计入解析环形进度（`docs/功能档案/29-增量向量化.md` 记录了这次功能）。

### 9.3 判定的精确语义（都是陷阱题）

| 场景 | contentHash 相同？ | 结果 |
|---|---|---|
| 同名 + 同内容重传（没改过） | 是 | **跳过**（目标场景） |
| 同名 + 内容变了 | 否 | 正常替换（走第八节状态机） |
| 改名 + 同内容 | 是，但 filename 不同 | **不跳过**，正常创建（文件名也是文档身份） |
| 换知识库重传 | knowledgeBaseId 不同 | 不跳过（每库独立） |

哈希绑定的三元组是 **(knowledgeBaseId, filename, contentHash)**。只看内容不行的原因：同名文档本来就要被替换，若只按哈希去重，用户改 1 个字节想"更新"就永远被跳过。**contentHash 回答"这一个文档变没变"，filename 回答"是不是同一个文档"，两者同时成立才跳过。**

> **设计眼光**：哈希比对是本地 CPU 运算几乎免费，而它省下的每一次嵌入调用都花钱——它是"省最贵一步"思路在入口的收口。

## 十、INDEX_VERSION 版本化与重算：规则升级了，旧文档怎么办

### 10.1 问题：派生数据的"保质期"

chunks/symbols/profile 都是按"当时的处理规则"切的。规则一升级（纯字符分块 → P1/P2/C/A），**库里所有旧文档的块都按旧规则切**——不是坏了，是"过时了"。怎么知道谁过时？怎么让它按新规则重来？

### 10.2 方案：文档记录"上次按哪版规则处理的"

`document-processor.service.ts` 顶部定义规则版本常量：

```ts
/**
 * 文档处理规则版本：分块/符号/档案/向量化规则变化时 +1——
 * v1 = 基础字符分块 + 向量化
 * v2 = 结构化分块(P1) / 父子分块(P2) / 符号索引(C) / 文件档案(A) 全量规则
 */
export const INDEX_VERSION = 2;
```

每次处理成功把当前版本写进文档：`data: { status: 'done', indexVersion: INDEX_VERSION }`。于是 `documents.index_version`（schema 默认 1）= 每篇文档的"出厂规则版本"，与常量对照即知谁落后。

### 10.3 重算怎么做：显式的"重新索引"，而不是自动

落地入口是三个接口 + 前端按钮（`documents.controller.ts` / `documents.service.ts`）：

| 接口 | 动作 | 返回值 |
|---|---|---|
| `POST :id/documents/:documentId/reprocess` | 单文档重跑全流程 | `{ reprocessed, filename }` |
| `POST :id/documents/reprocess-all` | 整库全部可解析文档入队 | `{ reprocessed, skipped }` |

`reprocessAll` 的写法要点：**直接对已有文档入队、绕过 contentHash 去重**（去重是上传优化，重算必须强制执行）；跳过附件与磁盘文件已丢失的文档；`@SkipThrottle()` 豁免限流：

```ts
async reprocessAll(userId: string, knowledgeBaseId: string) {
  await this.knowledgeService.findOne(userId, knowledgeBaseId);
  const docs = await this.prisma.document.findMany({ where: { knowledgeBaseId }, select: {...} });
  let queued = 0, skipped = 0;
  for (const doc of docs) {
    const fileType = detectFileType(doc.filename);
    if (!fileType) { skipped++; continue; }                       // 附件不参与重算
    if (!existsSync(storedPath(doc.filepath))) { skipped++; continue; } // 文件已清理
    await this.queueService.addDocumentJob({ ... });              // 入队，走同一队列
    queued++;
  }
  return { reprocessed: queued, skipped };                        // 数字可观察
}
```

前端工具条"重新索引"按钮即调用这两个接口（注释："处理规则升级后旧文档重跑，无需删除重传"）。

**注意常量注释里"下次访问知识库时自动后台重算（用户无感）"这句**——那是早期迭代的设想（autoReindex），最终**没有落地成"访问即自动重算"**，而是做成显式按钮。为什么？把"自动重算"的代价摊开：

| 风险 | 说明 |
|---|---|
| **读操作引发写风暴** | 打开知识库只是 GET，若触发整库重嵌入 = 一次无害浏览烧掉几千次嵌入 API、占满 worker 并发（别人的上传全在排队） |
| **不可预期** | 用户三个月没来，一来就被动等几分钟后台任务，没人能预判"打开页面"会触发什么 |
| **不可见、难验证、难回滚** | 自动任务失败往往是静默的；手动触发有按钮、有 `{reprocessed, skipped}` 计数、有状态流转可观察 |

最后一条与 docs/42 的教训同构：CI 假绿事故根因是"**看似成功其实没跑**"（`GITHUB_OUTPUT` 没写导致部署静默跳过）；自动重算的隐患是反面——"**看似没动其实在偷偷重算**"。**凡是会改数据的批量动作，都应显式触发、进度可见、结果可数**。于是版本升级流程是：发版把 INDEX_VERSION +1 → 界面上点一次"重新索引"（或跑脚本）→ 用 `index_version` 过滤确认全部更新。

> 顺带纠正易混点：v1→v2 是**真实发生过的升级**（v2 = P1/P2/C/A 全量规则）。如果你在库里看到 `index_version = 1` 的 done 文档，那批就是"还没按 v2 重算"的历史遗留——重索引按钮正是为它们准备的。

## 十一、编辑内容：写回磁盘，让"两份事实"再次一致

### 11.1 前情：磁盘文件与索引的分岔

第 02 章元规则：**磁盘文件是事实，chunks/symbols/profile 是派生数据**。用户编辑时若只重算索引不改磁盘，就会出现"检索到新内容、下载却拿到旧文件"的分裂。`documents.service.ts` 的 `updateContent()`（PATCH）同时处理改名与改内容，这里只讲改内容链路：

```ts
if (dto.content !== undefined) {
  const cleaned = cleanText(dto.content);
  if (!cleaned) throw new BadRequestException('内容为空，无法入库');

  // 纯文本类（md/txt/代码）：编辑即真实改文件——写回磁盘，保证查看/下载/再次编辑看到新内容
  // （docx/pdf 只能抽取纯文本编辑，写回会破坏原格式 → 保持只更新索引，原文件仍为原格式内容）
  const isPlainText = ['md', 'markdown', 'txt', 'code'].includes(doc.fileType);
  if (isPlainText) {
    writeFileSync(storedPath(doc.filepath), dto.content, 'utf8'); // ← 写回原文件
    data.fileSize = Buffer.byteLength(dto.content, 'utf8');       //    同步更新大小
  }

  // 重新分块 + 向量化（向量库同步更新，之后按新内容检索）
  // md 文档走结构化分块（按标题分节、表格保表头，块带章节路径——P1）
  const structuredChunks = doc.fileType === 'md' ? splitStructuredMd(cleaned) : undefined;
  const chunkCount = await this.processor.indexText(documentId, cleaned, undefined, structuredChunks);
  data.status = 'done';
}
```

### 11.2 按类型分流的"写回策略"

关键判断是 `isPlainText`：md/txt/code 是**无损可写回**的类型——编辑器拿到的文本就是文件全部内容，直接 `writeFileSync` 覆盖原文件，然后走**与上传队列完全相同的 `indexText()`**（删旧块 → 建新块 → 批量嵌入），所以编辑后检索、下载、再次编辑看到的都是新内容，`fileSize` 同步更新。

而 pdf/docx 只能被 `extractText` 抽成纯文本，**写回会破坏原格式**，所以策略是：**只重算索引，不碰磁盘文件**——编辑结果影响检索，下载/查看原文件仍是原格式内容。这是诚实的取舍：编辑 PDF 在技术上等于"重建一份 PDF"，成本远超收益，产品选择"索引跟随编辑、原件保持原样"。

**md 编辑复用结构化分块**：`doc.fileType === 'md'` 时先跑 `splitStructuredMd` 得到结构化父块再喂 `indexText`——编辑保存后 md 的 P2 父子结构与上传时完全一致，"命中子块取父块全文"照样生效。

### 11.3 为什么这个链路值得单独立节

它是全章元规则的**收尾闭环**：

```
上传：  磁盘文件（事实）──extractText──► 文本 ──► 分块/符号/档案 ──► 索引（派生）
编辑：  新文本 ──(纯文本)写回磁盘──► 事实更新 ──► indexText 重跑 ──► 派生同步更新
        └──────────────(pdf/docx)只重索引，磁盘原样─────────────────┘
```

**事实和派生可以各自独立变化，但每次变化都需显式同步动作**——上传是入口，编辑是出口，全靠"磁盘文件 + indexText 可重跑"两条腿。编辑一次 = 一次小型的"删除重建"，这也是"派生数据永远先删后建、随时推倒重来"（第 02 章结论）在编辑场景的价值兑现。

## 十三、本章自测

## 十四、本章小结

你现在应该能完整讲出这条流水线：**用户上传（文件/目录/替换）→ upload() 只做校验、哈希去重、存盘、建 pending 记录、入队 → BullMQ worker 后台跑 processDocument：类型识别与二进制体检 → 三层防线清洗防 NUL → 按类型分流分块（md 走 P1/P2 结构化父子分块、code 走行边界代码分块 + TS AST 符号索引、其余字符分块）→ bge-m3 批量嵌入并原始 SQL 写回 pgvector → 生成文件档案 A → 新文档成功后才删同名旧版（replacing 状态机）→ 写 indexVersion 收尾**。最值得反复咀嚼的三条设计主线：**① 事实与派生分离**——磁盘文件是原文、索引可推倒重建，所以编辑/重算/替换全部"先删后建"；**② 异步边界**——重活全在队列，接口只负责登记，一切长任务状态落库可轮询；**③ 每个优化都在省最贵的一步**——内容哈希跳过、增量替换、显式重算，全围绕"少调一次嵌入 API"展开。下一章从这些块/符号/档案出发，看检索时它们如何被混合召回、重排、门控，最终变成回答里带 [来源N] 的那段话。
