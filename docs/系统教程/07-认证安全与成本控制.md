## 一、认证整体设计：为什么是"双 Token"，而不是一个

### 1.1 先看一张接口清单，理解"认证"要解决什么

打开 `apps/server/src/modules/auth/auth.controller.ts`，整个认证面就 10 个接口，按"要不要登录"分两类：

```
# —— @Public()：不需要登录（注册 / 登录 / 找回密码的前置步骤）——
POST /auth/send-code        发送邮箱验证码（register / forgot / bind）
POST /auth/verify-code      只校验验证码不消费（注册向导第一步用）
POST /auth/register         注册：邮箱 + 验证码 + 密码 → 返回 Token
POST /auth/login            登录：邮箱 + 密码 → 返回 Token
POST /auth/forgot-password  忘记密码：邮箱 + 验证码 → 设置新密码
POST /auth/refresh          用 refreshToken 换一对新 Token

# —— 需要登录（@UseGuards(JwtAuthGuard) 或全局守卫兜底）——
POST /auth/logout           登出（吊销 refreshToken）
GET  /auth/profile          当前用户信息
POST /auth/delete-account   注销账号（需输入当前密码确认）
POST /auth/bind-email       更换邮箱绑定（新邮箱 + 验证码）
```

除 `refresh` 外，其余需要登录的接口**前端不会再手动传用户身份**——身份来自请求头里的 `Authorization: Bearer <accessToken>`，后端从 Token 里解出"你是谁"。

### 1.2 为什么不是一个 Token？类比：门禁卡和身份证

先想清楚：登录成功后，服务端要证明"之后的每次请求确实是同一个人"。两种经典方案：

| 方案 | 玩法 | 问题 |
|---|---|---|
| **Session（服务端会话）** | 登录后服务端开一张"会话表"记下你，发你一个随机 sessionId，你每次带着它来，服务端查表确认 | 每次请求都要查一次库/内存；多台服务器还要共享这张表（粘性会话或 Redis）；会话表是**有状态**的，横向扩容的敌人 |
| **JWT（自包含令牌）** | 登录后服务端把 `{userId, email}` 用密钥签名成一段字符串发你，你每次带来，服务端**验签**即可——验签不需要查任何共享状态 | Token 一旦签发，在过期前**服务端无法主动让它失效**（无状态的另一面） |

项目选的是 **JWT 双 Token**：不完全是 Session，也不只是一个 JWT。

```
accessToken  （15 分钟）    = 门禁卡：短时高频使用，验签即过，丢了损失小
refreshToken （7 天）       = 身份证：低频使用，用来"补办"门禁卡，服务端记得它（Redis）
```

打个比方：你上班刷门禁卡（accessToken），卡过期了不会让你重新办身份证，而是去前台出示身份证（refreshToken）**换一张新门禁卡**——前台手里有一本"已发身份证登记簿"（Redis），你说身份证丢了要注销，登记簿上划掉即可。

拆开看每一半承担什么：

- **accessToken（15 分钟）**：真正"干活"用的凭证，几乎每个请求都带。它必须**短**，因为它是无状态的——一旦泄露，在它过期前服务端拦不住（想吊销也吊销不了，只能等 15 分钟自然失效，把损失窗口压小）。
- **refreshToken（7 天）**：不参与日常请求，只在 accessToken 过期后调用一次 `POST /auth/refresh` 换新。它**长**，所以用户体验上"一次登录管一周，期间完全无感"。而它**可以有状态**：签发时把 `refresh_token:{token} → userId` 写进 Redis，登出 / 刷新时删掉这个键 = **吊销**。

一句话总结设计动机（面试直接背）：

> **把"高频、无状态、必须短命"的 accessToken，和"低频、可吊销、可以长命"的 refreshToken 拆开**，既享受 JWT 无状态验签的扩容便利，又用 Redis 给"登出 / 换绑 / 注销"留出真正能吊销的抓手——**两害相权，把不可控的泄露窗口压到 15 分钟**。

### 1.3 一个 Token 的三种错误做法，为什么都不行

| 做法 | 表面省事 | 致命问题 |
|---|---|---|
| 只发一个 7 天的 accessToken | 前端简单 | 泄露一次，攻击者 7 天畅通无阻；**想踢人踢不掉**（无状态） |
| 只发一个 15 分钟的 accessToken | 泄露窗口小 | 用户每 15 分钟就要重新输密码，体验没法用 |
| 只发一个 refreshToken 当 access 用 | 少一种 | refreshToken 本该低频，被高频使用等于把"可吊销的长凭证"暴露在每次请求里，泄露概率大增 |

### 1.4 真实代码：generateTokens 逐段看

签发逻辑在 `auth.service.ts` 的私有方法 `generateTokens`，登录/注册成功后都调它：

```ts
// apps/server/src/modules/auth/auth.service.ts
private async generateTokens(user: {
  id: string; email: string; nickname: string | null; avatar: string | null;
}): Promise<AuthResult> {
  // ① Token 里装什么：sub=用户 id（JWT 标准字段）、email、nickname
  //    绝不装密码、绝不装密钥——Token 只签名不加密，任何拿到它的人都能读到 payload
  const jwtPayload: JwtPayload = { sub: user.id, email: user.email, nickname: user.nickname };

  // ② accessToken：JWT_SECRET 签名，15 分钟（.env 里 JWT_EXPIRES_IN 可调）
  const accessToken = await this.jwtService.signAsync(jwtPayload, {
    secret: this.configService.get<string>('JWT_SECRET'),
    expiresIn: this.configService.get<string>('JWT_EXPIRES_IN', '15m'),
  });

  // ③ refreshToken：用另一个密钥 JWT_REFRESH_SECRET 签名，7 天
  //    两个 Token 用两个密钥：access 泄露不影响 refresh 的伪造/验证体系
  const refreshToken = await this.jwtService.signAsync(jwtPayload, {
    secret: this.configService.get<string>('JWT_REFRESH_SECRET'),
    expiresIn: this.configService.get<string>('JWT_REFRESH_EXPIRES_IN', '7d'),
  });

  // ④ 把 refreshToken 记进 Redis，7 天过期——这就是"可吊销"的抓手
  const refreshExpiresIn = 7 * 24 * 60 * 60; // 秒
  await this.redis.set(this.REFRESH_PREFIX + refreshToken, user.id, 'EX', refreshExpiresIn);

  // ⑤ 返回给前端的是 accessToken + refreshToken + 用户资料
  return { accessToken, refreshToken, user: { /* id/email/nickname/avatar */ } };
}
```

对应 `.env`（值一律见 `apps/server/.env`，示例看仓库 `.env.example`，全文不出现任何真实密钥）：

```bash
JWT_SECRET=                # accessToken 签名密钥，至少 32 位随机串
JWT_EXPIRES_IN=15m         # accessToken 有效期
JWT_REFRESH_SECRET=        # refreshToken 签名密钥，另一个独立的随机串
JWT_REFRESH_EXPIRES_IN=7d  # refreshToken 有效期
```

要点注释里已经写了：**access 和 refresh 用两个不同的密钥签名**。这样即使 access 的密钥泄露，攻击者也伪造不了 refresh，不能"越换越多"。

### 1.5 刷新 = 轮换：旧 refreshToken 作废

`POST /auth/refresh` 做的事（`auth.service.ts` 的 `refresh` 方法）：

```ts
async refresh(refreshToken: string): Promise<AuthResult> {
  // ① 先用 JWT_REFRESH_SECRET 验签：无效/过期 → 直接 401，请重新登录
  let payload: JwtPayload;
  try {
    payload = await this.jwtService.verifyAsync<JwtPayload>(refreshToken, {
      secret: this.configService.get<string>('JWT_REFRESH_SECRET'),
    });
  } catch {
    throw new UnauthorizedException('refreshToken 无效或已过期，请重新登录');
  }

  // ② 查 Redis：登出时这个键会被删掉 → 这里查不到就等于"已被吊销"
  const stored = await this.redis.get(this.REFRESH_PREFIX + refreshToken);
  //    容错分支：Redis 重启会清空键，但 JWT 本身仍有效 → 允许换新，
  //    避免用户被基础设施故障莫名踢出登录（登出吊销依然生效）
  if (stored) {
    await this.redis.del(this.REFRESH_PREFIX + refreshToken); // 旧 refresh 键删掉 = 作废
  }

  // ③ 再查一次用户：账号被注销过 → 拒绝
  const user = await this.prisma.user.findUnique({ where: { id: payload.sub }, select: {...} });
  if (!user) throw new UnauthorizedException('用户不存在');

  // ④ 重新发一对新 Token（新 refresh 再写回 Redis）——旧 refresh 已经用不上了
  return this.generateTokens(user);
}
```

**轮换（rotation）**的意思是：每次刷新不是"拿旧 refresh 换一个新 access"就完事，而是**换出一整对新 Token**，同时把旧 refresh 在 Redis 里的键删掉。效果：

- 刷新后旧 refreshToken 的 Redis 记录没了，服务端记忆里的"合法 refresh"只剩新那一条；
- 就算旧 refresh 被偷走，偷到的人也只能用它换一次（第一次刷新就把它删了），换出来的新 Token 在攻击者手里无意义；
- 真正的**登出吊销**在 `logout`：`await this.redis.del(this.REFRESH_PREFIX + refreshToken)`——键在，refresh 就能被拒；键没了，refresh 请求才会 401，前端收到后清登录态跳登录页。

> ⚠️ 一个值得知道的诚实权衡（代码注释也写了）：第 ② 步的容错分支意味着"**键不存在 = 放行**"。正常情况下刷新会把旧键删掉，旧 refresh 立即作废；但如果 Redis 恰好重启丢过键，一个仍在 7 天 JWT 有效期内的旧 refresh 理论上还能再换一次。这是"吊销状态放在 Redis 而不是数据库"的固有代价——项目选择用"允许换新"换"别把用户莫名踢下线"，并在注释里写明了取舍。真正的强吊销（每次刷新都检测旧 token 重放并封号）需要付出更多状态成本，小项目不值当。

### 1.6 一整个生命周期的时序

```
浏览器                          后端
  │  POST /auth/login            │
  │  {email, password}           │ bcrypt.compare 验密码
  │◄──── { accessToken(15m),     │ generateTokens：
  │        refreshToken(7d),     │   refresh_token:{refresh} → userId 写入 Redis
  │        user }                │
  │                              │
  │  GET /auth/profile           │
  │  Authorization: Bearer <accessToken>
  │                              │ JwtStrategy 验签 → 查库 → request.user
  │◄──── { id, email, ... }      │
  │  ... 15 分钟后 access 过期 ...│
  │  GET /api/xxx（带旧 access）  │
  │◄──── 401 Unauthorized        │
  │  POST /auth/refresh          │
  │  { refreshToken }            │ 验签 → 删旧键 → 发新对
  │◄──── { 新 access, 新 refresh }│
  │  带新 access 重发刚才的请求   │
  │  ... 7 天后或用户点登出 ...   │
  │  POST /auth/logout           │
  │  { refreshToken }            │ 删除 Redis 键 = 吊销
```

## 二、密码存储：bcryptjs 的"盐 + 慢哈希"

### 2.1 为什么：明文和单次 MD5 都过不了"脱库"这一关

密码是用户资产里最敏感的一档——很多人一个密码走天下。所以密码存储的假设永远是：**数据库可能被拖走**（SQL 注入、备份泄露、内鬼……），我们要保证"库被拖走，密码也拿不到"。

| 存法 | 脱库后攻击者拿到什么 | 结果 |
|---|---|---|
| **明文** | 直接可登录 | 灾难。连"破解"都不需要 |
| **单次 MD5**（如 `md5("123456")`） | 32 位十六进制串 | 等于明文。`123456` 的 MD5 是公开的，彩虹表/在线库秒查；GPU 算 MD5 每秒数十亿次，8 位纯数字密码几分钟穷举完 |
| **MD5 + 固定盐** | 每库一个盐的 MD5 | 同一库内相同密码仍产生相同摘要，且盐一旦泄露整库可并行彩虹表 |
| **bcrypt（本项目）** | `$2a$10$...` 一串带盐的慢哈希 | **每个密码自带随机盐** + **单次计算刻意要 ~100ms**。攻击者想爆破一个密码，只能一个盐一个盐地硬算，且每试一个都要付出 100ms——GPU 并行优势被"内存密集 + 慢"抵消 |

一句话：**哈希不是给"加密"用的，是给"不可逆"用的；而"不可逆"还不够，还得"慢 + 带随机盐"，让每个密码的破解成本都独立且昂贵**。

### 2.2 bcrypt 做了什么（30 秒直觉）

`bcrypt.hash(password, 10)` 的产物长这样：

```
$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
└┬┘ └┬┘ └────────────────────────┬─────────────────────────┘
版本  代价因子(10=2^10轮)          盐(22字符) + 哈希结果拼在一起
```

- **随机盐**：22 个字符的随机盐拼在结果里，同一个密码两次 hash 结果完全不同——预计算的彩虹表全部失效；
- **代价因子 10**：内部做 2¹⁰ 轮 Blowfish 密钥扩展，单次约 100ms。验证密码 = 把盐提取出来重算一遍再比对，**验证和生成一样慢**；
- **自包含**：盐和参数都嵌在结果串里，验证时不需要另外存盐、不需要记住代价因子——`bcrypt.compare(明文, 库里的串)` 就够。

### 2.3 真实代码：hash 只在"写入"出现，compare 只在"登录"出现

注册（`auth.service.ts` 的 `register`）：

```ts
// 先查邮箱占用（409）→ 再校验验证码 → 最后才 hash 建号
const existing = await this.prisma.user.findUnique({ where: { email } });
if (existing) throw new ConflictException('该邮箱已被注册');
await this.emailCodeService.verifyCode(email, 'register', dto.code);

// hash 的 10 是代价因子：数字越大越慢越安全，10 是当下性价比平衡点
// 注意：hash 是异步的（bcrypt 内部在 libuv 线程池算，不卡事件循环）
const hashedPassword = await bcrypt.hash(dto.password, 10);
const user = await this.prisma.user.create({
  data: { email, password: hashedPassword, nickname: dto.nickname || email.split('@')[0], ... },
  select: { id: true, email: true, nickname: true, avatar: true }, // 绝不把 password 带回响应
});
```

登录（`auth.service.ts` 的 `login`）：

```ts
const user = await this.prisma.user.findUnique({ where: { email: dto.email.toLowerCase() } });
if (!user) throw new UnauthorizedException('邮箱或密码错误');   // ①

const isPasswordValid = await bcrypt.compare(dto.password, user.password);
if (!isPasswordValid) throw new UnauthorizedException('邮箱或密码错误');  // ②

// ③ 登录成功才更新 lastLoginAt，再发 Token
await this.prisma.user.update({ where: { id: user.id }, data: { lastLoginAt: new Date() } });
return this.generateTokens({ id: user.id, email: user.email, nickname: user.nickname, avatar: user.avatar });
```

忘记密码 / 注销账号也一样：`forgotPassword` 里 `bcrypt.hash(dto.newPassword, 10)` 覆盖旧密码；`deleteAccount` 里先 `bcrypt.compare(dto.password, user.password)` 确认"你确实知道当前密码"才允许删号。

### 2.4 四个细节，全是安全设计

1. **邮箱或密码错误的文案必须一模一样**（代码里 ① 和 ② 抛的是同一个 `UnauthorizedException('邮箱或密码错误')`）。如果邮箱不存在说"用户不存在"、密码错说"密码错误"，等于给攻击者开了**用户枚举**接口——先试邮箱，报"用户不存在"的就是没注册的，剩下的一律去撞密码。
2. **注册先查重再 hash**：已注册邮箱直接 409 返回，不浪费一次 bcrypt 计算（也是防"注册接口被人用来消耗 CPU"的顺手防护）。
3. **任何响应都不回传 password 字段**：`register` 的 `select`、`login` 的 `generateTokens`、`profile`，所有查用户的地方都只取 `id/email/nickname/avatar`。
4. **hash 用 await，别用同步版**：`bcrypt.hashSync` 会阻塞事件循环，每个登录请求卡 ~100ms，QPS 一高整个服务全卡。异步版把计算扔线程池。

> 💡 面试补充：为什么不用 SHA-256 加盐？SHA 系列是**为速度设计**的，硬件加速后每秒可算亿次，加再长的盐也只是"每次多算一遍"，攻击者仍能并行爆破；bcrypt/scrypt/argon2 是**为慢设计**的（内存密集 + 多次迭代），这是"密码哈希"和"普通哈希"的本质区别。

## 三、邮箱验证码链路：从 TOTP 到"真实邮箱即证据"

### 3.1 背景故事：先做 TOTP，被用户一句话推翻

这个功能最早不是验证码，是 **TOTP 双因素认证**（用户扫码绑 Google Authenticator 之类）。做成后请真实用户试，得到的反馈一针见血：

> "登录还要打开验证器 App 太麻烦了。"

于是推翻重做，把 2FA 整体移除（数据库迁移直接 `DROP COLUMN totp_secret / totp_enabled / recovery_codes`），换成**邮箱验证码**。完整取舍在 `docs/功能档案/21-邮箱验证码认证.md`，核心对比：

| 方案 | 优点 | 致命伤 |
|---|---|---|
| 短信验证码 | 人人有手机 | 每条要钱、要短信资质，个人项目跑不起 |
| TOTP 验证器（原方案） | 免费、离线、安全 | 用户要先装 App 再扫码，**门槛太高**（真实用户实测反馈） |
| **邮箱验证码（现方案）** | 免费、零安装、零门槛 | 邮件可能进垃圾箱（用开发模式 / 真实 SMTP 双通道缓解） |

复盘结论：这四件事（注册 / 忘记密码 / 换绑邮箱）的本质要求是**"证明这个邮箱是你真的能收到信的"**——邮箱验证码恰好完成这个证明，还免费零门槛；而**日常登录**只验密码，和主流网站体验一致，验证码只出现在"敏感操作"里，不骚扰正常使用。这是典型的"跟着真实用户反馈做减法"的产品决策，面试聊起来很加分。

### 3.2 验证码出现的三个场景 + 关键边界

```
register（注册）    ：新邮箱 → 发码 → 验证码正确才允许建号
forgot（忘记密码）  ：已注册邮箱 → 发码 → 验证码正确才允许改密码
bind（更换邮箱）    ：登录态下 → 新邮箱 → 发码 → 验证码正确才允许换绑

登录（login）       ：只有邮箱 + 密码 —— 没有验证码环节
```

**场景分型**是安全细节：验证码的 Redis 键带 type（`email_code:register:xxx@x.com`、`email_code:forgot:...`、`email_code:bind:...`），**注册的码不能拿去改密码，改密码的码不能拿去换绑**——互不通用，攻破一个场景不影响另一个。

### 3.3 为什么验证码数据不进数据库，进 Redis

打开 `apps/server/prisma/schema.prisma`：**全库没有 EmailCode 表**（第 02 章专门讲过这个"没有的表"）。因为验证码是**6 位数、活 10 分钟、用完即焚**的一次性数据：

- 它**需要自动过期**（10 分钟）——Redis 的 `EX` 过期正好，PostgreSQL 要自己写定时清理；
- 它**访问极高频**（每次校验一次 GET）——Redis 内存操作毫秒级；
- 它**生命周期极短**、无需长期审计——不值得占一张业务表、不值得进备份。

```
Redis 键设计（email-code.service.ts 顶部常量）：
  email_code:{type}:{email}        → 验证码本体          ，TTL 10 分钟
  email_code:{type}:{email}:sent   → "刚才发过"的冷却标记  ，TTL 60 秒
```

| 防线 | 参数 | 作用 |
|---|---|---|
| 6 位随机数字 | 10⁶ 组合 | 10 分钟内暴力尝试上限约 166 次/秒才可能撞中，加上全局限流基本不可行 |
| 有效期 | 10 分钟（`CODE_TTL = 10 * 60`） | 过期即作废，不给攻击者无限时间猜 |
| 重发冷却 | 60 秒（`RESEND_INTERVAL = 60`） | 同一邮箱同一场景 60 秒内不能重发，防刷接口烧 SMTP 配额 |
| 消费即删 | `verifyCode` 里 `redis.del` | 验证码一次性：用过就不能再用，防重放 |
| 场景隔离 | 键里带 type | 注册码不能用于改密，见上 |

### 3.4 真实代码：sendCode 的双通道与 verifyCode 的"消费"

`apps/server/src/modules/auth/email-code.service.ts` 全貌只有 100 行，逐段看：

```ts
// —— 发送 ——
async sendCode(email: string, type: EmailCodeType) {
  const key = CODE_PREFIX + type + ':' + email.toLowerCase();
  const lastSent = await this.redis.get(key + ':sent');       // 冷却标记还在？
  if (lastSent) throw new BadRequestException('验证码发送过于频繁，请稍后再试');

  const code = String(Math.floor(100000 + Math.random() * 900000)); // 100000~999999
  await this.redis.set(key, code, 'EX', CODE_TTL);                   // 本体：10 分钟
  await this.redis.set(key + ':sent', String(Date.now()), 'EX', RESEND_INTERVAL); // 冷却：60 秒

  if (this.transporter) {
    // 通道 A：配了 SMTP（MAIL_HOST 等）→ 发真实邮件（nodemailer）
    const subject =
      type === 'register' ? '【AI 知识库】注册验证码'
      : type === 'forgot'  ? '【AI 知识库】重置密码验证码'
      :                      '【AI 知识库】更换邮箱验证码';
    await this.transporter.sendMail({ from: ..., to: email, subject,
      html: `你的验证码是 <b>${code}</b>，10 分钟内有效。如非本人操作请忽略。` });
    return { sent: true };                       // 生产：绝不回传 code
  }
  // 通道 B（开发模式）：没配 SMTP → 验证码随响应返回，方便本地联调
  return { sent: true, devMode: true, code };
}
```

**双通道的精妙之处**：`transporter` 在构造函数里根据 `MAIL_HOST` 是否存在决定是否创建——**同一个函数，配了 SMTP 就发真实邮件且绝不回传 code；没配就自动降级成开发模式把 code 回显**。本地开发零成本（不用真邮箱），生产部署时把 SMTP 配置填上，行为自动切换，代码一行不用改。这就是"开发模式回显验证码"的原因：**联调要快**——前端注册页拿到 `{ devMode: true, code }` 还能自动填入输入框，省去查 Redis 的麻烦（见 `Register.vue` / `ForgotPassword.vue` / `Settings.vue` 里的 `res.devMode && res.code` 分支）。

> ⚠️ 开发模式回显在**生产必须被配置消灭**：只要 `.env` 里配了 `MAIL_HOST/MAIL_PORT/MAIL_USER/MAIL_PASS/MAIL_FROM`，`transporter` 非空，code 就绝不会出现在任何响应里。上线检查清单第一条就是"确认 SMTP 已配置"。

```ts
// —— 校验并消费（一次性）——
async verifyCode(email: string, type: EmailCodeType, code: string) {
  // 必须 await：verifyOnly 失败时抛 BadRequestException，
  // 不 await 会成为未处理 rejection 直接打崩进程（源码注释原话）
  await this.verifyOnly(email, type, code);
  const key = CODE_PREFIX + type + ':' + email.toLowerCase();
  await this.redis.del(key);            // 删验证码本体：用过即焚
  await this.redis.del(key + ':sent');  // 同时删冷却标记：成功消费后可立即重发
  return true;
}

// —— 只校验不消费（不删键）——
async verifyOnly(email: string, type: EmailCodeType, code: string) {
  const key = CODE_PREFIX + type + ':' + email.toLowerCase();
  const stored = await this.redis.get(key);
  if (!stored || stored !== code.trim()) {
    throw new BadRequestException('验证码错误或已过期');
  }
  return true;
}
```

### 3.5 为什么注册要"先 verifyOnly、提交时再真正消费"

注册是**两步向导**：① 填邮箱 → 发码 → 填验证码 → 点下一步；② 设密码 + 昵称 → 提交注册。中间隔着一整个填写密码的步骤，验证码不能在第①步就被删掉（否则第②步提交时码没了）。

真实踩过的坑（`docs/功能档案/21` 里记录过）：初版在注册接口里**先 `verifyCode` 消费再查邮箱占用**，用户第一次提交其实成功了、只是前端没跳转，再次点击提交时——验证码已被第一次消费删除 → 后端报"验证码错误"，把用户绕晕。修复后的顺序：

```
POST /auth/verify-code（第①步"下一步"时）：
   1. 先查邮箱是否已注册 → 已注册抛 409「该邮箱已被注册」
   2. 再 verifyOnly 校验验证码正确且未过期（不删键）
   → 通过才进入第②步设置密码

POST /auth/register（第②步最终提交时）：
   1. 再次查邮箱占用（防第①步和第②步之间被人抢先注册）→ 409
   2. verifyCode 真正消费验证码（删键）
   3. bcrypt.hash 密码 → 建号 → 发 Token
```

顺序原则一句话：**先给用户明确、准确的业务错误（"已被注册"），验证码这种"一次性资源"留到真正落库前最后一刻才消费**。

`forgot-password` 与 `bind-email` 同理：忘记密码先查 `该邮箱尚未注册` 再消费验证码；换绑邮箱则先消费新邮箱的 bind 验证码，再确认新邮箱没被别人占用。

## 四、JWT 守卫、@Public 与 CurrentUser：鉴权的"默认关闭"

### 4.1 为什么是"默认全部要登录"而不是"默认都公开"

最安全的访问控制是**白名单**不是黑名单：先假设"这个系统里没有接口可以裸奔"，再把确实不需要登录的（注册、登录、发码、健康检查）一个个**显式放行**。

- 黑名单思路（默认公开，个别接口加鉴权）：新同事加一个接口忘了加守卫 → **裸奔上线**，直到出事；
- 白名单思路（默认鉴权，个别接口 `@Public()`）：新接口不加注解 → 默认要登录，最多是"前端调不通"（立刻暴露），绝不会"静默裸奔"。

NestJS 里实现"全局默认鉴权"就是把守卫注册成 `APP_GUARD`（`app.module.ts`）：

```ts
// apps/server/src/app.module.ts（节选）
providers: [
  // 全局 JWT 守卫：所有接口默认需要登录，用 @Public() 标记公开接口
  { provide: APP_GUARD, useClass: JwtAuthGuard },
  // 全局限流守卫（第 8 节讲）
  { provide: APP_GUARD, useClass: ThrottlerGuard },
],
```

### 4.2 守卫本体：只有 30 行

```ts
// apps/server/src/modules/auth/guards/jwt-auth.guard.ts
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {   // 复用 passport 的 'jwt' 策略
  constructor(private reflector: Reflector) { super(); }

  canActivate(context: ExecutionContext) {
    // 反射读取接口上有没有 @Public() 标记（方法级优先，其次类级）
    const isPublic = this.reflector.getAllAndOverride<boolean>(IS_PUBLIC_KEY, [
      context.getHandler(),
      context.getClass(),
    ]);
    if (isPublic) return true;          // 打了 @Public() → 直接放行，不校验
    return super.canActivate(context);  // 否则走 passport-jwt 验签流程
  }
}
```

配套的两个装饰器（`apps/server/src/common/decorators/`）：

```ts
// public.decorator.ts：给方法打元数据 isPublic=true
export const IS_PUBLIC_KEY = 'isPublic';
export const Public = () => SetMetadata(IS_PUBLIC_KEY, true);

// current-user.decorator.ts：从 request.user 里取当前登录用户
// 用法：@CurrentUser() user: JwtPayload   或   @CurrentUser('id') userId: string
export const CurrentUser = createParamDecorator(
  (data: string | undefined, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest();
    const user = request.user;
    return data ? user?.[data] : user;
  },
);
```

于是 Controller 里"需要登录的接口"干净得像没做鉴权一样——身份由守卫注入，业务代码只消费：

```ts
// auth.controller.ts 的写法对比：
@Public()
@Post('login')                       // ① 公开接口：显式打 @Public()
login(@Body() dto: LoginDto) { ... }

@UseGuards(JwtAuthGuard)             // ② 其实全局守卫已兜底，这里显式写更醒目
@Get('profile')
getProfile(@CurrentUser('id') userId: string) {   // ③ 谁在请求？从 token 里来
  return this.authService.getProfile(userId);
}
```

注意：因为守卫是全局的，`@UseGuards(JwtAuthGuard)` 在很多 Controller 里是**冗余但醒目**的写法（`user.controller.ts`、`documents.controller.ts` 等都写了）；去掉它接口依然受全局守卫保护。

### 4.3 JwtStrategy：验签之后为什么还要查一次库

`AuthGuard('jwt')` 会去找 passport 里注册名为 `'jwt'` 的策略——`strategies/jwt.strategy.ts`：

```ts
export class JwtStrategy extends PassportStrategy(Strategy, 'jwt') {
  constructor(private configService: ConfigService, private prisma: PrismaService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(), // 从 Authorization: Bearer 取
      ignoreExpiration: false,        // accessToken 过期直接拒绝（绝不放行）
      secretOrKey: configService.get<string>('JWT_SECRET', 'default_secret'),
    });
  }

  // 验签通过后自动调用；返回值会挂到 request.user
  async validate(payload: JwtPayload) {
    const user = await this.prisma.user.findUnique({
      where: { id: payload.sub },
      select: { id: true, email: true, nickname: true, avatar: true },
    });
    if (!user) throw new UnauthorizedException('用户不存在或已被删除');
    return user;
  }
}
```

**为什么验签通过还要查库？** JWT 是无状态的，payload 里的 `sub` 只代表"签发那一刻这个用户存在"。如果用户已被注销（`deleteAccount` 级联删除），旧 accessToken 在 15 分钟内仍然验签通过——查一次库就能让"已删除的用户"立刻失效。这就是 `auth.service.ts` 注销注释里写的"删除后旧 accessToken 因 JWT 策略查库失败而自动失效，前端会收到 401 并登出"。代价是每次请求多一次主键查询（毫秒级），换来的是一致性——**身份校验链 = 验签（无状态，快）+ 查库（有状态，准）**。

### 4.4 ownerId 数据隔离：越权一律 404，绝不 403

拿到 `request.user.id`（即 `@CurrentUser('id')`）之后，所有业务查询都带 ownerId 过滤。看模型配置模块的标准写法（`model-config.service.ts` 的 `findOwned`）：

```ts
private async findOwned(userId: string, id: string) {
  const config = await this.prisma.modelConfig.findFirst({
    where: { id, ownerId: userId },   // ① 条件同时带"资源 id"和"归属者"！
  });
  if (!config) throw new NotFoundException('模型配置不存在');  // ② 查不到 = 404
  return config;
}
```

要点全在 ① 和 ②：

- 用的是 `findFirst({ where: { id, ownerId } })` 而不是先按 id 查出再手动比较 ownerId——**归属校验做进查询条件**，数据库层面就保证"别人的东西你根本查不到"；
- 查不到抛的是 `NotFoundException`（404）而不是 `ForbiddenException`（403）。**404 = "这东西不存在"，403 = "这东西存在但你没权限"**。返回 403 等于告诉攻击者"你猜对了，确实有这条记录，就差权限"——给爆破/枚举喂情报。一律 404，攻击者无法区分"没有"和"不是你的"。

第 01 章删文档的例子同款逻辑（`documents.controller` → service 里 `findFirst({ where: { id, knowledgeBase: { ownerId: userId } } })`，查不到抛"文档不存在"）。整库的规矩是**所有"按 id 操作自己资源"的接口都走这条模式**：知识库、文档、会话、报告、Agent 任务、模型配置，无一例外。

## 五、BYO 成本控制：商业核心——"用户带粮，平台只出厨房"

### 5.1 为什么 BYO 是"架构级决策"而不是一个功能

任何 AI 应用都要直面一道算术题：**一次回答烧的 token 钱，平台出还是用户出？** 个人/小团队平台没有资本补贴，100 个活跃用户天天问，平台先破产。

这个项目的解法是 **BYO（Bring Your Own Key）**：所有对话 / 研究报告 / 自主研究 Agent 的推理，**强制用用户自己绑定的大模型 API Key**，token 由用户买单。而且这不是平台单方面的省钱决定，是真实用户的明确产品诉求（记录在 `docs/功能档案/20-用户模型配置BYO.md`）：

> "如果用户不用自己的模型，那么所有消耗的 token 都是我自己的。我只提供框架，用户要用的每个功能，首先要用户输入自己的 key，所有费用用户承担，不用我的 key。"

于是产品规则定成三条硬约束：

1. 用户**必须先绑定**自己的大模型 Key，才能用对话 / 研究报告；
2. 未绑定就去用 → **明确引导错误**（对话 SSE 直接 error、研究报告标记失败），**绝不静默回退系统 Key**——既省钱，也守"不用我的 key"的承诺；
3. 平台仍承担的部分只有**检索基础设施**：Embedding（bge-m3）、重排（bge-reranker）、向量检索、Web 搜索——这些与"用户推理成本"无关，且硅基流动有免费额度（`SILICONFLOW_API_KEY`，平台侧系统 Key）。

成本边界一图流：

```
用户 Key（自己承担推理费）                平台系统 Key（承担检索基建费）
  ┌──────────────────────┐              ┌──────────────────────────┐
  │ 对话回答 / 查询改写    │              │ Embedding  bge-m3         │
  │ 研究报告拆解-撰写-汇总 │              │ Rerank     bge-reranker   │
  │ 自主研究 Agent 全程    │              │ Web 搜索   Tavily(免费额度)│
  │ 视觉模型看图          │              │ 向量检索   pgvector(本机)  │
  └──────────────────────┘              └──────────────────────────┘
```

> 💡 面试一句话：**"BYO 把'谁为 token 付费'从平台成本问题变成了产品架构问题——所有 LLM 调用都走用户自己的 OpenAI 兼容客户端，平台只保留检索链路的系统 Key，推理成本对平台归零。"**

### 5.2 第一道安全关：用户的 API Key 也是"密码"

BYO 意味着数据库里要存**每个用户的第三方 API Key**（如 DeepSeek 的 `sk-***`）。API Key 就是钱：拿它调 `deepseek-chat` 烧的是用户账户余额。所以它在系统里的地位等同于密码，甚至更危险——**密码泄露要撞库才能用，API Key 泄露直接就是钱**。明文存 Key 等于把用户的钱包密码写在收银台。

对照表（为什么不用更"省事"的方案）：

| 方案 | 为什么不行 |
|---|---|
| 明文存 `api_key` 列 | 脱库 = 批量偷钱。等于替攻击者把各家 Key 汇总好 |
| 可逆弱加密 / 固定 IV 的 AES-ECB | ECB 模式同样明文块产生同样密文块，可被模式分析；无 IV 或固定 IV 让相同 Key 前缀可被识别 |
| **AES-256-GCM（本项目）** | 每条记录**随机 12 字节 IV** + GCM **认证标签**（防篡改），密文格式 `iv:tag:data`，密钥只在服务端 env |

### 5.3 AES-256-GCM 落库：`iv:tag:data` 三段式

先看 `.env` 里怎么管理密钥（值一律占位，见 `.env.example`）：

```bash
# ========== BYO 模型配置（用户自带大模型 Key） ==========
# 用户配置的 API Key 用 AES-256-GCM 加密落库，
# 此密钥用 `openssl rand -hex 32` 生成（缺失时自动由 JWT_SECRET 派生，生产务必显式配置）
MODEL_KEY_SECRET=用openssl-rand-hex-32生成的64位hex
```

再看 `model-config.service.ts` 的加解密（`node:crypto` 原生实现，没有第三方依赖）：

```ts
// ① 密钥来源：优先取 env 的 MODEL_KEY_SECRET（64 位 hex = 32 字节 = AES-256），
//    没配或格式不对 → 用 sha256(JWT_SECRET) 派生 32 字节兜底（生产必须显式配置）
private get secret(): Buffer {
  const s = this.configService.get<string>('MODEL_KEY_SECRET');
  if (s && /^[0-9a-f]{64}$/i.test(s)) return Buffer.from(s, 'hex');
  return createHash('sha256').update(this.configService.get<string>('JWT_SECRET', 'dev-secret')).digest();
}

// ② 加密：随机 IV + GCM 加密 + 取认证标签，拼成 iv:tag:data
private encrypt(plain: string): string {
  const iv = randomBytes(12);                                  // 每条记录独立随机 IV（12 字节，GCM 推荐值）
  const cipher = createCipheriv('aes-256-gcm', this.secret, iv);
  const enc = Buffer.concat([cipher.update(plain, 'utf8'), cipher.final()]);
  const tag = cipher.getAuthTag();                             // GCM 认证标签：密文被改一个字都会验出
  return `${iv.toString('base64')}:${tag.toString('base64')}:${enc.toString('base64')}`;
}

// ③ 解密：按 : 拆三段还原
private decrypt(payload: string): string {
  const [ivB64, tagB64, dataB64] = payload.split(':');
  const decipher = createDecipheriv('aes-256-gcm', this.secret, Buffer.from(ivB64, 'base64'));
  decipher.setAuthTag(Buffer.from(tagB64, 'base64'));
  return Buffer.concat([decipher.update(Buffer.from(dataB64, 'base64')), decipher.final()]).toString('utf8');
}
```

三个设计点讲清楚：

1. **为什么要随机 IV？** 同样的明文 + 同样的密钥，如果 IV 固定，密文就固定——攻击者能看出"这两个用户用的是同一个 Key 前缀"等模式。随机 IV 让相同明文每次加密结果都不同（语义安全）。
2. **为什么要 GCM 而不是 CBC？** GCM 是**认证加密**：加密输出的 `tag` 是密文的"校验和"，解密时 `setAuthTag` 后再 `final()`，密文或 IV 被篡改任何一个字节，解密直接抛错而不是吐出乱码——防止攻击者改密文搞破坏。**加密 ≠ 防篡改，GCM 一起做**。
3. **密钥为什么单独用 MODEL_KEY_SECRET 而不是复用 JWT_SECRET？** 职责分离：JWT 密钥泄露只影响登录令牌，MODEL_KEY_SECRET 泄露影响用户真金白银的 Key。单点密钥越少越好；即便 JWT_SECRET 泄露，也不至于连带解密出所有用户的 API Key（派生兜底只用于开发环境，生产必须显式配）。

### 5.4 接口永不回传明文：只给掩码

加密是为了防脱库，但**接口响应里也不能有明文**——响应要过浏览器、可能被插件/代理/日志记录。`model-config.service.ts` 定义了对外类型：

```ts
export interface SafeModelConfig {
  id: string;
  name: string;         // 备注名，如"我的 DeepSeek"
  baseURL: string;
  model: string;
  models: string[];
  isDefault: boolean;
  apiKeyMasked: string; // ← 只有掩码，没有 apiKey 明文字段！
  createdAt: Date;
  updatedAt: Date;
}

// 掩码规则：前 6 后 4，中间打星（Key 太短则整串 ****）
private mask(key: string): string {
  if (key.length <= 8) return '****';
  return `${key.slice(0, 6)}****${key.slice(-4)}`;   // 例：sk-1234****abcd
}

// 入库的密文 → 出库前先解密再掩码（解密失败给空串，不把异常抛给前端）
private toSafe(c): SafeModelConfig {
  let plain = '';
  try { plain = this.decrypt(c.apiKey); } catch { plain = ''; }
  return { ...c, models: ..., apiKeyMasked: this.mask(plain) };
}
```

于是列表 / 创建 / 更新响应里，用户只能看到 `apiKeyMasked: "sk-1234****abcd"`——够他认出来"这是我那把 Key"，又拿不到完整 Key。**完整 Key 只在服务端内存里活几毫秒**：解密 → 拼进 OpenAI 客户端请求 → 用完即弃。

配套的两个交互安全细节：

- **编辑保留原 Key**：`update` 里 `...(dto.apiKey ? { apiKey: this.encrypt(dto.apiKey) } : {})`——更新时**不传 apiKey 字段就保留原密文**。前端编辑表单把 Key 输入框留空 = "不改 Key"，避免用户改个备注名结果把 Key 弄丢（明文 Key 无法找回，只能重新去平台生成）。
- **归属校验**：所有 CRUD 走 `findOwned(userId, id)`（第 4.4 节），他人配置一律 404。

### 5.5 测试连接：验证 Key 真能用的最小代价探测

`POST /model-configs/:id/test`（`model-config.service.ts` 的 `test`）：解密出 Key，向 `{baseURL}/chat/completions` 发一个 5 token 的最小请求 `{ model, messages: [{role:'user', content:'ping'}], max_tokens: 5 }`，15 秒超时：

```ts
const res = await fetch(`${config.baseURL.replace(/\/+$/, '')}/chat/completions`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', Authorization: `Bearer ${apiKey}` }, // 解密后的 Key 只出现在这里
  body: JSON.stringify({ model: config.model, messages: [{ role: 'user', content: 'ping' }], max_tokens: 5 }),
  signal: AbortSignal.timeout(15_000),
});
if (!res.ok) return { ok: false, message: `接口返回 ${res.status}：${...}` };
return { ok: true, message: '连接成功' };
```

返回只有 `{ ok, message }`，**永远不带 Key**。顺手一提：`POST /model-configs/models`（探测该 Key 下有哪些模型名，供前端下拉选）也一样——新建时用请求里临时传的 baseURL+Key（不落库），编辑时按 configId 解密已存 Key，同样不落新库、不回传。

## 六、模型配置解析链：会话绑定 → 用户默认 → 无配置引导

### 6.1 三层解析的"为什么"

模型配置可以建多条（用户可以配 DeepSeek 一把、硅基流动一把、智谱一把……），那"这次对话到底用哪把 Key"得有个明确规则。数据模型里埋了两个锚点（`schema.prisma`）：

```prisma
model ChatSession {
  ...
  modelConfigId String? @map("model_config_id")  // 会话绑定的配置；null = 不绑定
  model         String?                          // 会话选中的模型名（同一配置多模型切换）；null = 用配置默认 model
  ...
  modelConfig ModelConfig? @relation(fields: [modelConfigId], references: [id], onDelete: SetNull)
}

model ModelConfig {
  ...
  isDefault Boolean @default(false) @map("is_default")  // 用户的"默认配置"标记
}
```

- `ChatSession.modelConfigId`：会话级绑定——"这个会话固定用我的 DeepSeek 配置"；
- `ModelConfig.isDefault`：用户级默认——新会话 / 研究报告 / Agent 没指定时用它；
- 注意 `onDelete: SetNull`：删掉某条配置后，绑定它的会话自动回到"未绑定"，不会因外键悬空而报错。

### 6.2 两个解析函数（`model-config.service.ts`）

```ts
// ① 会话绑定解析：configId 为空 → null；配置不属于该用户 → 视同不存在（隔离）
//    modelName 只在该配置的 models 白名单里才生效（防前端乱传模型名），否则回落默认 model
async resolveForChat(userId, configId?: string | null, modelName?: string | null): Promise<ChatTarget | null> {
  if (!configId) return null;
  const config = await this.prisma.modelConfig.findFirst({ where: { id: configId, ownerId: userId } });
  if (!config) return null;
  const models = config.models?.length ? config.models : [config.model];
  const model = modelName && models.includes(modelName) ? modelName : config.model;
  return { baseURL: config.baseURL, apiKey: this.decrypt(config.apiKey), model };  // ← 这里才解密
}

// ② 用户默认解析：isDefault=true 那条
async resolveDefaultForUser(userId: string): Promise<ChatTarget | null> {
  const config = await this.prisma.modelConfig.findFirst({ where: { ownerId: userId, isDefault: true } });
  if (!config) return null;
  return { baseURL: config.baseURL, apiKey: this.decrypt(config.apiKey), model: config.model };
}
```

两者返回的都是 `ChatTarget`：`{ baseURL, apiKey(解密后的明文), model }`——**明文 Key 的出口只有这一个**，调用方拿到它立刻去建 OpenAI 客户端，绝不再往外传。

`isDefault` 的维护有个细节：一个人只能有一条默认配置，所以在设默认前先清掉旧的（`clearDefault`：`updateMany({ where: { ownerId, isDefault: true }, data: { isDefault: false } })`）；并且**用户的第一条配置自动成为默认**（`create` 里 `hasAny === 0` 时 `isDefault = dto.isDefault ?? true`）——保证"刚绑完 Key 打开就能用"，不用再手动勾选。

### 6.3 对话里的解析链：`??` 一把梭 + 明确的错误收尾

真正消费解析链的是 `chat.service.ts` 的 `askAndStream`——RAG 问答的入口（第 05 章讲过它的完整编排），模型目标解析在最前面：

```ts
// 模型目标（BYO 强依赖）：会话绑定的配置（含选中的模型名）→ 用户的默认配置 → 都没有则提示先绑定 Key。
// 所有 token 消耗由用户自己的 Key 承担，系统不提供兜底模型。
const target =
  (await this.modelConfigService.resolveForChat(
    userId,
    session.modelConfigId,   // 第 1 层：会话绑定
    session.model,           //       + 会话选中的模型名
  )) ??
  (await this.modelConfigService.resolveDefaultForUser(userId));  // 第 2 层：用户默认

if (!target) {
  // 第 3 层：都没有 → 绝不静默用系统 Key，而是写一条明确的 SSE error 并结束
  writer('error', {
    message:
      '使用前请先在「模型配置」里绑定你自己的大模型 API Key（设置 → 模型配置，或对话页右上角「模型」入口）。绑定后本会话所有 AI 消耗都由你的 Key 承担。',
  });
  return;
}
```

解析链图：

```
askAndStream(userId, sessionId):
    │
    ├─① resolveForChat(userId, session.modelConfigId, session.model)
    │    会话绑定了配置？→ 有：解密出 {baseURL, apiKey, model} 用它
    │                     → 无 / 配置不是本用户的：null
    │        （?? 空值合并：左侧为 null 才走右侧）
    ├─② resolveDefaultForUser(userId)
    │    用户有 isDefault=true 的配置？→ 有：用它
    │                                   → 无：null
    └─③ target === null
          → writer('error', 绑定引导文案) 并 return
          → 用户看到明确指引，平台零 token 消耗
```

**为什么"没有就明确报错"而不是像很多教程那样回退系统 Key？** 两层原因：一是成本承诺——文档 20 里用户说得清楚"不用我的 key"，偷偷回退等于违约还烧平台钱；二是可诊断性——用户看到"请先绑定"知道下一步做什么，而静默回退会让用户以为"没绑也能用"，某天系统 Key 欠费才发现全站失灵。

### 6.4 同一把钥匙，三处消费 + 视觉模型自动路由

BYO 不只服务对话。同一解析链被多处复用：

| 消费方 | 用哪层解析 | 说明 |
|---|---|---|
| 对话回答（askAndStream） | 会话绑定 → 默认 | 见上 |
| 多轮查询改写（rewriteQuery） | 与回答同一个 `target` | 改写也算一次 LLM 调用，必须用用户同一把 Key 计费 |
| 研究报告 / 自主研究 Agent | 默认配置 | 任务创建时解析，没有则任务标记 failed（原因含"模型配置"） |
| 发图自动路由（resolveVisionForUser） | 遍历全部配置找视觉模型 | 见下 |

**视觉模型自动路由**（`resolveVisionForUser`）是个锦上添花的细节：用户当前模型不支持看图（如 deepseek-chat），但消息里带了图片时，自动在用户全部配置 × 全部模型名里找名字含 `vision/VL/4V/Omni/glm-4v` 等关键字的模型（`isVisionModelName` 正则），找到就**只把这一次调用的目标换过去**（`target.model/baseURL/apiKey` 临时替换，不改变会话绑定）——文字对话仍走原模型，两个模型各司其职，用户不用手动切。

### 6.5 一张表回顾整条 BYO 链路

```
前端填 Key → POST /model-configs（encrypt 落库，只回掩码）
    → 首页/对话页横幅引导、下拉选择配置与模型
    → 会话创建/切换绑定 modelConfigId（PATCH /chat/sessions/:id/model）
    → 提问 → askAndStream → resolveForChat ?? resolveDefaultForUser
    → target 解密明文 Key → OpenAI 兼容客户端（baseURL + Bearer Key）
    → 模型流式回答，token 全部记在用户 Key 账上
    → 失败（上游 401/余额不足）→ 把上游错误转成可读文案回给前端
```

## 七、前端安全细节：localStorage、无感刷新与并发队列

### 7.1 Token 存哪：为什么项目选 localStorage

前端拿到 `{ accessToken, refreshToken }` 后要存起来（`stores/auth.ts`），否则一刷新页面就丢登录态。可选位置各有取舍：

| 存储位置 | 优点 | 缺点 |
|---|---|---|
| **localStorage（本项目）** | 刷新/关浏览器不丢；纯前端代码即可读写，简单 | **可被 XSS 读取**（任何能执行脚本的注入都能偷 Token） |
| sessionStorage | 关标签页即失效，泄露窗口小 | 用户体验差：换个标签页要重登 |
| Cookie（HttpOnly） | XSS 读不到 | 需要后端配合 `Set-Cookie` + CSRF 防护；跨域配置麻烦；SSE/流式也要带 cookie |
| 内存变量（不进持久层） | XSS 也偷不到 | 刷新页面即丢，需要配合 refresh 恢复，实现最重 |

项目选了 localStorage，隐含前提是**"这个前端没有 XSS"**——这也是为什么第 08 章要专门讲 Markdown 渲染器如何转义、代码高亮如何兜底转义：**把用户内容当纯文本渲染是 Token 安全的第一道防线**。存法本身（`stores/auth.ts`）：

```ts
// 状态从 localStorage 初始化（刷新页面后依然"记得"登录态）
const accessToken = ref<string>(localStorage.getItem('accessToken') || '');
const refreshToken = ref<string>(localStorage.getItem('refreshToken') || '');
const isLoggedIn = computed(() => !!accessToken.value);

function setTokens(access: string, refresh: string) {
  accessToken.value = access;  refreshToken.value = refresh;
  localStorage.setItem('accessToken', access);
  localStorage.setItem('refreshToken', refresh);
}
function clearAuth() {         // 登出/刷新失败：三处一起清
  user.value = null;  accessToken.value = '';  refreshToken.value = '';
  localStorage.removeItem('accessToken');
  localStorage.removeItem('refreshToken');
}
```

登出 `logout()` 先调后端 `POST /auth/logout`（吊销 Redis 里的 refreshToken），再 `clearAuth()`——**先吊销再清本地**，顺序别反。

### 7.2 请求层：一个 axios 实例管所有（`apps/web/src/api/request.ts`）

- **请求拦截器**：从 localStorage 拿 accessToken，拼成 `Authorization: Bearer <token>`；
- **响应拦截器**：后端统一信封 `{ code, message, data }`，`code !== 0` 直接 reject，业务代码拿到的是解包后的 `data`。

### 7.3 401 无感刷新：核心难点在"并发"

accessToken 只有 15 分钟，过期是常态。过期瞬间，用户可能正同时发出 N 个请求（切页面、滚动加载、轮询……），N 个请求会**几乎同时**收到 401。这时候最直觉但也最错的写法是"每个 401 都自己去刷新一次"：

```
❌ 各自为政（每个 401 自己 refresh）：
   请求 A 401 → refresh#1
   请求 B 401 → refresh#2   ← 同时！
   请求 C 401 → refresh#3   ← 同时！
   → refresh 轮换的副作用：第一个 refresh 成功就把旧 refreshToken 的
     Redis 键删了、换发了新对；第 2、3 个 refresh 拿着同一个旧 refreshToken
     再来，验签虽过但键已被删 / 或与容错分支纠缠 → 大概率失败
   → 其中一个失败 → "refreshToken 无效" → 清登录态 → 用户被莫名踢下线
```

即使没被踢，**N 个并发 refresh 也全是浪费**——刷新一次就够，结果所有人共享同一对新 Token。正确姿势是**单飞（single-flight）+ 排队重放**：

```
✅ 单飞 + 队列：
   请求 A 401 → 发现没人正在刷新 → 自己当"刷新者"，isRefreshing = true
   请求 B 401 → 发现 isRefreshing = true → 不刷新，进 pendingQueue 排队
   请求 C 401 → 同上，排队
   刷新者拿到新 accessToken → 依次唤醒队列：A/B/C 换上新 Token 各自重发
   刷新失败 → 队列清空 + 清登录态 + 跳登录页（一个失败 = 全体失败，本来就是同一条登录态）
```

`request.ts` 的真实实现，逐段注释：

```ts
let isRefreshing = false;                              // 是否正在刷新（单飞开关）
let pendingQueue: Array<(token: string) => void> = []; // 等待刷新的请求队列

response 拦截器错误分支（核心逻辑）：
async (error) => {
  const originalRequest = error.config;
  // 触发刷新的前提：401 && 没重试过 && 不是公开接口的业务错误（见 7.4）
  if (error.response?.status === 401 && !originalRequest._retry &&
      !PUBLIC_AUTH_PATHS.some((p) => (originalRequest.url || '').includes(p))) {

    if (isRefreshing) {
      // 别人正在刷新：我不刷，把"用新 token 重发我"这件事挂进队列
      return new Promise((resolve) => {
        pendingQueue.push((token: string) => {
          originalRequest.headers.Authorization = `Bearer ${token}`;  // 换上新鲜 token
          resolve(request(originalRequest));                          // 重放原请求
        });
      });
    }

    originalRequest._retry = true;   // 标记已重试，防止自己再进这个分支死循环
    isRefreshing = true;

    try {
      const refreshToken = localStorage.getItem('refreshToken');
      if (!refreshToken) throw new Error('no refresh token');
      // 用原生 axios 调 refresh：若用本实例，响应 401 会再进本拦截器 → 死循环
      const { data } = await axios.post('/api/auth/refresh', { refreshToken });
      const accessToken = data.data.accessToken as string;
      localStorage.setItem('accessToken', accessToken);

      // 依次唤醒所有排队的请求
      pendingQueue.forEach((cb) => cb(accessToken));
      pendingQueue = [];

      // 自己（触发刷新的那个请求）也换上新 token 重发
      originalRequest.headers.Authorization = `Bearer ${accessToken}`;
      return request(originalRequest);
    } catch (refreshError) {
      // refreshToken 也过期/被吊销：清队列、清本地、硬跳登录页
      pendingQueue = [];
      localStorage.removeItem('accessToken');
      localStorage.removeItem('refreshToken');
      window.location.href = '/login';
      return Promise.reject(refreshError);
    } finally {
      isRefreshing = false;
    }
  }
  // 其他错误：把后端 message 转成中文错误抛给业务层 toast
  const message = error.response?.data?.message || error.message || '网络错误';
  return Promise.reject(new Error(message));
}
```

四个容易被忽略但都是坑的点：

1. **`_retry` 标记**：重发后的请求如果又 401（比如 refresh 换来的 token 依然无权），不会再进刷新分支，否则 A→刷→A→刷 死循环；
2. **refresh 请求用原生 axios，不用本实例**：本实例的响应拦截器会对 refresh 的 401 也触发"刷新"逻辑 → 递归刷新自己 → 死循环。原生 axios 绕开拦截器，refresh 失败直接走 catch；
3. **刷新失败全体一起走**：队列里的请求和刷新者是同一条登录态，refresh 失败意味着 refreshToken 真死了，清空队列 + 清登录态 + `window.location.href = '/login'`（整页跳转顺便重置所有内存状态）；
4. **`finally { isRefreshing = false }`**：无论成败都复位单飞开关，下次 401 才能重新发起刷新。

### 7.4 PUBLIC_AUTH_PATHS：哪些 401 是"业务错误"，绝不能触发刷新

`request.ts` 顶部有一段容易被新手删掉的数组，注释写得很清楚：

```ts
/**
 * 这些公开接口的 401 是业务错误（邮箱/密码/验证码错误），不是 token 过期，
 * 绝不能触发"刷新 token"流程——否则登录输错密码会被误判成登录态失效，
 * 刷新失败后硬跳登录页，把用户正在填的表单清空。
 */
const PUBLIC_AUTH_PATHS = [
  '/auth/login',
  '/auth/register',
  '/auth/send-code',
  '/auth/forgot-password',
  '/auth/verify-code',
];
```

为什么必须有它？试想：用户在登录页输错密码，后端正确返回 `401 邮箱或密码错误`。拦截器分不清"401 是因为 token 过期"还是"401 是因为密码错"，如果没有这张白名单，它会把"密码错"当成"登录态过期"去刷新——刷新（拿不到 refreshToken 或失败）→ 清 localStorage → `location.href = '/login'`，用户刚输到一半的表单被整页刷新清空，体验崩坏。**按 URL 前缀白名单把认证类接口的 401 排除在刷新逻辑之外**——它们的 401 是业务语义，不是会话语义。（`/auth/refresh` 没列进来是因为它走原生 axios，根本不经这个拦截器。）

### 7.5 路由守卫：最后一层"没登录就别进"

请求层兜住了"登录态过期"，路由层兜住"压根没登录就点进页面"（`router/index.ts`）：

```ts
router.beforeEach((to) => {
  const auth = useAuthStore();
  // 已登录还去登录/注册页 → 送回首页
  if (to.meta.public && auth.isLoggedIn && to.name !== 'not-found') return { name: 'home' };
  // 没登录访问受保护页 → 送去登录页，并记住想去哪（登录后跳回）
  if (!to.meta.public && !auth.isLoggedIn) {
    return { name: 'login', query: { redirect: to.fullPath } };
  }
});
```

页面级（`views/Layout.vue` 等）在挂载时还会调 `fetchProfile()` 把用户资料拉回来填进 store——**登录态的三层防线：路由守卫（没 Token 不让进）→ 请求层（Token 过期自动续）→ 接口层（后端全局守卫兜底）**。前端任何一层被绕过，后端 404/401 都是最后的安全网。

## 八、其他防护与密钥管理

### 8.1 全局限流：ThrottlerGuard，60 秒 60 次

`app.module.ts` 里和 JwtAuthGuard 一起注册了 NestJS 的限流守卫：

```ts
ThrottlerModule.forRoot([{ ttl: 60_000, limit: 60 }]),   // 每 60 秒窗口最多 60 次请求
...
{ provide: APP_GUARD, useClass: ThrottlerGuard },
```

全局默认**按来源 IP、60 秒窗口、上限 60 次**。登录接口反复撞密码、send-code 被脚本狂点、任何接口被刷，都会被这个全局闸门拦下（超出直接 429）。

值得注意的例外：部分接口用 `@SkipThrottle()` 显式豁免（`documents.controller.ts` 里的批量上传等）——**上传是批量操作，一个目录可能几百个文件却只算几次请求，按请求次数限流会误伤**；SSE 长连接类接口同理，一次连接挂很久，按次数限不合理。豁免原则是"按请求数限流与业务特性冲突时才豁免，而不是偷懒"。

叠加在验证码上的第二道闸是 60 秒重发冷却（第 3 节），两层合起来：脚本想爆破 6 位验证码，先被"同邮箱 60 秒一发"卡死，再被"同 IP 60 秒 60 请求"卡死。

### 8.2 用户枚举的两处取舍（值得知道的边界）

- **登录**：统一报"邮箱或密码错误"，不区分"邮箱不存在"和"密码错误"（第 2.4 节）——防枚举；
- **注册 / 忘记密码**：注册对已占用邮箱报 409"该邮箱已被注册"，忘记密码对未注册邮箱报"该邮箱尚未注册"——这两处**会暴露邮箱的注册状态**，属于为了产品体验接受的取舍（提示准确，用户不迷惑）。如果你要更严格，可以在 send-code 阶段对 forgot 也统一返回"如果邮箱存在我们会发送邮件"之类的模糊文案。**知道取舍在哪、代价是什么，比盲目堆砌"安全"重要**。

### 8.3 密钥管理清单：哪些秘密、存在哪、怎么生成

全部秘密只存在于服务端 `.env`（`apps/server/.env`，模板见仓库 `.env.example`），**代码仓库里永远只有占位符**：

| 秘密 | 用途 | 生成/保管建议 |
|---|---|---|
| `JWT_SECRET` | accessToken 签名 | 随机 ≥32 位串；access 与 refresh **分两个** |
| `JWT_REFRESH_SECRET` | refreshToken 签名 | 另一个独立随机串；泄露其一不影响另一个 |
| `MODEL_KEY_SECRET` | AES-256 加密用户 API Key | `openssl rand -hex 32` 生成 64 位 hex；**一旦生成别再改**，改了所有已存 Key 全部解不开 |
| `MAIL_USER` / `MAIL_PASS` | SMTP 发信 | 邮箱服务商的授权码（不是登录密码） |
| `SILICONFLOW_API_KEY` | Embedding / 重排（平台侧） | 平台自己的 Key，与用户 Key 严格隔离 |
| `DATABASE_URL` / `REDIS_PASSWORD` | 数据库 / Redis | 仅服务端可见 |
| `DEEPSEEK_API_KEY` | 系统兜底参考 | BYO 后业务链路不再读取，仅保留给运维/演示场景 |

管理纪律三条：**不进代码库（.env 在 .gitignore）→ 每把钥匙各司其职不混用 → 轮换时考虑牵连**（换 JWT_SECRET 只需重新登录，换 MODEL_KEY_SECRET 会丢所有用户已存 Key，要提供"重新绑定"迁移路径）。

### 8.4 别忘了 XSS 才是前端最大的洞

Token 在 localStorage、能被脚本读到——所以这个项目的**前端渲染安全**（第 08 章 Markdown 转义、外部链接新标签、代码高亮兜底转义）不是体验优化，是**认证安全的一部分**。任何把用户内容当 HTML 注入的地方都是偷 Token 的入口。后端同样守规矩：所有需要展示的内容（昵称、文件名、消息正文）都当纯文本存、当纯文本出，绝不在服务端拼 HTML。

## 九、动手实验

> 前提：本地项目已跑起来（后端 3000 / 前端 5173，见 00 章启动步骤），数据库与 Redis 可用。打开浏览器开发者工具 Network 面板，勾选"Preserve log"。

**实验 A：注册全流程，观察验证码接口的响应（开发模式回显）**

1. 打开 `http://localhost:5173/register`，Network 面板清空；
2. 输入一个没注册过的邮箱，点"发送验证码"；
3. 找到 `POST /api/auth/send-code`，看响应体——本地没配 SMTP 时应是：
```json
{ "code": 0, "message": "ok", "data": { "sent": true, "devMode": true, "code": "482913" } }
```
`devMode: true` 就是双通道的开发模式分支（`email-code.service.ts` 的 `sendCode` 末尾）；页面会把 code 自动填进输入框并提示"（开发模式）验证码已自动填入"。
4. 立刻再点一次"发送验证码"→ 应返回 400"验证码发送过于频繁"——这就是 60 秒冷却（`email_code:{type}:{email}:sent` 键还活着）。
5. 输入密码完成注册，回到 Network 看 `POST /api/auth/register` 响应——里面有 `accessToken` / `refreshToken` / `user`。注册成功即登录。

**实验 B：把密码改错，观察 401 与"是否触发刷新"**

1. 在已登录状态打开 Network，调出登录页（或退出重登）；
2. 故意输错密码提交，观察 `POST /api/auth/login` 的响应是 `401 邮箱或密码错误`；
3. **关键观察**：虽然状态码是 401，但它**没有**触发刷新流程——因为 `/auth/login` 在 `PUBLIC_AUTH_PATHS` 白名单里。你也不会被跳转、不会被清空表单。如果去掉那个白名单，这条 401 会走刷新分支 → 刷新失败 → `location.href = '/login'` 整页刷新清空输入（实验 B 可以亲手验证这个"如果没有白名单会怎样"）。
4. 对照：登录成功后，在 Console 里把 localStorage 的 `accessToken` 改成 `abc`（一个假 token），随便点一个功能页触发请求 → 观察该请求先 401，然后 Network 里出现一次 `POST /api/auth/refresh`，随后原请求带着新 token 自动重发成功——**无感刷新 + 单飞队列**的现场。

**实验 C：错误 Key 的 BYO 引导（省钱验证）**

1. 未绑定任何模型配置时，去对话页问一句；
2. Network 里看 `POST /api/chat/sessions/:id/messages` 的 SSE 流——第一条事件是 `error`，文案是"使用前请先在「模型配置」里绑定你自己的大模型 API Key……"，**没有任何模型调用发生**（平台零消耗）；
3. 到「模型配置」页新建配置，填一个**故意写错的 Key**（如 `sk-****` 格式但乱填），点"测试连接"→ 返回 `ok: false` 且带上游错误信息；再填真实 Key → `ok: true`；
4. 用错误 Key 建好配置后再去对话 → 这次不再提示"绑定"，而是流式里报上游认证错误——**证明系统真的把你的 Key 发出去了**（token 记在你账上）。

## 本章自测

1. **【面试必背】为什么用"15 分钟的 accessToken + 7 天的 refreshToken"双 Token，而不是一个长 Token？**（提示：从泄露窗口、无状态无法吊销、体验三个角度答；再补一句 refreshToken 为什么能吊销——Redis 键。）
2. **【面试必背】BYO 是怎么做到"省钱又安全"的？**（提示：成本端——推理走用户 Key、平台只出 Embedding/重排等检索基建；安全端——AES-256-GCM `iv:tag:data` 落库、`MODEL_KEY_SECRET` 服务端持有、接口只回掩码、更新留空保留原 Key、归属 404。）
3. 密码为什么必须用 bcrypt（盐 + 慢哈希）？直接用明文、单次 MD5、MD5+固定盐分别死在哪个环节？
4. 邮箱验证码的"60 秒冷却、10 分钟过期、消费即删、场景分型"分别防什么？注册流程为什么要有 `verifyOnly`（只校验不消费）这一步？
5. 401 无感刷新为什么要"单飞 + 队列重放"？如果每个请求收到 401 都各自去刷新，会发生什么？`PUBLIC_AUTH_PATHS` 和"用原生 axios 调 refresh"各自防什么？
6. 越权访问别人的模型配置/文档，为什么后端要返回 404 而不是 403？`JwtStrategy.validate` 验签通过后为什么还要再查一次数据库？

## 本章小结

这一章走完了"一个用户从注册到对话"的整条安全链：**注册靠邮箱验证码证明邮箱所有权**（Redis 存码、10 分钟有效、60 秒冷却、消费即删，开发模式回显是本地联调的恩物），**密码用 bcryptjs 慢哈希落库**（脱库也拿不到明文），**身份靠双 Token 维持**（15 分钟 access 无状态高频 + 7 天 refresh 可吊销低频，刷新即轮换），**接口靠全局 JWT 守卫默认全锁 + @Public 显式放行**，**数据靠 ownerId 过滤 + 越权 404**，**AI 成本靠 BYO 转嫁给用户自己的 Key**（AES-256-GCM 加密存库、接口永不回传明文、会话绑定 → 默认配置 → 明确引导的三层解析链），**前端靠 localStorage + 单飞式无感刷新**把"Token 过期"变成用户无感知的事，最后用**全局限流和密钥分治**收尾。

下一章（08）讲前端工程化，其中"Markdown 渲染转义"等章节会反复呼应本章的一个结论——**前端的 XSS 防线就是 Token 安全的防线**。
