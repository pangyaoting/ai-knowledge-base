## 一、读 schema 的正确姿势

先把「读 Prisma schema」这件事讲清楚，后面才不会被 `@map`、`Unsupported` 这些东西绕晕。

### 1.1 schema.prisma 在项目里的位置与作用

`apps/server/prisma/schema.prisma` 是**唯一权威数据源（single source of truth）**：数据库长什么样，以它为准。它不是一份"文档"，而是活的定义——`pnpm --filter @app/server prisma:migrate` 会根据它生成迁移 SQL 去改真库；`Prisma Client`（代码里那个 `this.prisma.document.create(...)`）的类型也是从它生成的。改字段名不改 schema，代码马上编译报错，这是它比"手写 SQL 建表"靠谱的地方。

文件顶部先声明三件事：

```prisma
// apps/server/prisma/schema.prisma
generator client {
  provider        = "prisma-client-js"
  previewFeatures = ["postgresqlExtensions"]   // ① 允许 datasource 声明扩展
}

datasource db {
  provider   = "postgresql"
  url        = env("DATABASE_URL")              // ② 连接串来自 .env，绝不写死在代码里
  extensions = [vector]                         // ③ 声明 pgvector 扩展（真正的扩展要迁移里 CREATE）
}
```

第 ③ 行的 `extensions = [vector]` 是 Prisma 的"扩展白名单"：告诉 Prisma 这个库装了 `vector` 扩展，你才能在字段类型里写 `Unsupported("vector(1024)")`。**注意 Prisma 并不会替你创建扩展**——`CREATE EXTENSION vector` 在原始 SQL 迁移里完成（见 1.3）。

### 1.2 命名约定：camelCase 给代码，snake_case 给数据库

这是全项目最统一的风格，也是读表时最常被问到的点：

```prisma
model KnowledgeBase {
  ownerId     String  @map("owner_id")   // 代码里叫 ownerId，物理列叫 owner_id
  createdAt   DateTime @default(now()) @map("created_at")
  @@map("knowledge_bases")               // model 名 KnowledgeBase → 物理表 knowledge_bases
}
```

| 层 | 风格 | 例子 | 为什么 |
|---|---|---|---|
| Prisma model / 字段 | camelCase | `KnowledgeBase.ownerId` | TypeScript/JS 惯例，代码读起来顺 |
| 物理表 / 列 | snake_case 复数 | `knowledge_bases`、`owner_id` | PostgreSQL 社区惯例；DBA 直接 psql 不别扭 |
| 表名 | 复数 | `documents` / `chunks` | 一行的"集合"语义；SQL 里 `FROM documents` 自然 |
| 时间戳 | `created_at` / `updated_at` | 全部表统一 | 后文按时间排序、查"最近上传"全靠它们 |

`@map` / `@@map` 的另一个隐藏价值：**列名可以随时改而代码不动**。早期一次大迁移（迁移目录里 `20260817060000_normalize_column_names`）就是把当时不统一的列名全部规整成 snake_case，靠映射层隔离，业务代码基本没受伤。

> 面试可讲：schema 上的命名映射 = "应用层语言"与"存储层语言"的解耦，代价是任何改列名的迁移必须同时改 `@map`。

### 1.3 Prisma 的边界：vector 类型与"原始 SQL 迁移"

这是本项目 schema 里最"反常"却最值得讲的一点：**`Chunk.embedding` 和 `FileProfile.embedding` 在 schema 里是 `Unsupported` 类型**：

```prisma
model Chunk {
  ...
  embedding  Unsupported("vector(1024)")? // 向量（bge-m3 1024 维）
}
```

原因：Prisma Client 认识的类型是 `String/Int/DateTime/Json/...`，**不认识 PostgreSQL 扩展类型 `vector`**。于是 schema 里用一个 `Unsupported("vector(1024)")` 占位——意思是"这张表确实有这一列，类型是 vector(1024)，但 Prisma Client 不提供读写它的 API"。真正的建列 SQL 在迁移文件里：

```sql
-- apps/server/prisma/migrations/20260817070000_add_chunk_embedding/migration.sql
ALTER TABLE "chunks" ADD COLUMN "embedding" vector(1024);

-- HNSW 近似最近邻索引（cosine 距离）：百万级向量检索毫秒级
CREATE INDEX "chunks_embedding_idx" ON "chunks" USING hnsw ("embedding" vector_cosine_ops);
```

于是代码里对 embedding 的读写全部走**原始 SQL**，而不是 Prisma 的 `create`：

```ts
// apps/server/src/modules/knowledge/document-processor.service.ts
// 写：把数字数组拼成 pgvector 字面量 "[0.1,0.2,...]"，$executeRaw 执行 UPDATE
await tx.$executeRaw`
  UPDATE "chunks" SET "embedding" = ${toPgVector(vectors[i])}::vector WHERE "id" = ${rows[i].id}
`;
```

一句话总结这个架构决策：**Prisma 管关系型部分（表/行/关系/级联），pgvector 的部分（建列、HNSW 索引、读写、检索排序）用原始 SQL 补齐**。两者通过 `Unsupported` 占位和平行迁移共存。检索时（RAG 服务）读 embedding 也是 `$queryRaw` + `<=>` 余弦距离运算符，见第 04 章。

## 二、十二张表的业务地图

先给全景，再逐个拆。schema.prisma 用注释分成了几个区块，正好就是业务的几大块：

```
┌──────────────────────────────────────────────────────────────────────┐
│                              users  用户系统                          │
└───────────────┬──────────────────────────────────────────────────────┘
                │ 1:N（ownerId + onDelete: Cascade）
   ┌────────────┼──────────────────────┬──────────────────┬────────────┐
   ▼            ▼                      ▼                  ▼            ▼
knowledge_bases  chat_sessions      reports         agent_tasks   model_configs
(知识库)          (对话会话)         (研究报告)        (自主研究Agent)  (BYO模型配置)
   │ 1:N          │ 1:N                 │                │            │ 1:N（SetNull）
   ▼              ▼                     │                │            ▼
documents      chat_messages            │                │      chat_sessions.model_config_id
(文档)           (消息: sources Json)    │                │
   │ 1:N          │ N:M 通过关联表        │                │
   ▼              ▼                     │                │
chunks         session_knowledge_bases  │                │
(分块+向量)       (会话⇄知识库)           │                │
   │ 1:N(符号)    │ 1:1(档案)            │                │
   ▼              ▼                     │                │
code_symbols   file_profiles            │                │
(C符号级索引)    (A文件档案层)            │                │
                                       ▼                ▼
                    报告/Agent 各自持有 Json 快照（sections/sources/progress…），不建关联表
└──────────────────────────────────────────────────────────────────────┘
```

先把 12 个 model 与物理表名、一句话职责列全（第 07 章会讲为什么**没有 EmailCode 表**——验证码住在 Redis 里）：

| # | Prisma model | 物理表 | 一句话职责 | 归属字段 | 删除语义 |
|---|---|---|---|---|---|
| 1 | `User` | `users` | 账号：邮箱登录、昵称头像、最后登录时间 | — | — |
| 2 | `KnowledgeBase` | `knowledge_bases` | 文档集合的容器，回答检索的作用域 | `owner_id` | 用户删→级联 |
| 3 | `Document` | `documents` | 一个已上传文件的元信息 + 处理状态机 | `knowledge_base_id` | 知识库删→级联 |
| 4 | `Chunk` | `chunks` | 检索的最小单元：文本块 + embedding | `document_id` | 文档删→级联 |
| 5 | `CodeSymbol` | `code_symbols` | 代码文件解析出的符号表（函数/类/组件…） | `document_id` | 文档删→级联 |
| 6 | `FileProfile` | `file_profiles` | 每文档一份"档案"（1:1），先定位文件再文件内检索 | `document_id`(unique) | 文档删→级联 |
| 7 | `ChatSession` | `chat_sessions` | 一次对话：模式开关、绑定的模型/知识库 | `owner_id` | 用户删→级联 |
| 8 | `SessionKnowledgeBase` | `session_knowledge_bases` | 会话⇄知识库 多对多关联表 | 复合主键 | 两侧都级联 |
| 9 | `ChatMessage` | `chat_messages` | 一条消息（含引用来源 sources 快照） | `session_id` | 会话删→级联 |
| 10 | `Report` | `reports` | 研究报告：主题→分节内容→汇总 Markdown | `owner_id` | 用户删→级联 |
| 11 | `ModelConfig` | `model_configs` | 用户自带的模型 Key（BYO），加密存储 | `owner_id` | 用户删→级联 |
| 12 | `AgentTask` | `agent_tasks` | 限时·限量·可续跑的自主研究任务 | `owner_id` | 用户删→级联 |

三个"读表先看"的心法，贯穿后文：

1. **几乎每张业务表都带 `ownerId` / 通过父链能追到 `ownerId`**——这是数据隔离的物理基础（第 01 章讲过"越权查他人数据返回 404"），后文每个 Service 的 `where` 都带归属过滤；
2. **删除语义几乎全是 `onDelete: Cascade`，只有一处例外**（`ChatSession.modelConfig` 是 `SetNull`）——第 八 节专门讲"谁删谁、删到哪"；
3. **凡是"过程快照"（消息的引用来源、报告的分节/来源/检索范围、Agent 的研究进度）都存 Json**，而不是建关联表——第 五、六 节讲为什么。

## 三、用户与知识库层

### 3.1 users：最小的账号表

```prisma
model User {
  id          String    @id @default(uuid())
  email       String    @unique
  password    String
  nickname    String?
  avatar      String?
  lastLoginAt DateTime? @map("last_login_at")
  createdAt   DateTime  @default(now()) @map("created_at")
  updatedAt   DateTime  @updatedAt @map("updated_at")
  ...
  @@map("users")
}
```

**① 这张表解决什么业务问题**：一个最小可用的账号系统——邮箱注册登录、个人资料、鉴权身份。它只解决"你是谁"，不解决"你能干什么"（权限粒度到资源所有者，即"你自己创建的"）。

**② 关键字段与类型选择理由**：

| 字段 | 类型 | 为什么这么选 |
|---|---|---|
| `id` | `String @default(uuid())` | UUID 而非自增数字：不泄露"注册人数"这种业务量；多实例/未来分库不撞号（面试点：自增主键会被爬虫枚举，`GET /users/1` 遍历即可拖库） |
| `email` | `String @unique` | 登录名即邮箱，唯一约束在数据库层兜底（应用层查重可能漏并发） |
| `password` | `String`（非空） | 存的是**哈希**（bcrypt，第 07 章讲），列类型只是个字符串容器 |
| `nickname` / `avatar` | `String?`（可空） | 注册时可留空，后补 |
| `lastLoginAt` | `DateTime?` | 纯统计/体验字段：记录最近一次登录（登录时 update），可为空 |

**③ 关系与级联**：`User` 往下挂 5 条 1:N——知识库、会话、报告、Agent 任务、模型配置，全部 `onDelete: Cascade`。含义：**删账号 = 把这个人在这套系统里的所有痕迹（含它的文档向量、对话、报告）一次清空**。这是产品语义："账号是资源生命周期的根"。

### 3.2 knowledge_bases：一切检索的"作用域"

```prisma
model KnowledgeBase {
  id          String     @id @default(uuid())
  name        String
  description String?
  ownerId     String     @map("owner_id")
  ...
  owner User @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  @@index([ownerId])
  @@map("knowledge_bases")
}
```

**① 这张表解决什么业务问题**：用户会往系统里塞**多个主题不相关的文档集合**——工作文档、学习笔记、某个开源项目源码。如果所有文档摊在一个大池子里，检索时"问工作问题"会命中"学习笔记"的段落。知识库就是一个**检索隔离域**：上传时选库、提问时选库（会话可绑多个库，见 3.3），向量检索默认只在自己的库里找。

**② 关键字段**：`name`、`description`（可选，给用户看的说明）、`ownerId`。

**③ 关系与级联**：

- `owner User`：知识库属于一个用户，用户删除 → 知识库级联删除；
- `documents Document[]`：一个库下有多个文档，**文档删的级联源头在这里**；
- `sessionLinks SessionKnowledgeBase[]`：一个库可以被多个会话绑定（多对多，反向关系）；
- `@@index([ownerId])`：所有查询都带"我的库"过滤，这个索引是**数据隔离查询的性能底座**（`WHERE owner_id = ?` 走索引）。

> **设计决策（面试可讲）为什么文档挂在 knowledge_bases 而不是直接挂 users？**
> 因为归属的"粒度"不同：权限校验最小单元是"一个知识库"，而不是"一个用户"——删一个库不应波及其余库；检索要能按库过滤。如果 Document 直接挂 user，那"库"就只剩一个名字字段，删库、库内检索全都要额外过滤。**表的层级 = 权限与操作的层级**，这是"从表结构看业务"的第一课。

## 四、文档加工层：documents / chunks / code_symbols / file_profiles

这一层是本项目的**心脏**：一个文件进来，经过第 03 章的流水线，最终在四张表里留下四种形态的"衍生数据"。先看四张表的关系：

```
documents（文件本身：元信息 + 状态）
   │ 1:N                chunks（文本块：检索命中与引用的单元，embedding 在这）
   │ 1:N                code_symbols（代码符号：按符号名精确命中实现源码）
   │ 1:1                file_profiles（文件档案：先定位文件，再文件内检索）
```

### 4.1 documents：流水线的"总调度台"

```prisma
model Document {
  id              String   @id @default(uuid())
  knowledgeBaseId String   @map("knowledge_base_id")
  filename        String // 原始文件名
  filepath        String // 服务器上存储路径
  fileSize        Int      @map("file_size") // 字节数
  fileType        String   @map("file_type") // pdf / docx / md / txt / code / 附件扩展名
  status          String   @default("pending") // pending / processing / done / failed / replacing
  error           String? // 失败原因
  contentHash     String?  @map("content_hash") // 文件内容 SHA-256
  indexVersion    Int      @default(1) @map("index_version") // 处理规则版本
  createdAt       DateTime @default(now()) @map("created_at")
  updatedAt       DateTime @updatedAt @map("updated_at")
  ...
  @@index([knowledgeBaseId])
  @@map("documents")
}
```

**① 这张表解决什么业务问题**：把"用户上传了一个文件"这件事**落成一条可跟踪的状态记录**。注意一个反直觉的点：**documents 表并不存文件全文**——原文在磁盘（`filepath` 指向 `uploads/` 下的文件），chunks 里的文本是从磁盘文件**抽取并切碎的可重建副本**。为什么？

- 磁盘文件是**原始事实**：查看/下载/编辑要的是原样文件；
- chunks / symbols / profile 是**派生数据**：任何时刻都可以删掉重算（第 03 章的重索引功能就是干这个的）；
- 那么 documents 表的职责就纯粹了：**记录"这个文件是谁的、长什么样、处理到哪一步了、上次按什么规则处理的"**。

**② 关键字段逐个讲**：

| 字段 | 类型 | 为什么这么选 | 背后的设计点 |
|---|---|---|---|
| `filename` | String | 展示名/引用来源里显示的名字 | **不是磁盘名**！磁盘名是 UUID（防重名/防路径注入），`filename` 才是人话。目录上传时还带相对路径如 `docs/子/a.md`（前端据此渲染文件夹树） |
| `filepath` | String | 存 `uploads/<uuid>.<ext>` 相对路径 | 相对路径可随 `UPLOAD_DIR`（见 `apps/server/src/common/paths.ts`）整体迁移；读盘时只取 basename 再拼当前 `UPLOAD_DIR`，目录搬了家旧记录仍能定位 |
| `fileSize` | `Int`（字节） | 单位定死为字节 | Int 上限约 21 亿字节 ≈ 2GB，而上传上限默认 20MB，**类型上限远大于业务上限**——不会溢出，又比 BigInt 省空间 |
| `fileType` | String | `pdf / docx / md / txt / code / bin / png…` | 五类可解析 + 附件（原扩展名）+ 误判兜底 `bin`。类型决定第 03 章走哪条解析/分块分支 |
| `status` | String | 状态机字段，见下 | **用 String 不用 PG enum**——后文专门讲 |
| `error` | String? | 处理失败时写原因 | 异步处理失败没法抛给当时的请求方，只能落库让前端展示（列表红字） |
| `contentHash` | String? | 文件内容 SHA-256（hex） | 增量向量化的依据：同名 + 同哈希 = 内容没变，跳过整条流水线 |
| `indexVersion` | Int | 默认 1 | 处理规则版本，与后端常量 `INDEX_VERSION` 对照，落后则需重算（第 03 章第 九 节） |
| `createdAt`/`updatedAt` | DateTime | 列表排序 + 并发乐观判断 | 后文队列任务里大量用"更新前先查"保证不覆盖并发结果 |

**status 状态机**是这张表最活的字段。schema 注释写的是 `pending / processing / done / failed`，但实际代码里还有第五态 `replacing`（上传同名文件时给旧版打的标，见第 03 章第 八 节）：

```
        upload/入队               worker 开工              全部成功
  (无记录) ──────► pending ──────────► processing ──────────► done
                       │                   │                   ▲
                       │  worker 失败       │ worker 失败       │ 上传同名新文件
                       ▼                   ▼                   │
                     failed ◄──────────── failed               │
                       ▲                                       │
                       │ upload 同名文件（新文档入队）           │
                       └────────────── replacing ◄─────────────┘
                        （旧版被标记"替换中"：新文档成功后删除 / 失败后恢复 done）
```

三个值得记住的点：

1. `pending` = "已接收，还没轮到处理"；`processing` = "worker 正在解析/分块/向量化"；两者都出现在上传接口秒回之后、后台任务完成之前——前端靠轮询看状态流转；
2. `replacing` 是**后来加的**状态（P0 系列并发修复引入），而 schema 注释没同步更新——这正是 **status 用 String 而非 PG enum 的原因**：enum 要加一个值得跑一次 `ALTER TYPE ... ADD VALUE` 迁移，字符串随时加，代价为零。**用 String 存状态机，是把"状态集合会演进"这个风险提前消化掉了**（代价是失去了数据库层的取值约束，用应用层校验补）。
3. 状态是"文档级"的：chunks 有没有、全不全，由文档状态间接表达——`done` 意味着"当时的 chunks 与文档一致"。

**③ 关系与级联**：`knowledgeBase`（反向）→ 库删则文档级联删；`chunks`/`codeSymbols`/`profile` 三个子表都从这往下级联。**注意一个细节：删除单个文档时，应用代码会手动 `unlinkSync` 磁盘文件（documents.service 的 remove），而删知识库是 DB 级联删记录、不经过应用删除逻辑，磁盘文件会滞留**——这是"DB 与磁盘两份事实"天然的不同步点，靠 `UPLOAD_DIR` 独立于代码目录的设计 + 运维定期清理兜底（`apps/server/src/common/paths.ts` 注释说明了为什么 uploads 目录要可配置到代码目录之外）。

### 4.2 chunks：检索的最小单元（embedding 的宿主）

```prisma
model Chunk {
  id         String                    @id @default(uuid())
  documentId String                    @map("document_id")
  content    String // 文本块原文
  chunkIndex Int                       @map("chunk_index") // 第几块（保证顺序）
  parentId   String?                   @map("parent_id")   // P2 父子分块：子块挂父块
  embedding  Unsupported("vector(1024)")? // bge-m3 1024 维向量，父块不参与检索可为空
  createdAt  DateTime                  @default(now()) @map("created_at")

  document Document @relation(fields: [documentId], references: [id], onDelete: Cascade)

  @@index([documentId])
  @@index([parentId])
  @@map("chunks")
}
```

**① 这张表解决什么业务问题**：第 00 章快问快答就埋过伏笔——"整篇文档塞给模型太长太贵，且哪段跟问题相关无从定位"。chunks 就是"定位"的物理载体：**每条 chunk 是一段可独立检索、可独立作为引用返回的文本**。向量检索命中哪条 chunk，就把它的 `content`（或它父块的 `content`）连同"文档名 + 第几段"给模型和用户。

**② 关键字段逐个讲**：

| 字段 | 类型 | 为什么这么选 |
|---|---|---|
| `content` | String | 块原文。从文档抽取文本后按策略切开（500 字左右，代码 900~1000，md 结构化块 1200——见第 03 章） |
| `chunkIndex` | Int | **文档内序号**：保证展示/引用顺序稳定。聊天里"第 N 段"的高亮定位就按它来（检索结果带 `chunkIndex`，前端滚动到对应位置） |
| `parentId` | String? | P2 父子分块的自关联：子块的 `parent_id` 指向父块行 id；`parentId` 为空 = 普通块（txt/pdf/code 的叶子块）或父块本身（md 的大章节容器）。**没有建外键**——迁移注释写得很明白："父块与子块同属一个文档，删除时按 document_id 级联清理，无孤儿风险" |
| `embedding` | `Unsupported("vector(1024)")?` | 可空不是可选项，而是**时序**：行先建（含 content），向量后补（异步 embedding 完成才 UPDATE 写回）。父块（容器）永远没有向量，不参与检索 |

> **关于 `parentId` 的精确语义**（schema 注释"父块无向量"是简化说法，精确行为见第 03 章第五节）：
> - `parentId = null` 且 `embedding IS NOT NULL` → 普通叶子块（txt/pdf/code），或"足够小的父块"（md 中 ≤500 字符的章节直接把自己当叶子向量化）；
> - `parentId = null` 且 `embedding IS NULL` → **父容器块**（md 大章节/大表格整块），只当"命中后喂模型的全文容器"；
> - `parentId = <某块id>` → 子块：小片、带向量，负责被检索命中；命中后把父块的完整内容交给模型。

**③ 关系与级联**：`document`（反向）级联删除——删文档，chunks 由数据库外键**一条 SQL 清光**，不用应用层遍历删。文档处理失败时也会 `deleteMany` 清半成品 chunk（第 03 章）。

**④ 索引全景**（一半在 schema，一半在原始迁移，说明"读表不能只读 schema"）：

| 索引 | 类型 | 在哪建的 | 服务谁 |
|---|---|---|---|
| `chunks_document_id_idx` | B-tree | schema `@@index([documentId])` | 按文档取全部块（预览/重算） |
| `chunks_parent_id_idx` | B-tree | 迁移 `20260905120000_add_chunk_parent` | 按父块取子块（P2 检索后的容器回填） |
| `chunks_embedding_idx` | **HNSW**（`vector_cosine_ops`） | 迁移 `20260817070000_add_chunk_embedding` | 向量近似最近邻检索（毫秒级） |
| `chunks_content_trgm_idx` | **GIN**（pg_trgm） | 迁移 `20260817161000_add_trgm_index` | 关键词检索 `similarity(content, ?)` / `ILIKE`（混合检索的另一路，第 04 章） |

一张 chunk 表同时挂着 B-tree、HNSW、GIN 三种索引——**每种索引服务一种查询模式**：等值/范围查、向量相似度查、文本模糊查。这就是为什么 vector 检索和关键词检索能"各自快"，也解释了为什么 schema.prisma 表达不了的东西必须散落在迁移 SQL 里。

### 4.3 code_symbols：代码的"符号级"结构化索引

```prisma
model CodeSymbol {
  id         String   @id @default(uuid())
  documentId String   @map("document_id")
  filename   String
  symbolName String   @map("symbol_name")
  kind       String // function / const / class / interface / type / enum / component
  signature  String
  body       String // 符号实现源码（命中后作为引用返回，无需再读盘）
  startLine  Int      @map("start_line")
  endLine    Int      @map("end_line")

  document Document @relation(fields: [documentId], references: [id], onDelete: Cascade)

  @@index([documentId])
  @@index([symbolName])
  @@map("code_symbols")
}
```

**① 这张表解决什么业务问题**：问"`Settings.vue` 里 `onAvatarChange` 是怎么实现的"——通用 RAG 只做文本相似度，问句和源码字面长得不一样就命中不了。本项目对代码文件用 **TypeScript Compiler API 解析 AST**，把每个文件"有哪些顶层符号"结构化提取出来（函数/类/接口/类型/枚举/const/Vue 组件），让**"符号名"可以被精确查询**：问题里出现 `onAvatarChange` → 符号表里精确命中 → 直接把实现源码返回，不靠向量碰运气。

**② 关键字段逐个讲**：

| 字段 | 类型 | 为什么这么选 |
|---|---|---|
| `symbolName` | String | 符号名。**有全局索引** `@@index([symbolName])`——跨文件问"谁定义了 `uploadDocument`"时可以直接按名查 |
| `kind` | String | function/const/class/interface/type/enum/component。String 而非 enum，理由同 `Document.status`：符号种类会随索引器演进 |
| `signature` | String | 单行签名（函数含参数列表，截断到 120~200 字符），用于列表/档案展示 |
| `body` | String | **符号实现源码快照**。命中符号后直接返回它，**不需要再回磁盘读原文件**——这是把"源码"复制进数据库换查询即时性 |
| `startLine`/`endLine` | Int | 1-based 行号范围。生成 body 时按行切（`code.split('\n').slice(startLine-1, endLine)`）；用户点引用可跳到源文件的对应行 |

**③ 关系与级联**：挂在 `document` 下、级联删除；重索引时先 `deleteMany({ documentId })` 再全量重建——**符号表是纯派生的，永远可以推倒重来**（第 03 章第 七 节）。

### 4.4 file_profiles：每个文件的"档案"（A 语义层）

```prisma
model FileProfile {
  id          String   @id @default(uuid())
  documentId  String   @unique @map("document_id")
  filename    String
  profileText String   @map("profile_text")
  embedding   Unsupported("vector(1024)")?

  document Document @relation(fields: [documentId], references: [id], onDelete: Cascade)
  @@map("file_profiles")
}
```

**① 这张表解决什么业务问题**：把**整个项目目录**喂进知识库后，检索是"文本片段对片段"的相似度，文件的边界在通用检索里被抹掉了——问"登录鉴权的代码在哪个文件"，答案散落在几十个文件的几百个块里，谁也说不清。file_profiles 给每个文档存一段**"档案"**（文件名 + 用途摘要 + 章节地图/符号清单，见第 03 章第 七 节），单独向量化，检索时**先档案命中锁定文件，再在文件内检索**。

**② 关键字段**：`documentId` **带 `@unique`**——一份文档只有一份档案，这就是 1:1 关系的表达方式（Prisma 里 1:1 不是特殊关键字，而是"反向字段加 unique 约束"）；`profileText` 档案正文；`embedding` 档案自己的向量（`file_profiles_embedding_idx` HNSW 索引在迁移 `20260905140000_add_file_profiles` 里）。

**③ 为什么档案单独一张表而不是塞进 documents？** 因为它是**检索侧的衍生数据**，和 documents 的生命周期（status 状态机、文件元信息）关注点不同；单独成表还可以单独建向量索引、单独重算，互不干扰。schema 注释把它叫作"A 语义层"（C 是代码符号，A 是档案），两个字母是当时功能代号。

### 4.5 四张表各自扮演什么（小结）

| 表 | 存什么 | 谁消费 | 能重建吗 |
|---|---|---|---|
| documents | 文件元信息 + 处理状态 | 列表/上传/轮询/删除 | 否（元信息） |
| chunks | 文本块 + 向量 | 混合检索、引用返回、编辑预览 | 能（从磁盘文件重跑流水线） |
| code_symbols | 符号 + 实现源码 | 代码问答的符号命中 | 能（AST 重解析） |
| file_profiles | 档案文本 + 向量 | 检索第一跳：锁定文件 | 能（从文档内容重生成） |

**"能重建吗"这一列是整个数据模型的灵魂**：只有 documents 是事实，其余三张全是派生视图。这也直接决定了删除/重算的写法——派生数据永远"先删后建"，不用心疼。

## 五、会话与消息层：chat_sessions / session_knowledge_bases / chat_messages

### 5.1 chat_sessions：一次对话的"驾驶舱"

```prisma
model ChatSession {
  id               String        @id @default(uuid())
  ownerId          String        @map("owner_id")
  title            String        @default("新对话")
  useKnowledgeBase Boolean       @default(true) @map("use_knowledge_base")
  modelConfigId    String?       @map("model_config_id")
  model            String?
  reasoningEffort  String?       @map("reasoning_effort")
  ...
  owner          User                   @relation(..., onDelete: Cascade)
  knowledgeBases SessionKnowledgeBase[]
  modelConfig    ModelConfig?           @relation(fields: [modelConfigId], references: [id], onDelete: SetNull)
  @@index([ownerId])
  @@map("chat_sessions")
}
```

**① 这张表解决什么业务问题**：把"一次对话"的状态集中起来——**这次问答要不要检索知识库、检索哪些库、用哪个模型回答、推理开多强**。会话是聊天页的左栏列表，也是消息的容器（`messages ChatMessage[]`）。

**② 关键字段逐个讲**：

| 字段 | 类型 | 语义 | 设计点 |
|---|---|---|---|
| `title` | String @default("新对话") | 会话标题 | 首问后自动用问题前 20 字替换（chat.service 里 `question.replace(/\s+/g,'').slice(0,20)`） |
| `useKnowledgeBase` | Boolean | **RAG 开关** | `true`=检索知识库再回答；`false`=纯对话模式（不检索）。schema 注释定义了三分语义：`true` + 绑了库 → 只在这几个库检索；`true` + 没绑库 → 检索该用户**全部**知识库；`false` → 不检索 |
| `modelConfigId` | String? 可空 | 用户自带的模型配置 | null = 用系统默认模型。**删除关系是 SetNull**（唯一例外，第 八 节细讲）：配置删了，会话不能跟着没，历史还能继续聊（回退默认模型） |
| `model` | String? 可空 | 会话里手动选的模型名 | 一个配置（一个 Key）下可挂多个模型（`model_configs.models`），会话只记住用户挑的那个；null = 用配置默认 |
| `reasoningEffort` | String? 可空 | 推理等级 low/high/max | 透传给支持 `reasoning_effort` 的模型（DeepSeek V4 等）；null = 不传 |

> 注意 `modelConfigId`（配置）与 `model`（模型名）是两个不同粒度的选择：配置决定 **Key/接口地址**，model 决定**用这把 Key 下的哪个模型**。会话表把两者分开存，是为了"同一配置下切模型"不重新选 Key。

**③ 关系与级联**：`owner` 用户删 → 会话级联删（连带消息，见 5.3）；`knowledgeBases` 多对多经关联表；`modelConfig` SetNull（例外）。

### 5.2 session_knowledge_bases：会话 ⇄ 知识库 的多对多

```prisma
model SessionKnowledgeBase {
  sessionId       String        @map("session_id")
  knowledgeBaseId String        @map("knowledge_base_id")
  session         ChatSession   @relation(fields: [sessionId], references: [id], onDelete: Cascade)
  knowledgeBase   KnowledgeBase @relation(fields: [knowledgeBaseId], references: [id], onDelete: Cascade)

  @@id([sessionId, knowledgeBaseId])
  @@index([knowledgeBaseId])
  @@map("session_knowledge_bases")
}
```

**① 这张表解决什么业务问题**：一个会话要能"只问这几个库"，一个库要被多个会话引用——标准多对多，需要一张关联表。它没有任何业务字段，纯粹表达关系，所以**用复合主键** `@@id([sessionId, knowledgeBaseId])` 而不是自增 id：同一对 (会话, 库) 只允许出现一次。

**② 级联语义**：两侧都 Cascade——删会话，关联行消失（不影响库）；删库，关联行消失（不影响会话）。库里文档没了，会话的历史消息还在（消息里的 sources 是快照，见 5.3）。

> **从表能看出的语义扩展**：这张关联表的存在让"会话绑定知识库"和 5.1 的 `useKnowledgeBase` 开关组合成三档检索范围。早期版本会话只能绑一个库（迁移历史 `20260817160000_session_multi_kb` 就是这次升级），关联表是"单库 → 多库"演进的产物。**看到一张关联表，第一反应应该是：这里原来是一对多，业务长大成多对多了。**

### 5.3 chat_messages：不可变的消息 + 引用来源快照

```prisma
model ChatMessage {
  id               String   @id @default(uuid())
  sessionId        String   @map("session_id")
  role             String // user / assistant
  content          String // 完整消息内容
  imageDataUrl     String?  @map("image_data_url")
  imageDataUrls    String?  @map("image_data_urls")
  sources          Json?
  promptTokens     Int?     @map("prompt_tokens")
  completionTokens Int?     @map("completion_tokens")
  createdAt        DateTime @default(now()) @map("created_at")

  session ChatSession @relation(fields: [sessionId], references: [id], onDelete: Cascade)
  @@index([sessionId])
  @@map("chat_messages")
}
```

**① 这张表解决什么业务问题**：聊天记录本身——左侧历史列表、多轮上下文的来源（history）、以及**每条回答的"出处"**（引用来源）。注意 schema 注释点明的写法纪律：**流式回答结束后才落库，中间态不写库**——用户看到的消息是内存里拼完的，只有终点状态进数据库，避免半截消息污染历史。

**② 关键字段逐个讲**：

| 字段 | 类型 | 语义 | 设计点 |
|---|---|---|---|
| `role` | String | user / assistant | 只有两种取值（System prompt 不落库，每次现拼） |
| `content` | String | 消息全文 | 含 Markdown（assistant 回答就是渲染给用户的 Markdown 原文） |
| `imageDataUrl` | String? | 单图 data URL | **兼容旧数据**：多图功能之前只支持一张图，字段就叫这个 |
| `imageDataUrls` | String? | 多图（JSON 数组字符串） | 多图扩展时**新增字段而非改旧字段**——老会话读旧字段不崩，新会话写新字段。存成字符串而非 Json 类型是历史取舍（前端直接 `JSON.stringify(images)`） |
| `sources` | Json? | **引用来源快照** | 见下方专讲 |
| `promptTokens`/`completionTokens` | Int? | 流式请求的 token 用量 | 依赖 `stream_options.include_usage` 的最后一个 usage chunk；数据看板（stats）按它统计用户消耗 |
| `createdAt` | DateTime | 消息时间 | **只有 createdAt、没有 updatedAt**——消息是不可变事件（写了就不改），需要排序+展示，不需要"最后修改" |

**③ sources 的 Json 结构**：这是本表最值得展开的字段。代码里（chat.service 落库）存的是：

```ts
// apps/server/src/modules/chat/chat.service.ts（落库时）
const sourcesJson = JSON.parse(
  sanitizeControlChars(JSON.stringify({ kb: kbSources, web: webSources })),
);
// kb 里的每一项形如：
// { documentId, filename, chunkIndex, content, similarity }
```

即 `{ kb: [...], web: [...] }` 两层：kb 是知识库命中的块（含**当时的 content 原文**和相似度），web 是联网搜索结果。前端渲染"来源 [1] 文档《xx》第 3 段"，点开能看引用原文——**全部来自这条 Json，不再查库**。

**④ 为什么 sources 用 Json 快照而不是"外键指向 chunk 的关联表"？**（本章的招牌面试题之一，第 九 节详答）这里先给结论，两个理由：

1. **历史必须"冻结"**：chunk 会被重索引、会被删除、内容会变。如果消息 sources 是外键，用户三个月前问过的一句话，引用来源会跟着 chunk 的消亡一起悬空甚至指向"现在的内容"——历史回答的出处被篡改。快照把**当时的块内容**拷进 Json，历史永远忠于历史；
2. **读取路径简单**：历史会话加载时一次把消息取回来就带全了 sources，不需要 JOIN 一堆可能已不存在的 chunk。

**⑤ 关系与级联**：挂在 `session` 下，会话删 → 消息级联删。`@@index([sessionId])` 保证"按会话拉全部消息"走索引。

## 六、长任务层：reports / agent_tasks

这两个 model 结构长得像（都有 topic/goal、status、sources、error、createdAt/updatedAt），但业务模型差别很大——一个是**离线报告生成**，一个是**限时限量的自主 Agent**。放一起对比着读，收获最大。

### 6.1 reports：研究报告

```prisma
model Report {
  id         String   @id @default(uuid())
  ownerId    String   @map("owner_id")
  topic      String // 研究主题
  status     String   @default("pending") // pending / processing / done / failed / cancelled
  step       Int      @default(0) // 1=拆解子问题 2=检索撰写章节 3=汇总成报告（完成写 4）
  tokensUsed Int      @default(0) @map("tokens_used")
  content    String? // 最终 Markdown
  sections   Json? // [{ index, question, content }]
  sources    Json? // [{ number, documentId, chunkIndex, filename, similarity }]
  kbScope    Json?   @map("kb_scope") // { scope: 'all'|'specific', knowledgeBaseIds?: [] }
  error      String?
  createdAt  DateTime @default(now()) @map("created_at")
  updatedAt  DateTime @updatedAt @map("updated_at")

  owner User @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  @@index([ownerId])
  @@map("reports")
}
```

**① 这张表解决什么业务问题**：用户丢一个主题（"帮我研究 PostgreSQL 的 JSONB 使用最佳实践"），系统自动拆 3~5 个子问题 → 每个子问题检索知识库/联网 → 分节撰写 → 汇总成一篇完整 Markdown。整个流程几分钟，**必须异步跑**（BullMQ），所以需要一张表记录：跑没跑完、跑到第几步、结果在哪、花了多少 token。

**② 关键字段逐个讲**：

| 字段 | 类型 | 语义 | 设计点 |
|---|---|---|---|
| `topic` | String | 研究主题 | 创建时用户给的，报告标题就是它 |
| `status` + `step` | String + Int | **双维度进度** | `status` 回答"活没活、成没成"（pending/processing/done/failed/cancelled——cancelled 是取消接口置的，见 `report.service`）；`step` 回答"跑到哪了"（1 拆解 → 2 逐节撰写 → 3 汇总 → 完成写 4）。前端进度条读 step，失败与否读 status |
| `content` | String? | 最终 Markdown | 只有 done 才有 |
| `sections` | Json | 分节明细 `[{index, question, content}]` | 前端"分节折叠"展示用（摘要 + 每节可展开），也是第 03 章里"索引结果排序"的来源 |
| `sources` | Json | 全部引用来源 `[{number, documentId, chunkIndex, filename, similarity}]` | `number` 是**去重后的全局编号**（多个小节引用同一块只编一次号，见 report-processor 的 sourceMap） |
| `kbScope` | Json | **创建时的检索范围快照** `{scope: 'all'\|'specific', knowledgeBaseIds?: []}` | 关键设计点：worker 在后台重试时**没有请求上下文**，不知道当时用户选了哪些库，所以创建时刻就把范围序列化进表里，失败重试直接读它回填 |
| `tokensUsed` | Int | 全流程 token 消耗 | 数据看板的统计源；每一步 LLM 调用累加 |

**③ 为什么 sections/sources/kbScope 全用 Json？** 三者的共同点：**结构是"产物"而不是"实体"**——分节是报告的内部组织，来源是引用快照，kbScope 是创建现场。它们不会被"按行 SQL 查询"（没人会 `WHERE section.question LIKE`），只会被**整体读出、整体写入、整体展示**；而各自要挂不同的父键、生命周期完全跟随报告。为这种"文档型"数据建规范化关联表，只会得到一堆只有外键没有业务含义的行，纯属给自己找 JOIN 的麻烦。**Json 在这里是"把文档当文档存"**（后面第 05/06 章会看到 Agent 的 progress 更极端）。

### 6.2 agent_tasks：能断点续跑的自主 Agent

```prisma
model AgentTask {
  id           String    @id @default(uuid())
  ownerId      String    @map("owner_id")
  mode         String    @default("targeted") // targeted=定向研究 / open=自主探索
  goal         String? // 研究目标（open 模式为空）
  startAt      DateTime  @map("start_at") // 时间窗开始
  endAt        DateTime  @map("end_at")   // 时间窗结束（停止硬上限）
  tokenBudget  Int       @map("token_budget") // token 预算（停止硬上限）
  tokensUsed   Int       @default(0) @map("tokens_used")
  searchRounds Int       @default(0) @map("search_rounds") // 已执行的联网搜索轮数
  pagesRead    Int       @default(0) @map("pages_read")     // 已精读页面数
  status       String    @default("pending") // pending / running / stopped / done / failed
  stopReason   String?   @map("stop_reason") // budget_exhausted / time_exhausted / user_stopped / cancelled / completed / error
  directions   Json? // [{ title, question, status, rounds }]
  progress     Json? // 续跑断点：{ directions: [{ notes, readUrls, searchTerms, sectionContent }] }
  report       String? // 最终（或阶段性）Markdown 报告
  summary      String? // 执行摘要
  sources      Json? // [{ number, title, url }] 网页引用
  error        String?
  finishedAt   DateTime? @map("finished_at")
  createdAt    DateTime  @default(now()) @map("created_at")
  updatedAt    DateTime  @updatedAt @map("updated_at")

  owner User @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  @@index([ownerId])
  @@map("agent_tasks")
}
```

**① 这张表解决什么业务问题**：比报告更"野"的长任务——Agent 在用户给的**时间窗 + token 预算**内自主"搜索 → 筛选 → 精读 → 提炼"多来源资料并成稿。它不是一次跑完的批处理，而是**可能被打断（预算用尽/时间到/用户手动停）但能续跑**的任务：停的时候保住部分成果，用户加预算/续时后**从断点继续**而不是从头再来。这张表的设计就是围绕"限时限量 + 断点续跑"展开的。

**② 关键字段逐个讲**（挑和 Report 不同的讲）：

| 字段 | 类型 | 语义 | 设计点 |
|---|---|---|---|
| `mode` | String | targeted（有目标）/ open（无目标，从知识库自主挖掘方向） | 两种完全不同的研究开局，同一张表用 mode 区分 |
| `goal` | String? | 研究目标 | open 模式为空——**表结构允许空，正好表达"无目标"是合法状态** |
| `startAt`/`endAt` | DateTime | 时间窗 | endAt 是**停止硬上限**：到点必停，不商量 |
| `tokenBudget` | Int | 预算上限 | 与 endAt 并列的第二个硬上限。**预算/时间双保险**是这类 Agent 防"跑飞烧钱"的关键 |
| `tokensUsed`/`searchRounds`/`pagesRead` | Int（默认 0） | 消耗计数器 | **续跑时累加不归零**——三兄弟就是"到底花了多少"的台账，也用于看板展示 Agent 工作量和停止原因判断 |
| `status` | String | pending/running/stopped/done/failed | `stopped` 是 Agent 特有的态：**因预算/时间/手动停止但保留成果**，区别于失败的 failed |
| `stopReason` | String? | 为什么停 | budget_exhausted / time_exhausted / user_stopped / cancelled / completed / error。前端靠它显示"为什么停了"并决定能否续跑 |
| `directions` | Json | 各研究方向大纲 `[{title, question, status, rounds}]` | 进度展示用：每个方向进行到哪 |
| `progress` | Json | **续跑断点** | 见下专讲 |
| `report` / `summary` | String? | 成稿 | summary 是"先摘要后展开"设计：报告顶部是执行摘要，正文小节可折叠 |
| `sources` | Json | 网页引用 `[{number, title, url}]` | Agent 的研究来源是网页不是知识库块 |
| `finishedAt` | DateTime? | 真正结束时刻 | 与 status=stopped/done/failed 配套：停了没？什么时候停的？续跑时要把它清回 null（agent-task.service 的 resume 逻辑） |

**③ progress：为什么断点要用 Json 而不是把中间态建成几十张表？** 看 schema 注释给的形状：

```
progress = {
  directions: [
    { notes: '…', readUrls: ['https://…'], searchTerms: ['…'], sectionContent: '…' }
  ]
}
```

这是"研究笔记 + 已读 URL + 已用搜索词 + 已缓存小节正文"——**结构深度不固定、字段随 Agent 迭代随意增减**。如果规范化成表，每加一种中间状态就要建一张表 + 一次迁移；而用 Json，Agent 内部想存什么就存什么，续跑时整体读出、改完整体写回。**凡是"内部工作记忆"这种结构会剧烈演化的数据，Json 是正确选择**（代价是失去查询能力——但这些中间状态确实没人用 SQL 查）。

**④ 与 reports 的同与不同**：

| 维度 | reports | agent_tasks |
|---|---|---|
| 任务形态 | 拆解→检索→撰写→汇总，一次性管线 | 自主循环，可被打断/续跑 |
| 预算控制 | 无硬预算 | **时间窗 + token 预算双硬上限** |
| 中途状态 | step（1→4）简单整数 | progress（深度 Json）+ 多计数器 |
| 停止后 | 只有失败/取消 | 有 stopped + stopReason，**可续跑** |
| 数据看板 | tokensUsed | tokensUsed + searchRounds + pagesRead |
| 共性 | 都属于 owner、异步执行、结果落 Markdown、失败记 error、引用存 Json 快照 | 同左 |

一句话：**reports 是"离线执行一段脚本"，agent_tasks 是"托管一个会自主行动的进程"**——前者需要 step 进度，后者需要断点、预算、停止原因。

## 七、BYO 模型配置与"没有的 EmailCode 表"

### 7.1 model_configs：用户自带 Key（BYO）

```prisma
model ModelConfig {
  id        String   @id @default(uuid())
  ownerId   String   @map("owner_id")
  name      String // 备注名，如"我的 DeepSeek"
  baseURL   String   @default("https://api.deepseek.com") @map("base_url")
  apiKey    String   @map("api_key") // AES-GCM 密文（iv:tag:data base64）
  model     String // 默认模型名
  models    String[] @default([]) // 该配置下的全部模型名
  isDefault Boolean  @default(false) @map("is_default")
  createdAt DateTime @default(now()) @map("created_at")
  updatedAt DateTime @updatedAt @map("updated_at")

  owner        User          @relation(fields: [ownerId], references: [id], onDelete: Cascade)
  chatSessions ChatSession[]
  @@index([ownerId])
  @@map("model_configs")
}
```

**① 这张表解决什么业务问题**：Cherry Studio 思路的 BYO（Bring Your Own Key）——平台不内置任何模型 Key，**用户填自己的 OpenAI 兼容 Key**，对话的 token 由用户买单，平台零对话成本。会话可选一个配置：回答走用户的 key/baseURL/model；不配置则回退系统默认。**注意边界**：嵌入/检索仍走系统 Key（schema 注释明说：保证检索质量一致、成本可控）——BYO 只覆盖"生成"，不覆盖"索引"。

**② 关键字段逐个讲**：

| 字段 | 类型 | 语义 | 设计点 |
|---|---|---|---|
| `baseURL` | String @default("https://api.deepseek.com") | OpenAI 兼容接口地址 | 默认 DeepSeek 但可填任意兼容服务（硅基流动/OpenAI…）——**schema 注释里一句"OpenAI 兼容接口地址"就是这个产品能"带任意家的 Key"的秘密** |
| `apiKey` | String | **AES-256-GCM 密文**（`iv:tag:data` base64） | 明文绝不落库，加解密在服务端用环境变量里的密钥；**接口永不返回明文**（第 07 章展开）。字段类型只是 String，安全在应用层 |
| `model` | String | 默认模型名 | 新建会话默认用它 |
| `models` | `String[]` | 该配置下全部模型名 | Prisma `String[]` → PG `text[]`。同一把 Key 常能用多个模型，列表存下来前端好下拉切换（迁移 `20260902090000_add_model_config_models` 加的，再次证明"功能演进 = 加列"） |
| `isDefault` | Boolean | 是否默认配置 | 新建会话默认选中它；`@default(false)` + 应用层保证每用户至多一个 true |

**③ 关系与级联**：`owner` 用户删 → 配置级联删；`chatSessions` 反向关系——注意这里**会话侧的引用是 SetNull**（5.1 讲过），所以"删配置"是安全的：会话变成"回退系统默认"，历史不丢。

### 7.2 为什么 schema 里没有 EmailCode 表？

任务清单里的"EmailCode"在本项目**不存在于 PostgreSQL**——这是刻意为之。看 `apps/server/src/modules/auth/email-code.service.ts`：

```ts
const CODE_PREFIX = 'email_code:';   // email_code:{type}:{email}
const CODE_TTL = 10 * 60;            // 验证码 10 分钟有效
const RESEND_INTERVAL = 60;          // 同一邮箱同一场景 60 秒内不能重发
...
await this.redis.set(key, code, 'EX', CODE_TTL);        // Redis 存，TTL 自动过期
await this.redis.set(key + ':sent', String(Date.now()), 'EX', RESEND_INTERVAL);
```

验证码的画像：**短命（10 分钟）、一次性（校验后消费删除）、天然自带过期语义、并发要求不高但要求快**。这四点几乎就是给 Redis 量身定做的：

| 需求 | Redis 怎么做 | 若用 PG 表会怎样 |
|---|---|---|
| 10 分钟过期 | `SET key code EX 600`，到点自动消失 | 得写个定时任务扫过期行，或每条记录带 expires_at 每次查询比较 |
| 一次性 | 校验成功后 `DEL` | DELETE 一行，也行，但为了删一行要建一张表 |
| 60 秒重发限制 | 另一个 `EX 60` 键即可 | 同一张表加字段/加行 |
| 读性能 | 内存，微秒级 | 也快，但为高频短命数据建表不值 |

**面试可讲的一句话**：数据库选型不是"越重型越好"，而是"数据活多久、怎么被消费"——**会自己过期的瞬态数据放 Redis（TTL 即垃圾回收），需要 ACID、跨实体关联、按结构查询的持久数据放 PostgreSQL**。验证码、会话短期状态、BullMQ 任务（第 06 章）都遵循这个判断；而登录后的长期会话、聊天记录、文档向量才是 PG 的地盘。

> 顺带印证：迁移目录里曾有过 `add_totp` 又被 `remove_totp` 回滚——**"什么该进库、什么不该进库"本身就是演进中的决策**，schema 的迁移历史就是决策日志（第 09 章讲如何用迁移历史复盘）。

## 八、级联删除语义全景（谁删谁、删到哪）

把 12 张表的 onDelete 汇总成一张表，是本项目数据模型的"宪法"：

| 关系（子 → 父） | onDelete | 含义 |
|---|---|---|
| KnowledgeBase → User | Cascade | 删账号 → 知识库全没 |
| Document → KnowledgeBase | Cascade | 删库 → 文档（及它的 chunk/symbol/profile）全没 |
| Chunk → Document | Cascade | 删文档 → 块（含向量）清光 |
| CodeSymbol → Document | Cascade | 删文档 → 符号表清光 |
| FileProfile → Document | Cascade | 删文档 → 档案清光 |
| ChatSession → User | Cascade | 删账号 → 会话全没 |
| ChatMessage → ChatSession | Cascade | 删会话 → 消息全没 |
| SessionKnowledgeBase → 两侧 | Cascade | 删任一侧 → 关联行消失 |
| Report → User | Cascade | 删账号 → 报告全没 |
| ModelConfig → User | Cascade | 删账号 → 配置全没 |
| AgentTask → User | Cascade | 删账号 → 任务全没 |
| **ChatSession → ModelConfig** | **SetNull** | 删配置 → **会话保留**，model_config_id 置空回退默认 |

**三个值得品的设计判断**：

1. **为什么几乎全 Cascade？** 因为这些数据**只属于它的父亲**，没有独立于父亲的价值：chunk 离开了文档毫无意义；消息离开了会话毫无意义。数据库级联比应用层手动删可靠——**外键约束保证"不可能漏删、不可能出现孤儿行"**，应用层 for 循环删总有漏网和并发竞态（这就是为什么上传替换逻辑里要反复用 `deleteMany + 幂等 catch` 去防并发——那是跨文档操作，外键帮不上忙）。

2. **为什么 ModelConfig 是例外（SetNull）？** 因为聊天历史是"用户资产"，而模型配置只是"当时的偏好"。配置删了，历史对话必须能继续打开、继续追问（回退默认模型）。**判断用 Cascade 还是 SetNull/Restrict，本质是问一句：子记录离开了父记录，还有存在价值吗？**

3. **DB 级联 ≠ 磁盘清理**。chunks 是 DB 里的行，级联即删；但 `documents.filepath` 指向的**磁盘文件不归数据库管**。删除单个文档时应用代码手动 `unlinkSync`（documents.service 的 remove/replace 路径都有）；而删除整个知识库走 DB 级联，**不会触发磁盘清理**——这是设计上接受的取舍（迁移/清理脚本、运维定期清 `UPLOAD_DIR` 兜底），也再次说明"DB 行 + 磁盘文件 = 两份事实"的同步问题永远要应用层/运维层显式处理。

## 九、从表能看出的设计决策（面试篇）

读表的价值不在记住列名，而在能从表结构**反推当时的业务权衡**。挑五条最值得讲的（前三条是本章主推，后两条是加分项）：

### 决策 1：为什么 Document 和 Chunk 分离，而不是"一篇文档一行、全文一个字段"？

反方方案：`documents` 直接存全文，检索时用 `LIKE`/全文索引。问题有三：

1. **检索粒度**：问答需要"命中哪一段就把哪一段给模型"（引用来源 `[3] 第 5 段`）。全文一行 = 检索单元是整篇，模型被塞进整篇文档、引用没法定位到段；
2. **异步进度**：处理是分阶段的（解析→分块→向量化），需要按"块"推进而不是按"整篇"推进；
3. **块是派生数据**：内容编辑后要"重新分块 + 重新向量化"，删旧块建新块，天然是行级操作。

而**真正的原文留在磁盘文件**（`filepath`），DB 里的 chunks 只是"可重建的检索视图"。表分离的背后是**两份事实 + 明确谁是权威**：磁盘文件是权威原文，chunks 是随时能推倒重来的衍生索引。面试话术："我们的数据模型区分了事实（文件、文档元信息）与派生（块、符号、档案），派生数据永远先删后建，这让重索引功能成为可能。"

### 决策 2：为什么父子分块用 `parentId` 自关联，而不是"子块表 + 外键"？

P2 父子分块需要表达"一个大块包含若干小块"。两种建模：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 独立 `chunk_children` 表 | 结构更"正规" | 内容存两份（父块正文 + 子块正文本来就在同一条血缘里）；删除要级联两次；查询"父块全文"要 JOIN |
| **chunks 自关联 `parent_id`** | 一张表统一表达"叶子/容器/父子"；级联删除一次搞定；`parent_id IS NULL` 一个条件就能区分结构 | 需靠 `chunk_index` 等约定维持展示顺序；父/子块行类型靠 embedding 有无隐含区分 |

这个项目的迁移注释给了数据库层的理由：**"FK 不建：父块与子块同属一个文档，删除时按 document_id 级联清理，无孤儿风险"**——既然生命周期的根是 document，父子关系只是文档内部的层次，加一层外键反而引入无谓的约束维护。**自关联 = 用同表表达树**，是"层次结构 + 统一生命周期"场景的经典解。

### 决策 3：为什么用户消息的引用来源、报告的分节/来源用 Json 快照而不是外键关联表？

这是全章最"反直觉"的一条——教科书教我们要**规范化**，这里却故意"反规范化"：

1. **历史必须冻结**：`ChatMessage.sources` 里的 `content` 是**命中那一刻的块原文快照**。chunk 之后会被重索引、删除、内容变化——如果 sources 外键指向 chunk 行，三个月前的回答引用会悬空或指向新内容。快照保证"当时引用了什么"永远可复现；
2. **读取无 JOIN**：加载历史会话一次 `findMany` 全带回；来源数据只在"展示"时用，不需要按行过滤/聚合/联表；
3. **结构跟随业务演化**：sources 从单库命中 → 加 web 联网 → 加图谱关联（`similarity: null` 表示非语义命中），字段增增减减，Json 不用迁移；报告同理——`sections` 是产物、`kbScope` 是创建现场，都会整体读写，没有 SQL 查询价值。

**判断标准（面试可背）**：数据"会变、要按行查、跨实体引用"→ 建表规范化；数据"一次性写、整体读、只作快照/产物、结构爱演化"→ Json 落库。本项目里 messages.sources、report.sections/sources/kbScope、agent.progress 全部命中后者。

### 决策 4：embedding 为什么可空、为什么用 Unsupported + 原始迁移？

`Chunk.embedding` 可空不是"向量可有可无"，而是**写库时序**的必然：异步流水线先建行（含 content）→ 调外部 embedding API → 再把向量 UPDATE 回去。若建表时就把 embedding 设为 NOT NULL，第一行插入就得先有向量，异步流程根本跑不起来。而 `Unsupported("vector(1024)")` + 原始 SQL 迁移，是 Prisma 生态下接入 pgvector 的标准姿势——**框架表达不了的类型，用框架的逃生舱（原始 SQL）+ 类型占位承接**，检索代码走 `$queryRaw`。这也是"为什么项目里到处是 `$executeRaw`/`$queryRaw`"的答案。

### 决策 5：状态字段为什么全用 String，主键为什么全用 UUID？

两问一答：`Document.status`、`Report.status`、`AgentTask.status`、`CodeSymbol.kind` 全部是 String + 应用层取值，没有用 PG enum——**因为状态集合在演进**（`replacing` 态、`cancelled` 态、新符号 kind 都是上线后加的），PG enum 每加一个值要 `ALTER TYPE` 且可能锁表；String 零迁移成本，代价是 DB 层不校验取值，用前端枚举 + 代码常量约束。而 UUID 主键的三个理由：防枚举拖库、多实例不撞号、前端拿到的 id 不泄露业务量。**一个管演进灵活性，一个管安全与扩展**。

## 十、动手实验

假设你已按第 00 章的步骤把项目跑起来并传过几个文档。打开新终端：

```bash
# 从 apps/server/.env 里取 DATABASE_URL，或者直接：
cd apps/server && grep DATABASE_URL .env
# 例如 postgresql://postgres:xxx@localhost:5432/kb?schema=public
psql "postgresql://postgres:xxx@localhost:5432/kb"
```

**实验 A：看文档与其块的真实分布**（验证 Document 与 Chunk 的 1:N、status 状态机、附件不产生块）：

```sql
SELECT d.filename, d.file_type, d.status,
       d.content_hash IS NOT NULL AS has_hash,
       count(c.id) AS chunk_count
FROM documents d
LEFT JOIN chunks c ON c.document_id = d.id
GROUP BY d.id
ORDER BY d.created_at DESC
LIMIT 10;
```

预期看到：md/txt/pdf/docx/code 的文档有若干块；附件（png 等）chunk_count = 0（它不参与检索）；若有人传过同名文件，历史上能见到 failed / replacing 的痕迹。**这张表就是第 03 章流水线跑完后的"成绩单"。**

**实验 B：验证 chunk 的三种形态与向量维度**（父子分块的结构 + pgvector 落库的证据）：

```sql
SELECT d.filename,
       count(*) FILTER (WHERE c.parent_id IS NULL AND c.embedding IS NOT NULL) AS leaf_or_small,
       count(*) FILTER (WHERE c.parent_id IS NULL AND c.embedding IS NULL)     AS parent_container,
       count(*) FILTER (WHERE c.parent_id IS NOT NULL)                         AS children
FROM documents d
JOIN chunks c ON c.document_id = d.id
GROUP BY d.id
ORDER BY children DESC;

-- 任意一块，确认向量是 1024 维（bge-m3）
SELECT vector_dims(embedding) AS dim FROM chunks WHERE embedding IS NOT NULL LIMIT 1;
```

第一条查询能把"父子分块"直接从数据里看出来：传一个带多级标题的长 md，你会看到 `parent_container` 和 `children` 同时 > 0（md 的大章节被切成子块）；传一个 txt/pdf，`children` 恒为 0（没有父块结构）。第二条查询返回 `1024`——这就是为什么 schema 里写 `vector(1024)`。

> 提示：想确认扩展与索引都在，可跑 `SELECT extname FROM pg_extension;`（应有 vector、pg_trgm）和 `\d+ chunks`（能看到 hnsw/gin 索引与 vector 列）。
