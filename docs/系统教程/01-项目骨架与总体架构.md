## 一、这是什么架构

一句话：**pnpm monorepo + NestJS(后端) + Vue3(前端) + PostgreSQL(pgvector) + Redis + BullMQ** 的全栈应用。

```
ai-knowledge-base/
├── apps/
│   ├── server/          # NestJS 后端（TypeScript）
│   │   ├── prisma/      # schema.prisma：全部数据模型 + 迁移
│   │   └── src/
│   │       ├── main.ts          # 启动入口（端口 3000）
│   │       ├── app.module.ts    # 根模块：装配所有功能模块
│   │       ├── common/          # 守卫/装饰器/拦截器/路径常量
│   │       └── modules/         # 按业务划分的 NestJS 模块
│   │           ├── auth/            # 登录注册（JWT）
│   │           ├── email-code/      # 邮箱验证码
│   │           ├── knowledge/       # 知识库/文档/分块/向量化
│   │           ├── chat/            # 对话（RAG 检索 + SSE 流式）
│   │           ├── research/        # 研究报告（BullMQ 长任务）
│   │           ├── research-agent/  # 自主研究 Agent（BullMQ 长任务）
│   │           ├── models/          # 用户模型配置（BYO）
│   │           ├── stats/           # 数据看板统计
│   │           └── user/            # 个人资料/头像
│   └── web/              # Vue3 前端（Vite + TS + Tailwind + Pinia）
│       └── src/
│           ├── main.ts           # 前端入口
│           ├── App.vue           # 根组件（挂 Toast/Confirm）
│           ├── router/           # 路由 + 登录守卫
│           ├── stores/           # Pinia（auth 等）
│           ├── api/              # 按模块封装的 axios 请求
│           ├── components/       # 组件（ui/ 基础件，chat/ 对话，knowledge/ 知识库…）
│           ├── composables/      # 组合式函数（toast/theme/confirm）
│           ├── views/            # 页面级组件
│           ├── types/            # TS 类型（与后端字段对应）
│           └── utils/            # 纯函数工具（markdown 渲染/文件图标/目录树）
├── packages/
│   └── shared/          # 前后端共享类型（当前未重度使用，为扩展预留）
└── docs/                # 全部笔记（本教程所在目录）
```

**为什么用 monorepo？**
- 前后端一个仓库：改一个功能常要同时动两端，分开仓库要开两个 PR、维护两套依赖；
- pnpm workspace：共享的依赖只装一份（node_modules 硬链接），`--filter` 可以单独跑某个包；
- 类型可以共享（`packages/shared`），虽然现在用得少，但为"API 类型前后端一致"留了路。

## 二、后端：NestJS 的分层哲学

NestJS 是"受 Angular 启发的 Node 框架"，核心是**模块化 + 依赖注入**。它的分层习惯：

```
路由进来 → Controller（接 HTTP，校验参数） → Service（写业务逻辑） → Prisma（访问数据库）
                ↑ 守卫 Guard（鉴权） / 管道 Pipe（校验 DTO） / 拦截器 Interceptor（统一返回）
```

看一个真实例子：**删除一个文档**（`apps/server/src/modules/knowledge/documents.controller.ts`）：

```ts
// ① Controller：只做"接请求 + 转发"
@Delete(':id')
remove(@CurrentUser('id') userId: string, @Param('id') id: string) {
  return this.documentsService.remove(userId, id);
}

// ② Service：真正的业务
async remove(userId: string, id: string) {
  const doc = await this.prisma.document.findFirst({ where: { id, knowledgeBase: { ownerId: userId } } });
  if (!doc) throw new NotFoundException('文档不存在');   // 他人文档 = 404（不泄露存在性）
  // 删数据库记录（chunk 级联删除）→ 删磁盘文件 → 幂等处理
  ...
}
```

**这套分层带来的好处（面试可以讲）**：
1. **职责单一**：Controller 不管业务、Service 不管 HTTP，测试 Service 不用起服务器；
2. **ownerId 数据隔离**：所有查询都带 `ownerId` 过滤（或通过 knowledgeBase 间接归属），越权访问返回 404 而非 403——不告诉攻击者"这东西存在"；
3. **依赖注入**：Service 通过构造函数注入 PrismaService 等，替换实现（测试 mock）容易。

## 三、前端：Vue3 的组织方式

Vue3 用 **组合式 API（`<script setup>`）**。页面级组件（`views/`）是"容器"，只管状态与数据流；业务组件（`components/`）是"展示"，只管渲染与交互事件。

```
Chat.vue（容器：会话列表状态、消息流式、滚动、网络开关）
  ├─ ChatSessionSidebar（展示：会话列表 → emit select/delete）
  ├─ ChatMessageItem（展示：单条消息 → 传 msg prop）
  └─ ChatMessageInput（展示：输入框 → emit send/pick-image…）
```

**为什么要拆组件？（面试高频）**
- 可维护：原来 Chat.vue 1600+ 行，所有状态挤在一起，改一个按钮都可能碰坏滚动逻辑；
- 关注点分离：流式状态留在容器，消息渲染只管"给一条消息，画出来"；
- 复用：`markdown-body` 的样式、`code-copy` 按钮逻辑，对话页/报告页共用。

前端请求层统一走 `apps/web/src/api/request.ts`（axios 实例）：
- 请求自动带 `Authorization: Bearer <accessToken>`；
- 响应 401 时**无感刷新**（拿 refreshToken 换新 accessToken，并把等待中的请求排队重放）——这是"登录不掉线"的关键；
- 错误统一转成中文提示，业务代码 catch 到直接 `toast.error(msg)`。

## 四、一条请求的完整旅程（以"问一个问题"为例）

把前面几节串起来，看一条消息从浏览器到数据库再回来的完整链路：

```
1. 前端 ChatMessageInput 输入问题 → 点发送
2. Chat.vue handleSend()：
   - 乐观渲染（用户消息立刻上屏，不等后端）
   - 组装 payload（含联网开关、图片 data URL）
   - 调 askQuestion()（fetch-event-source，POST /api/chat/sessions/:id/messages）
3. Nginx /api → 后端 3000
4. ChatController → ChatService.ask()：
   a. 查会话归属 → 解析用户模型配置（BYO）
   b. 【检索】调用 RagService：知识库向量检索 + 关键词检索 → RRF 融合 → 重排 → 门控
   c. （可选）Tavily 联网搜索
   d. 落库用户消息
   e. 组装 Prompt → 调 DeepSeek 流式接口
5. 后端把模型输出转成 SSE 事件流：sources → delta × N → done
6. 前端 fetch-event-source 逐段收到 → rAF 节流渲染 markdown
7. onDone：落一条 assistant 消息到本地列表 → loadSessions() 刷新会话标题
```

> 第 4b 步的检索是整个项目的灵魂，第 04 章专门讲。

## 五、动手实验

**实验 A（后端）：加一个时间接口**
1. 在 `apps/server/src/modules/user/` 下（或新建 demo 模块）加：
```ts
// demo.controller.ts
@Controller('demo')
export class DemoController {
  @Get('time')
  time() { return { now: new Date().toISOString() }; }
}
```
2. 在对应 module 的 `controllers` 数组注册它；
3. `curl http://localhost:3000/api/demo/time` 应返回当前时间。

**实验 B（前端）：改首页问候**
1. 打开 `apps/web/src/views/Home.vue`，找到欢迎语；
2. 改成你自己的话，保存后浏览器热更新立刻生效。

**自测题**
1. monorepo 相比两个独立仓库，最大的两个好处是什么？
2. NestJS 里 Controller / Service / Guard 各管什么？"他人文档返回 404 而不是 403"为什么更安全？
3. 前端乐观渲染解决什么问题？如果等后端确认再上屏，用户体验会怎样？
4. 401 无感刷新是怎么实现的？（提示：拦截器 + refreshToken + 请求队列）
5. 说出"问一个问题"全链路里，前端、后端、数据库、大模型各扮演什么角色。
