## 一、先给结论：这一章在解决什么问题

前几章我们把后端链路（入库、检索、流式、队列）全部打通，前端能"问一句、答一句"了。但一个能用的对话页和**一个让人愿意一直用的对话页**之间，隔着整整一层工程：

| 问题 | 不做会怎样 | 本章解法 |
|---|---|---|
| 首屏加载慢 | 全部页面打进一个 JS 包，首屏几 MB | 路由懒加载 + 大依赖独立分包（第 2 节） |
| 切导航状态全丢 | 从对话页去一趟「模型配置」，回来会话/消息/草稿全没了 | KeepAlive 缓存页面实例（第 2 节） |
| 流式回答卡成 PPT | 每个 token 全量渲染 markdown + 代码高亮 | rAF 节流 + 渲染缓存 + 增量渲染（第 4 节） |
| 翻历史时被强制拽到底 | 自动滚动不识别用户意图 | autoScroll 意图状态机（第 5 节） |
| 网络 401 后整站要重新登录 | accessToken 过期即打断所有操作 | axios 拦截器无感刷新 + 排队重放（第 7 节） |
| 回答到一半想停、失败了想重试 | 停不掉 / 重发重复 | AbortController + 重试上下文（第 8 节） |

一句话概括本项目的打磨哲学：**把"用户可感知的状态"当一等公民设计**——流式内容、滚动位置、会话草稿、网络身份，全都不是"顺手处理"的东西，而是有明确生命周期、明确归属、明确竞态防护的对象。

## 二、路由懒加载与 KeepAlive：SPA 的"要什么给什么"

### 2.1 为什么单页应用要路由懒加载

单页应用（SPA）只有一张 HTML，其余全是 JS 动态渲染。如果不做任何处理，`main.ts` 里 import 的所有页面组件会被打成一个巨大的 bundle——用户可能只想登录看一眼，却被迫下载整个应用的代码。

**懒加载的本质**：把"页面组件"从"启动就加载"改成"路由命中才加载"，Vite/Rollup 会自动为每个动态 import 切出一个 chunk：

```ts
// apps/web/src/router/index.ts（真实代码）
const router = createRouter({
  history: createWebHistory(),
  routes: [
    {
      path: '/chat',
      name: 'chat',
      // 组件不再被 import 进来，而是写成"返回 Promise 的工厂函数"
      component: () => import('@/views/Chat.vue'),
    },
    // ...其余路由同款写法
    {
      path: '/:pathMatch(.*)*',           // 兜底路由：未匹配路径 → 404
      name: 'not-found',
      component: () => import('@/views/NotFound.vue'),
      meta: { public: true },             // 任何登录态都展示 404
    },
  ],
});
```

配套的还有依赖级分包。`vite.config.ts` 里把几乎不变的大体积库单独拆包：

```ts
// apps/web/vite.config.ts
build: {
  chunkSizeWarningLimit: 600,
  rollupOptions: {
    output: {
      manualChunks: {
        // echarts 单独成包：体积大但极少变更，利于浏览器长缓存
        echarts: ['echarts/core', 'echarts/charts', ...],
      },
    },
  },
},
```

> 类比：把整本词典背在身上再出门，不如**查哪个词翻哪页**。懒加载 = 按需翻页；manualChunks = 把"厚且不常改的章节"装订成册，让浏览器缓存整册（版本号不变就不重新下载）。

### 2.2 KeepAlive：缓存哪些页面、为什么

懒加载解决"下载慢"，KeepAlive 解决"**重建贵**"。看一下 Layout.vue 里 RouterView 的写法：

```html
<!-- apps/web/src/views/Layout.vue（真实代码） -->
<RouterView v-slot="{ Component }">
  <KeepAlive :include="['ChatView', 'ResearchAgentView', 'ResearchView', 'HomeView']">
    <component :is="Component" />
  </KeepAlive>
</RouterView>
```

三个细节必须讲清楚：

1. **include 匹配的是组件名，不是路由名**。KeepAlive 靠 vnode 的 `type.name` 判断要不要缓存，所以四个被缓存的页面都在 `<script setup>` 顶部写 `defineOptions({ name: 'ChatView' })`。子组件也统一写 name——Vue DevTools 里可读，也避免未来被缓存时匹配不上。
2. **没被 include 的页面 = 普通组件**，切换走后正常销毁，下次进入重新 `onMounted`（重新拉数据、重新初始化）。这是"缓存名单"的另一种含义：名单之外的东西，每次都是新鲜的。
3. **Layout 特意没用 `<Transition>`**（代码注释原话：out-in 串行处理大组件树在低配设备上切换明显卡顿）。经验教训记录在部署文档里：早期加了页面切换过渡动画，进出对话页"卡一下"，最后定位到两大元凶——串行过渡动画 + 首页 Canvas 每次重建 5000+ 粒子（后文 9.3 讲）。

**为什么偏偏缓存这四个页面？** 每个页面都有自己的"舍不得丢的状态"：

| 页面 | 缓存它的理由（不可重建 or 重建贵） |
|---|---|
| `ChatView`（对话） | 当前会话、全部消息、每会话的输入草稿/图片草稿、滚动位置、流式进行中的回答——切去「模型配置」加个 Key 再回来，谁愿意对话从头来？ |
| `ResearchAgentView`（自主研究） | 选中的任务、任务详情轮询、几十分钟的 Agent 进度——切走轮询状态就没了，等于任务"失联" |
| `ResearchView`（研究报告） | 报告列表 + 正在生成中的任务轮询，理由同上 |
| `HomeView`（首页） | 宇宙 Canvas 建一次要生成 5000+ 粒子的初始化数据（9.3），每次重建就是一次可感知的卡顿；首页本无服务器数据，缓存零成本 |

反过来说，**知识库列表、文档管理、数据看板、模型配置、个人中心为什么不缓存**？因为它们是"数据在服务器上"的页面，`onMounted` 里拉一次就是最新的；缓存反而让用户看到陈旧数据，还得手动加"刷新"按钮。缓存不是越多越好——**缓存列表 = 值得用内存换状态的页面清单**。

### 2.3 缓存的代价：内存与"看不见的定时器"

KeepAlive 不是免费的：

- **内存**：被缓存的页面实例、响应式状态、甚至 DOM 子树都留在内存里（Vue 把停用的子树移进一个隐藏容器，第 5 节会讲清"脱管"意味着什么）。四个页面全缓存，内存占用显著上升——这是"为什么只缓存四个、而不是所有页面"的另一个理由。
- **定时器/动画会空转**：组件销毁时才执行的 `onBeforeUnmount` 清理不会在"切走"时触发！切到别的页面，`setInterval` 依然每秒回调、`requestAnimationFrame` 依然每帧重绘——**用户看不见，CPU 却在烧**。

所以项目给"被缓存的页面"补了第二对生命周期钩子 `onActivated` / `onDeactivated`（KeepAlive 专用：激活/停用）。看两个真实例子：

```ts
// ResearchAgent.vue（片段）——1Hz 界面时钟：切走即停，回来即开
onActivated(() => startClock());
onDeactivated(() => stopClock());
// 注意：任务详情轮询不在这里停——轮询是"后台任务完成"的支撑，
// 只有活跃任务在跑，且这是通知用户"报告好了"的机制（取舍见注释）

// HomeCosmos.vue（片段）——Canvas 动画循环：不可见就停 rAF
onActivated(() => {
  if (!raf) raf = requestAnimationFrame(loop);
});
onDeactivated(() => {
  cancelAnimationFrame(raf);
  raf = 0;
});
```

> 记忆口诀：**`onBeforeUnmount` 管"销毁"，`onDeactivated` 管"隐身"**。凡是会被 KeepAlive 缓存的组件，清理逻辑要按这两种场景分别写。

Chat.vue 里的"思考计时器"（首 token 前的等待秒数）同理：发送时启动、停止/完成时清零停表，卸载时兜底清除——被缓存期间它只在流式进行中有意义，不会无谓空转。

## 三、组件拆分：巨石组件是怎么长成一棵树的

### 3.1 为什么要拆（历史与动机）

查看功能档案 33 的记录，`Chat.vue` 最胖时 **1639 行**——会话列表、消息渲染、流式、滚动、输入框、弹窗全部挤在一个文件里。那是一种"能跑但不敢动"的状态：改一个按钮都可能碰坏滚动逻辑；两个开发者同时改一个文件天天冲突；面试官打开文件就想走人。

拆分遵循一条**保守原则**（档案原话）：**只拆纯展示/独立子组件，状态与业务逻辑留在容器**。KeepAlive、流式、自动滚动、草稿记忆、轮询这类横跨全局的状态**不硬拆**——强行拆出去要引入一堆"回调下钻/事件上抛/状态外提"，回归风险远大于收益。

### 3.2 拆完之后长什么样

```
Chat.vue（容器：会话/消息/流式/滚动/草稿/网络开关 —— 状态与业务逻辑的"家"）
  ├─ ChatSessionSidebar  展示：会话列表（搜索/选中/删除/新建/收起）
  ├─ ChatMessageItem     展示：单条消息（图片/文件 chip/气泡/Markdown/复制/分支/来源）
  │    └─ ChatSourcePanel     引用来源面板（知识库 + 网络，details 折叠）
  ├─ ChatThinkingBar     展示：首 token 前的"检索思考中"光条动画 + 计时
  ├─ ChatMessageInput    展示：输入区（模型下拉/推理等级/图片文件/发送停止）
  ├─ ChatKbPickerModal   展示：新建对话 / 改问答范围弹窗
  └─ DocPreviewDrawer    展示：引用来源 → 原文定位抽屉
```

同一个模式的另外两个巨石（KnowledgeDocuments、ResearchAgent）也拆了，并把**纯函数逻辑下沉到 `utils/`**（doc-tree、file-icons），把**全局共用的排版样式上收到 `index.css`**——这两点分别是"便于单测"与"消除三份重复 CSS"的关键，第 8、9 节和第 09 章的测试策略都会再遇到它们。

### 3.3 组件接口三件套：props 只读、emit 清单化、defineModel / defineExpose

拆组件后，父子之间的"契约"要清晰。本项目几乎每个子组件都长这样：

```ts
// ChatMessageInput.vue（片段）
const props = defineProps<{
  streaming: boolean;          // 父给：当前是否流式中
  canSend: boolean;            // 父给：能否发送
  pendingImages: string[];     // 父给：待发送图片
  // ...
}>();

// 事件清单：子组件"能力边界"的文档，等于给父组件一张可用的遥控器面板
const emit = defineEmits<{
  (e: 'send'): void;                            // 点发送
  (e: 'stop'): void;                            // 点停止
  (e: 'pick-image', files: File[]): void;       // 选了本地图片（原始 File[]，压缩在容器做）
  (e: 'pick-file', files: File[]): void;        // 选了本地文件
  (e: 'remove-image', i: number): void;
  // ...
}>();

// 双向绑定主文本：defineModel 替代手写 prop + update:xxx 事件
const input = defineModel<string>('input', { default: '' });

// 暴露命令式方法：父组件分支后要"预填问题并聚焦"
const messageTextarea = ref<HTMLTextAreaElement | null>(null);
function focusTextarea() {
  messageTextarea.value?.focus();
}
defineExpose({ focusTextarea });
```

三个要点：

1. **props 是父的、状态是父的、事件是孩子的嘴**。输入框自己不留"这条消息内容"的副本——`v-model:input` 绑的是父组件的 `input` ref。这样"发送失败要保留内容供重试""切会话要存草稿"这类逻辑全部发生在容器里，输入框组件永远不需要知道。
2. **`defineModel` 是糖，本质还是 prop + event**。这里 `input` 用 defineModel，而布尔开关 `useWebSearch` 用的是普通 prop + `emit('update:useWebSearch')`——同一个组件里两种风格并存，恰好说明 defineModel 只是"省掉样板代码"，底层的单向数据流没有变。
3. **`defineExpose` 只在"命令式确实更顺"时用**（聚焦一个 DOM 是天然的副作用，不适合用 props 表达）。Chat.vue 里通过模板 ref 调用：`messageInputRef.value?.focusTextarea()`。

ChatMessageItem 的事件契约同样是一张清晰的清单（`copy` / `branch` / `open-source` / `preview-file`），它完全不认识 `handleSend`、`handleBranch` 这些函数——**子组件只报告"发生了什么"，不决定"然后怎么办"**。这就是容器/展示分层后调试时最舒服的地方：所有"怎么办"都能在容器文件里一次看完。

## 四、流式渲染性能三板斧：为什么"每 token 全量渲染"会卡死

### 4.1 先算一笔账，理解瓶颈在哪

DeepSeek 这类模型的流式输出速度大约每秒 20~60 token。如果每个 token 到达都：

1. 把**累计的整段文本**丢给 markdown-it 重新解析；
2. 对每个代码块重新跑 highlight.js（正则/词法分析整段代码）；
3. 把结果写进 DOM、触发一次 layout（回流/重排）和 paint；

那就是**每秒 20~60 次全量重渲染**。浏览器一帧只有约 16.6ms（60Hz 显示器）——一次"整段 markdown + 高亮 + DOM 替换 + 布局"轻松超过 16.6ms，主线程被塞满，输入、点击、滚动全部排队，画面变成"一卡一卡地吐字"。而且回答越长每次渲染越贵（要解析的内容线性增长），卡顿会**随回答长度加剧**，到后期可能一次渲染要几百毫秒。

> 类比：你要把一篇文章逐字抄到黑板上。正常人会**攒一小段、抄一段**；"每 token 全量渲染"等于每写一个字就把黑板全擦掉重抄一遍全文——擦写本身比写字还贵，还越抄越长。

### 4.2 第一板斧：rAF 节流（每帧最多一次 DOM 写入）

显示器刷新率决定了：**一帧之内做两次 DOM 更新，第二次的中间结果用户根本看不见**（浏览器只 paint 最后一帧）。所以正确的做法是：token 随便来，先攒着；真正的"刷屏"交给 `requestAnimationFrame`——浏览器会在**下一次绘制前**回调一次，天然和刷新率对齐：

```ts
// Chat.vue sendPayload() 内部（真实代码，注释为原意）
let pendingStream = '';
let streamRaf = 0;
const flushStream = () => {
  streamRaf = 0;
  streamContent.value = pendingStream;   // 一次帧回调只写一次响应式状态
};

// onDelta 回调（每个 token 触发）：
onDelta: (delta) => {
  pendingStream += delta;                // ① 只做字符串拼接（内存操作，毫秒级）
  if (!streamRaf) {                      // ② 本帧还没排过刷新任务才排
    streamRaf = requestAnimationFrame(flushStream);
  }
},
// onDone（流结束）：
onDone: () => {
  if (streamRaf) {                       // ③ 收尾：取消未执行的帧回调，强制刷最后一次
    cancelAnimationFrame(streamRaf);
    streamRaf = 0;
    streamContent.value = pendingStream;
  }
  // 把完整回答 push 成一条正式 assistant 消息……
},
```

节奏变成：**每秒最多 60 次渲染，且每次只发生在浏览器即将绘制前**。中间丢掉的几十次渲染是"用户反正看不见的中间态"，省下的是一次次全量解析和布局。60fps 的重渲染对几百到几千字的回答仍然可接受，因为：

- 大部分内容是纯文本 + 少量代码块，markdown-it 解析几千字在 1ms 量级；
- 高亮只在出现代码块时才贵，而 AI 回答通常不会每帧都长出新代码块；
- DOM 更新只有"那一个正在流的气泡"，不是整页。

### 4.3 第二板斧：渲染缓存（Map 缓存已渲染 HTML）

再看 `utils/markdown.ts` 的出口：

```ts
// markdown.ts（片段）
const renderCache = new Map<string, string>();
const RENDER_CACHE_MAX = 200;

export function renderMarkdown(text: string): string {
  const hit = renderCache.get(text);          // 同文本 → 直接返回已渲染 HTML
  if (hit !== undefined) return hit;
  if (renderCache.size >= RENDER_CACHE_MAX) renderCache.clear();  // 封顶防内存失控
  const html = md.render(text);               // 全量 markdown-it + highlight.js
  // ……包一层代码块容器 + 复制按钮……
  renderCache.set(text, wrapped);
  return wrapped;
}
```

以**完整文本为 key** 缓存渲染结果。这解决了三类场景的重复劳动：

1. **流式完成的那一下**：流式期间最后一帧渲染的内容 = 完整回答。`onDone` 把它 push 成正式消息，ChatMessageItem 挂载时调 `renderMarkdown(完整内容)` → **Map 命中，一次高亮都不重跑**；
2. **父组件无关重渲染**：Chat.vue 里任何状态变化（比如 sidebar 开合、切了一个无关 ref）都会让模板重跑；但 `ChatMessageItem` 内部把渲染包在 `computed` 里——内容没变，computed 不重算，即便重算也有 Map 兜底；
3. **重进会话**：切走再切回，历史消息从服务器拉回来，文本和上次渲染过的一模一样（除非别人改了）→ 全部缓存命中，秒开。

> Map 缓存的上限 200 条、超限整表清空：长会话几百条消息时不会无限占内存；被清掉后下次再渲染也只是"重新算一次"，正确性无损。

### 4.4 第三板斧：增量渲染策略（结构上隔离"流的"和"历史的"）

前两板斧是"省力"，第三板斧是"**少干活**"——从渲染结构上保证每个 delta 到来时，**只有流式气泡一个节点需要更新**：

```html
<!-- Chat.vue 消息区结构（示意） -->
<div v-else class="mx-auto max-w-5xl space-y-6">
  <!-- 历史消息：每个 msg 一个独立子组件，key=msg.id -->
  <ChatMessageItem v-for="(msg, i) in messages" :key="msg.id" :msg="msg" ... />

  <!-- 流式回答中：只有这个 div 在随 streamContent 变化 -->
  <div v-if="streaming" class="flex justify-start">
    <div class="w-full">
      <ChatThinkingBar v-if="!streamContent" :thinking-seconds="thinkingSeconds" />
      <div v-else class="markdown-body px-1" v-html="renderMarkdown(streamContent)" />
      <!-- ……来源计数…… -->
    </div>
  </div>
</div>
```

关键点：**进行中的回答根本不进 `messages` 数组**，它活在独立的 `streamContent` 里。于是：

- 每次 delta 更新只碰"流式气泡"这一个 vnode 的 innerHTML；
- 已经完成的几十条历史消息是 `v-for` 里 key 稳定的子组件，props 引用没变 → Vue 直接跳过它们的重渲染（父组件更新不会传染给 props 未变的子组件）；
- 等流结束，才把完整文本**一次性** push 进 `messages`，历史区只多出"一条"新消息——而不是"流式期间把半截回答反复塞进列表"。

这套"**流外渲染 + 完成后并入列表**"就是增量渲染策略的本体：不是逐 token 去 diff 长文本（那样等于回到全量渲染），而是把"正在变的"和"已定型的"分成两个互不干扰的渲染单元，让每帧的开销只和"这一帧新长的部分"相关，而不是和历史总量相关。

> 面试一句话版：**rAF 把每 token 一次的渲染合并成每帧至多一次；Map 缓存让同一文本只算一次；结构上把流式气泡和历史列表隔离，让每帧只更新一个节点。** 三板斧分别解决"太频繁""重复算""范围太大"三个问题。

配套细节：流式气泡上还挂了 `@click="handleStreamClick"`——因为气泡的 HTML 每次整段重写，**"复制代码"按钮不能按块绑定监听**（绑定会被下一次 innerHTML 覆盖），而要用**事件委托**（9.3 节展开）：监听容器 click，判断点中的是不是 `.code-copy`。这样生成到一半的代码也能随时复制。

## 五、KeepAlive 滚动位置恢复：autoScroll 意图 vs 历史位置

### 5.1 为什么 deactivated 时读不到滚动位置

KeepAlive 停用组件时，会把它的整棵 DOM 子树**从文档里移走**（放进一个隐藏容器保管）。脱离文档的元素没有布局——`scrollHeight` 归零、`scrollTop` 读取无意义。

Chat.vue 里有一句非常重要的注释（实测根因）：

> 注意：不要在 deactivated 里保存——此时 DOM 已脱管（scrollHeight=0），读到 0 会覆盖掉正确值，导致切回永远恢复不了（实测根因）。

也就是说，"等切走时再保存滚动位置"是**不可行**的（读到的是 0）。正确做法是**平时滚动时就持续记录**——这正是下面这个状态机的设计动机。

### 5.2 两套意图：autoScroll（要不要跟着走）与 savedChatScrollTop（停在哪）

```ts
// Chat.vue（真实逻辑，注释为原意）
let autoScroll = true;          // 意图 A：跟随最新（默认）
let savedChatScrollTop = 0;     // 意图 B：记录的用户位置（翻历史后恢复用）

function onMessageScroll() {
  const el = messageContainer.value;
  if (!el) return;
  // 距底部 120px 以内 = 用户"待在底部"→ 保持自动跟随；上翻超过 120px = 用户在看历史 → 停跟
  autoScroll = el.scrollHeight - el.scrollTop - el.clientHeight < 120;
  savedChatScrollTop = el.scrollTop;   // 任何滚动都记录当前位置
}
```

为什么需要两个变量？因为"是否自动滚到底"和"最后停在哪"是**两个正交问题**：

- 用户上翻看历史时，如果新 token 来了就强制滚到底，用户会被反复拽走——所以用 `autoScroll` 表达"用户此刻想不想被跟随"（距底 120px 是"在底部的宽松判定"，防止差几个像素就误判）；
- 用户停在半山腰时，位置要记下来，供切走再回来时恢复——`savedChatScrollTop`。

新内容到来时按意图行动：

```ts
watch([() => messages.value.length, streamContent], async () => {
  if (!autoScroll) return;          // 用户在看历史 → 新内容来了也不打扰
  await nextTick();
  const el = messageContainer.value;
  if (el) {
    el.scrollTop = el.scrollHeight; // 跟在底部 → 滚到最新
    savedChatScrollTop = el.scrollTop;
    // ↑ 关键细节：程序赋值 scrollTop 不会触发 scroll 事件！
    //   不手动记一笔的话，onMessageScroll 永远不会执行，位置就丢了
  }
});
```

> **细节考点**：`el.scrollTop = x` 是程序滚动，**不派发 scroll 事件**。所以"程序滚到底"也必须手动同步 `savedChatScrollTop`，否则记录停留在上一次用户滚动的位置。这正是"自动记录依赖事件、程序滚动需手动记录"的完整故事。

### 5.3 activated 时恢复：DOM 重插后 top 归零

切回对话页时，KeepAlive 把 DOM 重新插回文档。此时内容完整，但浏览器的 scrollTop 被清成 0（Chat.vue 注释：实测 activated 时内容完整但 top=0）。于是 `onActivated` 里按意图恢复：

```ts
onActivated(async () => {
  loadModelConfigs();   // 从「模型配置」页回来：刷新模型列表，否则新 Key 不进下拉
  await nextTick();     // 等 DOM 真正重插完成（activated 时布局可能还没就绪）
  const el = messageContainer.value;
  if (!el) return;
  if (autoScroll) {
    el.scrollTop = el.scrollHeight;        // 意图是"贴底" → 滚到底
  } else if (savedChatScrollTop > 0) {
    el.scrollTop = savedChatScrollTop;     // 意图是"翻历史" → 回原位置
  }
});
```

为什么要 `nextTick`？activated 生命周期里 DOM 刚被移回来，此刻直接读/写滚动属性能不能生效取决于浏览器是否已完成这帧布局——nextTick 保证在 Vue 完成本轮 DOM 更新后再动手。

### 5.4 会话切换：位置和草稿都是"每会话一份"

滚动位置还有一个归属问题：**会话 A 翻了历史，切到会话 B 时不能把 A 的位置带到 B**。Chat.vue 在 `selectSession` 里显式重置：

```ts
async function selectSession(id: string) {
  if (streaming.value) return;                       // 流式中禁止切会话
  sessionStorage.setItem('chat-active-session', id); // 记住当前会话：切导航再回来仍停留
  // 先把当前会话的输入草稿、图片草稿存好（不串台也不丢失）
  if (currentSessionId.value) {
    inputDrafts.value[currentSessionId.value] = input.value;
    imageDrafts.value[currentSessionId.value] = [...pendingImages.value];
  }
  input.value = inputDrafts.value[id] ?? '';
  pendingImages.value = imageDrafts.value[id] ?? [];
  currentSessionId.value = id;
  messages.value = [];
  // P2：新会话默认停在最新消息，并清掉上一个会话记录的历史位置
  autoScroll = true;
  savedChatScrollTop = 0;
  // 竞态防护：快速连切只采用最后一次请求结果（详见 8.6 的三连对照）
  const reqNo = ++sessionReqNo;
  const list = await getChatMessages(id);
  if (reqNo === sessionReqNo) messages.value = list;
  // ...
}
```

这个文件里状态很多，但它们不是无组织堆着——正好分成"三份记忆 + 两套意图"：

| 记忆/意图 | 归属 | 存哪 |
|---|---|---|
| 输入文字草稿 | 每会话一份 | `inputDrafts`（内存） |
| 待发图片草稿 | 每会话一份 | `imageDrafts`（内存） |
| 当前停留在哪个会话 | 全局 | `sessionStorage`（跨刷新存活） |
| 自动跟随意图 | 每会话 | `autoScroll`（切换时重置 true） |
| 历史位置 | 每会话 | `savedChatScrollTop`（切换时清零） |

> 面试可以这样总结滚动恢复：**"位置是滚动事件的副产品，不是 deactivated 的副产品"**——所以平时滚动就记录；恢复时按"贴底意图/历史位置"分派；每切一个会话就重置意图与位置，避免跨会话串台。

## 六、全局反馈体系：Toast / Confirm / 主题，模块级状态与全局宿主

### 6.1 一个贯穿全站的设计决策：模块级状态，不依赖 Pinia 上下文

看 `composables/useToast.ts` 的开头：

```ts
// useToast.ts（片段）
import { reactive } from 'vue';

// 模块级响应式状态：任何组件/非组件代码都能用，无需 Pinia 上下文
const state = reactive<{ toasts: ToastItem[] }>({ toasts: [] });
```

"模块级"三个字是这组设计的灵魂。对比两条路：

- **Pinia store**：必须先 `useAuthStore()`（要 Pinia 实例注入到当前组件上下文，通常依赖 setup 或 app 级 provide）；
- **模块级 reactive**：文件被 import 时就创建好状态，**任何地方**——组件 setup、普通 .ts 工具、甚至 request.ts 拦截器里——都能 `toast.error('...')`。

本项目选择后者的场景判断很准确：Toast/Confirm/主题是**与业务数据无关的全局 UI 状态**，不需要 devtools 时间旅行、不需要跨 store 引用，用模块级状态 + 全局宿主组件就是最轻的方案。而真正的登录态（`stores/auth.ts`）是业务状态、被几十处引用，才需要 Pinia。

宿主组件的挂载也很有意思——`App.vue` 只有三行内容：

```html
<template>
  <RouterView />
  <ToastContainer />      <!-- 全局 Toast 渲染宿主 -->
  <ConfirmDialogHost />   <!-- 全局确认/输入框宿主 -->
</template>
```

状态在模块里，**渲染在全局挂载一次的组件里**，中间的桥梁就是模块导出的状态对象。这一"状态与渲染分离"的模式，让**业务代码（任何 .ts/.vue）只 import 函数调用，永远不用关心弹层 DOM 长在哪**。

### 6.2 Toast：reactive 队列 + TransitionGroup + 自动/手动关闭

`toast.success('已保存')` 的三层分工：

1. **useToast.ts**：`push` 往 `state.toasts` 塞一条 `{ id, type, message, duration }`，错误 5s、成功/提示 3s 后自动 `dismiss`（duration 传 0 则常驻，需要手动关）；`seed` 自增保证 id 唯一（动画 key）；
2. **ToastContainer.vue**：`v-for="t in state.toasts"` 渲染右上角堆叠区，套 `TransitionGroup` 做进出场动画（`translate-x` 滑入/滑出）；
3. **业务代码**：一行调用，完事。

`ToastContainer` 里用 `<TransitionGroup>` 而不是 `<Transition>` 的原因：多个 toast 会同时存在，进出场需要**对列表整体**做 move 过渡（新 toast 顶上来时旧的平滑让位）。图标和颜色用映射表（`iconMap`/`colorMap`），按类型取值，避免模板里写一坨 v-if。

### 6.3 Confirm：把"弹窗确认"变成一句 await

原生 `window.confirm` 有三大缺点：样式丑且不可定制、阻塞式 API 与异步代码不协调（弹窗期间 JS 停摆）、浏览器差异大。项目用 Promise 化方案替换（useConfirm.ts，P1-6 档案记录）：

```ts
// 业务代码里的用法（Chat.vue 删除会话）：
if (!(await confirmDialog('删除该会话及其全部消息？此操作不可恢复。'))) return;
```

实现核心是**resolver 模式**：

```ts
// useConfirm.ts（片段）
type Resolver = (value: boolean) => void;
let resolver: Resolver | null = null;

export function confirmDialog(opts: string | ConfirmDialogOptions): Promise<boolean> {
  state.options = { ...defaults, ...(typeof opts === 'string' ? { message: opts } : opts) };
  state.open = true;
  return new Promise((resolve) => { resolver = resolve; });  // 先把"怎么答复"存起来
}

// ConfirmDialogHost 里用户点了确认：
export function resolveConfirm(ok: boolean): void {
  state.open = false;
  const r = resolver;
  resolver = null;
  if (r) r(ok);        // 把用户选择"投喂"给等待中的 Promise
}
```

于是业务逻辑可以写得很线性："确认删除？是 → 发请求 → toast 结果"。ConfirmDialogHost 还负责：

- **键盘**：Esc = 取消、Enter = 确认（打开时挂 document keydown 监听，关闭时移除）；
- **防连点**：确认按钮的处理器先 `await new Promise(r => setTimeout(r, 30))`——让"loading 转圈"先渲染出来，再执行调用方随后的异步，双保险禁连点；
- **promptDialog 模式**（替换 window.prompt）：打开后聚焦输入框并全选预填值（重命名场景直接打字覆盖），空输入等同取消；
- 整层 `Teleport to="body"` + `fixed inset-0` 遮罩：保证任何祖先的 transform/overflow 都关不住它。

> 类比：`confirmDialog` 像"点外卖下单（返回小票 Promise），商家（宿主组件）备好餐后凭小票送货（resolve）"。业务代码永远不需要碰弹窗 DOM，它只关心"小票上最终写的是确认还是取消"。

### 6.4 主题切换：CSS 变量 + `.dark` 类，双色板一套代码

**为什么用 CSS 变量而不是两套组件类？** 想象每个组件都要写"浅色背景、暗色背景"两份类，还要处理几十个语义色——直接爆炸。正确做法是把颜色抽象成**语义 token**，组件只引用 token：

```css
/* styles/index.css（片段） */
@layer base {
  :root {
    /* 蓝色 AI 风浅色主题 */
    --background: 220 30% 98%;
    --primary: 221 83% 53%;
    /* …… background/foreground/card/muted/accent/destructive/border…… */
  }
  .dark {
    /* 暗色：深蓝黑底 + 亮蓝主色 */
    --background: 222 47% 6%;
    --primary: 221 83% 58%;
    color-scheme: dark;  /* 原生控件（日历/时钟图标）暗色渲染，否则看不见 */
  }
}
```

注意值都是 **HSL 三段式**（`色相 饱和度 明度`）而不是 `#fff`——因为 Tailwind 生态用 `hsl(var(--x) / alpha)` 可以**叠加透明度**（比如 `bg-primary/10`、`border-destructive/30`），hex 做不到。tailwind.config.js 里把每个 token 映射成 Tailwind 颜色：

```js
// tailwind.config.js（片段）
darkMode: ['class'],              // 暗色模式由 <html class="dark"> 驱动
colors: {
  background: 'hsl(var(--background))',
  primary: { DEFAULT: 'hsl(var(--primary))', foreground: 'hsl(var(--primary-foreground))' },
  // ...
},
```

于是组件里写 `bg-card text-muted-foreground`，切主题**零组件改动**——只是 `<html>` 上 `.dark` 类的有无，让同一批 CSS 变量换了一组值。

驱动它的 useTheme.ts 本身也只有 30 行：

```ts
// useTheme.ts（全文要点）
const isDark = ref(false);
function applyTheme(theme: Theme) {
  isDark.value = theme === 'dark';
  document.documentElement.classList.toggle('dark', isDark.value);  // 根元素挂类
  localStorage.setItem('kb-theme', theme);                           // 持久化用户选择
}
function initTheme() {
  const saved = localStorage.getItem('kb-theme');
  const prefersDark = window.matchMedia?.('(prefers-color-scheme: dark)')?.matches;
  applyTheme(saved ?? (prefersDark ? 'dark' : 'light'));  // 用户选择优先，否则跟随系统
}
```

`App.vue` 的 setup 里执行 `useTheme().initTheme()`——在第一个页面组件渲染前就把类挂好，登录页/注册页同样生效（它们不经过 Layout）。`Layout.vue` 顶部还有一行值得记的注释：

> 解构顶层 ref：模板中自动解包（直接 `theme.isDark` 拿到的是 Ref 对象，恒为真值）。

这是组合式 API 反模式的一个典型：把整个 useTheme() 返回值塞进模板变量，忘了它内部是 ref。

**防 FOUC 的取舍**（首帧闪白）：主题类要在**内容第一次绘制前**就位才算彻底防闪。本项目在 App.vue setup（挂载早期）同步执行 initTheme，空白 #app 里没有可闪的内容，窗口很小；如果未来首帧真出现闪白，标准解法是把一段极小的内联脚本放进 index.html 的 `<head>`，抢在 CSS 绘制前根据 localStorage 给 `<html>` 挂 `.dark`——两种做法的差别只在于"多早"。

## 七、请求层：axios 拦截器与 401 无感刷新

### 7.1 为什么要有统一请求层

后端所有接口统一返回 `{ code, message, data }`，业务请求要：带鉴权头、解包 data、错误转中文、token 过期不打断用户。如果每个 API 函数各自处理，逻辑会复制几十份且极易漏。于是所有业务请求都走 `api/request.ts` 导出的同一个 axios 实例：

```ts
// api/chat.ts 的用法（业务层只关心"我要什么数据"）
export function getChatSessions(q?: string) {
  return request.get<unknown, ChatSession[]>('/chat/sessions', { params: q ? { q } : undefined });
}
```

### 7.2 请求拦截器：自动带 Token

```ts
request.interceptors.request.use((config) => {
  const token = localStorage.getItem('accessToken');
  if (token && config.headers) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});
```

Token 存 localStorage、请求时读取——简单直接。刷新页面后 token 还在，配合 Layout 挂载时 `auth.fetchProfile()` 恢复登录态（第 7 章讲过双 token 机制）。

### 7.3 响应拦截器：统一解包

```ts
(response): any => {
  const res = response.data as ApiResponse;
  if (res.code !== 0) return Promise.reject(new Error(res.message || '请求失败'));
  return res.data;            // 业务代码拿到的直接是 data，不带 {code,message} 壳
}
```

失败分支把错误 message 统一包装成 Error 抛出，页面 catch 到后 `toast.error(e.message)`。**业务代码永远见不到 axios 的报错结构**。

### 7.4 401 无感刷新：并发请求排队重放

这是全站"登录不掉线"的机制。先看数据流，再看代码：

```
时间线：t1 同时发出 3 个请求，accessToken 恰好已过期
─────────────────────────────────────────────────────
 t1: 请求A/B/C 都带旧 token 发出
 t2: A 先返回 401 → isRefreshing=false → 它"抢到"刷新权：
     A 自己发起 POST /auth/refresh（用 refreshToken）
 t3: B、C 也返回 401 → 看到 isRefreshing=true → 不自己刷新，
     各自把"带着新 token 重发自己"的函数 push 进 pendingQueue，挂起等待
 t4: refresh 成功 → 新 accessToken 写回 localStorage
     → 依次执行 pendingQueue 里 B、C 的重发函数
     → 自己也用新 token 重发 A
 t5: 3 个请求全部成功返回，用户毫无感知
```

代码骨架（request.ts，注释为原意）：

```ts
let isRefreshing = false;
let pendingQueue: Array<(token: string) => void> = [];

// 响应拦截器的错误分支
async (error) => {
  const originalRequest = error.config;
  if (
    error.response?.status === 401 &&
    !originalRequest._retry &&                                  // 没重试过（防死循环）
    !PUBLIC_AUTH_PATHS.some((p) => (originalRequest.url || '').includes(p))
  ) {
    if (isRefreshing) {
      // 有人正在刷新 → 排队：等新 token 到了把自己重发掉
      return new Promise((resolve) => {
        pendingQueue.push((token: string) => {
          originalRequest.headers.Authorization = `Bearer ${token}`;
          resolve(request(originalRequest));
        });
      });
    }

    originalRequest._retry = true;
    isRefreshing = true;
    try {
      const refreshToken = localStorage.getItem('refreshToken');
      if (!refreshToken) throw new Error('no refresh token');
      // 用原生 axios 调刷新接口——绝不能用 request 实例！
      // 否则刷新请求本身 401 会再次进入本拦截器，形成无限递归
      const { data } = await axios.post('/api/auth/refresh', { refreshToken });
      const accessToken = data.data.accessToken;
      localStorage.setItem('accessToken', accessToken);

      pendingQueue.forEach((cb) => cb(accessToken));  // 放行排队的请求
      pendingQueue = [];

      originalRequest.headers.Authorization = `Bearer ${accessToken}`;
      return request(originalRequest);                // 重发最初的请求
    } catch (refreshError) {
      // refreshToken 也过期：清登录态，硬跳登录页
      pendingQueue = [];
      localStorage.removeItem('accessToken');
      localStorage.removeItem('refreshToken');
      window.location.href = '/login';
      return Promise.reject(refreshError);
    } finally {
      isRefreshing = false;
    }
  }
  const message = error.response?.data?.message || error.message || '网络错误';
  return Promise.reject(new Error(message));
}
```

三个必须理解的细节：

1. **PUBLIC_AUTH_PATHS 豁免名单**：登录/注册/发验证码等接口的 401 是**业务错误**（密码错、验证码错），不是 token 过期。如果它们也触发刷新流程，用户输错密码会被误判成"登录态失效"，刷新失败后硬跳登录页、把正在填的表单清空。名单：`/auth/login`、`/auth/register`、`/auth/send-code`、`/auth/forgot-password`、`/auth/verify-code`。
2. **刷新请求用原生 axios**：`request` 实例的响应拦截器对 401 一律走刷新逻辑——刷新请求若自己也走它，refreshToken 过期时就会"刷新→刷新→刷新"死循环。原生 `axios.post` 没有这层拦截器，天然免疫。
3. **`_retry` 标志防环**：重发后若新 token 仍被拒（极端情况），`originalRequest._retry` 已为 true，不再进入刷新分支，直接把错误抛给业务层。

### 7.5 流式请求为什么不用 axios：fetch-event-source

对话的 SSE 请求在 `api/chat.ts` 里用 `@microsoft/fetch-event-source`：

```ts
// api/chat.ts（片段）
export function askQuestion(sessionId, content, useWebSearch, signal, callbacks, imageDataUrls?) {
  return fetchEventSource(`/api/chat/sessions/${sessionId}/messages`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      Authorization: `Bearer ${localStorage.getItem('accessToken')}`,
    },
    body: JSON.stringify({ content, useWebSearch, ... }),
    signal,                       // 传入 AbortController 的信号：支持"停止生成"
    onmessage(ev) {
      const msg = JSON.parse(ev.data);   // 后端把事件类型写进 data 的 JSON 里
      switch (msg.event) {
        case 'sources': callbacks.onSources?.(msg.data); break;
        case 'delta':   callbacks.onDelta?.(msg.data.content); break;
        case 'done':    callbacks.onDone?.(); break;
        case 'error':   callbacks.onError?.(msg.data.message); break;
      }
    },
    onerror(err) {
      if (!signal.aborted) { /* 翻译成中文错误提示 */ }
      throw err;   // 抛出以终止重连（SSE 默认会自动重连，这里不需要）
    },
  });
}
```

选它而不是原生 `EventSource` 的原因（代码注释原话）：**原生 EventSource 只支持 GET，无法带 Authorization 头**——对话接口是 POST 且要鉴权。选它而不是 axios 的原因：axios 对 SSE 流式响应支持很别扭，而 fetch-event-source 原生支持 POST + 自定义头 + `AbortController` 中止（停止按钮就是靠它）。

## 八、对话页交互状态机：发送 / 流式 / 停止 / 重试

### 8.1 状态清单：先盘清楚有多少"会变的"

Chat.vue 的流式状态机由一组状态 + 一个控制器组成：

| 状态 | 含义 | 谁改它 |
|---|---|---|
| `streaming` | 是否在生成中 | 发送时 true；done/error/stop/finally 复位 |
| `streamContent` | 流式中的累计文本（未入列表） | rAF flush 每帧一次 |
| `streamSources` | 本次回答的引用来源（kb + web） | onSources 事件 |
| `abortController` | 本次请求的中止控制器 | 发送时 new；stop/unmount 时 abort |
| `optimisticId / localMsgSeq` | 乐观消息的临时 id | 自增序号保证唯一 |
| `retryDraft` | 失败内容快照（供重试） | 失败时写；重试/放弃/新发送时清 |
| `lastOptimisticMsgId` | 最近一条乐观用户消息 | 重试/放弃前移除它 |

### 8.2 乐观渲染：先上屏、再问后端

发送的瞬间，用户消息**不等后端确认**直接插进列表——这就是"乐观渲染"（optimistic UI）：体感零延迟。真正的坑在于这条消息的 **id 必须是全局唯一的**：

```ts
const optimisticId = `local-${Date.now()}-${++localMsgSeq}`;
```

为什么这么较真？消息列表的渲染键是 `v-for="msg in messages" :key="msg.id"`。**key 相同 = Vue 认为是同一条消息 = 复用同一个 DOM 节点**。历史消息的 id 是后端 UUID；若乐观 id 恰好与某条历史 id 相同（比如草率地用 `Date.now()` 或固定字符串），Vue 会把新消息画进旧消息的 DOM——多图消息会"图片堆叠在旧消息上"（这是真实踩过的 bug，注释写明）。`Date.now() + 自增序号` 组合保证同毫秒内连续发送也不撞车。

发送的同时还做了：清空输入框/待发图片/待发文件、`streaming = true`、启动思考计时器、**强制滚到底**（`autoScroll = true` + nextTick 后滚到 scrollHeight）——即使用户刚才在翻历史，新问题发出后也要把视线带回"战场"。

### 8.3 停止：abort 之后，半截回答不能丢

```ts
function handleStop() {
  abortController.value?.abort();       // 中止 fetch-event-source → 后端停止生成
  // 保留已生成的部分回答：停止后把流式累积的内容落成一条 assistant 消息
  // （否则中止时 onDone 不触发，回答到一半的内容就丢了）
  if (streamContent.value.trim()) {
    messages.value.push({ id: ..., role: 'assistant', content: streamContent.value, ... });
  }
  streaming.value = false;
  stopThinkingTimer();
}
```

设计要点：**"停止" ≠ "丢弃"**。用户按停止是嫌回答跑偏了，但已经生成的内容往往是有效的——落成一条正式消息，用户还能复制、还能分支追问。注意 onDone 在 abort 后不会触发（连接断了），所以"把累积内容转正"必须在 handleStop 里自己完成。

### 8.4 finally 里的竞态防护：`abortController.value === ac`

发送函数最容易被忽略的是收尾竞态：**Stop 后立刻再发一条**，旧请求的 finally 晚到，会不会把新请求的 streaming 状态清掉？看代码怎么防：

```ts
const ac = abortController.value;   // 局部持有"本次"请求的控制器（P1-3）
try {
  await askQuestion(..., ac.signal, { onDelta, onDone, onError });
} finally {
  stopThinkingTimer();
  // 仅当 abortController.value 仍指向本次请求（ac）才复位——
  // 否则可能误清新流的 streaming 状态
  if (abortController.value === ac) {
    streaming.value = false;
    abortController.value = null;
  }
}
```

把"本次请求的身份"（ac）存进局部变量，finally 里核对"全局控制器还是不是我"——不是就不动。这就是 JavaScript 单线程下最朴素的**令牌核对**竞态防护——和 8.6 节的 `sessionReqNo`、图片压缩的 `fromSession` 是同一个思想的三次现身。

### 8.5 失败重试：上下文快照 + 幂等语义

模型接口失败时（onError），后端**已回滚未成功的用户消息**（服务端语义，注释写明），前端要做的是：

1. 把失败内容快照进 `retryDraft`（问题原文 + 图片 + 文件都留着），错误条上出现「重试/放弃」按钮；
2. 用户点重试 → 先**移除失败的乐观用户消息**（后端已回滚，不删会残留一条假消息）→ 用快照原样重新发送；
3. 点放弃 → 同样移除乐观消息 + 清空草稿。

```ts
async function handleRetrySend() {
  const d = retryDraft.value;
  if (!d || streaming.value) return;
  if (lastOptimisticMsgId.value) {   // 移除失败的乐观消息，避免与重发结果重复
    messages.value = messages.value.filter((m) => m.id !== lastOptimisticMsgId.value);
    lastOptimisticMsgId.value = null;
  }
  await sendPayload(d.question, d.images, d.files, true);  // isRetry=true：不再清 retryDraft
}
```

这里"重试"与"新发送"共用同一个 `sendPayload`，用 `isRetry` 区分两处小差异（要不要先清 retryDraft、要不要移除旧乐观消息）——状态机的正确姿势就是**把可复用路径收敛成一个函数**，差异用参数表达，而不是复制粘贴一版。

### 8.6 会话级竞态防护：异步操作要"绑定发起时会话"

对话页有大量异步操作（拉消息、压缩图片、提取文件文本），而用户可以在等待期间切走会话。三种防护一一对应：

```ts
// ① 切会话拉消息：只采用最后一次请求（sessionReqNo 递增令牌）
const reqNo = ++sessionReqNo;
const list = await getChatMessages(id);
if (reqNo === sessionReqNo) messages.value = list;   // 旧的晚到？作废

// ② 压缩图片是异步的：结果归属"发起选择时的会话"（fromSession 绑定）
async function onPickImage(files: File[]) {
  const fromSession = currentSessionId.value;   // 发起时的会话
  const imgs = await Promise.all(files.map(compressImage));
  if (fromSession && currentSessionId.value !== fromSession) {
    // 期间用户切走了 → 图片放进原会话草稿，并 toast 提示，不污染当前输入
    imageDrafts.value[fromSession] = [...(imageDrafts.value[fromSession] ?? []), ...imgs];
    toast.info('图片已加入原会话草稿（你已切换到其他会话）');
    return;
  }
  // ...
}

// ③ 流式中禁止切会话、禁止删除当前会话（双保险：按钮禁用 + 函数内 return）
async function selectSession(id: string) {
  if (streaming.value) return;
}
```

> 面试总结这三处：**凡是"发起后要等一会儿才完成"的操作，都必须记住发起时的上下文（会话/请求序号/控制器），完成时校验"世界还是不是我离开时的样子"，不是就丢弃或改道**——否则就是经典的竞态串台 bug。

最后，真正的卸载（登出）用 `onBeforeUnmount` 兜底：中止进行中的 SSE、清思考计时器、清搜索防抖 timer——**避免登出后后台还在替用户烧 token**（P1-4）。

## 九、Markdown 渲染与代码高亮：安全、性能、交互一把抓

### 9.1 渲染器配置：每一处选项都是安全决策

`utils/markdown.ts` 创建一个 markdown-it 实例：

```ts
const md = new MarkdownIt({
  html: false,     // ① 禁止原始 HTML —— AI 输出里出现 <script> 也不执行（防注入）
  linkify: true,   // 裸链接自动转 <a>
  breaks: true,    // ② 换行渲染成 <br> —— AI 回答习惯单换行分段，不开的话全糊成一段
  highlight(code, lang) { /* 见 9.2 */ },
});
```

`html: false` 是 XSS 的第一道闸：AI 的 markdown 里如果夹带 `<img onerror=...>`，markdown-it 不渲染原始 HTML 就执行不了。`breaks: true` 是体验决策——大模型的回答用单个 `\n` 分段，markdown 默认要空行才算段落，不设 breaks 的话回答会挤成一大块。

### 9.2 代码高亮：按需注册 + 自动检测子集 + 兜底转义

highlight.js 全量引入所有语言会带来约 **1MB 的打包增量**。项目只引入核心 + 常用语言（`highlight.js/lib/core` + 每语言的独立模块），并给常用语言注册了别名：

```ts
import hljs from 'highlight.js/lib/core';
import javascript from 'highlight.js/lib/languages/javascript';
import typescript from 'highlight.js/lib/languages/typescript';
// ……python/bash/json/xml/css/sql/c/cpp/java/go/rust/php/ruby/kotlin/swift/yaml/ini/markdown/diff

hljs.registerLanguage('javascript', javascript);
hljs.registerLanguage('js', javascript);   // 别名：AI 常写 ```js
hljs.registerLanguage('typescript', typescript);
hljs.registerLanguage('vue', xml);         // .vue 用 xml 高亮（标签结构近似）
// ……
```

自定义的 `highlight` 回调分三级处理：

```ts
highlight(code: string, lang: string): string {
  // 第 1 级：有语言标注且已注册 → 按语言高亮（最准确）
  if (lang && hljs.getLanguage(lang)) {
    try {
      return `<pre class="hljs"><code class="language-${lang.replace(/[^\w-]/g, '')}">` +
        hljs.highlight(code, { language: lang }).value + `</code></pre>`;
    } catch { /* fallthrough */ }
  }
  // 第 2 级：未标注语言 → 自动检测（解决 AI 输出 ``` 不带语言时整块无色的痛点）
  if (code.trim()) {
    try {
      const detected = hljs.highlightAuto(code, AUTO_SUBSET);  // 限定候选语言集
      // AUTO_SUBSET = 常见语言白名单，避免误判冷门内容
      return `<pre class="hljs"><code${...}>${detected.value}</code></pre>`;
    } catch { /* fallthrough */ }
  }
  // 第 3 级：兜底 → 纯文本转义（用户数据永远先转义再进 DOM）
  return `<pre class="hljs"><code>${md.utils.escapeHtml(code)}</code></pre>`;
}
```

第 2 级值得一提：`highlightAuto` 如果不限子集，会对"一段没有特征的普通文本"猜一个离谱语言（甚至把中文文本识别成某种冷门语言），所以传 `AUTO_SUBSET` 白名单（js/ts/py/bash/json/xml/css/sql/java/go/rust/cpp/yaml/markdown 等 14 种常见语言）。

### 9.3 代码块容器与复制按钮：为什么用事件委托

markdown 渲染完的 HTML 只是 `<pre class="hljs">`，复制按钮是渲染后用字符串替换**包**上去的：

```ts
const wrapped = html
  .replace(/<pre class="hljs">/g,
    '<div class="code-block"><button type="button" class="code-copy" title="复制代码">复制</button><pre class="hljs">')
  .replace(/<\/pre>/g, '</pre></div>');
```

按钮的点击不绑定在每个按钮上（流式气泡的 innerHTML 每帧整段重写，逐个绑定的监听会被覆盖丢失；历史消息也是 v-html 一次性注入，逐个绑定成本高），而是**在容器上监听一次 click、按目标判断**：

```ts
async function handleMessageClick(e: MouseEvent) {
  const target = e.target as HTMLElement;
  if (target.classList.contains('code-copy')) {
    const code = getCopyCode(target);        // 向上找 .code-block → 取 <pre> 文本
    if (code && (await copyText(code))) {
      target.textContent = '已复制';          // 按钮文案瞬时反馈
      setTimeout(() => (target.textContent = '复制'), 1500);
    }
  }
}
```

事件委托的好处：**无论 DOM 怎么被 v-html 重写/新增，监听都在祖先身上，永不失效**——这正是流式中代码块"复制"也能用的原因（Chat.vue 的 `handleStreamClick` 绑在流式气泡容器上，与历史消息的委托逻辑一致）。`copyText` 也有降级：`navigator.clipboard` 只在 HTTPS/安全上下文可用，纯 IP 的 http 部署会被禁，所以失败后回退 `execCommand('copy')`（临时 textarea 方案，见 `utils/clipboard.ts`）。

### 9.4 外部链接一律新标签页

AI 回答里经常带链接。如果直接渲染，点一下整页跳走——**对话状态、流式上下文全丢**。markdown-it 允许改写渲染规则（renderer rule）：

```ts
md.renderer.rules.link_open = (tokens, idx, options, env, self) => {
  const token = tokens[idx];
  const href = token.attrGet('href') ?? '';
  // 内部锚点/引用跳转不加 target；外部 http(s) 链接一律新标签打开
  if (/^https?:\/\//i.test(href) || href.startsWith('www.')) {
    token.attrSet('target', '_blank');
    token.attrSet('rel', 'noopener noreferrer');   // 防 tab-nabbing 反向钓鱼
  }
  return defaultLinkOpen(tokens, idx, options, env, self);
};
```

`rel="noopener noreferrer"` 是安全细节：不写的话，新页面里的恶意脚本可以通过 `window.opener` 篡改原页面。

### 9.5 与渲染缓存、全局排版的分工

最后串一遍渲染链路的分层：

```
AI 文本 → renderMarkdown(text)        [utils/markdown.ts：markdown-it + hljs + 包按钮 + Map 缓存]
        → ChatMessageItem 的 msgHtml  [computed：内容不变不重算]
        → v-html 注入 .markdown-body   [styles/index.css：全局排版，对话页/报告页共用]
```

`.markdown-body` 的排版（标题分级、行高、表格边框、内联代码、blockquote 等）曾经在 Chat/Research/ResearchAgent 三个页面各有一份几乎相同的 scoped 副本（每个约 100 行），功能档案 33 里把它**合并进 styles/index.css**——消除三份漂移的样式，新页面直接可用。代码高亮的两套 token 配色也在这里，随 `.dark` 类切换（见下节）。

## 十、CSS 体系与视觉亮点

### 10.1 Tailwind + CSS 变量：运行时切主题的基石

全站样式 = Tailwind 工具类 + 语义色 token。`darkMode: ['class']` 意味着暗色不是媒体查询（跟随系统），而是**跟随 `<html>` 上的 `.dark` 类**——这才能支持"用户手动选择"并即时切换。CSS 变量是 token 的物理载体，Tailwind 类只是 token 的别名，组件代码里从来看不到具体色值。

高亮的双主题也在这一层用级联解决：`index.css` 里定义两套 `.hljs-*` token 配色——浅色 = VSCode Light Modern 色板，`.dark .markdown-body .hljs-*` = One Dark Pro 色板；代码块背景同理（浅色 `#f6f8fa`，暗色 `#282c34`）。代码块是 markdown-it 输出的静态 HTML，**切主题时不需要重新渲染任何东西**——纯 CSS 级联切换。这是"CSS 变量主题"相比"JS 换肤"最优雅的地方。

### 10.2 氛围层：不抢内容的"呼吸感"

Layout.vue 底部有三个 `blur-3xl` 的蓝青色光斑，`pointer-events-none`（绝不挡点击）+ 缓慢漂移动画，暗色下更亮、明度都压得很低（`bg-blue-500/10` 之类）——视觉亮点但零交互干扰。这类"氛围背景"的实现要点是：**pointer-events-none + 低透明度 + 放最后（-z-10）**，保证永远不影响可读性与操作。

### 10.3 首页宇宙：Canvas 粒子背景（视觉亮点，略读）

`components/HomeCosmos.vue` 是首页的 Canvas 实时渲染背景（751 行，非 CSS 贴图），理念值得一看：

- **主题联动**：暗色模式渲染"黑洞"（开普勒吸积盘、多普勒聚束、光子环、事件视界遮挡、背景星引力透镜畸变）；浅色模式渲染它的时间反演——"白洞"（物质从核心向外喷射减速淡出）。切换时两套场景**交叉淡入淡出**（watch isDark 设 targetBlend，帧循环里 lerp blend）；
- **物理模拟**：开普勒角速度 ω=K/r^1.5、粒子受鼠标"引力/斥力"偏转、黑洞悬停时整盘粒子加速坠入视界（vr 设下限防数值爆炸）——每帧位置由 rAF 循环推进；
- **性能纪律**：5000+ 粒子只在 resize 时重建一次（注释明确：不做 onActivated 重建，那是切页卡顿的元凶）；配合 KeepAlive 的 onDeactivated 停掉 rAF（第 2.3 节）；`canvas.dataset.particles` 暴露粒子数供自动化测试断言规模。

它演示了 Canvas 场景与 Vue 生命周期打交道的完整模式：**onMounted 启动 rAF + 绑监听，onDeactivated 停 rAF，onBeforeUnmount 清监听，主题变化用 watch 而非轮询**。

## 十一、动手实验

**实验 A：用 Performance 面板看流式渲染帧**
1. 打开对话页，F12 → Performance → 点录制；
2. 问一个会让模型输出**长代码**的问题（触发高亮），观察整个流式回答过程，然后停止录制；
3. 看 Main 火焰图：正常时是"密集小任务 + 每帧一次较长任务"的节奏（rAF flush）；如果能看到每 token 一次长任务堆积，说明节流失效了；
4. 再留意 Rendering 面板：流式期间只有气泡区域 invalidated，而不是整页。

**实验 B：切走再切回，验证滚动恢复与"不重建"**
1. 在对话页翻到一条很长的历史回答（上滚，autoScroll 应变 false）；
2. 切到「模型配置」页再切回来——预期：**停在你刚才的位置**（历史位置恢复），而不是被拽到底；
3. Network 面板对照：切回来只看到 model-configs 请求，**没有 messages 请求、没有 SSE 请求**——证明组件没重建、消息没重拉（KeepAlive 生效）；
4. 切到「数据看板」再切回对话页——预期：滚到底（新会话意图），因为 Dashboard 不在 include 名单、Chat 的激活态每次都会重新判断。

**实验 C：手动制造一次 401**
1. DevTools → Application → Local Storage 把 `accessToken` 改成 `xxx`（假 token）；
2. 在对话页随便发一条消息或切换会话（触发任意接口）——预期：页面**没有**跳登录，接口自动刷新后成功（Network 里能看到一次 `/auth/refresh` 请求后原请求重发）；
3. 再把 `refreshToken` 也改坏再操作——预期：这次跳转到 `/login`。

## 十二、自测题

1. **（面试必背）为什么流式渲染要用 requestAnimationFrame 节流？直接每个 token 更新 DOM 会怎样？**（提示：帧预算 16.6ms、全量 markdown+highlight 的成本随回答长度增长、一帧内多次 DOM 写只有最后一次被 paint）
2. **（面试必背）KeepAlive 缓存组件有哪些坑？**（提示：DOM 脱离后 scrollHeight=0 读不到滚动位置；定时器/rAF 不会因切走而停止，需 onDeactivated 暂停；内存占用；include 匹配的是组件名而非路由名，需要 defineOptions name）
3. 乐观渲染的用户消息 id 为什么要全局唯一？用固定 id 会发生什么？（提示：v-for key 相同 = Vue 复用 DOM → 图片堆叠）
4. 401 无感刷新里，为什么刷新接口要用原生 axios 而不用自己的 request 实例？PUBLIC_AUTH_PATHS 豁免名单解决什么问题？
5. 为什么"程序滚动 scrollTop 赋值后"还要手动记录一次 savedChatScrollTop？（提示：赋值不触发 scroll 事件）
6. markdown 渲染做了哪三层防注入/兜底？外部链接为什么统一加 target="_blank" 和 rel="noopener noreferrer"？

## 十三、本章小结

本章把前端从"能显示回答"打磨到"用起来像原生应用"：**懒加载 + KeepAlive** 决定代码与状态的加载边界；**容器/展示拆分**把 1600 行巨石收敛成有清晰契约的组件树；**rAF + 渲染缓存 + 流外渲染**让每秒几十 token 的流式输出保持 60fps；**autoScroll/savedChatScrollTop** 让滚动听懂用户意图；**模块级状态 + 全局宿主**给全站一套不依赖上下文的 Toast/Confirm/主题；**拦截器无感刷新**让 token 过期不再打断用户；**状态机与令牌核对**兜住发送/停止/重试/切会话的每一个竞态。

下一章我们把镜头拉远：这些代码怎么被测试保护、怎么自动部署上线、线上出问题时怎么一步步排——从"能跑"走向"可靠"。
