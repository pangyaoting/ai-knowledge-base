## 一、为什么长任务必须异步

### 1.1 三类"分钟级"任务

回顾全书主线（00 章的知识地图），这个平台里所有"要调用大模型干重活"的场景，都逃不开一段**很长的等待**：

| 任务 | 耗时量级 | 触发方式 | 前台体验 |
|---|---|---|---|
| 文档入库（解析→分块→向量化） | 秒~分钟（看文件大小） | 上传文件 | 上传要"秒回"，处理慢慢来 |
| 研究报告 | 1~2 分钟（注释原话，一份报告要拆 3~5 个子问题、每个都检索+调模型） | 丢一个主题 | 用户想看到"拆解中→检索撰写中→汇总中"的过程 |
| 自主研究 Agent | 十几分钟到几小时（10 万 token ≈ 40 分钟，见 `estimateMinutes`） | 丢一个目标（可选） | 用户想中途停、想续时、想看方向进度 |

如果让 HTTP 请求**同步等完**再返回，会发生什么？

```
用户点"开始生成报告"
   └─ HTTP 请求进入 NestJS（Node 单进程、单线程事件循环）
        └─ 后台开始：拆解(1次LLM) → 每子问题检索+撰写(3~5次LLM) → 汇总(2次LLM)
        └─ 期间：这个请求的线程/上下文一直被占着……
        └─ 1~2 分钟后终于返回
```

### 1.2 同步方案的三个死穴

**① 请求会"超时死"**。浏览器、Nginx、云厂商的负载均衡都对单个 HTTP 请求设超时（常见 30s~120s）。报告要 1~2 分钟、Agent 要几十分钟——请求早就被掐断了。更糟的是请求虽然断了，**后端却还在闷头干活**，干完了没地方交付，白烧 token。

**② 占死进程**。Node 是单线程事件循环：一个 handler 里若真的 `await` 一个 2 分钟的循环，这个进程在等待期间虽然能响应其他事件，但大量同步计算（比如反复组装大字符串、JSON 序列化）会阻塞事件循环，其他用户的请求全部卡顿。更本质的问题是——**HTTP 连接是"弱交付契约"**：用户刷新页面、关标签页，连接就没了，正在执行的工作没有任何载体。

**③ 没有韧性**。LLM API 是外部依赖，网络抖动、429 限流、超时随时发生。同步代码遇到一次抖动就是"整份报告失败"，没有重试机会；也没有"排队中/进行中/失败"这些中间状态可查，前端无从展示进度。

类比：同步方案像是"前台接待员亲自跑一趟工厂，把零件一个个搬回来组装完才接待下一位客人"——接待员被一个客人占死，其他客人全排队；而**队列方案**是"接待员只负责收单开票，把工单丢进车间流水线，车间有专门的工人（Worker）按顺序加工，做完通知你取货"。接待员永远只忙"收单"这一下，HTTP 秒回。

### 1.3 队列方案给的四样东西（面试常问）

| 能力 | 说明 | 本项目落点 |
|---|---|---|
| **异步解耦** | 接口只负责"建记录 + 入队"，立刻返回 | `report.service.create()` 建 `pending` 记录后调 `addReportJob()` 就 return |
| **持久化** | 任务存在 Redis 里，进程重启、任务失败都不丢 | BullMQ 把 job 数据、重试次数都写在 Redis |
| **失败重试** | worker 抛错 → 自动按策略重跑 | 报告 `attempts: 2`（瞬时网络错误重试一次）；文档处理 `attempts: 3` |
| **并发控制** | 队列限定同时跑几个任务，防止把外部 API 打爆 | 三个队列 worker 的 `concurrency` 分别是 1/1/2 |

而"进度可查、可取消、可续跑"这些**业务层**能力，是建在这四样之上的——任务的状态存在 PostgreSQL（`reports.status`、`agent_tasks.status`），前端轮询数据库即可，不用依赖队列内部结构。这是本项目一个重要的分层选择：**队列管"执行"，数据库管"状态"**。

> 概念对应：BullMQ 是 Node 生态最主流的 Redis 队列库（本仓库 `bullmq@^6`）。它把 Redis 当存储介质，因此你的服务器本来就要装 Redis——这个项目里 Redis 同时还承担会话 Token、验证码、限流（见 07 章），一套 Redis 多种用途。

## 二、BullMQ 基础：Queue、Worker、重试与延迟

### 2.1 三个角色

```
        ┌──────────────┐  add(job)   ┌───────────────┐
        │  API / Service │ ─────────▶ │  Queue（队列） │──存──▶ Redis（持久化）
        └──────────────┘             └───────────────┘
                                               │ 取任务
                                               ▼
        ┌──────────────┐  处理完回调    ┌───────────────┐
        │  业务收尾逻辑  │ ◀────────── │ Worker（工人） │──▶ 你的 processor
        └──────────────┘              └───────────────┘
```

- **Queue**：入队端。`queue.add(name, data, opts)` 把一个任务塞进 Redis。
- **Worker**：消费端。轮询/订阅 Redis，取到任务就执行你传入的回调；同一队列可以起多个 Worker、每个 Worker 也可以配 `concurrency`（同时取几个任务）。
- **Job**：一次任务 = 一份数据 + 配置（重试几次、失败怎么退避、完成后要不要留痕）。

### 2.2 项目里 BullMQ 到底注册在哪

先破一个直觉：**如果你去 `apps/server/src/main.ts` 里找 `new Queue` 会扑空**。main.ts 只负责 Nest 的 HTTP 装配（全局前缀、CORS、校验管道、Swagger）。三套队列都各自"长在"所属模块的 `*-queue.service.ts` 里，靠 Nest 生命周期钩子启动/关闭：

```ts
// apps/server/src/modules/research/report-queue.service.ts（全文骨架，注释即文档）
const QUEUE_NAME = 'report-generate';                     // 队列名 = Redis key 前缀

@Injectable()
export class ReportQueueService
  implements OnApplicationBootstrap, OnApplicationShutdown {   // 两个生命周期钩子

  private get connection() {
    return {
      host: this.configService.get<string>('REDIS_HOST', 'localhost'),
      port: this.configService.get<number>('REDIS_PORT', 6379),
      password: this.configService.get<string>('REDIS_PASSWORD') || undefined,
      maxRetriesPerRequest: null,   // BullMQ 必需：等待期间不限制重试
      retryStrategy: (times: number) => Math.min(times * 500, 5000), // 显式重连
    };
  }

  onApplicationBootstrap() {   // 应用启动完成后：建 Queue + Worker
    this.queue = new Queue(QUEUE_NAME, { connection: this.connection });
    this.worker = new Worker(
      QUEUE_NAME,
      async (job) => {                                   // 消费回调：真正干活
        await this.processor.processReport(job.data as ReportJobData);
      },
      { connection: this.connection, concurrency: 1 },   // 单并发：一份报告很重
    );
    this.worker.on('completed', (job) => this.logger.log(`研究报告任务完成: ${job.id}`));
    this.worker.on('failed', (job, err) =>
      this.logger.warn(`研究报告任务失败(重试后将再次执行): ${job?.id} → ${err.message}`),
    );
  }

  async addReportJob(data: ReportJobData): Promise<void> {
    await this.queue.add('generate', data, {            // 入队，job name 叫 'generate'
      attempts: 2,                                      // 总共尝试 2 次（= 失败重试 1 次）
      backoff: { type: 'exponential', delay: 3000 },    // 指数退避：3s → 6s → …
      removeOnComplete: true,                           // 成功后立刻从 Redis 清掉 job
      removeOnFail: 50,                                 // 失败保留最近 50 条（排查用）
    });
  }

  async onApplicationShutdown() {                        // 优雅停机：先停 worker 再关 queue
    await this.worker?.close();
    await this.queue?.close();
  }
}
```

逐点讲：

- **为什么用 `OnApplicationBootstrap` 而不是构造函数**：构造时 Nest 依赖还没全部就绪、Redis 可能还没连上；等应用启动完再建队列最稳。同理用 `OnApplicationShutdown` 优雅关闭——否则进程退出瞬间 worker 还拿着任务，会造成任务"被取走却没执行完"的悬挂。
- **连接配置里 `maxRetriesPerRequest: null` 是 BullMQ 硬性要求**：ioredis 默认在请求失败几次后拒绝后续命令，而 worker 要长时间挂着等任务，必须允许无限重试。`retryStrategy` 则保证 Redis 重启（注释里举例 WSL 冷启动后 docker 恢复）后 worker 能自动重连继续消费。
- **消费回调抛错 = 任务失败**：BullMQ 自动把 job 标记为 failed 并安排重试（如果没到 `attempts` 上限）。重试是**整份 job 重跑**——所以 processor 内部必须自己处理"这任务其实已经不想跑了"的情况（见第四节取消竞态）。

### 2.3 失败重试与延迟任务的参数对比

三套队列几乎同构，只是参数不同，对照着看更清楚：

| 队列（QUEUE_NAME） | 文件 | concurrency | attempts | backoff | removeOnFail |
|---|---|---|---|---|---|
| `report-generate` | research/report-queue.service.ts | 1 | 2 | 指数 3s | 50 |
| `agent-task` | research-agent/agent-queue.service.ts | 1 | 2 | 指数 3s | 50 |
| `document-process` | knowledge/document-queue.service.ts | 2 | 3 | 指数 2s | 100 |

Agent 队列还支持**延迟入队**——`startAt` 设在未来时，`create` 计算毫秒差传给 `addAgentJob(data, delayMs)`，队列把 job 放进 `delayed` 区，到点才被 worker 取走：

```ts
// agent-task.service.ts：创建任务
const delay = Math.max(0, startAt.getTime() - Date.now());
await this.queue.addAgentJob({ userId, taskId: task.id }, delay);
```

这就是 BullMQ 的 `delay` 选项：任务先睡在 Redis 的 delayed 有序集合里，时间到了自动进入等待队列。**调度未来的研究任务**零成本，不用自己写定时器。

### 2.4 Redis 里队列长什么样（实验 B 的答案）

Queue/Worker 是 Node 侧的对象，**真正的状态全在 Redis**。以 `report-generate` 为例，Redis 里会出现一组 `bull:report-generate:*` 键（BullMQ 默认前缀 `bull` + 队列名）：

```
redis-cli KEYS 'bull:report-generate:*'
# bull:report-generate:wait        ← 等待中的任务（list）
# bull:report-generate:active      ← 正在被 worker 处理的任务
# bull:report-generate:delayed     ← 延迟任务（Agent 定时启动在这）
# bull:report-generate:failed      ← 重试次数用尽/失败的任务（保留 50 条）
# bull:report-generate:events      ← 事件流（job 状态变化日志）
# bull:report-generate:1           ← 单个 job 的完整数据（hash：jobId 递增）
```

job hash 里存着 `data`（入队时传的 `{ userId, reportId }`）、`attemptsMade`（已尝试次数）、`timestamp` 等。这就是"任务持久化在 Redis"的字面含义——**进程重启、甚至把 Queue 对象删了重 new，任务都还在**，新 Worker 一上线就会接着消费。

> 排查提示：如果任务卡在"排队中"很久，先 `redis-cli KEYS 'bull:*'` 看 wait/active 里堆了什么，再 `HGETALL bull:report-generate:<id>` 看单条 job 的重试状态——比翻业务日志快得多。

### 2.5 为什么不用 @nestjs/bullmq 官方模块

Nest 官方有 `@nestjs/bullmq`（`@InjectQueue` 注入 + `@Processor` 装饰器），本项目却手写 `new Queue`/`new Worker`。原因在代码结构上很清楚：

1. 三套队列**都是同一套 10 行样板**，手写反而直观；
2. 队列生命周期（何时建、并发多少、失败策略）紧贴着各自模块的业务注释，集中在一个文件里好读；
3. 减少了依赖与装饰器魔法，processor 就是普通的 Injectable Service，单测时 mock 更直接。

技术选型上没高下之分，面试可以说：**"项目规模下手写样板比引入框架耦合更清晰；若队列数量与策略复杂到需要统一管理，再迁 @nestjs/bullmq 或独立的队列配置中心也不迟。"**

## 三、研究报告三步曲：拆解 → 并行检索撰写 → 汇总

### 3.1 第一步：创建接口"秒回"

`POST /api/research/reports` 只做四件事（`report.service.ts`）：

```ts
async create(userId: string, dto: CreateReportDto) {
  // ① 归属校验：knowledgeBaseIds 里的库必须都属于当前用户（防绑定他人库）
  const owned = await this.prisma.knowledgeBase.findMany({
    where: { id: { in: kbIds }, ownerId: userId },
    select: { id: true },
  });
  if (owned.length !== new Set(kbIds).size) {
    throw new NotFoundException('知识库不存在');   // 他人库 = 404，不泄露存在性
  }
  // ② 建一条 status=pending 的记录，并持久化检索范围（第 5 节细讲）
  const report = await this.prisma.report.create({
    data: {
      ownerId: userId,
      topic: dto.topic.trim(),
      kbScope: { scope: kbIds ? 'specific' : 'all', knowledgeBaseIds: kbIds ?? [] },
    },
  });
  // ③ 入队：worker 拿走 job.data 后会自己再查这条记录
  await this.queueService.addReportJob({ userId, reportId: report.id });
  return report;   // ④ 立刻返回 pending 记录
}
```

注意分工：**入队的数据只有 `userId + reportId` 两个 id，没有主题、没有内容**。真正干活时 processor 拿着 reportId 重新查库取最新数据——因为入队与执行之间隔着排队时间，任何"入队时快照"都可能过期（比如用户已经取消了）。

### 3.2 status 与 step：两个维度描述进度

数据库 `reports` 表用两个字段描述进度（详见 02 章 schema）：

| 字段 | 取值 | 含义 |
|---|---|---|
| `status` | `pending` → `processing` → `done` | 粗粒度：排着 / 干着 / 完了 |
| | `failed` / `cancelled` | 终态：失败了 / 被取消了 |
| `step` | 1 / 2 / 3 / 4 | 细粒度：拆解中 / 检索撰写中 / 汇总中 / 完成 |

前端 `Research.vue` 把二者组合成给人看的文案：

```ts
const progressText = computed(() => {
  switch (r.status) {
    case 'pending':   return '已提交，排队中...';
    case 'processing':
      if (r.step === 1) return '正在拆解研究问题...';
      if (r.step === 2) return '正在检索知识库资料并撰写章节...';
      if (r.step === 3) return '正在汇总成完整报告...';
      return '正在生成中...';
    case 'done':      return '已完成';
    // …
  }
});
```

### 3.3 处理器骨架：每一步之前先"抢锁"

`report-processor.service.ts` 的 `processReport()` 是整条管线的心脏。它的特殊之处在于**所有状态推进都通过一个条件更新函数 `advance()`**：

```ts
const ACTIVE = ['pending', 'processing'];   // 只有这两种状态算"活着"
// 所有状态推进都走 updateMany(status ∈ pending/processing)：
// 排队期间/生成中被取消 → 0 行匹配 → 立即中止，绝不覆盖 cancelled、不继续扣 token。
const advance = (step: number, extra: Prisma.ReportUpdateManyMutationInput = {}) =>
  this.prisma.report.updateMany({
    where: { id: reportId, ownerId: userId, status: { in: ACTIVE } },
    data: { status: 'processing', step, ...extra },
  });
```

先记住 `advance` 的样子，第四节取消竞态全靠它。现在按正常流程走一遍三步曲。

### 3.4 ① 拆解子问题（step 1）

```ts
// ① 拆解子问题（入口预检：排队期间已被取消 → 0 行，直接结束，不开始生成）
const claimed = await advance(1);
if (claimed.count === 0) {
  this.logger.log(`研究报告在排队期间已被取消，跳过生成: ${reportId}`);
  return;
}
const subQuestions = await this.splitTopic(target, report.topic);
await ensureRunning();
```

`splitTopic()` 是**第一次 LLM 调用**：让模型把用户的一句话主题拆成 **3~5 个具体的子问题**，只输出 JSON 字符串数组。

```ts
const raw = await this.complete(target,
  '你是研究规划助手。把用户的研究主题拆解为 3~5 个具体的子问题，覆盖该主题的主要方面，用于后续检索资料和分节撰写。只输出 JSON 字符串数组，如 ["子问题一","子问题二"]，不要任何其他内容。',
  `研究主题：${topic}`, 300);
try {
  const arr = JSON.parse(raw);
  if (Array.isArray(arr) && arr.length > 0) {
    return arr.map(String).map(s => s.trim()).filter(Boolean).slice(0, 5);
  }
} catch { /* fallthrough */ }
// 兜底：JSON 解析失败就按行拆分（去掉 "1." 之类序号），同样截 5 个
```

这里有两个很实用的健壮性设计：
- **要求模型"只输出 JSON"但从不信任它**：解析失败有按行拆分的兜底，宁可要"长句方向"也不能让任务崩掉；
- **`complete()` 里监控 `finish_reason === 'length'`**：输出撞到 `max_tokens` 上限说明内容被截断，打 warn 日志（弱点排查全靠它）。

### 3.5 ② 每个子问题：检索 + 撰写（step 2，并行）

拆出 3~5 个子问题后，进入最重的阶段。核心思想：**每个子问题独立成小节，小节之间互不依赖，可以并发**。

```ts
const sections: ReportSection[] = [];
const sourceMap = new Map<string, ReportSource>();   // 来源全局编号（见 3.6）
let cancelledEarly = false;
const CONCURRENCY = Math.min(3, subQuestions.length); // 最多 3 路并发

// 用"并发池"而不是 Promise.all：
// 取消后尚未启动的小节直接跳过（止损），已在跑的 LLM 调用无法硬断，跑完即止。
const worker = async () => {
  while (!cancelledEarly && nextSection < subQuestions.length) {
    const index = nextSection++;          // 取下一个子问题（线程安全：JS 单线程）
    const question = subQuestions[index];
    await ensureRunning().catch((e) => { cancelledEarly = true; throw e; });
    if (cancelledEarly) return;

    // 检索：知识库(限定范围，4 条) + 联网搜索 并行
    const [kbRows, webRows] = await Promise.all([
      this.ragService.retrieve(userId, question, this.scopeDocIds(report), 4),
      this.webSearchService.search(question, this.webResults),
    ]);

    // 检索期间可能收到取消：再查一次，取消则不再调用 LLM（LLM 花钱）
    await ensureRunning().catch((e) => { cancelledEarly = true; throw e; });
    if (cancelledEarly) return;

    // …为检索结果编 [来源N] 全局号（3.6）…
    const content = await this.writeSection(target, question, sources, webRows);
    if (cancelledEarly) return;           // 撰写期间被取消：丢弃本节，不写入结果
    sections.push({ index, question, content });
  }
};
await Promise.all(Array.from({ length: CONCURRENCY }, () => worker()));
sections.sort((a, b) => a.index - b.index);   // 并发写完了，按原顺序排回来
```

**为什么用并发池而不是 `Promise.all`？** 注释说得很明白：取消后"尚未启动的小节直接跳过（止损）"。`Promise.all` 会把所有子问题一次性全部启动，取消信号来了也只能等全部跑完——白烧 token；并发池让每个 worker 在启动下一节**之前**先检查取消标记，能停就停。

`writeSection()` 把检索到的知识库片段和网页资料拼进 prompt，让模型"看着资料写小节"，要求标注 `[来源N]`/`[网N]`，还带一道**质量门控**：

```ts
const looksThin =
  content.length < 80 ||                                   // 输出过短
  (hasKb && !content.includes('[来源')) ||                 // 有知识库资料却完全没引用
  (hasWeb && !content.includes('[网'));
if (looksThin) {                                          // 重写一次（限 1 次，控成本）
  content = await this.complete(target, '你是严谨的研究撰写助手。上次输出不合格…', user, max);
}
```

### 3.6 来源编号：一份报告内的"全局 Map"

每小节检索到的片段可能重复（两个子问题命中同一文档段落），但最终报告里的 `[来源N]` 必须**全局唯一、稳定对应**。做法是一个挂在整份报告生命周期上的 Map：

```ts
const sourceMap = new Map<string, ReportSource>();
// 每个片段：chunkId 出现过就复用老编号，没出现过就发一个新编号
const sources = kbRows.map((s) => {
  const existing = sourceMap.get(s.chunkId);
  const num = existing?.number ?? sourceMap.size + 1;   // 新来源 = 现有数量 + 1
  if (!existing) {
    sourceMap.set(s.chunkId, { number: num, documentId: s.documentId,
      chunkIndex: s.chunkIndex, filename: s.filename, similarity: s.similarity ?? 0 });
  }
  return { ...s, num };
});
```

- Map 的 key 是 `chunkId`（知识库里的分块，见 03 章）——**内容去重按块算**，同一段被引用两次也只占一个号；
- 编号是"现有数量 + 1"，**不按小节重置**——所以是全报告全局编号，正文、来源面板（`Research.vue` 里 `current.sources` 可点击跳原文）按号对得上；
- `ReportSource` 记录 `documentId + chunkIndex`，前端 `openSource()` 用这两个字段打开 `DocPreviewDrawer` 定位到原文段落——"报告可溯源"的产品卖点就是这么落地的。

### 3.7 ③ 汇总成完整报告（step 3）

最后把各小节拼成完整 Markdown。这里藏着一个**踩坑换来的教训**（代码注释完整记录了背景）：

```ts
/**
 * 组装完整报告：引言 / 结论由 LLM 单独写（短调用），正文直接拼各小节原文。
 * 背景：旧实现让模型一次"复述"整份报告（引言+全部小节+结论），输出上限一到就被截断
 * （实测报告 4.2k 字结尾断句、缺结论）。改成代码拼接后，正文绝不截断，只剩短段落有上限。
 */
private async assembleReport(...) {
  // 引言：一段 120~200 字（max_tokens 300）
  // 结论：一段 150~250 字（max_tokens 400）
  // 正文：代码拼接各小节，而不是让模型复述
  const body = sections.map((s) => `### ${s.question}\n\n${s.content}`).join('\n\n');
  return `# ${topic}\n\n## 引言\n\n${intro}\n\n${body}\n\n## 结论\n\n${conclusion}`;
}
```

**为什么不能整篇交给模型重写一遍？** 因为 LLM 的输出有 `max_tokens` 硬上限（本项目默认单次调用几档都是几百到几千 token）。报告正文可能 4k+ 字，让模型"把全部小节复述成一篇"必然在结尾被截断——引言正文结论都烂尾。改成**代码拼接**后：正文是检索撰写阶段逐节写好的原文，逐字保留；只有引言、结论这种短段落走 LLM，输出上限绰绰有余。这是"**能用代码做的事别让模型做**"的典型例子——模型只写增量（短段落），机器负责拼接（确定性强）。

### 3.8 落终态：done 的条件更新

```ts
const done = await this.prisma.report.updateMany({
  where: { id: reportId, ownerId: userId, status: { in: ACTIVE } },  // 关键：只认活状态
  data: {
    status: 'done', step: 4, content,
    tokensUsed: this.tokensUsed,                                     // 累计 token 落库（数据看板用）
    sections: JSON.parse(JSON.stringify(sections)),
    sources: JSON.parse(JSON.stringify([...sourceMap.values()].sort((a,b) => a.number - b.number))),
  },
});
if (done.count === 0) {   // 汇总完成前已被取消 → 放弃写入
  this.logger.log(`研究报告汇总完成前已被取消，放弃写入: ${reportId}`);
  return;
}
```

`sections`、`sources`、`kbScope` 都是 JSON 列（见 02 章），`JSON.parse(JSON.stringify(...))` 是 Prisma 写 JSON 前转纯 JSON 的通用习惯（避免类型不兼容）。`tokensUsed` 是本份报告消耗的总 token——`complete()` 每次调用都 `this.tokensUsed += total`，从 usage 里取 `total_tokens`。

至此正常流程走完。但上面反复出现的 `advance`、`ensureRunning`、`count === 0 就 return` 到底在防什么？下一节是本章的"题眼"。

## 四、取消竞态：谁也别想覆盖"已取消"

### 4.1 竞态从哪来

一份报告有两个"写入者"：

- **HTTP 层**（`cancel` 接口）：用户点取消 → 立刻把 `status` 改成 `cancelled`；
- **Worker 层**（processor）：在后台一步步推进 `pending → processing(step1/2/3) → done`，随时可能写 `failed`。

两者**没有任何同步关系**，全靠数据库里的状态字段协调。如果 processor 傻乎乎地无条件 `update`，会发生什么？

```
t0  用户点取消 → HTTP 把 status 改成 cancelled ✓
t1  worker 正在写第 3 个小节的 LLM 调用（无法硬断，只能等它跑完）
t2  这个 LLM 调用刚花完钱返回 → worker 照常推进：update status = processing, step++
     → cancelled 被覆盖成 processing！用户看到"又活了"
t3  worker 跑完全部 → update status = done
     → 一份用户明确取消的报告，最终显示"已完成"，还烧掉了取消后的所有 token
```

这就是经典的**读写竞态（check-then-act 失效）**：worker 在 t0 之前读过一次状态是 processing，之后的操作基于过期认知。HTTP 和 worker 之间隔着网络与事件循环，谁先谁后完全不可控。

### 4.2 解法：把"检查+写入"合并成一条条件 SQL

检查与写入分开就会竞态，那就**让数据库在一条语句里同时做检查与写入**——`updateMany` 的 `where` 就是检查：

```ts
// 只有 status 仍然 ∈ {pending, processing} 的行才允许更新
// 用户取消后 status = cancelled → where 匹配 0 行 → 什么都不改 → count = 0
this.prisma.report.updateMany({
  where: { id: reportId, ownerId: userId, status: { in: ACTIVE } },
  data: { status: 'processing', step, ... },
});
```

PostgreSQL 对单条 UPDATE 是原子加锁的，`WHERE` 判定与写入之间不可能插入别的更新——**要么这一行状态还是活的，被推进；要么它已经被取消/删除，0 行匹配，整个推进作废**。不存在"先读到活的、写的时候已经被取消"的窗口。

这套机制在本项目代码里就是 `advance()` 和最后的 `done` 更新：**所有推进状态都走 `updateMany + where status in ACTIVE`，谁推进谁自己先过条件**。取消（HTTP 层）只是把状态改成 `cancelled`，它不需要锁——因为"置取消"永远生效，而"推进"必须赢过条件才能生效。

### 4.3 三个检查点：把取消损失压到最小

光有原子门控还不够：worker 可能在一段很长的 LLM 调用中才收到取消，这段调用已经烧钱。所以还要在**调用 LLM 之前**插入轻量检查，能省一笔是一笔：

```ts
const ensureRunning = async () => {
  const cur = await this.prisma.report.findUnique({
    where: { id: reportId },
    select: { status: true },
  });
  if (!cur || cur.status === 'cancelled') {        // 被取消或已被删除
    const e = new Error('报告已被用户取消') as Error & { cancelled?: boolean };
    e.cancelled = true;                            // 打标记：不是真失败
    throw e;
  }
};
```

然后按"花钱密度"布置检查点：

| 检查点 | 位置 | 止损效果 |
|---|---|---|
| ① `advance(1)` 入口预检 | 拆解前 | 排队期取消 → 0 行 → 一个 LLM 调用都不发 |
| ② `ensureRunning()` | 拆解后、每节检索前、检索后 | 检索阶段取消 → 不再调用撰写 LLM |
| ③ `ensureRunning()` + 并发池轮询 | 每节启动前 | 未启动的小节直接跳过（3.5 已讲） |
| ④ `done` 条件更新 | 汇总后 | 汇总期间取消 → 0 行 → 放弃写入 |

配合并发池结构，取消的最坏代价是：**已经在途的那一两个 LLM 调用跑完即止**（无法硬断 HTTP 请求），之后一节不跑、一个字不写。

### 4.4 三种取消时机的完整走查

**场景 A：排队期取消**（status 还是 pending，worker 还没轮到它）
1. `cancel` 接口：pending ∈ 可取消集合 → status = `cancelled`；
2. worker 终于取到 job，`advance(1)` 的 where 匹配 0 行；
3. 打日志"排队期间已被取消，跳过生成"，**不产生任何 LLM 调用**。

**场景 B：生成中取消**（status = processing，正跑 step2）
1. `cancel` 接口 → status = `cancelled`；
2. worker 的下一个 `ensureRunning()` 查到 cancelled → 抛带 `cancelled` 标记的错；
3. 各 worker 置 `cancelledEarly = true`，未启动小节跳过；在途调用跑完返回后被丢弃；
4. 外层 catch 看到 `err.cancelled`，只打日志不落库（见下）。

**场景 C：汇总完成后才点取消**（status 已经 done）
1. `cancel` 接口检查 `!['pending','processing'].includes(status)` → 直接抛 400"当前状态不可取消（仅生成中可取消）"；
2. 前端按钮只在 `generating`（pending/processing）时出现，也到不了这一步。

### 4.5 取消 ≠ 失败：catch 里的判别

processor 最外层 catch 要区分"真失败"和"用户取消"，否则会把 cancelled 覆盖成 failed：

```ts
} catch (err) {
  // P1-4：用户主动取消 → 不覆盖成 failed（cancel 接口已置 cancelled）
  if ((err as Error & { cancelled?: boolean }).cancelled) {
    this.logger.log(`研究报告已被用户取消: ${reportId}`);
    return;                                    // 什么也不写，cancelled 保留
  }
  this.logger.warn(`研究报告失败: ${reportId} → …`);
  await this.prisma.report.update({
    where: { id: reportId },
    data: { status: 'failed', error: (err as Error).message, tokensUsed: this.tokensUsed },
  });
}
```

同理，`advance()` 返回 0 行时的提前 `return`，本质上也是"不覆盖 cancelled"。**两条防线叠加**：条件更新的原子门控负责"写不进去"，catch 判别负责"就算异常也要尊重 cancelled"。

顺带一提，delete（删除报告）与 cancel 走的是同一套防线：报告被删后 `ensureRunning()` 查不到记录（`!cur`）同样抛 cancelled 标记错误、所有 updateMany 0 行——所以**生成中删掉报告也不会让 worker 把记录写回来**（Prisma 删行后任何按 id 的 update 都是 0 行）。

## 五、kbScope：把"检索范围"钉在报告上

### 5.1 问题背景：失败的报告重试，为什么不能退化成全库

报告生成有两个可选"检索范围"（前端单选）：
- **全部知识库**：检索该用户所有库；
- **指定知识库**：只检索勾选的几个库。

早期版本只在创建请求里用一下范围，没存库。于是出现一个怪 bug：用户针对"库 A"生成报告失败 → 点"重新生成" → 检索范围丢了 → worker 按**全库**检索 → 报告里混入库 B、库 C 的内容。用户：**"我明明只选了 A，报告里怎么有 B 的内容？"** 这就是注释里写的 P1-7：失败重试"退化全库"。

修复思路很朴素：**创建时把范围当数据存下来，失败重试时原样回填**。

### 5.2 存储：`kbScope` JSON 列

`reports` 表加了一个 JSON 列 `kb_scope`，schema 注释写着设计意图：

```prisma
kbScope Json? @map("kb_scope")
// 创建时的检索范围 { scope: 'all'|'specific', knowledgeBaseIds?: [] }（失败重试回填用）
```

创建时写入（3.1 已见）：

```ts
kbScope: {
  scope: kbIds ? 'specific' : 'all',
  knowledgeBaseIds: kbIds ?? [],
},
```

### 5.3 读取：worker 执行时用它限定检索

processor 每次检索前把 JSON 解出来，转成"限定文档 id 列表"：

```ts
/** 从 report.kbScope 取限定检索的文档范围（specific 无 ID 时退化为全库） */
private scopeDocIds(report: { kbScope: unknown }): string[] | undefined {
  const scope = (report.kbScope ?? null) as { scope?: string; knowledgeBaseIds?: string[] } | null;
  if (scope?.scope === 'specific' && scope.knowledgeBaseIds?.length) {
    return scope.knowledgeBaseIds;      // 指定库：返回 id 数组给 ragService.retrieve
  }
  return undefined;                     // 全库：返回 undefined（检索时不过滤）
}
```

然后每节检索都带着范围：`this.ragService.retrieve(userId, question, this.scopeDocIds(report), 4)`。**范围与任务同生共死**——失败重试重跑的是同一份 job（同一 reportId），读到的还是同一份 kbScope，自然精确回填，永不退化。

### 5.4 前端：失败报告"重新生成"即原样重发

`Research.vue` 的 `handleRetryFailed()` 不是把旧报告原地复活，而是**用旧报告的字段重新走一遍创建**：

```ts
async function handleRetryFailed() {
  const r = current.value;
  topic.value = r.topic ?? '';
  // 回填失败时记录的检索范围（旧报告无 kbScope 时按全库兜底）
  const ks = r.kbScope;
  if (ks) {
    scope.value = ks.scope === 'specific' ? 'specific' : 'all';
    pickingKbIds.value = ks.scope === 'specific' ? [...(ks.knowledgeBaseIds ?? [])] : [];
  } else {
    scope.value = 'all'; pickingKbIds.value = [];
  }
  await openKbs();
  void handleCreate();      // 直接重新提交 → 新报告 + 新队列任务
}
```

配套的两个防呆细节：前端"指定知识库"模式下**必须至少勾一个库**才允许提交（防直发空数组 = 全库，语义不符）；后端 DTO 校验 `knowledgeBaseIds` 每个都必须是 UUID，且 create 时做归属校验。范围与权限在两端都钉死。

## 六、自主研究 Agent：从"报告"到"Agent"

研究报告解决了"给定主题产出一篇结构化综述"，但它是**一次性、无反馈**的。自主研究 Agent 更进一步，它是**限时·限量·可交互的自主研究系统**（`agent-runner.service.ts` 顶部注释原话）：

> 流程：初始化方向（定向=拆解目标；开放=从知识库挖掘）→ 各方向并行自主推进（生成搜索词 → 联网搜索 → 摘要预筛 → 精读正文 → 提炼笔记），共享 token 预算盒与停止标记 → 全部完成或停止时，把各方向笔记撰写成 Markdown 报告（含来源）。
> 停止三条件（用户锁定规则）：token 预算用尽永远停；否则用户设定的结束时间到了就停；用户手动停止随时生效。

### 6.1 Agent 比报告多了什么（对比表）

| 维度 | 研究报告（Research） | 自主研究 Agent（ResearchAgent） |
|---|---|---|
| 输入 | 主题（topic）+ 可选知识库范围 | 模式（定向/开放）+ 目标 + **token 预算** + **时间窗** |
| 拆解 | 3~5 个子问题，直接开跑 | 8~10 个方向 → **停下等用户确认**（可挑选 1~5 个） |
| 研究手段 | 每节：知识库检索 + 1 次联网搜索 + 1 次撰写 | 循环：生成搜索词→搜索→预筛→精读→提炼笔记，每方向最多 8 轮 |
| 约束 | 无硬约束（靠单次 max_tokens 限长） | **共享预算盒**（总 token 用尽即停）+ **结束时间**（到点即停） |
| 中断 | 只能取消（cancelled，不可恢复） | 手动停止后**保留阶段成果**，可续时/加预算**从断点续跑** |
| 产出 | 一次性完整报告 | 各方向研究笔记 → 润色成正式报告；任何停止都交付"阶段性报告" |
| 消费主体 | 用户默认模型配置（BYO） | 同左（BYO 强依赖） |

一句话：**报告是"一次性的批处理"，Agent 是"有预算、有时间、可中断、可续跑的研究进程"**。

### 6.2 创建：预算与时间窗的边界

`CreateAgentTaskDto` 定义了用户能设的边界（常量名要背下来）：

```ts
export const AGENT_BUDGET_MIN = 10_000;    // 最少 1 万 token
export const AGENT_BUDGET_MAX = 500_000;   // 单档最多 50 万 token（前端档位：快速10万/标准20万/深度30万/自定义）
// DTO：tokenBudget @Min(AGENT_BUDGET_MIN) @Max(AGENT_BUDGET_MAX)
```

`agent-task.service.ts` 创建时做三件事：校验（定向必须有 goal、时间窗合法）、**按预算预填结束时间**、按 startAt 决定是否延迟入队：

```ts
/** 预算 → 预估研究时长（分钟）：10万≈40 分钟，线性外推，封顶 6 小时 */
export function estimateMinutes(tokenBudget: number): number {
  return Math.min(360, Math.round((tokenBudget / 100_000) * 40));
}

// 未传结束时间 → 按预算预填；用户始终可以在前端改
const endAt = dto.endAt
  ? new Date(dto.endAt)
  : new Date(startAt.getTime() + estimateMinutes(dto.tokenBudget) * 60_000);
```

另外任务总预算（含续时追加）封顶 100 万 token：`const AGENT_TOTAL_BUDGET_MAX = 1_000_000`（`extend` 时 `Math.min(旧预算+追加, 100万)`）。这些上限都是为了**防止单个用户把队列和上游 API 打到失控**——BYO 模式下虽然 token 用户买单，但队列资源与外部 API 配额是全平台共享的。

### 6.3 状态机：用户确认是分水岭

Agent 比报告多一个中间态 `awaiting_confirm`。完整状态机（前端 `types/research-agent.ts` 与后端 Service 一致）：

```
               创建（预算+时间窗+目标）
                      │
                      ▼
              ┌── pending（排队中）────────────┐
              │                                │  startAt 在未来 → 延迟入队
              ▼                                ▼
       worker 开跑 → running ──────────────► 等开始时间（每 15s 醒一次检查）
              │
              ▼ 方向拆解完成（8~10 个方向）
     ┌─ awaiting_confirm（待确认：停下等用户挑方向）
     │        │ 用户确认（可只选 1~5 个方向）
     │        ▼
     │   pending（重新入队）→ running → 各方向自主推进
     │        │
     │        ├─ 预算耗尽 / 到结束时间 / 手动停止 ──► stopped（保留阶段成果）
     │        │        └─ 续时/加预算（extend）→ pending 重新入队（断点续跑）
     │        └─ 所有方向研究完 ──► done（stopReason=completed）
     │
     │   （awaiting_confirm 时点"停止"= 取消：stopReason=cancelled）
     └── 任意时刻失败 → failed（stopReason=error，BullMQ 会重试一次）
```

两个关键点：
1. **pending 这个状态被复用了两次**：首次创建后排队、以及确认/续跑/重新拆解后重新入队，都是 pending——worker 入口不区分"首跑"与"续跑"，全靠 `progress` 断点（见 6.6）；
2. **awaiting_confirm 期间 job 其实已经 completed 了**：runner 拆完方向、把状态置 awaiting_confirm 就 `return`，BullMQ 认为这个 job 干完了。等用户 confirm 再 `addAgentJob` 重新入队。**队列 job 的生命周期 ≠ 业务任务的生命周期**——业务状态永远以数据库为准，队列只是"执行引擎"。

### 6.4 方向从哪来：定向拆解 vs 开放挖掘

`agent-runner.service.ts` 按 mode 分支初始化方向：

```ts
const dirs = task.mode === 'open'
  ? await this.mineDirections(target, taskId, userId, budget, stop)   // 开放：从知识库挖
  : await this.splitDirections(target, taskId, task.goal ?? '', budget, stop); // 定向：拆目标
```

- **splitDirections（定向）**：LLM 把研究目标拆成 **8~10 个方向**（比报告的 3~5 个子问题多，因为要覆盖全面、给用户挑选空间），每项 `{title, question}`，只输出 JSON；
- **mineDirections（开放）**：用户没给目标，就从用户知识库取主题样本（最多 10 个库名 + 最近 24 个 chunk 各 150 字当种子），让 LLM 从"知识库关心什么"出发挖掘方向；知识库为空则退到 AI/效率/行业趋势等通用主题。

两者共用一个**解析失败兜底**（`splitDirections` 尾部注释写得很细）：

```ts
const dirs = this.parseDirections(res?.text ?? '');
if (dirs.length) return dirs;
// 解析失败兜底（仅当预算未耗尽）：把目标本身作为唯一方向继续研究，
// 而不是误报"预算不足"——否则用户追加预算重跑也永远卡在同一处
if (!budget.exhausted && !stop.flag) {
  this.logger.warn(`方向拆解解析失败，回退为单一方向: ${taskId}`);
  return [{ title: goal.slice(0, 20) || '自主研究', question: goal }];
}
return [];
```

为什么宁可退化成"目标本身当方向"也不能空手返回？看外层逻辑：`dirs.length === 0` 时 runner 会 `finish(..., '研究未启动…')` 并说明是"预算不足/时间到"。如果解析失败也返回空，用户会看到"预算不足"的误导提示，追加预算重跑**还是卡在同一处解析失败**——死循环。解析失败是 LLM 的问题，不是预算的问题，所以要区分对待。

### 6.5 确认、重拆、续时：三个交互入口

**confirm（确认方向）** —— 用户挑方向后开始研究。代码里有个漂亮细节：选中部分方向时，**直接按下标过滤 progress 断点**，只保留选中的方向，其余方向从断点数据里丢弃：

```ts
if (dto.directionIndexes?.length) {
  const dirs = ((raw?.progress ?? null) as { directions?: unknown[] } | null)?.directions;
  // …校验下标合法、数量 1~5…
  data.progress = JSON.parse(JSON.stringify({ directions: idxs.map((i) => dirs[i]) }));
}
await this.prisma.agentTask.update({ where: { id }, data });   // awaiting_confirm → pending
await this.queue.addAgentJob({ userId, taskId: id });          // 重新入队
```

**redecompose（重新拆解）** —— 对拆解结果不满意？清空断点重新入队：

```ts
data: {
  status: 'pending',
  progress: Prisma.DbNull,     // 断点清空 → runner 会重新拆解
  directions: Prisma.DbNull, searchRounds: 0, pagesRead: 0,
  stopReason: null, error: null,
}
```

注意"重新拆解会**再消耗一次拆解 token**"——前端待确认卡片上就写着这句提示（`ResearchAgent.vue`），诚实告知成本。

**extend（续时/加预算）** —— 只在 `stopped` 状态可用（预算耗尽/时间到/手动停止后），已完成或失败（stopReason=completed/error）的不能续：

```ts
if (task.status !== 'stopped') throw new BadRequestException('只有已停止的任务才能续时/加预算');
if (task.stopReason === 'completed' || task.stopReason === 'error') throw new BadRequestException('已完成或失败的任务不能续时');
const newBudget = Math.min(task.tokenBudget + extraTokens, AGENT_TOTAL_BUDGET_MAX);   // 100万封顶
const newEndAt = new Date(new Date(task.endAt).getTime() + extraMinutes * 60_000);    // 单次≤720分钟
// status 回 pending、stopReason/finishedAt/error 清空 → 重新入队续跑
```

### 6.6 progress：对外只露元信息，断点藏在内里

`AgentTask` 的 `progress` JSON 是**续跑断点**（schema 注释）：

```ts
interface AgentProgress {
  directions: Array<{
    title: string; question: string;
    status: 'pending' | 'active' | 'done';   // 方向级状态（前端进度卡片的依据）
    rounds: number;                          // 已研究轮数
    searchTerms: string[];                   // 用过的搜索词（防重复）
    readUrls: Array<{ url: string; title: string }>;  // 已精读 URL（续跑去重）
    notes: string;                           // 研究笔记（越积越长）
    sectionContent?: string;                 // 已缓存的小节正文（续跑不重复生成，省 token）
  }>;
}
```

但 `PublicAgentTask`（返回前端的结构）只映射其中四个字段：`{ title, question, status, rounds }`。`agent-task.service.ts` 的 `toPublic()` 注释写明原因：

```ts
/** 给前端的任务结构（progress 只暴露方向元信息，内部断点不外泄） */
```

**为什么不外泄 notes/readUrls？** 因为 `notes` 是给 LLM 续跑用的"私人工作记忆"，动辄几千字，前端既不需要也容易把报告剧透；接口面越小，改动断点格式越自由（内部随便重构，不破坏 API 契约）。后端隐藏复杂度、前端只拿展示数据，是长任务系统的常见分层。

## 七、预算盒与预算互斥：成本安全的最后一道锁

Agent 的"预算"不只是展示用的，它是**运行时的硬约束**。实现上是三个配合的组件：`BudgetBox`（账本）、`BudgetMutex`（互斥锁）、`StopFlag`（全局停止标记）。

### 7.1 BudgetBox：所有方向共用一个账本

```ts
/** 共享预算盒：所有方向的 LLM 调用都从这里扣 token */
class BudgetBox {
  used = 0;
  constructor(readonly limit: number) {}
  get exhausted(): boolean { return this.used >= this.limit; }
  spend(totalTokens: number) { this.used += totalTokens; }
}
```

每次 LLM 调用返回后 `box.spend(usage.total_tokens)`，一旦 `used >= limit`，`exhausted` 为 true——研究循环的 while 条件直接把它当刹车。注意**各方向共享一个 box**：10 个方向不是各分一份预算，而是抢同一份，谁先用完谁触发全局停。这正是"总预算"语义：用户说 10 万 token，就是总共 10 万，不管几个方向。

### 7.2 BudgetMutex：为什么 LLM 调用必须串行

如果让方向们**完全并行**地去花预算，会出现经典超支问题：

```
预算剩 3k token，5 个方向同时各发起一个 4k token 的调用
→ 5 个都通过"used < limit"检查（检查时谁都没花）
→ 5 个全部发出 → 实际超支 5 × 4k
```

所以代码把所有 LLM 调用塞进一把**链式 Promise 互斥锁**：

```ts
/** 预算互斥锁：LLM 调用是唯一消耗 token 的操作，串行扣费保证预算精确。
 *  各方向并发跑在"搜索/正文提取"（不耗 token）上，只在 LLM 调用处排队；
 *  预算用尽时最多一个在途调用（约 1~4k token 的软超支），而不是整批并发超支。 */
class BudgetMutex {
  private chain: Promise<void> = Promise.resolve();
  async run<T>(fn: () => Promise<T>): Promise<T> {
    let release!: () => void;
    const next = new Promise<void>((r) => (release = r));
    const prev = this.chain;
    this.chain = prev.then(() => next);   // 把"释放"接在队尾：新的 run 必须等前面的完成
    await prev;                            // 等前面的锁释放
    try { return await fn(); } finally { release(); }
  }
}
```

`llmCall()` 在锁内做"检查预算 → 真正请求 → 扣费"：

```ts
return this.mutex.run(async () => {
  // 组装调用（ignoreStop=true）只看组装预算；研究调用还看停止标记
  if (box.exhausted || (!ignoreStop && stop?.flag)) return null;  // 锁内再查一次预算！
  const res = await client.chat.completions.create({ … });
  const total = …usage 合计…;
  box.spend(total);
  this.tokenCounter.total += total;
  // 研究预算用尽 → 立即触发全局停止（用户锁定规则：token 用完永远停）
  if (box.exhausted && !ignoreStop && stop) {
    stop.flag = true; stop.reason = 'budget_exhausted';
  }
  …
});
```

**为什么检查必须挪到锁内？** 锁外检查（7.2 开头那种）在并发下必然竞态；锁内检查 + 锁内扣费，同一时刻只有一个调用在途，**软超支最多等于一次调用的量**（注释估 1~4k token）。代价是 LLM 调用串行会慢一些，但换来了"预算像银行账户一样精确"。这是一个教科书级的"**一致性 vs 吞吐**"取舍：搜索、网页提取这些不花钱的步骤照常并发；只有花钱的步骤排队。注释原话："各方向并发跑在搜索/正文提取上，只在 LLM 调用处排队"。

> 面试可以这样讲：**"预算控制不能靠'调用前看一眼'，因为并发下检查与扣费之间会竞态。我用一把 Promise 链互斥锁把'查预算→请求→扣费'做成临界区，多方向并发只在免费步骤上发生，花钱的 LLM 调用严格串行，超支被压到一次调用以内。"**

### 7.3 停止标记与"研究未启动"的诚实收尾

```ts
interface StopFlag {
  flag: boolean;
  reason: 'budget_exhausted' | 'time_exhausted' | 'user_stopped' | '';
}
```

`researchDirection` 的 while 条件把三个约束放在一起：`!stop.flag && !budget.exhausted && Date.now() < endAtMs`——任一不满足就退出方向循环。方向拆解阶段如果因为预算/时间已经耗尽而拆不出方向，`splitDirections` 返回空数组，runner 不假装成功，落一段如实说明（6.4 讲过）；`processTask` 里还有专门分支处理"排队太久，时间窗已过"（P1-2，第 8.5 节展开）。

### 7.4 ASSEMBLY_BUDGET：给"收尾成稿"单独留钱

这是整个 Agent 设计里最人性化的一个常量：

```ts
/**
 * 独立"报告组装预算"（token）：与用户设定的研究预算分开，专门用于把研究笔记
 * 润色成正式报告（引言/结论/小节撰写）。任何停止（预算/时间/手动）都会先花这笔钱
 * 把正式报告交付——用户不需要追加 token 才能拿到报告；研究预算的停止规则不变。
 */
const ASSEMBLY_BUDGET = 12000;
```

启动时开两个独立的 Box：

```ts
const budget = new BudgetBox(task.tokenBudget);
budget.spend(task.tokensUsed);            // 续跑：已消耗部分计入研究预算
const assembly = new BudgetBox(ASSEMBLY_BUDGET);  // 组装预算独立于研究预算
```

**为什么要独立？** 假设没有这笔钱：用户研究预算用完 → 立即停 → 手里一堆零散笔记，但没有预算把它们润色成报告 → 用户必须"继续研究"追加预算才能看到正式报告。体验上像"饭都吃完了才告诉你还要加钱才能上甜点"。独立预算保证：**无论研究怎么停（预算/时间/手动），系统都预留 1.2 万 token 把笔记整理成可交付的报告**。组装调用走 `assembleCall()`，`ignoreStop = true`——它不理会研究停止标记，只看自己的组装盒：

```ts
private async assembleCall(…, assembly: BudgetBox) {
  return this.llmCall(target, taskId, system, user, maxTokens, assembly, null, true); // ignoreStop=true
}
```

前端展示也呼应这个设计（`ResearchAgent.vue`）：

```ts
// 总预算展示：tokenBudget + 12000（与后端 ASSEMBLY_BUDGET=12000 保持一致）
{{ fmtTokens(current.tokenBudget + 12000) }}
// P2-9：进度分母 = 研究预算（tokenBudget）——整理报告的固定 12k 是收尾阶段，
// 混进分母会让研究进度天然偏慢（研究 10 万 + 整理 1.2 万 ≈ 偏慢 12%）
```

进度条分母是研究预算、展示总额含整理 12k——**同一个数字，两处口径各取所需**，注释把原因写清楚了。

组装阶段的执行顺序也按"最坏情况也能交付"设计（`assemble()` 内）：① 执行摘要（优先级最高，先摘要后展开，预算哪怕只剩一点也要先出摘要）→ ② 结论（用户明确要求必须有）→ ③ 引言 → ④ 按笔记量从多到少逐方向润色小节；**组装预算不够润色的方向，正文直接拼原始研究笔记**——报告结构始终完整（有主题/摘要/引言/结论），只是某些小节朴素一些。

### 7.5 其他防失控常量

```ts
/** 单个方向最多研究轮数（防止 LLM 判断失灵无限循环） */
const MAX_ROUNDS_PER_DIRECTION = 8;
/** 单个方向最少精读页数：模型喊"资料足够"结束方向前，必须至少精读这么多页，
 *  防止方向草草了事（只搜一轮、笔记为空就"完成"）。 */
const MIN_READS_PER_DIRECTION = 3;
```

- **8 轮上限**：`nextQuery()` 让 LLM 决定"下一个搜索词还是够了"，但 LLM 可能抽风永远说"再搜一个"——`rounds >= 8` 硬性转 done；
- **3 页下限**：反过来，模型可能偷懒第一轮就喊"资料够了"——`readUrls.length < 3` 时强制再来一轮（最多到第 7 轮兜底，防止"模型持续喊停→我持续强制→死循环"）。一头防贪、一头防懒，都是对付同一个不可靠组件（LLM 自主决策）的护栏。

## 八、停止语义与断点续跑

### 8.1 三种停止条件，各自的收尾

停止入口有三个（`agent-task.service.ts` + runner）：

| 触发者 | stopReason | status | 说明 |
|---|---|---|---|
| 用户点停止（running 中） | `user_stopped` | `stopped` | stop 接口先落状态，runner 在检查点感知 → 补写阶段报告 |
| 用户点停止（还没开跑） | `cancelled` | `stopped` | pending/awaiting_confirm 时停止 = 取消，**不会产出报告** |
| 时间到（endAt） | `time_exhausted` | `stopped` | runner 各方向 while 条件自动退出；**跑完会补报告** |
| 预算耗尽 | `budget_exhausted` | `stopped` | 锁内扣费后 `used >= limit` 置 stop.flag → 全局收尾，**会补报告** |
| 全部方向完成 | `completed` | `done` | 无停止标记的分支 |
| 异常 | `error` | `failed` | 外层 catch，updateMany where running 防覆盖 |

stop 接口的代码把"没开跑"和"跑着"区分开：

```ts
async stop(userId: string, id: string) {
  const task = await this.findOne(userId, id);
  if (!['pending', 'running', 'awaiting_confirm'].includes(task.status)) {
    throw new BadRequestException('任务已结束，无法停止');
  }
  const notStarted = task.status === 'pending' || task.status === 'awaiting_confirm';
  await this.prisma.agentTask.update({
    where: { id },
    data: {
      status: 'stopped',
      stopReason: notStarted ? 'cancelled' : 'user_stopped',
      finishedAt: new Date(),
    },
  });
  return this.findOne(userId, id);
}
```

注意：**手动停止（running 时）只是把状态置 stopped，runner 自己并不知情**。runner 通过 `isRunning()` 轮询感知——每个方向每轮循环开始都查一次：

```ts
/** 任务是否仍在运行（被手动停止/删除 → false） */
private async isRunning(taskId: string): Promise<boolean> {
  const t = await this.prisma.agentTask.findFirst({ where: { id: taskId }, select: { status: true } });
  return !!t && t.status === 'running';
}
```

查到不是 running → `stop.flag = true; stop.reason = 'user_stopped'; break;`——然后进入收尾组装（用组装预算），把已经攒下的笔记整理成报告，用不带状态条件的 `updateMany` 补写报告/来源/进度（状态已由 stop 接口置好，runner 只补内容）：

```ts
} else if (stop.reason === 'user_stopped') {
  // 用户已把 status 置为 stopped（stop 接口），这里只补写报告/来源/进度，不动状态
  // （updateMany：任务若已被删除则 0 行匹配，不报错）
  await this.prisma.agentTask.updateMany({
    where: { id: taskId },
    data: { report, summary,
      sources: sources ? JSON.parse(JSON.stringify(sources)) : null,
      progress: JSON.parse(JSON.stringify(progress)) },
  });
}
```

### 8.2 等开始时间：15 秒醒一次的"睡美人"

`startAt` 设在未来时，runner 不是傻等——每 15 秒醒来查一次任务是否还在 running（用户可能已停止/删除）：

```ts
// ① 等开始时间（startAt 设在未来时；等待期间可手动停止/删除）
while (Date.now() < new Date(task.startAt).getTime()) {
  await sleep(15_000);
  const t = await this.prisma.agentTask.findFirst({ where: { id: taskId, ownerId: userId } });
  if (!t || t.status !== 'running') return;   // 已被停止/删除
  task = t;
}
```

睡醒后发现"已经过了 endAt"？直接按时间到收尾（8.5 的说明性报告）：

```ts
if (Date.now() >= endAtMs) {
  // 排队太久导致时间窗已过：直接按"时间到"收尾（无成果）——
  // report 给说明而非 null，前端才不会无限轮询（P1-2）
  await this.finish(taskId, 'time_exhausted', 'stopped',
    '# 研究未启动\n\n排队时间过长，到达设定的结束时间时任务仍未开始，已自动结束。…', [], null, null, null);
  return;
}
```

### 8.3 断点续跑：从哪停，就从哪接着干

"续跑"不是玄学，是 `progress` 断点 + runner 入口"不区分首跑续跑"的组合。启动时恢复现场：

```ts
const budget = new BudgetBox(task.tokenBudget);
budget.spend(task.tokensUsed);        // 已用部分从新预算里扣掉（新预算 = 旧预算 + 追加）
this.tokenCounter = { total: task.tokensUsed };
const counters = { searchRounds: task.searchRounds, pagesRead: task.pagesRead }; // 计数器续上
```

读取 progress 后，`researchDirection` 开头两行就是续跑逻辑：

```ts
if (dir.status === 'done' || dir.sectionContent) return;  // 断点续跑：已完成方向跳过
```

方向循环内部，续跑时：
- **已精读 URL 不再重读**：`readUrls` 集合过滤搜索结果 `const fresh = results.filter(r => !readUrls.has(r.url))`；
- **已写小节正文直接复用**：`dir.sectionContent` 命中就跳过润色（注释"续跑不重复生成，省 token"）；
- **被打断的方向**回到 pending：`if (dir.status === 'active') dir.status = 'pending'`——下次续跑接着研究；
- **提炼笔记成功才记为已精读**：`extractNotes` 返回 true 才 `dir.readUrls.push(...)`——中途被打断的页面（预算/时间/手动）续跑时会**重新精读补齐笔记**，而不是丢内容（代码注释原话）。

断点保存时机是"每轮精读后"（`saveProgress` 无条件更新 progress + 计数器，不动状态）。所以即使进程在这一刻崩溃，最多丢一轮进度。

### 8.4 终态落法统一走 finish（条件更新）

预算耗尽/时间到/完成的收尾都走 `finish()`，它再次使用条件更新防覆盖：

```ts
/** 落终态（条件更新：仅在任务仍处于 running 时生效，避免覆盖用户手动停止/续跑状态） */
private async finish(taskId, stopReason, status, report, sources, progress, summary, error) {
  await this.prisma.agentTask.updateMany({
    where: { id: taskId, status: 'running' },   // 只认 running！
    data: { status, stopReason, finishedAt: new Date(), report, summary,
      sources: …, progress: …, error },
  });
}
```

**为什么 finish 也要条件更新？** 因为 worker 从"决定收尾"到"执行收尾"之间还有时间窗口：用户可能恰好在这时点停止（把状态改成 stopped）、或续时（把状态改成 pending 重新入队）。如果 finish 无条件写，会把用户刚置的 stopped 覆盖成 done，或把续跑状态覆盖掉。`where status = 'running'` 保证：**只有任务确实还在 running 时，收尾才生效**——否则 0 行，静默让位给用户操作。

### 8.5 无成果时：给"说明"，不给 null（P1-2）

如果任务在攒出任何笔记之前就停了（预算太小/时间太短/极早手动停止），`assemble()` 返回 null 会怎样？看前端的活跃判定：

```ts
/** 任务是否仍在活跃（需要被跟踪/轮询）：未结束，或已停止但阶段报告还没写完 */
function isActiveTask(t: AgentTask | null): boolean {
  if (!t) return false;
  return t.status === 'pending' || t.status === 'awaiting_confirm' || t.status === 'running'
      || (t.status === 'stopped' && !t.report && t.stopReason !== 'cancelled');
}
```

`stopped && !t.report` 会被判成"还在活跃"（因为 stopped 后 runner 理论上还会补报告，前端要继续轮询等报告）。**如果 runner 永远不写 report（null），前端就会永远轮询下去**——用户看到的是"已停止"却一直转圈。修复（注释 P1-2）是：没成果也落一段**说明性报告**，而不是 null：

```ts
const hasContent = progress.directions.some((d) => d.sectionContent || d.notes);
if (!hasContent) {
  return {
    report:
      '> ⚠️ 本次研究在产出任何内容之前就结束了（预算耗尽 / 到达设定时间 / 手动停止），没有可整理的研究笔记。\n\n'
      + '你可以：\n'
      + '- 点击右上角「继续研究」追加预算或时间后重跑（会重新从研究方向开始）；\n'
      + '- 或删除本任务后重新创建。\n\n'
      + '> 提示：研究任务需要联网检索并精读若干网页后才开始沉淀笔记，预算/时间设置过小或过早停止都会导致无产出。',
    sources: [],
    summary: '研究在产出内容前结束，无可用报告',
  };
}
```

report 一旦非空，`isActiveTask` 的 `!t.report` 分支不再命中 → 轮询自然停止。**让"终态一定有可展示内容"，前端就不用靠猜来停轮询**——这是前后端契约设计里很值钱的一条经验。

## 九、前端轮询、通知与多任务同步

### 9.1 为什么用轮询，不用 WebSocket/SSE

研究报告与 Agent 都是**分钟到小时级**任务，且用户经常切走页面再回来。三个方案对比：

| 方案 | 优点 | 本项目不用的原因 |
|---|---|---|
| SSE / WebSocket 推送 | 实时、省请求 | 长任务低频（秒级变化），推送通道要长期占连接；HTTP 断连重连逻辑更复杂 |
| **轮询** | 实现简单、天然断连自愈、切走回来就续上 | 有少量空请求开销（1.5s~2.5s 一次 GET，可忽略） |
| 前端模拟/后端回调 | — | 浏览器关了就收不到；还得推消息系统 |

本项目结论：**低频长任务，1.5~2.5 秒轮询一个轻量 GET 接口是最优解**。请求成本约等于零（查一条记录），换来的是"无论网络怎么断、页面怎么切，状态都不会丢"。

### 9.2 Research.vue：1.5 秒轮询 + 取消按钮

报告页 `startPolling()` 的核心循环：

```ts
pollTimer = setInterval(async () => {
  if (!currentId.value) return;
  try {
    const r = await getReport(currentId.value);
    pollFails = 0;
    current.value = r;
    const i = reports.value.findIndex((x) => x.id === r.id);
    if (i >= 0) reports.value[i] = r;          // 详情页与左侧列表同步更新
    if (r.status === 'done' || r.status === 'failed' || r.status === 'cancelled') {
      // 从非终态跳转到终态 → 弹通知（只在真正完成那一刻通知一次）
      const notTerminal = lastStatus !== 'done' && lastStatus !== 'failed' && lastStatus !== 'cancelled';
      if (notTerminal) { …notifyUser… }
      stopPolling();                            // 终态：停表
    }
    lastStatus = r.status;
  } catch {
    // P0-1：网络抖动不能停轮询——连续失败 3 次才停（后端仍可能正常生成）
    pollFails++;
    if (pollFails >= 3) stopPolling();
  }
}, 1500);
```

要点：
- **lastStatus 记忆**：记录"进入轮询时的状态"，只在"非终态 → 终态"的**那一次转移**弹通知，避免每次刷新都弹；
- **连续 3 次失败才停**：一次网络抖动就停表的话，任务真完成了用户也看不到；3 次容错兼顾了抖动与断网；
- 页面只在**选中某份报告**时轮询它（`selectReport` 里 `if (generating) startPolling()`），生成中的面板显示 `progressText` + 三步步骤指示器（`拆解问题 › 检索与撰写 › 汇总报告`，按 `current.step` 点亮）+「取消生成」按钮。

### 9.3 ResearchAgent.vue：2.5 秒轮询 + 状态转移通知

Agent 任务更重，轮询间隔放宽到 2.5 秒，通知的判定也更细——**四种值得打扰用户的转移**：

```ts
if (prevStatus !== undefined) {           // 跳过刚进入页面时已是终态的情况
  if (t.status === 'done' && prevStatus !== 'done') {
    notifyUser('研究任务完成', t.goal ? `《${t.goal}》已完成…` : '…');
  } else if (t.status === 'failed' && prevStatus !== 'failed') {
    notifyUser('研究任务失败', '…');
  } else if (t.status === 'awaiting_confirm' && prevStatus !== 'awaiting_confirm') {
    // Agent 停下来等你确认方向 → 值得弹一次（可能等了几分钟）
    notifyUser('等待确认研究方向', 'Agent 已拆解完研究方向，请回来选择后继续');
  } else if (t.status === 'stopped' && t.report && !prevHadReport) {
    // 手动停止后，阶段/最终报告整理完成
    notifyUser('研究报告已整理完成', '任务已停止，报告可查看与导出');
  }
}
```

`awaiting_confirm` 也要通知是有产品道理的：Agent 拆方向只需一两分钟，但用户可能已经切走干别的了——**任务是"卡在等用户"而不是"卡住不动"**，必须把用户叫回来。

轮询停止条件用 `polling` computed（基于 8.5 的 `isActiveTask`），并且停表时**不是简单清理**，还要评估列表同步是否需要继续（见下）。

### 9.4 P1-5：多任务列表同步，每 10 秒静默整表刷新

Agent 详情轮询只跟当前选中的任务。但用户可以同时开多个 Agent 任务——如果另一个任务早完成了，侧边栏还显示"研究中"，等用户切过去才刷新，体验就滞后了。注释（P1-5）写清了方案：

```ts
// 只要列表中存在活跃任务，就每 10s 静默整表刷新一次，让所有任务状态保持新鲜。
// 全部结束后自动停（不再发请求）。
function syncListIfNeeded() {
  // 只有「列表里存在非当前选中任务的活跃任务」时才需要整表同步：
  // 当前选中任务由详情轮询覆盖，单任务运行时不发多余请求
  const hasOtherActive = tasks.value.some((t) => isActiveTask(t) && t.id !== currentId.value);
  if (!hasOtherActive) { …清表…; return; }
  if (listSyncTimer) return;   // 已在跑
  listSyncTimer = setInterval(async () => {
    const all = await getAgentTasks();
    tasks.value = all;
    if (!stillOtherActive) { …停表，不再发请求… }
  }, 10_000);
}
```

几个克制点值得学：
- **只在"存在其他活跃任务"时才开表**——单任务运行时一个多余请求都不发；
- **详情轮询停表时重新评估一次**（`stopPolling` 末尾调 `syncListIfNeeded`）——当前任务结束不代表别的任务也结束，同步器要继续；
- 列表同步失败**静默忽略**（与详情轮询的 3 次容错不同，列表是低优先级兜底，丢一轮无所谓）。

### 9.5 notify.ts 与通知权限的请求时机

`apps/web/src/utils/notify.ts` 包了一层浏览器 Notification API，只做三件事：判断支持/权限、请求权限、弹通知（15 秒自动关、点击聚焦窗口、`tag: 'kb-long-task'` 防止堆积）。

这里有个**浏览器平台规则的坑**（代码注释 P2-11/P1-7 记录得明明白白）：

```ts
// 通知权限必须在用户点击的同步阶段请求（浏览器激活窗口内）——
// 放在 await 之后会超窗，Chrome 静默拒绝并永久 denied。拒绝也不影响生成。
void ensureNotifyPermission();
```

Chrome 只允许在**用户手势（点击）的同步代码里**弹权限询问；`await createReport()` 之后请求就会"超窗"被静默拒绝，而且一旦 denied 是**永久**的（用户得手动去站点设置里改回来）。所以两个页面的 `handleCreate` 都是在发请求之前就 `void ensureNotifyPermission()`。

### 9.6 KeepAlive：只停时钟，不停轮询

页面用了 `<KeepAlive>` 缓存（08 章细讲），Agent 页切走时**停 1Hz 的倒计时时钟、但保留详情轮询和列表同步**：

```ts
// KeepAlive 缓存：切走时停 1Hz 界面时钟（倒计时不可见，纯耗电）；
// 详情轮询/列表同步保留——它们只在有活跃任务时跑，且是后台完成通知的支撑
onActivated(() => startClock());
onDeactivated(() => stopClock());
```

原因很实际：倒计时（`剩余 N 分钟`）切走后没人看，1 秒一次的 setInterval 纯属耗电；而轮询是"后台完成通知"的引擎——**用户切到别的页，任务完成了依然能收到系统通知**，这是长任务体验的关键一环。

## 十、取消研究报告的 P1-4 全链路复盘

把第四节到第九节串成一条完整链路（这也是动手实验 A 的走查脚本）：

```
用户点「取消生成」（Research.vue handleCancelReport）
  │ ① 前端：cancelReport(id) → POST /api/research/reports/:id/cancel
  ▼
cancel 接口（research.controller.ts）→ report.service.cancel()
  │ ② 校验：status 必须 ∈ {pending, processing}，否则 400「当前状态不可取消」
  ▼
prisma.report.update({ data: { status: 'cancelled' } })
  │ ③ HTTP 层把状态钉死为 cancelled（此刻 worker 可能正在跑第 N 节）
  ▼
前端：toast('已取消生成') → stopPolling() → loadReports() 刷新列表
  │       cancelled 徽章变灰「已取消」，重试按钮出现
  ▼
Worker 视角（时间线不确定，但结果确定）：
  ├─ 若还没开始（排队期）：advance(1) 的 WHERE status∈{pending,processing} 匹配 0 行
  │    → 日志「排队期间已被取消，跳过生成」→ 一个 LLM 调用都没发
  ├─ 若正在检索/撰写：下一个 ensureRunning() 发现 cancelled
  │    → 抛 cancelled 标记错误 → 并发池 cancelledEarly=true → 未启动小节跳过
  │    → 在途的 1~2 个调用跑完即止 → catch 识别 cancelled → 只打日志不落库
  └─ 若已到汇总收尾：done 的条件更新匹配 0 行 → 日志「放弃写入」→ return
所有路径的共同点：cancelled 一旦落库，没有任何一条 worker 路径能把它改回去。
```

防竞态的三层，缺一不可：

| 层 | 机制 | 防的是什么 |
|---|---|---|
| 1 | cancel 接口限状态（pending/processing） | 已完成的报告不允许"取消"（done 是不可逆终态） |
| 2 | worker 所有推进走 `updateMany + WHERE status ∈ ACTIVE` | HTTP 与 worker 双写者的原子门控（4.2） |
| 3 | `ensureRunning()` 检查点 + `err.cancelled` 判别 | 在途 LLM 调用止损、catch 不把 cancelled 覆盖成 failed |

## 十一、并发 worker 数量：2C4G 能扛多少

### 11.1 三个队列的并发配置一览

| 队列 | worker concurrency | 理由（代码注释原话/推断） |
|---|---|---|
| `report-generate` | 1 | "单并发（每份报告很重）"——一份报告就要并行检索+多次 LLM |
| `agent-task` | 1 | "单并发（一个研究任务很重）"——一个任务内部已有多方向并发 |
| `document-process` | 2 | "concurrency 2：两个任务并行处理（embedding 是外部 API，并行能显著提速）" |

### 11.2 先破除一个误解：Node 的 worker 并发不是多进程

三个队列可能同时各取一个 job，加起来最多 4 个任务并发——但**它们都在同一个 Node 进程里跑**。BullMQ 的 `concurrency` 含义是"这个 Worker 同时从队列取出并执行几个 job"，不是开几个线程/进程。Node 靠事件循环在这些异步任务之间切换：LLM 请求在等待网络返回时几乎不占 CPU，所以**并发任务的瓶颈从来不是 CPU，而是外部 API 的速率限制和你每个任务的常驻内存**。

### 11.3 为什么研究报告/Agent 反而只用并发 1

并发大听起来更快，但这三个原因让并发 1 反而是对的：

1. **任务内部已经并发**：一份报告内 3 路并发撰写、一个 Agent 任务内多个方向并行——任务自己是"多路"的，队列层再叠并发会指数放大 LLM 请求；
2. **BYO key 的速率限制**：LLM 调用用的是**用户自己的 key**，不同用户的 key 各有 QPS 上限；平台自己的 embedding key（硅基流动免费额度）也有 QPS 限制（`embedding.service.ts` 注释"防止触发免费额度 QPS 限制"，批次间强制 300ms 延时）——队列并发 1 是最稳妥的"不把外部 API 打爆"策略；
3. **任务很重、互相挤压**：两个 Agent 同时跑会把进程内存和 Tavily Extract 免费额度吃紧（`agent-runner` 里有"同一 URL 只提取一次"的 readCache，注释点名"Tavily Extract 免费额度有限"）。

而文档处理用 2，是因为 embedding 是**纯外部 API 等待型**负载：一次文档入库可能调十几次 embedding，任务自身内部没有并发，队列并发 2 就能把吞吐提一倍——这正是注释说的"embedding 是外部 API，并行能显著提速"。

### 11.4 2C4G 上的实测口径

项目真实部署环境是**腾讯云轻量 2C4G（Ubuntu 22.04）**，PostgreSQL、Redis、Node 全部容器化跑在同一台（见 `docs/部署运维/39-部署全流程实战记录.md`、`38-密钥与Key管理-部署环境说明.md` 的"2C4G 独享 + SSD，PG/Redis/Node 都是容器轻量跑，解析并发 2，全流程顺畅"）。

在这个配置下的现实结论：

| 资源维度 | 为什么 2C4G 够用 |
|---|---|
| CPU | 长任务的 CPU 大头是文本处理（解析、向量计算其实在远端 embedding API）；Node 事件循环模型下，4 核给 PG/Redis/Node 分完全够 |
| 内存 | 每个长任务常驻的是"方向笔记 + 报告正文"字符串（几百 KB 级），不是大数据集；Node 默认堆上限内同时 4 个任务很宽松 |
| 外部配额 | 真正的天花板是 LLM/embedding/Tavily 的 API 速率与免费额度，而不是服务器规格 |
| 扩容路径 | 队列在 Redis 里，想扩就**多起一个 Node 进程跑同一队列名**（水平加 worker），或把 PG/Redis 拆出去——业务代码一行不用改 |

**面试一句话**："队列并发不是'越大越好'。本项目报告/Agent 队列并发 1、文档队列并发 2，因为前者任务内部已并行且吃外部 API 配额、后者是纯 IO 等待型负载；2C4G 单机跑 PG/Redis/Node 三个容器实测顺畅，瓶颈在 API 配额而非服务器，真要扩容多起一个 worker 进程即可。"

**实验 B：看 Redis 里的队列键**

```bash
redis-cli KEYS 'bull:*'                     # 看到三套队列：report-generate / agent-task / document-process
redis-cli KEYS 'bull:report-generate:*'     # wait / active / failed / events…
redis-cli LRANGE bull:report-generate:wait 0 -1        # 等待中的 jobId
redis-cli HGETALL bull:report-generate:<jobId>         # 单 job：data/attemptsMade/timestamp
```
再创建一份报告不取消，观察 job 从 `wait` 移到 `active`，完成后从 Redis 消失（`removeOnComplete: true`）；故意让任务失败一次，看 `failed` 集合里保留 50 条内的失败记录、`attemptsMade` 显示重试次数。

**实验 C：Agent 的预算耗尽与说明性报告**
1. 新建自主研究任务，预算选自定义 **1 万 token**（下限），时间窗 30 分钟，确认方向后让它跑；
2. 观察前端：搜索轮数增加 → 预算耗尽 → 状态变"已停止"，stopReason 显示"预算用尽"；
3. 打开报告：如果 1 万 token 在攒出笔记前就花完，你会看到**说明性报告**（"本次研究在产出任何内容之前就结束了…"），且轮询自动停止不再转圈——验证 P1-2；
4. 点「继续研究」追加 10 万 token → 观察状态回"排队中"→ 从断点续跑（已精读 URL 不再重复读，进度条从之前的值接着涨）。
5. 进阶：`redis-cli KEYS 'bull:agent-task:*'`，创建任务时把 startAt 设在 1 分钟后，观察 job 先出现在 `delayed` 里、到点才进 `wait`。

## 本章小结

长任务编排的完整图景在这一章拼齐了：**BullMQ 把"执行"从 HTTP 里解放出来**（Queue 入队、Worker 消费、Redis 持久化、失败指数退避重试、`delay` 延迟调度），业务层再用**数据库状态机**表达进度（报告的 `pending→processing→done`、Agent 的 `pending→awaiting_confirm→running→stopped/done`）。

两个最难也最值钱的设计，值得合上书复述一遍：

1. **取消竞态靠"条件更新"而不是"加锁"**：HTTP 与 worker 是天然的两个写入者，谁也没法锁谁；把"检查状态 + 推进状态"合并成一条 `updateMany(WHERE status ∈ 活跃态)`，由数据库保证原子性——取消永远生效，推进必须赢过条件才能生效，再配 `ensureRunning()` 检查点把在途 LLM 调用的损失压到一次以内。
2. **Agent 的成本安全 = 预算盒 + 互斥锁 + 停止标记**：`BudgetBox` 记账、`BudgetMutex` 把"查预算→请求→扣费"做成临界区（软超支 ≤ 单次调用）、`StopFlag` 统一三种停止（预算/时间/手动）；`ASSEMBLY_BUDGET` 独立预留让"任何停止都能交付正式报告"；`progress` 断点 + 入口不区分首跑续跑 = 断点续跑；无成果时给"说明"不给 null = 前端不会死轮询。

前端则用"轻量轮询 + 状态转移通知 + 多任务列表同步"把分钟级等待变成可控体验。下一章我们转向防御面：这套系统怎么认证用户、怎么保护用户的 Key（BYO 加密）、平台怎么做到"对话零成本"——也就是 07 章。
