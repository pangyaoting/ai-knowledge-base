# 阶段 4+：限时 · 限量 · 自主研究 Agent

> 一句话：给平台装了一个"会自己干活的研究员"——用户只设定 **时间窗 + token 预算 + 研究目标（可选）**，
> Agent 在窗口内自主"联网搜索 → 摘要预筛 → 精读正文 → 提炼笔记 → 成稿"，
> 预算用尽 / 时间到 / 手动停止都保留阶段成果，**续时或加预算后从断点继续，绝不从头再来**。
> 所有 LLM 消耗走用户自己的 Key（BYO），平台零成本。

---

## 一、需求与决策记录（为什么做、为什么这么做）

### 1.1 背景：从"被动工具"到"主动智能体"

平台已有的研究报告是**被动式**的：用户丢主题 → 系统检索用户知识库 → 分节成稿，1~2 分钟出结果。
它的局限：只能基于用户**已有**的资料，不能去网上找新信息，也不能长时间自主迭代。

"自主研究 Agent"是把工具升级成**主动智能体**的第一步：
给它一个目标、一个预算、一段窗口，它自己决定搜什么、读什么、怎么组织成稿——人只负责验收。

### 1.2 方案对比（用户选定：B 并行多源）

| 维度 | A 串行单源 | **B 并行多源（选定）** |
|---|---|---|
| 搜索方式 | 一个搜索词接一个搜索词，串行推进 | 目标拆成 3~5 个方向，**多方向并行**搜索 |
| 精读 | 一篇读完再读下一篇 | 多篇候选**同时预筛**，挑 2 篇精读 |
| 效率 | 慢，40 分钟只够 1~2 个角度 | 同一时间窗覆盖 4~6 个角度 |
| 报告结构 | 单线叙述 | 多章节（每方向一章），结构完整 |

用户选 B 的原因：预算和时间窗是有限的，"并行多源"才能在窗口内榨出最多的有效信息。

### 1.3 预算档位与停止规则（用户锁定，写进代码的硬规则）

- **预算档位**：快速 10 万 / 标准 20 万 / 深度 30 万 / 自定义 1万~50万 token；
  预估时长 10万≈40 分钟、20万≈1.5 小时、30万≈2 小时（前端展示"预计 X 分钟 · 可随时停止/续时"）。
- **停止规则（三选一，先到先停）**：
  1. **token 预算用尽 → 永远停**（最硬，成本红线）；
  2. 否则 **用户设定的结束时间到了 → 停**（用户时间永远优先，预估时间只是预填建议）；
  3. **手动停止 → 随时停**。
- **续时机制**：停止（任何原因）后，可以追加 token 预算和/或分钟数，
  任务从 **progress 断点**续跑——已精读的 URL 不重读、已完成的方向不重写、已缓存的小节正文直接复用。

## 二、系统设计

### 2.1 数据模型：AgentTask

```prisma
model AgentTask {
  id           String    @id @default(uuid())
  ownerId      String    @map("owner_id")
  mode         String    @default("targeted") // targeted=定向研究 / open=自主探索
  goal         String?                          // 研究目标（open 模式为空）
  startAt      DateTime  @map("start_at")       // 时间窗开始（未来时间 = 定时开跑）
  endAt        DateTime  @map("end_at")         // 时间窗结束（停止硬上限）
  tokenBudget  Int       @map("token_budget")   // token 预算上限（停止硬上限）
  tokensUsed   Int       @default(0) @map("tokens_used") // 已消耗（续跑累加）
  searchRounds Int       @default(0) @map("search_rounds") // 联网搜索轮数
  pagesRead    Int       @default(0) @map("pages_read")    // 精读页数
  status       String    @default("pending") // pending/running/stopped/done/failed
  stopReason   String?   @map("stop_reason") // budget_exhausted/time_exhausted/user_stopped/completed/error
  directions   Json?     // [{ title, question, status, rounds }] 进度展示
  progress     Json?     // 断点：每方向的 notes/readUrls/searchTerms/sectionContent
  report       String?   // 最终（或阶段）Markdown 报告
  sources      Json?     // [{ number, title, url }] 网页来源
  error        String?
  finishedAt   DateTime? @map("finished_at")
  createdAt / updatedAt
  owner User @relation(... onDelete: Cascade)
  @@map("agent_tasks")
}
```

关键设计：**progress 列就是断点**。方向列表、研究笔记、已读 URL、已用搜索词、已缓存的小节正文
全部序列化在里面——续跑时 runner 从这恢复，而不是从零开始。

### 2.2 架构：接口 → 队列 → Runner

```
POST /research-agent/tasks (创建)
  → 落库 pending + BullMQ agent-task 队列（startAt 在未来则 delay 到点再执行）
  → AgentRunner.processTask()（worker 并发 1，同研究报告队列）
      ① 解析用户默认模型配置（BYO，无配置直接 failed 提示去绑定）
      ② 初始化方向：定向=拆目标成 3~5 个方向 / 开放=从用户知识库挖方向
      ③ 各方向并行推进（共享预算盒 + 停止标记）
      ④ 收尾：按停止原因落终态 + 组装（阶段或完整）报告
```

### 2.3 核心循环（一个方向的一轮）

```
生成下一个搜索词（LLM，模型觉得资料够了 → 输出 null → 方向完成）
  → 联网搜索 5 条（Tavily）
  → 摘要预筛：LLM 从候选中挑 2 条最值得精读的
  → 精读正文（Tavily Extract，失败回退搜索摘要）
  → 提炼要点并入该方向笔记（LLM）
  → 保存断点 → 下一轮
```

每轮 3~4 次 LLM 调用、1 次搜索、2 页精读；单方向封顶 8 轮防失控。

### 2.4 预算盒 + 互斥锁（踩过的坑，重点）

第一版让 5 个方向**完全并发**地调 LLM——结果实测预算超支 **92%**（1 万预算花了 1.9 万）：
多个方向的调用同时通过"预算还够"的检查，然后一起扣费，谁也拦不住谁。

修复：**LLM 调用串行化**（BudgetMutex 互斥锁），只有不耗 token 的联网搜索/正文提取保持并行。
预算用尽时最多只有一个**在途调用**（约 1~4k token 的软超支）：
实测 1 万预算 → 实际消耗 10608（超支 6%）。预算精确性 > LLM 级并行。

> 说明：这仍然是"并行多源"——多方向同时搜、多页面同时读，只是最贵的 LLM 调用排队扣费。

### 2.5 停止与续跑（三个停止条件的落地）

- **预算用尽**：complete() 扣费后立即置全局停止标记 → 各方向在当前调用边界收尾；
- **时间到**：方向循环 while 条件检查 `Date.now() < endAt`，收尾前再补一次判定
  （防止"时间刚好在循环条件处耗尽"导致误判成完成）；
- **手动停止**：stop 接口把 status 置 stopped → runner 每轮/每步前查状态，发现非 running 立即收尾；
- **收尾不花一分钱**：停止后不再调 LLM 组装，直接拿各方向**原始研究笔记**拼成"阶段成果"
  （`## 方向名\n\n笔记`），用户立刻能看到已经研究到的内容；续跑完成时正式报告会替换它；
- **续跑**：extend 接口只允许 stopped 任务，追加 token（总预算封顶 100 万）和/或分钟
  （封顶 720 分钟）→ status 回 pending 重新入队 → runner 读 progress 断点续跑。

### 2.6 报告组装（复刻研究报告的防截断思路）

- 每个方向一节，正文用 LLM 写（max_tokens 2000，引用带 [来源](URL) 链接）；
- 引言/结论是独立的短调用（300/400 token），正文代码拼接——**绝不让模型复述全文**，
  杜绝研究报告曾经踩过的"输出上限截断"坑；
- 停止时走零成本路径（原始笔记直接拼），保证任何情况下用户都有产出。

## 三、接口一览

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/research-agent/tasks` | 创建（mode/goal/startAt/endAt/tokenBudget） |
| GET | `/research-agent/tasks` | 我的任务列表 |
| GET | `/research-agent/tasks/:id` | 详情（轮询进度） |
| POST | `/research-agent/tasks/:id/stop` | 手动停止（保留阶段成果） |
| PATCH | `/research-agent/tasks/:id/extend` | 续时/加预算（仅 stopped，从断点续跑） |
| DELETE | `/research-agent/tasks/:id` | 删除 |

校验要点：定向必须有目标；endAt > startAt；预算 1万~50万；
extend 只允许 stopped 且 stopReason 不是 completed/error；至少追加一项。

## 四、前端（ResearchAgent.vue，路由 /research-agent）

- **创建表单**：研究模式（定向/自主探索）→ 目标 textarea → 时间窗（datetime-local，默认
  立即开始 + 40 分钟）→ 预算四档卡片（快速/标准/深度/自定义，选档自动预填结束时间）；
  底部展示"预计 X 分钟 · 可随时停止/续时"，以及换算成本（¥1/万 token）——让用户对"花多少钱"有数。
- **进度面板**：token 预算进度条（90% 变红）、剩余时间（每秒刷新）、搜索轮数/精读页数、
  方向列表（待研究/研究中转圈/已完成打勾）、手动停止按钮。
- **停止态**：黄色横幅说明停止原因 + "继续研究"按钮 → 弹窗追加 token（+5万/+10万/+20万/自定义）
  和分钟数（+30/+60/+120/自定义）。
- **完成态**：Markdown 报告（复用渲染器）+ 来源列表（可点击跳转外链）+ 导出 .md。

## 六、成本画像（为什么是"限时限量"）

以标准档 20 万 token 为例：约 15~20 次搜索、80~120 条候选、24~35 页精读、
4~6 个方向、6000~10000+ 字报告，配合 1~2 小时窗口；按 DeepSeek ≈ ¥1/百万 token 计，**约 ¥0.2**。
预算真正限制的是**时间与噪音**：防止 Agent 无限搜索下去、防止无关网页灌入。
真正的瓶颈是时间——20 万 token 半小时花不完，所以时间窗才是主要停止条件。

## 七、经验与坑（这个功能教会我的）

1. **并发扣费 = 预算失控**：多个协程同时"看一眼余额"再消费，必然集体超支。
   预算类逻辑要么单线程串行，要么加互斥锁。实测：超支从 92% 降到 6%。
2. **停止 ≠ 立即停止**：API 调用一旦发出就收不回来，能控制的是"下一调用是否还发"。
   所以手动停止的收敛速度 = 状态检查频率（每轮/每步查一次，比只查每轮快 4 倍）。
3. **停止后必须能交出点什么**：第一版停止后报告为空（组装被停止标记挡住），
   用户花了钱什么也拿不到。改成"零成本拼原始笔记"后，任何停止都有阶段成果。
4. **时间边界的静默退出**：while 条件里"时间到"自然退出不会设停止原因，
   收尾前必须再补一次判定，否则任务会被误标成"已完成"。
5. **表单默认值要覆盖"首次进入"**：创建表单默认结束时间只在点"新建"时初始化，
   首次进页面直接创建会因空时间被拦截——默认值要在声明时就给。
6. **测试脚本也会骗你**：UI 冒烟"创建按钮不出来"排查半天，结果是测试脚本自己忘了
   给测试用户建模型配置——页面行为完全正确。

## 八、后续演进（朝着"24 小时自主研究"）

- **更长窗口**：当前单任务最长 12 小时续时，未来可支持"过夜研究"（定时开跑，人睡醒收报告）；
- **Agent 融入知识库检索**：研究时把用户知识库也作为来源之一（open 模式已在用知识库挖方向，
  可以更进一步：检索命中就本地精读，不重复上网搜）；
- **多 Agent 分工**：拆解、搜索、精读、撰写拆成独立 Agent 各司其职（当前是一个 Runner 内部循环）；
- **研究报告互通**：Agent 的成果可以直接存成研究报告/知识文档，沉淀进知识库形成闭环；
- 用户愿景（路线图待办）：**"AI 24 小时自主做市场/需求研究"**——本功能是它的第一个落地形态。
