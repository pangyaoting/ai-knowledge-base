# 43 · RAG 行业级优化蓝图（四大问题的行业方案）

> 一句话：针对实测发现的四个 RAG 短板（表格检索差 / 只认字面重合 / topK 少 / 不如直接上传），
> 给出**行业最佳实践的完整升级设计**：结构感知切片 + 父子分块 + HyDE + 宽召回精排 + 全文/检索自动分流。
> 按 P0→P3 排期落地，每期可独立上线、可写进简历。

---

## 〇、总架构（升级后）

```
上传文档
  │
  ├─ ① 结构感知切片（md 按标题层级、表格保留表头）+ ② 父子分块
  │
  ▼
入库：chunk 带"路径上下文" + parent 关系 + 结构化元数据
  │
查询时
  ├─ ③ 查询预处理：改写（已有）→ 可选 HyDE 扩写
  ├─ ④ 宽召回（向量+关键词，30-50 条）→ rerank 精排 → 动态 topK（8-10）
  │
  ▼
⑤ 回答模式自动分流：
    绑定文档总量小（< 阈值）→ 全文模式（全文进上下文，不走检索）
    绑定文档海量        → 检索模式（走上面检索链）
```

## P0 · 全文/检索自动分流（解决"不如直接上传"）

**问题**：RAG 对"单文件/小文档 + 需要看全文的任务"（如逐行解析 html）天生残缺——模型只见片段不见全文。

**行业方案**（2025+ 大厂主流）：**长上下文优先，RAG 退居超长文档索引层**。

**设计**：
1. 会话/请求级增加模式判定：
   - 统计本次问答范围（绑定知识库/上传文件）的总字符数
   - `总字符 < THRESHOLD（如 6 万）` → **全文模式**：把文档全文直接拼进 prompt（模型上下文内）
   - `总字符 ≥ THRESHOLD` → **检索模式**：走现有 RAG 链路
2. 上传文件场景（对话中上传）已天然是全文（extractFile 截断 3 万字符），需支持"多文件合并全文"。
3. 前端：会话设置加"自动 / 强制全文 / 强制检索"三态开关，展示当前模式。

**改动点**：
- 后端：`chat.service.askAndStream` 加模式判定与全文组装分支（复用 buildPrompt 的资料注入）
- 前端：Chat 设置 UI + 模式指示器
- 阈值常量放 .env 可配（`FULLTEXT_MAX_CHARS`）

**验证**：上传小 html 问"逐行解析" → 全文模式 → 不再出现"资料未显示完整结构"。

## P1 · 结构感知切片 + 上下文注入（解决"表格检索差"）

**问题**：字符级切片把表格行切碎成无头碎片，检索命中率与重排分双低。

**行业方案**：**Markdown AST（mdast）按标题层级切块，块携带章节路径**；表格作为整体节点保留表头；代码块按函数/段落边界切。

**设计**：
1. 用 `remark` + `mdast-util-*` 解析 md 成树：`#/##/###` 标题 → 子树，叶 = 段落/表格/列表/代码块。
2. 每块生成 `contextPrefix`：`文档名 > 一级标题 > 二级标题`。
3. 落库 content = `[contextPrefix]\n正文`，chunk 表加 `section_path` 列（可检索、可展示出处）。
4. 表格块：整表作为一个"父块"，不跨行切；超长表才按行切并每行带表头（列名）前缀。
5. 非 md（txt/pdf/docx/代码）保持字符切，但代码块按空行边界（现有 splitCode 已按行）并在块首注入文件路径（已有 `文件: xxx` 前缀，保留）。
6. 兜底：无标题的文档仍走字符切（结构感知失败不阻塞）。

**改动点**：
- `document-processor.indexText`：md 走结构感知分块器（新增 `structured-splitter.ts`）
- Prisma：`chunks` 加 `section_path String?`（迁移）
- 检索展示：ChatSourcePanel 显示章节路径

**验证**：docs/41 类表格文档检索"W1 周一练习"→ 命中的块自带"W1｜周计划表"上下文，rerank 分显著提升。

## P2 · 父子分块（解决"命中但不完整"）

**问题**：小片检索准但上下文残缺（模型拿到 200 字片段答不全）。

**行业方案**：**Parent-Child Chunking**——小片（~200 字）向量化做检索定位，命中后取父块（整节/整表，~2000 字）喂模型。

**设计**：
1. 入库时建两层：`child_chunks`（小片，带 embedding）与父块关系（`parent_id`）。
2. 检索命中 child → 按 parent_id 取父块 content 返回（RetrievalSource 返回父块全文）。
3. 与 P1 结合：父块 = 标题下的整节；无结构时父块 = 500 字字符块。
4. 控制 token：父块上限 3000 字，超出截断或只取命中 child 前后文。

**改动点**：
- schema：chunk 加 `parent_id` 自关联（或独立父子表）
- 入库：先切父块再细分 child，写两批
- 检索：rag.service 命中后 `parent_id` join 取父块

**验证**：命中第 3 个表格行，返回整表 + 章节上下文，回答完整性提升。

## P3 · 查询改写增强 + HyDE（解决"只认字面重合"）

**问题**：embedding 语义弱 + 门控一刀切，导致"问法不同就检索不到"。

**行业方案**：
1. **查询改写**（已有 rewriteQuery）保留：口语问题 → 检索友好查询。
2. **HyDE**（Hypothetical Document Embeddings）：先用 LLM 把问题扩写成一段"假设答案/相关描述"，用**假设答案**做向量检索——假设答案与文档的语义重合度远高于原问题。
3. **门控参数化 + 动态阈值**：向量相似度阈值不设死，先宽召回再靠 rerank 兜底；rerank 分按查询类型动态（事实型问题阈值低，宁可多给让 LLM 判断）。

**改动点**：
- `rag.service`：可配 `ENABLE_HYDE`，retrieve 前多一步 HyDE 扩写（成本：一次 LLM 调用，只对检索结果差时触发兜底重试）
- .env：`MIN_SIMILARITY` / `RERANK_MIN_SCORE` / `TOP_K` 参数化并给出推荐值

**验证**：用"第一周第一天学什么"问 docs/41（文档里是"W1 周一"）→ HyDE 扩写后能命中。
