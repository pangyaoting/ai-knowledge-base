# 阶段 4+：双因素认证（TOTP）

> 一句话：开启后登录要"密码 + 验证器 App 动态码"两道关，丢了手机还有一次性恢复码兜底。
> 对标：Google Authenticator 的 TOTP 方案（RFC 6238），不是短信验证码（免短信费、离线可算）。

---

## 一、大白话：TOTP 是什么

- 绑定阶段：后端生成一个**密钥**，把它编码进一个 `otpauth://` 链接（二维码）；
- 验证器 App（Google Authenticator / Microsoft Authenticator）扫二维码后**本地保存密钥**；
- 之后 App 每秒都用"密钥 + 当前时间（30 秒一格）"算出一个 **6 位动态码**；
- 服务器用同一个算法验证——**两边都离线可算**，不依赖短信/网络，所以零成本。

## 二、实现拆解

### 1. 数据模型（User 扩展）

```prisma
totpSecret    String?  // base32 密钥（启用后存库）
totpEnabled   Boolean  // 是否已开启
recoveryCodes Json?    // 恢复码的 sha256 哈希数组（一次性）
```

### 2. 绑定流程（设置页）

```
生成密钥+二维码（Redis 暂存 10 分钟，未确认不落库）
  → 用户扫码 / 手动输密钥 → 输入 6 位动态码
  → 校验通过 → 启用 + 存密钥 + 生成 8 个恢复码（哈希存储，明文只显示这一次）
```

### 3. 登录两步（关键安全设计）

```
① 邮箱+密码 → 校验通过但开了 2FA → 只返回 need2fa + loginToken（Redis 5 分钟，未登录成功）
② 动态码 / 恢复码 → 换取正式 Token（JWT 双 Token）
```

- 第一步**不返回任何正式 Token**，杜绝"密码对了就放行"；
- loginToken 存在 Redis、5 分钟过期，防暴力重放。

### 4. 恢复码

- 8 个 `xxxx-xxxx` 随机码，**服务端只存 sha256 哈希**（码高熵随机无需加盐）；
- 登录时当验证码用，**命中即从数组移除**（一次性）；
- 防丢手机——这是 2FA 的完整闭环。

### 5. 关闭 2FA

- 需验证当前密码（二次确认），清空 secret/恢复码。

## 三、踩过的坑（面试真实素材）

**otplib v13 的 `verifySync` 返回 `{ valid: boolean }` 对象而不是布尔值**——
`!!verifySync(...)` 对任何对象都是 true，导致所有 6 位码都"验证通过"。
用探针脚本复现后改为取 `.valid === true`。教训：**库的新版 API 变了，返回值结构要实测，不能想当然**。

## 四、面试话术

- "TOTP 是 RFC 6238：密钥 + 时间步长 → HMAC-SHA1 → 截断成 6 位，30 秒一变；验证器 App 和服务器各自离线计算，所以零成本、不依赖短信。"
- "登录改成两步：密码验证通过只发临时 loginToken（Redis 5 分钟），第二步动态码才换正式 Token——把'知道密码'和'持有设备'两件事分开验证。"
- "恢复码只存 sha256 哈希、一次性消费，防丢手机是 2FA 的完整闭环。"
- "时钟偏移用 epochTolerance ±30s（一个时间窗）容忍，避免设备时间不准导致验证失败。"

## 五、自测清单（已实测）

- [x] API：生成密钥/URI → 动态码启用 → 返回 8 恢复码
- [x] 登录两步：need2fa + loginToken（第一步无正式 Token）
- [x] 正确动态码登录 / 错误码 401 / 恢复码登录（一次性，二次用 401）
- [x] verify 实时校验、错误密码不能关闭 2FA
- [x] UI：二维码绑定 → 恢复码展示 → 两步登录 → 密码关闭 2FA
