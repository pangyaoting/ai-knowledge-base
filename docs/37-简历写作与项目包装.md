## 一、简历写作 4 条心法（先记住这个）

1. **动词开头、结果导向**：句式 = 做了什么 + 怎么做的 + 结果/学到什么。
   - ❌ "负责开发了登录功能"（谁都会写）
   - ✅ "实现基于邮箱验证码 + JWT 双 Token 的认证体系，Redis 轮换刷新令牌，支持无感刷新"（有技术点）
2. **技术名词 + 业务价值成对出现**：光写技术栈没人信，要说明技术解决了什么问题。
   - ✅ "用 RRF 融合向量检索与关键词检索，解决单一检索召回不全的问题"
3. **量化优先**：有数字就写数字——粒子数、用例数、接口数、体积优化、响应时间。
   - ✅ "37 个单测全绿"、"首页 Canvas 粒子引擎 5000+ 粒子 60fps"、"构建产物体积从 1.6MB 降到 900KB"
4. **诚实可答辩**：写上去的每一条，你都要能展开讲 2 分钟。写之前问自己：面试官问"这个怎么实现的"我能答吗？

## 四、STAR 法则：把每一条讲成完整故事（面试核心武器）

### 4.1 STAR 是什么

面试官听项目经历最怕三句话讲完的流水账。**STAR 是公认的讲故事结构**，四段缺一不可：

| 字母 | 含义 | 一句话模板 |
|---|---|---|
| **S** Situation | 背景/困境：当时遇到什么问题 | "项目要 XX，但发现 XX 行不通/很慢/会出错" |
| **T** Task | 你的目标/要解决的矛盾 | "我的目标是让 XX 达到 XX" |
| **A** Action | 你具体做了什么（技术方案） | "我调研后选 XX 方案：……（关键技术点）" |
| **R** Result | 结果/量化/学到了什么 | "上线后 XX 从 X 提升到 Y / 问题消失 / 我因此理解了 XX" |

**为什么吃这套**：S 制造"这个问题你遇到过吗"的共鸣，T 显示目标感，A 展示技术深度，R 用数字证明。面试官听完能判断你的**真实经历 + 解决思路**，而不是背稿。

### 4.2 本项目的六个 STAR 故事卡（面试前练熟 2~3 个）

> 每个都是真实发生的事，按 S/T/A/R 整理 + 60 秒口述版 + 简历一行版。

#### 故事卡① 上传从"会超时"到"秒回"（异步队列）
- **S**：文档上传要同步"解析+分块+向量化"，大文档几十秒，前端等超时；
- **T**：让上传接口秒回，长任务不阻塞请求；
- **A**：引入 **BullMQ（Redis 队列）**：上传只做"校验+存盘+建记录+入队"立即返回；worker 后台并发 2、失败自动重试 3 次（指数退避）；前端轮询文档状态流转（pending→processing→done）；
- **R**：接口响应 <1s，大文档不再卡死；失败可恢复（保留 failed 行展示原因）；增量上传按内容哈希去重省 API 费；
- **口述 60 秒**："最早上传大文档会超时，因为解析分块向量化是同步的。我调研后上了 BullMQ 队列——上传接口只存盘入队就返回，worker 在后台解析，失败自动重试。现在 200MB 的项目代码目录上传也是秒回，进度靠轮询，解析失败还能看到原因重新传。这个改造让我理解了为什么生产系统都要异步化。"
- **简历一行**："上传链路改 BullMQ 异步队列（并发 2、失败重试 3 次指数退避），接口 <1s 秒回 + 前端轮询进度"

#### 故事卡② 检索从"搜不准"到"语义精准"（混合检索 + 重排）
- **S**：只做向量检索，关键词精确匹配召回不全（"图片识别"搜不到"图像分类"）；单一检索方式分数不可比；
- **T**：提高检索准确率，且回答必须可溯源、不瞎编；
- **A**：向量 + **pg_trgm** 关键词**双路召回** → **RRF 融合**（只看排名不看分数）→ **bge-reranker 交叉编码器两阶段精排** → **相关性门控**（够不着就拒答/明说无资料）→ 多轮查询改写做指代消解；
- **R**：Top-15 重排后取 Top-5，命中质量明显提升；回答逐条带来源可点击溯源；无资料时披露"未检索到知识库资料"不硬编；
- **口述**："最开始只有向量检索，用户搜'图片识别'查不到'图像分类'。我加了 pg_trgm 关键词路，但两路分数不可比，所以用 RRF 只看排名融合；再上 bge-reranker 交叉编码器精排 15 条取 5 条；最后加门控——检索质量不够就明说没资料，不喂错上下文。这条链路让我真正理解了 RAG 为什么是工程问题而不是调 API。"
- **简历一行**："RAG 检索链路：向量+关键词双路 RRF 融合 → BGE-Reranker 精排 → 相关性门控 + 查询改写，回答带来源可溯源"

#### 故事卡③ 巨石组件拆分（前端工程化）
- **S**：Chat.vue 1639 行，加功能要上下翻几百行，改一处怕坏一片；
- **T**：拆分但**零回归**；
- **A**：只拆**纯展示子组件**（消息项/来源面板/输入框/思考动画 6 个），**状态/流式/KeepAlive/自动滚动/草稿记忆留在容器**，每个子组件 `defineOptions({name})` + 事件上抛；
- **R**：Chat.vue 降到 ~800 行；37 个单测佐证行为不变；后续加功能（多图上传、推理等级）都在子组件内完成，回归为零；
- **口述**："Chat.vue 长到 1639 行。我按'纯展示拆、状态留容器'拆成 6 个子组件——流式、自动滚动、KeepAlive 这些横跨全局的状态不硬拆，避免回归。拆完主文件降一半，再往后加多图、推理等级都是在子组件里加，很稳。"
- **简历一行**："1639 行巨石组件按'纯展示拆、状态留容器'拆 6 个子组件，主文件减半、后续功能零回归"

#### 故事卡④ 从手动部署到 push 即上线（CI/CD）
- **S**：服务器手动部署要 SSH 下载代码、跑迁移、重建、重启，一次十几步；大陆服务器连 GitHub 还不稳定；
- **T**：自动化部署，改代码一键上线；
- **A**：GitHub Actions 两条 job：check（类型检查+37 测试+构建，防坏代码上线）+ deploy（SSH 密钥登录 → 加速代理下载 → 备份 .env/数据 → 迁移 → 构建 → pm2 重启）；服务器端用密钥对授权，Secrets 不落仓库；
- **R**：push 到 main 全自动测试+部署；没配密钥自动跳过不误伤 CI；之后每次改代码不用碰服务器；
- **口述**："最早我每次上线都要手动 SSH 十几步，还容易漏。我配了 GitHub Actions：check job 先跑类型检查和 37 个单测，过了才走 deploy job 用 SSH 密钥登服务器自动拉代码、跑迁移、重启。现在 push 就上线，坏代码过不了测试根本到不了线上。"
- **简历一行**："GitHub Actions CI/CD：push 自动 类型检查+37 单测+构建+SSH 部署，无密钥自动跳过，坏代码无法上线"

#### 故事卡⑤ 图片叠满屏的线上 bug 排查（真实排障，最加分）
- **S**：上线后用户反馈"带图片的历史会话，重新进入后满屏'图片'叠字、页面卡死"；
- **T**：定位并根治，不是重启糊弄；
- **A**：排查发现数据库把图片数组存成 **JSON 字符串**，但接口没解析直接返回；前端类型声明 `string[]` 实际收到字符串，**v-for 遍历字符串=逐字符渲染** → 每个字符生成一张无效图；修：后端 `JSON.parse` 还原数组 + 前端防御性解析（兼容旧数据）；
- **R**：满屏叠字消失、历史图片正常显示；顺手加了消息 key 唯一化 + 切换会话防竞态；总结出"存储格式≠接口格式，跨端字段要防御"的经验；
- **口述**："上线后用户说带图片的会话重进就满屏图片卡死。我查数据库发现图片存的是 JSON 字符串，接口没还原，前端类型写了 string[] 但运行时是字符串——v-for 遍历字符串会按字符拆，几万字符就生成几万张废图。后端补了 JSON.parse，前端也加了兼容。这个 bug 让我明白接口边界的数据契约和运行时防御有多重要。"
- **简历一行**（可选，体现排查力）："排查并根治线上'图片叠满屏' bug：定位为存储 JSON 字符串未解析 + 前端按字符遍历，修复后历史图片正常"

#### 故事卡⑥ 一配置多模型 + 视觉自动路由（产品化思维）
- **S**：BYO 设计里一个 Key 一个配置，用户想换模型/发图片要建多条配置，体验繁琐；
- **T**：一个配置挂多个模型、发图自动路由视觉模型；
- **A**：ModelConfig 加 models 数组 + 会话记录选中模型名；下拉按"配置×模型"平铺切换；后端遍历配置的模型名按启发式（vision/VL/4V）自动路由视觉模型识别图片；
- **R**：一个 DeepSeek Key 可挂对话/推理/视觉多个模型直接切换；发图无需手动选模型；
- **口述**："最早一个 Key 要建多条配置才能切换模型，很啰嗦。我改成一条配置可挂多个模型名，对话下拉直接平铺切换；发图片时后端按模型名关键字自动路由到视觉模型。这让 BYO 的体验接近商业产品了。"
- **简历一行**："模型配置升级'一 Key 多模型'（配置挂模型名数组 + 会话级切换），发图按启发式自动路由视觉模型"

### 4.3 简历上怎么压缩 STAR（简历 ≠ 口述）

- 简历只写 **A + R**（行动 + 结果），**S/T 一行带过**——简历是"点"，面试才是"故事"；
- 写法模板：`[动词] + [关键技术方案]，[量化结果]`（见上面每卡"简历一行"，直接可用）；
- 上面 6 个故事卡的简历一行，挑 3~4 个放进项目经历即可（推荐②④③①，最能体现深度）；
- 面试被问"讲一个项目里最难的/最有成就感的"，就从故事卡⑤或①展开（有真实痛点+排查过程，最可信）。

## 五、针对"软件技术"学生的包装与避坑

### 4.1 项目少怎么办？—— 一个项目打多个点

很多同学只有"课程作业"或"跟着视频抄的"项目。本项目是**全栈 + AI + 工程化 + 视觉**四合一，
一份项目经历就能覆盖：前端、后端、数据库、算法、测试、部署、AI——**把它吃透，等于别人 3 个项目的面试储备**。
面试官问什么方向，你都能从这一个项目里抽对应部分讲。

### 4.2 千万别写的（诚实原则）

- ❌ 没真会的框架（写了"熟悉 React"，实际只写过 Vue——面试官一句话就问穿）；
- ❌ 夸大数据（"日活 10 万"——这种项目不可能有，问了就露馅）；
- ❌ 模板化自我评价（"吃苦耐劳、抗压能力强"——没有证据，等于没写）；
- ❌ 把 AI 生成的功能写成"自己设计的"（本项目所有代码都是你敲的，但要说清哪些是 AI 辅助——2026 年面试官不排斥 AI 辅助，反感的是不懂装懂）。

### 4.3 排版与投递

- 一页以内（应届生一页足够）；导出 PDF（别发 Word/在线链接）；
- 文件名规范：`姓名-求职意向-学校.pdf`；
- GitHub 仓库 README 放项目截图 + 架构图 + 部署地址（本项目 README 已备好，面试官大概率会点开看）；
- 投递前根据 JD 微调"技能清单"顺序：JD 偏前端就把前端放前面，偏后端就倒过来。

## 六、面试时怎么讲这个项目（衔接 docs/12）

1. **开场 30 秒**："我独立做了一个 AI 知识库全栈项目——解决'文档搜不到、AI 没依据'的问题：上传文档自动向量化，问答带来源可溯源，还能自动生成研究报告"；
2. **讲"为什么这么做"**：每个功能先讲痛点再讲方案（RRF 是因为两种检索分数不可比；门控是因为不能瞎编；队列是因为大文档同步会超时）；
3. **主动暴露"取舍"**（加分项）：TOTP 做过又因体验繁琐回滚成邮箱验证码、知识网络做过又下线——讲"我做了取舍"比"我全做成了"更可信；
4. **现场演示**（如果能带电脑）：3 分钟 demo 路线见 `docs/36` 阶段 7，比任何口头描述都有说服力；
5. **不会的问题**：诚实说"这块我了解不深，但我可以讲讲我项目中类似的 XX"——把问题引回你熟悉的地盘。
