# 阶段 4+：知识网络（GraphRAG-lite 多跳问答）

> 一句话：文档入库时自动抽出"概念 + 概念关系"形成知识网络；问答时沿关系链扩展召回，
> 治普通 RAG 的公认短板——**"A 和 B 是什么关系"这种跨概念问题**。
> 对标：微软 GraphRAG（2024-2025 最热方向，落地产品极少）。

---

## 一、大白话：解决了什么

普通 RAG 把文档切成片段"平铺"着找相似度——它知道"哪段文字像问题"，但不知道"哪个概念连着哪个概念"。
所以问"RAG 和 Embedding 有什么关系"，如果没有任何一篇文档**同时**提到两者，模型只能靠常识硬拼。

知识网络的做法：**入库时多花一点点 token，让模型把文档里的概念和关系抽出来**，存成一张知识地图：

- 概念（实体）：RAG、向量库、Embedding、大语言模型…
- 关系：RAG →使用→ 向量库；RAG →解决→ 幻觉问题…

提问时：问题命中实体（如 RAG、Embedding）→ **沿关系找到相邻概念** → 把这些概念的原文片段一起取回 →
模型回答就有了"文档里真实存在的关系链"，而不是通用常识。

## 二、实现拆解

### 1. 抽取（入库时，DocumentProcessor 新增一步）

```
文档处理：解析 → 分块 → 向量化 → 【图谱抽取】→ done
```

- 一次 LLM 调用：从文档全文（截断 4000 字控成本）抽 `{entities, relations}` JSON；
- 实体按 知识库+文档+名称 去重，并记录"名称出现在哪些 chunk"（`chunkIds`）——多跳扩展靠它取回原文；
- 抽取失败只记日志不影响文档状态（图谱是增强不是依赖）；
- 幂等：重新抽取先删该文档旧图谱。

### 2. 数据模型

```prisma
model GraphEntity   { kbId, documentId, name, type, chunkIds Json }   // 唯一(kb,doc,name)
model GraphRelation { kbId, documentId, sourceName, relation, targetName } // 唯一(kb,doc,三元组)
```

### 3. 多跳扩展（ChatService 检索阶段并行加入）

```
问题 → ① 图谱实体名匹配（实体名出现在问题里，≥2 字）
     → ② 1 跳关系：命中实体相连的相邻实体
     → ③ 取相关实体的 chunkIds → 取回原文片段
     → 并入来源（similarity=null 标记"图谱关联"，按 chunkId 去重）
```

只做 1 跳：控制成本与噪声（2 跳以上准确率骤降，作为面试"为什么只做一跳"的决策点）。

### 4. 前端：知识网络页（/knowledge/:id/graph）

- ECharts **力导图**：节点=概念（大小=出现文档数，颜色=类型），边=关系（标签显示关系词），可拖拽/缩放；
- 点节点 → 右侧面板：关联关系（可点相邻节点跳转）+ 原文片段（"定位到原文第 N 段"→ 复用预览抽屉）；
- 「重建知识网络」：对库内全部已完成文档重新抽取（异步，轮询节点数变化刷新）。

## 三、面试话术

- "RAG 的公认短板是多跳推理：片段平铺没有关系。我加了一层**实体/关系抽取**（入库时一次 LLM 调用），问答时问题命中实体后**沿关系扩展召回**——'A 和 B 什么关系'这类问题从'靠模型猜'变成'有文档里的关系链作证据'。"
- "只做 1 跳扩展是刻意的：2 跳以上噪声和成本都翻倍，1 跳已经能覆盖大多数跨概念问题——这是'控制复杂度'的取舍。"
- "图谱是增强不是依赖：抽取失败不影响文档入库，问答时扩展失败自动跳过，主检索不受影响——所有 AI 增强环节都遵循这个原则。"
- "可视化把图谱从后台手段变成前台产品：知识库打开是一张能点的知识地图。"
