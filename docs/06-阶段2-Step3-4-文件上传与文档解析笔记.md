## 1. 上传的原理：multipart/form-data 和 Multer

### 1.1 普通 JSON 请求 vs 文件上传

平时接口传 JSON：

```
POST /api/knowledge
Content-Type: application/json
{"name": "我的知识库"}
```

文件上传不能这样——文件是二进制，JSON 塞不下（转 base64 会膨胀 33%）。浏览器用 **multipart/form-data** 格式：

```
POST /api/knowledge/:id/documents
Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryXXX

------WebKitFormBoundaryXXX
Content-Disposition: form-data; name="file"; filename="vue3资料.md"
Content-Type: text/markdown

（这里是文件二进制内容）
------WebKitFormBoundaryXXX--
```

一个请求体里可以塞**多个字段 + 多个文件**，用 `boundary` 分隔。`name="file"` 是字段名——**前端传的字段名必须和后端 `FileInterceptor('file')` 一致**，不然收不到。

### 1.2 Multer 是什么

Multer 是 Express 生态最常用的 multipart 解析中间件，NestJS 把它封装成 `FileInterceptor`：

```ts
@UseInterceptors(FileInterceptor('file', { storage: memoryStorage(), limits: { fileSize: 50MB } }))  // multer 兜底硬上限 50MB；业务上限 20MB（MAX_FILE_SIZE_MB）在 service 层校验
```

**storage 两种模式（面试可能问）：**

| 模式 | 文件去哪了 | 优点 | 缺点 |
|------|-----------|------|------|
| `diskStorage` | 直接写磁盘 | 大文件省内存 | 校验失败时文件已落盘，要手动清理 |
| `memoryStorage`（本项目） | 先存在内存（`file.buffer`） | **校验通过后才写盘**，非法文件不落盘 | 大文件占内存（业务上限 20MB，没问题） |

我们选 memoryStorage：**先校验（大小）再写盘**——超限文件不会出现在磁盘上；类型白名单外的文件作为附件原样保管（不解析、不检索）。

### 1.3 MulterError 处理

文件太大时 Multer 抛 `MulterError (LIMIT_FILE_SIZE)`。它**不是** HttpException，不加处理会变成 500。我们在全局异常过滤器里加了分支：

```ts
} else if (exception instanceof MulterError) {
  status = 400;
  message = exception.code === 'LIMIT_FILE_SIZE' ? '文件不能超过 50MB' : ...;  // multer 兜底上限；20MB 业务上限（MAX_FILE_SIZE_MB）在 service 层先拦
}
```

**知识点**：NestJS 全局异常过滤器按 `instanceof` 分支处理不同类型异常——这是可扩展的写法，以后加别的异常类型照葫芦画瓢。

## 2. 文件校验与安全（"想周全"清单）

| 检查项 | 做法 | 防止什么 |
|--------|------|----------|
| 文件必须存在 | `if (!file) throw 400` | 空请求 |
| 类型白名单 | 按扩展名分类：pdf/docx/md/txt 解析；**code 类型（几十种代码扩展名，splitCode 分块 chunkSize 900）**；白名单外类型**不拒绝**，作为附件原样保管（不解析、不检索） | 恶意/不可解析文件不进解析流水线 |
| 大小限制 | ≤20MB（MAX_FILE_SIZE_MB 默认 20，service 校验；multer 兜底 50MB） | 撑爆磁盘/内存 |
| 文件名 | **UUID 改名存储**（`randomUUID() + 扩展名`） | 重名覆盖、`../../` 路径注入 |
| 原文件名 | 单独存进 `Document.filename` 字段 | 展示用，不参与文件系统路径 |
| 越权上传 | 先 `knowledgeService.findOne(userId, kbId)` | 用户往别人知识库里塞文件 |

**面试点**："上传我做了类型白名单（可解析类型走解析，其余作附件保管）+ 大小限制（20MB）+ UUID 改名防路径注入，校验通过才落盘（memoryStorage），越权先查归属返回 404。"

## 3. 文档解析：三种文件三套方案

| 类型 | 方案 | 代码 |
|------|------|------|
| PDF | `pdf-parse`（纯 JS 提取文本） | `pdfParse(buffer)` → `.text` |
| Word .docx | `mammoth`（专做 docx→文本） | `mammoth.extractRawText({ buffer })` → `.value` |
| Markdown/TXT | 直接 `buffer.toString('utf-8')` | 本身就是文本 |

**边界（面试要主动说）：**
- `.doc` 老格式不支持（需要 COM 自动化，成本高）→ 前端提示转 .docx
- 扫描件 PDF（纯图片）提取不到文字 → 报"未能提取到文本"，我们检测空文本并给出明确错误
- OCR（图片文字识别）留作扩展

## 4. 文本清洗

解析出的原文很脏，清洗规则（`cleanText`）：

```ts
.replace(/\r\n/g, '\n')        // Windows 换行统一成 Unix
.replace(/[ \t]+/g, ' ')       // 连续空格 → 单个
.replace(/\n{3,}/g, '\n\n')    // 多余空行 → 最多一个
.replace(/[\u0000-\u0008\u000b\u000c\u000e-\u001f]/g, '') // 控制字符
.trim()
```

不洗的后果：分块时把"空行"当语义边界切出大量垃圾块，浪费 token 和检索精度。

## 5. 递归字符分块（本项目核心算法，面试重点）

### 5.1 为什么递归？

一句话：**先按"最自然的语义边界"切，切不动再换更细的边界**。

```
分隔符优先级：段落(\n\n) → 换行(\n) → 句号(。) → 感叹问号(！？) → 分号(；) → 逗号(，) → 空格 → 硬切
```

算法流程（`text-splitter.ts`）：

```
splitText(文本, 500, 100):
  如果文本 ≤ 500 字 → 直接并入上一块（或作为第一块）
  否则：
    用当前优先级最高的分隔符切分
    每片如果还 > 500 字 → 用下一个更细的分隔符递归切
    每片如果 ≤ 500 字 → 并入上一块（超了就开新块）
```

### 5.2 三个细节（面试官会深挖）

**① 保留分隔符**——用正则"向后断言"切分，标点不丢：

```ts
"你好。世界".split(/(?<=。)/)   // → ["你好。", "世界"]  句号留在句尾
```

如果不保留，拼接时"你好"+"世界"中间少个句号，语义受损。

**② overlap（重叠 100 字）**——防"答案刚好被切在边界上"：

```
块1: [……前400字……]
块2: [前块尾巴100字 + 后400字……]
```

边界附近的内容在相邻两块里各出现一次，检索时无论切到哪边都能拿到完整上下文。

**③ chunkSize 500 / overlap 100 怎么定的**——中文 500 字约等于一段完整论述；太小上下文不全，太大检索不精准、token 贵。**这两个参数以后要做成可配置，做对比实验**（这是面试的实验数据素材）。

### 5.3 测试怎么验证的

单测已固化为永久测试 `apps/server/test/text-splitter.spec.ts`（splitText 5 例 + splitCode 4 例），覆盖：
- 长文按句子切，每块 ≤500、句子完整、标点保留
- 无标点长文触发"硬切"，相邻块重叠正确
- 短文本只有 1 块
- overlap 参数生效（每块开头 = 上一块结尾 30 字）

**方法论**：纯函数先单测（不依赖网络/数据库），跑通了再接进接口——这是"小步验证"。

## 6. 状态机：文档生命周期

```
上传 → Document(status: pending)
        ↓ 开始解析
      processing
        ↓ 成功                ↓ 失败
      done（含 chunk 数）    failed（error 字段存原因）
        ↓ 同名再次上传        ↓ 移入回收站/跳过
      replacing → 替换完成回到 done    bin / skipped
```

- `done`：chunk 已入库（`_count.chunks` 返回数量）
- `failed`：保留 Document 行（前端能展示错误）；**失败只 `chunk.deleteMany` + 标记 failed，磁盘文件保留**（仅同名替换/显式删除才 unlink）
- `replacing`：同名上传替换旧文档时进行中；`bin`：回收站；`skipped`：附件（白名单外）跳过解析，不生成 chunk
- 删除文档：chunk 靠数据库外键 `ON DELETE CASCADE` 级联删，磁盘文件手动删

## 7. 本阶段踩的坑（记录在案）

| 坑 | 原因 | 解决 |
|----|------|------|
| Prisma generate 报 EPERM 删不了 DLL | 后端进程运行中锁住了 `query_engine-windows.dll` | 先停后端再 generate |
| 列名 camelCase/snake_case 混用 | 三张表字段没统一 @map | 手写 `RENAME COLUMN` 迁移（Prisma 自动迁移会把重命名误判成删列+加列，非空列有数据时无法执行） |
| `migrate dev` 报"非交互环境" | CI/脚本环境没有终端交互 | 手写迁移文件 + `migrate deploy`（非交互命令） |
| curl 上传中文文件名变乱码 | curl.exe 用系统 GBK 编码发文件名 | 浏览器/axios 发 UTF-8 无此问题；测试用 ASCII 文件名 |
| PowerShell 路径含单引号（qie'li） | PS 5.1 传参 bug | 测试文件放项目内无单引号路径 |
