# 阶段 2 详细规划：知识库管理 + 文档解析流水线

> 目标：让用户能**创建知识库 → 上传文档 → 文档被自动解析、分块、向量化 → 存进 pgvector**
> 这是 RAG 的"入库"半程（Indexing），做完它，阶段 3 的"问答"才有数据可查。
> 预计 4-6 周，本阶段结束前需要你提供：**硅基流动的 API Key**（免费额度够用）。

## 1. 阶段 2 结束时，产品长什么样

```
前端（Web）:
  知识库页面：新建/重命名/删除知识库（列表 + 卡片）
  文档页面：上传文件（拖拽）、查看解析进度/状态、删除文档
后端（API）:
  POST   /api/knowledge           创建知识库
  GET    /api/knowledge           我的知识库列表
  PATCH  /api/knowledge/:id       重命名
  DELETE /api/knowledge/:id       删除（连带文档和向量数据）
  POST   /api/knowledge/:id/documents      上传文档
  GET    /api/knowledge/:id/documents      文档列表
  DELETE /api/knowledge/:id/documents/:docId  删除文档
数据库:
  KnowledgeBase 表（知识库）
  Document 表（文档，含解析状态）
  Chunk 表（文本块 + 向量）
```

**验收标准（做完自测）：**
1. 上传一个 PDF/Word/Markdown，数据库里能看到 chunk 记录
2. 每个 chunk 有 1024 维向量（bge-m3），能查到
3. 用 pgAdmin/psql 能看到向量数据
4. 删除知识库，文档和 chunk 一并清掉（事务）
5. Swagger 里所有接口能调通

## 2. 决策点 1：数据模型设计（三张表）

### 方案对比：chunk 数据怎么存？

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. Chunk 单独一张表**（推荐） | `chunks` 表存：content、embedding 向量、doc_id、chunk_index、metadata | 检索时只查 chunk 表，速度快；删除文档好清理；结构清晰 | 表多一张 |
| B. chunk 存 Document 表里的 JSON 字段 | 一个文档一行，chunk 数组塞 JSON | 表少 | 检索要全表扫 JSON，慢；删除/更新麻烦；PostgreSQL 对 JSON 检索支持有限 |

**选 A**：RAG 每次提问都要做向量检索，chunk 必须是独立表 + 向量索引才能快。

### 三张表的字段设计（Prisma schema 草案，实现时微调）

```prisma
model KnowledgeBase {
  id          String   @id @default(uuid())
  name        String
  description String?
  ownerId     String   // 所属用户
  documents   Document[]
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}

model Document {
  id          String        @id @default(uuid())
  knowledgeBaseId String
  filename    String        // 原始文件名
  filepath    String        // 服务器上存储路径
  fileSize    Int           // 字节数
  fileType    String        // pdf / docx / md / txt
  status      String        // pending(待处理) processing(解析中) done(完成) failed(失败)
  error       String?       // 失败原因
  chunks      Chunk[]
  createdAt   DateTime      @default(now())
}

model Chunk {
  id          String   @id @default(uuid())
  documentId  String
  content     String   // 文本块原文
  embedding   Unsupported("vector(1024)")?  // pgvector 类型，Prisma 不支持直接声明，用原始 SQL
  chunkIndex  Int      // 第几块，保证顺序
  meta        Json?    // 页码等元数据
}
```

> **注意点（提前告诉你，避免踩坑）**：
> - `vector(1024)` 是 pgvector 的扩展类型，Prisma 的 schema 不支持它。
> - 主流做法：Prisma 只管普通字段，向量字段用**原始 SQL 迁移**加进去（`ALTER TABLE ... ADD COLUMN embedding vector(1024)`）。
> - 这正好是个面试点："pgvector 类型 Prisma 不直接支持，我通过自定义迁移解决"。

## 3. 决策点 2：文件上传方案

| 方案 | 做法 | 优点 | 缺点 | 适合 |
|------|------|------|------|------|
| **A. Multer 本地磁盘存储**（推荐先做） | 用 NestJS 内置的 Multer，文件存服务器 `uploads/` 目录，数据库只存路径 | 零成本、零第三方依赖、代码最少、本地调试直观 | 文件单机存储，扩容/备份要自己管 | 学生项目、前期开发 |
| B. 云 OSS（阿里云/腾讯云） | 文件传 OSS，数据库存 URL | 无限容量、自带 CDN、不怕服务器磁盘满 | 要申请、要花钱（有免费额度）、要配 SDK | 后期上线可换 |
| C. base64 传数据库 | 文件转 base64 字符串直接存表 | 一个请求搞定 | 数据库暴涨、慢、最多几 MB | 只适合小图，不适合文档 |

**选 A 起步，B 留作后期升级**——这是"能跑 vs 完美"的典型权衡：先让功能转起来，上线前再评估换 OSS。Multer 的坑提前说：**默认有 10MB 上传限制、文件名要自己处理防重名**（用 UUID 改名），这些实现时处理。

## 4. 决策点 3：文档处理同步还是异步？

上传一个文档后，要干的事不少：解析 → 清洗 → 分块 → 向量化（每个 chunk 调一次 API）→ 入库。一个 50 页 PDF 可能产生 100 个 chunk，向量化要调 100 次 API，**同步做的话，用户上传后要等几分钟接口才返回**。

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 同步处理**（推荐先做） | 上传接口里一口气处理完再返回 | 实现最简单，一个函数搞定；调试直观 | 大文件请求会很久；并发上传会占满进程 |
| B. 异步任务队列 | 上传只存文件+标记 pending，立刻返回；后台队列（BullMQ + Redis）慢慢处理，前端轮询/SSE 看进度 | 体验好（秒回），支持大文件、支持进度 | 要引入 BullMQ、队列、进度推送，复杂度翻倍 |

**推荐：先 A 后 B。** 阶段 2 先用同步把整条流水线跑通（这是学习价值最大的部分），阶段 4 再升级异步队列 + 进度推送（那是面试加分项："我用了 BullMQ 异步任务队列 + Redis，上传秒回，后台处理，SSE 推送进度"）。

## 5. 决策点 4：文档解析方案

| 文件类型 | 首选库 | 备选 | 说明 |
|----------|--------|------|------|
| PDF | `pdf-parse`（已装） | pdfjs-dist（浏览器端渲染用） | pdf-parse 简单，直接出纯文本；中文 PDF 提取效果一般，够用 |
| Word (.docx) | `mammoth`（已装） | docx 库（生成用） | mammoth 专做 docx→HTML/纯文本，效果好 |
| Markdown / TXT | 直接 fs 读 | — | 零依赖 |
| Word (.doc) 老格式 | 不支持（提示用户转 .docx） | — | 老格式解析要调 COM，成本高，学生项目不做 |

> **面试点**："文档解析我对比了 pdf-parse 和 pdfjs-dist，最终选了 pdf-parse——服务端纯文本提取它最轻量；PDF 里如果带图片内容，目前不处理（OCR 留作扩展）"。诚实说边界，比假装全能强。

## 6. 决策点 5：分块策略（RAG 最核心的调优点）

为什么必须分块：整篇文档丢给模型 = 又长又贵又检索不准。切成小块，提问时只取最相关的几块。

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A. 固定大小分块 | 每 500 字硬切一刀 | 简单 | 可能从句子中间切断，语义断裂 |
| B. **递归字符分块**（推荐，手写） | 优先按段落切；段落太长按句号切；再长按逗号/空格切；每块约 500 字，相邻块重叠 100 字 | 兼顾语义完整和长度可控；LangChain 的经典方案，面试好讲 | 要写递归逻辑（其实就 20 行） |
| C. 语义分块 | 用模型判断哪里是语义边界 | 质量最高 | 每块都要调 API，慢且贵，学生项目不值 |

**选 B 手写**——这是 LangChain 的 `RecursiveCharacterTextSplitter` 思路，我们手写一遍，面试时就能讲透原理（"为什么先按段落切？因为段落是中文里最自然的语义单元；重叠 100 字是为了避免答案刚好被切在边界上丢了上下文"）。

**参数含义（面试会问）：**
- `chunkSize = 500`：每块目标长度（字）。太小 → 上下文不全；太大 → 检索不精准、token 贵
- `overlap = 100`：相邻块重叠。防止答案内容恰好跨块被切丢
- 这两个参数后续可以做成"设置项"，对比不同参数下的回答质量——这就是"调参实验"的面试素材

## 7. 决策点 6：Embedding 方案（已确认，这里讲清楚）

- **模型**：硅基流动 `BAAI/bge-m3`（中文顶尖、免费额度大、输出 1024 维向量）
- **调用方式**：OpenAI 兼容格式（`https://api.siliconflow.cn/v1/embeddings`），用已装的 `openai` SDK
- **工程细节（实现时做）**：
  - **批量**：一次请求传多个 chunk（bge-m3 支持批量），10 个一批，100 个 chunk 只要 10 次请求
  - **失败重试**：指数退避，最多 3 次
  - **限速**：硅基流动有 QPS 限制，控制并发
- **存储**：向量写进 `chunks.embedding` 列，并建 **HNSW 索引**（pgvector 的近似最近邻索引，百万级数据检索毫秒级）——建索引的 SQL 也走原始迁移

## 8. 开发顺序（每一步：做什么 + 验证什么）

> 每一步都有独立验证点，做完一步确认一步，不会出现"写了一大堆然后全错"的情况。

| 步骤 | 做什么 | 验证 |
|------|--------|------|
| **Step 1** | Prisma schema 加 KnowledgeBase + Document 模型；写迁移；建表 | `npx prisma migrate dev` 成功；psql 能看到表 |
| **Step 2** | Knowledge 模块 CRUD（controller/service/dto） | Swagger 里建/查/改名/删知识库 |
| **Step 3** | 上传接口（Multer：存文件 + 校验类型/大小 + 建 Document 记录，状态 pending） | 上传 PDF 成功，uploads/ 里有文件，DB 有记录 |
| **Step 4** | 文档解析 + 清洗 + 递归分块（独立 util，可单测） | 传一段测试文本，能按预期切块 |
| **Step 5** | 接硅基流动 Embedding + 写入 Chunk 表 + 建向量索引 | psql 查 chunks 有 1024 维向量 |
| **Step 6** | 文档状态流转（pending→processing→done/failed）+ 错误记录 | 上传后状态自动变成 done |
| **Step 7** | 前端知识库页面（列表 + 新建 + 删除） | 浏览器能操作 |
| **Step 8** | 前端文档页（上传 + 列表 + 状态展示 + 删除） | 浏览器能上传并看到解析结果 |

Step 1-6 是后端（这轮先做），Step 7-8 是前端。
