| 问题 | 修复 |
|------|------|
| 知识库进页面不加载列表 | 补上 `onMounted(load)`（此前漏了调用，要新建/刷新才显示） |

| 文件不能重复选择 | 点击文件框时清空 value，同文件也能触发 change |
| 上传无进度反馈 | axios `onUploadProgress` 进度条 |
| 首页四个卡片不可点 | 改为功能入口（知识库/对话可跳转），进度文案更新到阶段 4 |
| 知识库不能改名/改描述 | 卡片加编辑按钮 + 弹窗（后端 PATCH 早已就绪） |
| 文档不能编辑 | 在线编辑弹窗：改内容/文件名 → 保存后**自动重新分块向量化**（磁盘文件同步重写为编辑后文本，单一事实来源；PDF/Word 编辑后类型转 txt）；txt/md 上传前可先「编辑文本」改完再入库 |
| 只能单文件上传 | **多文件**（`input multiple` + 逐个上传，单文件失败不影响批次，失败汇总展示）+ **整目录上传**（`webkitdirectory`，相对路径经独立 `name` 字段传递——浏览器会剥掉 multipart 文件名里的路径分隔符，已踩坑） |
| 一键启动 卡死 | 根因①bat 是 UTF-8 编码、中文路径被 GBK cmd 解析成乱码 → 改用 `%~dp0` + `wslpath` 动态路径（纯 ASCII，编码免疫）；②WSL docker 偶发"容器活着但端口转发丢失" → keep-docker-running.sh 加端口自愈（容器健康但端口未绑则自动重启）③服务已在跑时重复启动 → 一键启动 加"端口已通则跳过"幂等逻辑 |

**面试可讲**："上线前我做了两轮自测：第一轮用 API 全链路回归；第二轮用无头 Chrome 自动化真实点击操作，抓到了 Vite 内存缓存吐旧模块、多轮对话上下文取错方向这类只在真实使用中才会暴露的问题。"

## 2. 混合检索（向量 + BM25）—— ✅ 已完成（2026-08）

### 最终实现（选型对比见下方"方案对比"）

- **关键词检索**：PostgreSQL 内置 `pg_trgm` 扩展（三元组子串匹配），`chunks.content` 建 GIN 索引，查询用 `content % $question`（索引加速）+ `similarity()` 排序。**中英文通吃、零额外依赖**（不需要装 pg_bigm/zhparser 等扩展）。
- **语义检索**：pgvector 余弦相似度，新增 `MIN_SIMILARITY`（默认 0.35）阈值——**低于阈值的片段直接丢弃，不再硬凑 5 条**；知识库没相关内容时如实返回空，Prompt 会回答"未找到相关内容"。
- **融合**：RRF（`score = Σ 1/(60 + rank)`），两路各取 Top-15 合并截断 Top-5，只比排名不比分数，无需归一化/调权重。
- **引用来源自适应**：知识库 0~5 条 + 联网 0~5 条，条数完全不对称，总条数不强制。

**实测结果**：多库会话问"量子比特"→ 命中正确文档；问"B+树"→ 命中另一文档（按会话绑定过滤生效）；无关问题 → 知识库来源 0 条（阈值生效，不编造引用）。

**踩坑**：Prisma `String` 列在 PG 是 `text` 类型，id 数组参数不能转 `::uuid[]`（报 `operator does not exist: text = uuid`），要转 `::text[]`。

**面试可讲**："纯向量检索对专有名词召回差，我加了 pg_trgm 关键词检索，用 RRF 排名融合——只比排名不比分数，不用归一化；同时给向量检索加相似度阈值，知识库没相关内容时如实返回空，而不是硬凑引用。"

### 方案对比（当初的选型过程）

| 方案 | 做法 | 优点 | 缺点 | 复杂度 |
|------|------|------|------|--------|
| A. 纯向量（原状） | 只用余弦距离 | 已实现 | 术语召回差 | - |
| **B. 向量 + 关键词混合（采用）** | pg_trgm 关键词检索 + RRF 融合 | 语义+关键词互补，中英文通吃，零额外依赖 | 关键词是子串匹配，非完整 BM25 公式 | 中 |
| C. 真 BM25（pg_search） | ParadeDB 扩展 | 标准 BM25 公式 | 中文分词要额外配置，部署多一步 | 高 |

**RRF（Reciprocal Rank Fusion）**：`score = 1/(k + rank1) + 1/(k + rank2)`，两个检索结果按名次融合——不依赖分数可比性，是业界标准做法（面试点）。

## 3. 数据看板（ECharts）—— ✅ 已完成（2026-08）

### 最终实现

- **Token 统计**：`chat.completions.create` 开启 `stream_options: { include_usage: true }`，流式最后一个 chunk 携带 usage → 存入 `chat_messages.prompt_tokens / completion_tokens` 两列（方案 A：存库可回溯聚合）。
- **统计接口** `GET /api/stats/overview`（按用户隔离）：知识库/文档/Chunk/消息数、今日提问、Token 总消耗（输入/输出分列）、近 7 日逐日聚合（`FILTER` 条件聚合 + 缺日补零）、Top 知识库。
- **看板页** `/dashboard`：统计卡片 + ECharts 折线（7 日提问）/柱状（7 日 Token）+ Top 知识库列表。
- **性能**：echarts **按需引入**（core + Line/Bar + Grid/Tooltip + CanvasRenderer），并 `manualChunks` 拆独立 vendor 包 → 看板页 chunk 523KB → **6.4KB（gzip 2.6KB）**，echarts 单独长缓存。

**实测**：一次问答后 overview 返回 tokens=1123、今日提问=1、7 日补零正确、图表双 canvas 渲染，控制台零错误。

**面试可讲**："流式接口默认不返回 usage，我通过 stream_options.include_usage 拿到真实 Token 消耗并落库；图表用 echarts 按需引入 + vendor 分包，把看板页 bundle 从 523KB 压到 6.4KB。"

### 方案对比（当初的选型过程）

| 方案 | 做法 | 优劣 |
|------|------|------|
| **A. 存数据库（采用）** | 每次问答后把 usage 写入消息表 token 列 | 数据可回溯、可聚合、面试好讲"埋点统计" |
| B. 只统计前端 | 前端拿 delta 长度估算 | 不准，且刷新丢失 |
| C. 实时推送 | WebSocket/SSE 推最新数据 | 炫但复杂，阶段 4 不需要 |

## 4. 2FA 双因素认证（TOTP）

### 原理（面试必讲）

TOTP（Time-based One-Time Password）：**密钥（secret）+ 当前时间** → HMAC-SHA1 → 截断成 6 位数字，**每 30 秒变化一次**。Google Authenticator 等 App 本地计算，服务器用同一算法验证——**两边都离线可算，不用发短信**。

### 流程

```
设置页 → 后端生成 secret → 返回二维码（otpauth:// 协议）
       → 用户扫码（Authenticator App）
       → 输入 App 上的 6 位码 → 后端验证 → 开启 2FA
登录时 → 密码 + 6 位码 → 都通过才发 token
```

### 方案对比

| 库 | 说明 | 选择 |
|----|------|------|
| `otplib`（推荐） | 正宗 TOTP 实现，纯 JS，API 简单 | ✅ 用它 |
| `speakeasy` | 老牌，功能全但更重 | 备选 |
| 手写 TOTP | 就几十行，但容易出边界 bug | 不推荐（有轮子别造） |
| 二维码 | `qrcode` 库生成 base64 图片 | ✅ 前端展示 |

### 需要做的

1. 用户表加 `twoFactorSecret`、`twoFactorEnabled` 字段
2. 设置页：生成 secret + 二维码 + 验证绑定
3. 登录流程：开启 2FA 的用户，密码验证后还要验 6 位码
4. **恢复码**（可选增强）：绑定成功生成 8 个一次性恢复码，防丢手机
